## Short answer

Blocking call засинає або чекає, поки data/resource стане доступним, наприклад `read` з порожнього device queue. Non-blocking call одразу повертає `EAGAIN`/`EWOULDBLOCK`, якщо операцію не можна виконати. У драйверах це впливає на wait queues, poll/select/epoll support, timeout-и й те, чи можна викликати API з конкретного context.[^dou-embedded-interview]

## Detailed explanation

### Концептуальна різниця: блокування проти негайного повернення

У драйверах периферії та системних інтерфейсах вводу-виводу (I/O API) вибір між блокуючим і неблокуючим підходом визначає поведінку викликаючого потоку при очікуванні готовності апаратного ресурсу чи даних:
1. **Блокуюча операція (Blocking / Synchronous I/O)**:
   - Якщо дані недоступні (наприклад, буфер прийому UART порожній) або апаратний блок зайнятий передачею, функція драйвера переводить викликаючий потік у стан очікування (Blocked / Suspended).
   - Потік припиняє споживання процесорного часу. Планувальник операційної системи реального часу (RTOS) перемикає ядро на виконання інших готових задач із нижчим або рівним пріоритетом.
   - Повернення з функції відбувається лише тоді, коли запитана дія повністю завершена (наприклад, усі байти надіслані шиною SPI) або сплив призначений тайм-аут (`timeout`).
2. **Неблокуюча операція (Non-blocking / Asynchronous I/O)**:
   - Функція ніколи не переводить потік у стан блокування і не очікує завершення апаратної передачі. Вона повертає керування негайно.
   - Якщо операція може бути виконана миттєво (наприклад, у FIFO-буфері драйвера є вільне місце), дані записуються, і функція повертає кількість оброблених байтів або код успіху.
   - Якщо ресурс зайнятий або даних немає, функція негайно повертає спеціальний код помилки. У POSIX `read()` з порожнього каналу, FIFO або пристрою з підтримкою неблокуючого читання при встановленому `O_NONBLOCK` повертає -1 і встановлює `errno` в `EAGAIN`, а без `O_NONBLOCK` блокує потік, доки не з’являться дані.[^posix-read] В RTOS-API код інший: наприклад, у Zephyr `uart_poll_in()` повертає -1, якщо даних немає.[^zephyr-uart]

### Контекст виконання та взаємодія з планувальником RTOS

Головне архітектурне обмеження вбудованих систем стосується **контексту виклику (Execution Context)**:[^freertos-kernel-book]
- **Заборона блокування в обробниках переривань (ISR)**: апаратні переривання виконуються в окремому режимі ядра (Handler Mode в ARM Cortex-M). Контекст переривання не має власного стека задачі і не контролюється планувальником RTOS. FreeRTOS прямо забороняє викликати з ISR будь-яку функцію API без суфікса `FromISR` у назві (наприклад, очікування семафора `xSemaphoreTake()`). Порушення цього правила не гарантує зрозумілої діагностики: збій може проявитися не відразу і не в місці виклику.
- **Виклики з ISR вимагають виключно неблокуючих API**: для цього в RTOS передбачено спеціалізовані неблокуючі функції (наприклад, `xQueueSendFromISR()` або `k_fifo_put()` у Zephyr), які лише додають подію в чергу й опціонально встановлюють прапорець запиту зміни контексту (`pxHigherPriorityTaskWoken`).
- **Синхронізація блокуючих викликів**: для блокування задач драйвери використовують системні примітиви очікування: бінарні семафори, черги повідомлень, прапорці подій (Event Groups) або прямі сповіщення задач (Direct-to-Task Notifications). Після завершення транзакції обробник переривання периферії сигналізує примітив, і планувальник повертає задачу в чергу готових до виконання (Ready).

### Асинхронні моделі сповіщення та роль DMA

Для побудови високоефективних драйверів використовують неблокуючі асинхронні моделі; наприклад, Zephyr дає для UART три способи доступу: polling API, interrupt-driven API і асинхронний API на основі DMA.[^zephyr-uart]
1. **Зворотні виклики (Callback-driven API)**: викликаючий код передає драйверу адресу функції зворотного виклику (`callback`) та вказівник на дані. Драйвер налаштовує апаратний блок (наприклад, прямий доступ до пам’яті – DMA) і миттєво повертає керування. Коли передача завершується, ISR викликає зареєстрований callback або ставить подію в чергу фонової робочої нитки (Workqueue).
2. **Опитування готовності (Polling / Ready check)**: функція типу `uart_poll_in()` перевіряє апаратний прапорець готовності приймача (на STM32 це `RXNE`) і зчитує байт без затримок; при цьому парна до неї `uart_poll_out()` у Zephyr є блокуючою.[^zephyr-uart]
3. **Механізми мультиплексування вводу-виводу (Poll / Select)**: у багаторівневих системах (Embedded Linux, Zephyr) одна задача може за допомогою системного виклику `poll()` або `select()` одночасно очікувати подій від десятків дескрипторів (сокетів, UART, кнопок), перебуваючи у стані сну, доки хоча б один драйвер не сигналізує про готовність.

### Архітектурні компроміси та керування життєвим циклом буферів

Вибір між двома моделями визначається вимогами до системи:
- **Простота коду проти використання CPU**: блокуючий код є лінійним і простим для розуміння:
  ```c
  // Блокуючий підхід: простий лінійний потік
  spi_write_blocking(SPI1, tx_buffer, length, TIMEOUT_MS);
  process_next_step();
  ```
  Проте якщо для кожного зовнішнього датчика виділяти окремий блокуючий потік RTOS, це вимагає значного обсягу оперативної пам’яті під стеки задач.
- **Життєвий цикл пам’яті (Buffer Ownership)**: критична пастка неблокуючого API на базі DMA. Якщо драйвер повертає керування негайно, передача даних з буфера `tx_buffer` апаратним каналом DMA ще триває у фоні. Якщо викликаючий потік повторно модифікує цей масив або виходить із функції, де масив був виділений на локальному стеку, дані спотворюються. При неблокуючому API розробник зобов’язаний гарантувати незмінність буфера (Zero-Copy) аж до отримання асинхронного підтвердження завершення передачі.
