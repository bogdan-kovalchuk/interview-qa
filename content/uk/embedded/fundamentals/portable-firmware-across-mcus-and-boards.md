## Short answer

Розділяй **portable core**, MCU-specific drivers, board support package і configuration data. Hardware differences описуй через target-specific build options, linker scripts, pin/clock tables і devicetree-like конфігурацію, а не через хаотичні `#ifdef` по всій логіці. CI має збирати ключові variants, щоб divergence ловився рано.[^dou-embedded-interview]

## Detailed explanation

### Шарувата архітектура прошивки (Layered Architecture)

Фундаментом підтримки єдиної кодової бази для різних сімейств мікроконтролерів і апаратних платформ є чітке розділення прошивки на ізольовані горизонтальні рівні з односпрямованими залежностями:

1. **Application Core (бізнес-логіка):** платформонезалежний код застосунку (алгоритми керування, протоколи зв’язку, парсери, обчислення, фільтри та кінцеві автомати). Цей рівень не повинен містити жодних прямих звернень до регістрів мікроконтролера чи вендорських заголовних файлів на кшталт `stm32f4xx.h` або `nrf.h`. Він взаємодіє із залізом виключно через абстрактні інтерфейси. Такий підхід дозволяє запускати повний набір модульних тестів (unit tests) на хост-машині без реального апаратного забезпечення.[^dou-embedded-interview]
2. **Hardware Abstraction Layer (HAL API):** типізований контракт для роботи з периферією (UART, SPI, I2C, GPIO, PWM, ADC). В чистому C інтерфейс формується у вигляді уніфікованих сигнатур функцій або таблиць покажчиків на функції (vtable / struct of function pointers), які передаються як контекст драйвера. В C++ для усунення накладних витрат віртуальних викликів часто застосовують статичний поліморфізм (шаблони або патерн CRTP).[^arm-cmsis-core]
3. **Target Drivers (реалізація під сімейство MCU):** конкретна низькорівнева реалізація уніфікованого HAL для вибраної родини чипів (наприклад, драйвери для STM32, ESP32, NXP чи Silicon Labs). Драйвер транслює абстрактні запити рівня HAL у взаємодію з апаратурою за допомогою вендорських бібліотек або безпосередньої роботи з регістрами (CMSIS-Core).[^arm-cmsis-core]
4. **Board Support Package (BSP):** найвищий шар апаратної конфігурації конкретної друкованої плати. BSP визначає фізичне розведення виводів (pinout), джерела та частоти тактування (clock tree), конфігурацію ліній живлення та підключення зовнішніх мікросхем (датчиків, прийомопередавачів, зовнішньої пам’яті).

### Відмова від спагеті з препроцесора на користь системи збірки

Поширена антипрактика – спроба керувати відмінностями апаратних платформ за допомогою розкиданих по коду директив `#ifdef BOARD_REV_A` або `#if defined(MCU_STM32F4)`. Такий підхід робить код нечитабельним, приховує помилки типізації у неактивних гілках та експоненційно ускладнює додавання нових платформ.

У професійному підході конфігурація виноситься на рівень системи збірки та декларативних описів:

- **Модульна компіляція в CMake або Make:** залежно від переданого цільового таргету (наприклад, `cmake -DBOARD=nucleo_f401re -DMCU=stm32f401`), система збірки підключає до лінкування лише відповідні файли драйверів (`gpio_stm32.c`, `uart_stm32.c`), правильний startup-файл (`startup_stm32f401xc.s`) і скрипт лінкера (`linker_stm32f401re.ld`). Бізнес-логіка залишається незмінною.[^zephyr-introduction]
- **Декларативний опис апаратури (Devicetree та Kconfig):** сучасні операційні системи реального часу (зокрема Zephyr RTOS) використовують Devicetree (`.dts`) для повного відображення топології плати (адреси периферії, номери переривань IRQ, альтернативні функції пінів) окремо від сирцевого коду драйверів.[^zephyr-devicetree] Механізм Kconfig дозволяє вмикати або вимикати функціональні модулі та оптимізації за допомогою булевих прапорців без модифікації коду.
- **Таблиці пінів та структурні конфігурації:** апаратні константи (номери портів, бітрейти, адреси шин) виносяться в константні структури даних (`board_config.c`), які передаються в драйвери як аргументи ініціалізації.

### Автоматизація в CI та перевірка сумісності

Коли один репозиторій обслуговує кілька різних мікроконтролерів, зміна в загальному коді може непомітно зламати сумісність або переповнити Flash/RAM на чипі з меншим обсягом пам’яті:

- **Матриця збірки (Build Matrix):** у CI (GitHub Actions, GitLab CI) налаштовується матричний запуск, де кожен комміт і Pull Request компілюється для абсолютно всіх підтримуваних плат і конфігурацій. Якщо на одній із плат переповнюється секція `.text` або виникає помилка лінкування, збірка падає до потрапляння коду в основну гілку.[^dou-embedded-interview]
- **Хостове модульне тестування (Host Unit Testing):** ізоляція бізнес-логіки від заліза дозволяє збирати тести під хостовий процесор (x86-64) з використанням бібліотек mock-об’єктів (наприклад, Google Test / FFF). Це дає можливість миттєво перевіряти граничні випадки без підключення налагоджувачів і реальних плат.
- **Hardware-in-the-Loop (HIL) тестування:** критичні релізи прошивки проходять автоматичне тестування на стендах із фізичними платами для валідації таймінгів периферії, споживання струму та стабільності зв’язку.
