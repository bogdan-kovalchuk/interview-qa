## Short answer

Cross-compilation – build на host-машині для іншого CPU/OS/ABI target. Типові помилки: зібрали під host, змішали wrong sysroot, soft/hard-float ABI, endian або libc, а потім отримали `Exec format error` чи runtime crash. Перевіряти треба `file`, `readelf -h`, target triplet і toolchain flags.[^dou-embedded-interview]

## Detailed explanation

### Концепція Cross-Compilation: поняття Host, Target та Build

Крос-компіляція (cross-compilation) – це процес збирання виконуваного коду на одній апаратній платформі (яка називається **Host**), призначеного для виконання на зовсім іншій архітектурі чи операційній системі (яка називається **Target**)[^gcc-overall-options].
У класичній схемі класифікують три машини:
- **Build**: машина, на якій фізично запускається процес збирання самого компілятора.
- **Host**: система, де працює крос-тулчейн (наприклад, ПК розробника під керуванням x86_64 Linux або Windows).
- **Target**: мікроконтролер чи одноплатний комп’ютер, де виконуватиметься фінальний бінарний образ (наприклад, ARM Cortex-M4, RISC-V або MIPS).

Конфігурація цільової системи визначається так званим target triplet (або quadruplet) виду `arch[-vendor][-os]-abi`:
- `arm-none-eabi`: архітектура ARM, вендор відсутній (generic), операційна система відсутня (bare-metal), стандартний Embedded ABI.
- `aarch64-linux-gnu`: 64-бітна архітектура ARMv8-A, операційна система Linux, стандартна бібліотека glibc.
- `arm-linux-gnueabihf`: 32-бітна архітектура ARMv7-A під Linux із підтримкою апаратного FPU (Hard Float ABI).

### Архітектурні розбіжності та апаратні пастки

Спроба виконати бінарник на несумісній або неправильно сконфігурованій цільовій платформі спричиняє негайні збої:

1. **Невідповідність архітектури набору команд (ISA)**:
   Компілятор генерує опкоди під конкретний процесор (прапорці `-mcpu`, `-march`). Наприклад, якщо бінарник скомпільовано під ARMv7E-M із використанням інструкцій DSP чи апаратного ділення (`SDIV`/`UDIV`), а завантажено в ядро ARMv6-M (Cortex-M0), під час спроби виконання непідтримуваної інструкції процесор миттєво згенерує виняток `UsageFault` (Undefined Instruction).
2. **Порядок байтів (Endianness)**:
   Більшість процесорів ARM працюють у режимі Little-Endian (LE), проте існують архітектури (або спеціальні мережеві процесори) у режимі Big-Endian (BE). Якщо бінарник скомпільовано з прапорцем `-mbig-endian` для процесора в режимі Little-Endian, усі багатобайтові числа, адреси переходів та вказівники інтерпретуватимуться з перевернутим порядком байтів, що призведе до катастрофічного руйнування виконання.
3. **Несумісність Floating-Point ABI (Float ABI)**:
   Згідно зі стандартом Arm AAPCS ([^arm-aapcs32]), існує три моделі передачі аргументів із плаваючою комою:
   - `-mfloat-abi=soft`: усі операції `float`/`double` емулюються програмно через виклики бібліотечних функцій, а аргументи передаються через звичайні регістри цілих чисел `r0-r3`.
   - `-mfloat-abi=softfp`: операції з плаваючою комою виконуються апаратними інструкціями FPU (VFP/NEON), проте аргументи у функції все одно передаються через регістри `r0-r3`.
   - `-mfloat-abi=hard`: аргументи безпосередньо передаються у спеціалізовані регістри FPU (`s0-s15`, `d0-d7`).

   Якщо скомпонувати об’єктний файл, скомпільований із `hard`, з бібліотекою, зібраною із `soft` чи `softfp`, викликана функція шукатиме параметри в регістрах FPU, тоді як викликач поклав їх у регістри `r0-r3`. Результатом буде робота зі сміттєвими даними або виліт програми.

### Системні помилки під час запуску в середовищі Linux

У embedded Linux системах додаються проблеми несумісності динамічного завантажувача та бібліотек:
- **`Exec format error` (errno 8, ENOEXEC)**: виникає, коли ядро Linux намагається виконати бінарник, магічні байти або поле архітектури (`e_machine`) заголовка ELF якого не підтримуються поточним ядром (наприклад, запуск бінарника x86_64 на платі ARM без емулятора QEMU, або несумісність 32-бітного бінарника з чистим 64-бітним ядром).
- **Помилки Sysroot та динамічного лінкера**: у бінарнику прописано шлях до завантажувача (ELF interpreter), наприклад `/lib/ld-linux-armhf.so.3`. Якщо цільова файлова система побудована на базі альтернативної libc (musl замість glibc) або шлях відсутній, ядро видасть повідомлення `No such file or directory`, навіть якщо сам файл програми присутній на диску.
- **Розбіжність версій символів `glibc`**: компіляція з крос-компілятором, що використовує новішу версію glibc (наприклад 2.38), для запуску на старій системі з glibc 2.31 призведе до аварійного завершення із повідомленням `version 'GLIBC_2.38' not found`.

### Інженерні методи перевірки та валідації бінарників

Для гарантії сумісності бінарного образу перед розгортанням застосовують такі кроки:
1. **Інспекція через утиліту `file`**:
   Команда `file <binary>` показує цільову архітектуру, порядок байтів, версію ELF та режим ABI (наприклад, `ARM, EABI5 version 1 (SYSV), dynamically linked, interpreter /lib/ld-linux-armhf.so.3`).
2. **Аналіз заголовка через `readelf -h`**:
   Відображає поле `Machine` (наприклад, `Advanced RISC Machines ARM`), прапорці заголовка `Flags` (включаючи версію EABI) та тип файлу.
3. **Перевірка архітектурних атрибутів через `readelf -A`**:
   Специфічна для ARM команда, що виводить параметри побудови: назву процесорного ядра (наприклад, `Tag_CPU_arch: v7E-M`), використання Thumb/Thumb-2, тип FPU (`Tag_FP_arch: VFPv4-D16`) та режим передачі аргументів (`Tag_ABI_VFP_args: VFP registers` для Hard Float).
4. **Контроль прапорців збирання у Makefile / CMake**:
   Забезпечення однакових архітектурних прапорців (`-mcpu`, `-mfpu`, `-mfloat-abi`) для абсолютно всіх компільованих файлів та статичних бібліотек проекту[^dou-embedded-interview].
