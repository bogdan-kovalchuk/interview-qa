## Short answer

Фіксуй версії залежностей, перевіряй licenses, supported toolchains, heap/RTTI/exceptions usage і footprint у map file. Краще явно додавати маленькі libraries з known configuration, ніж тягнути generic package з прихованими POSIX, filesystem або allocation assumptions. **Dependency review** для MCU має включати RAM/flash cost і behavior у ISR/RTOS context.[^dou-embedded-interview]

## Detailed explanation

### Специфіка залежностей у мікроконтролерних C/C++ проектах

На відміну від розробки під настільні операційні системи чи сервери, де обсяг пам’яті вимірюється гігабайтами, вбудовані мікроконтролерні системи (MCU) функціонують в умовах суворих апаратних обмежень: обсяг Flash часто становить від кількох десятків кілобайт до 1–2 мегабайт, а RAM – від 4 до 512 кілобайт.

У bare-metal та RTOS-системах відсутні віртуальна пам’ять, механізм сторінкової підкачки (paging) та підвантаження динамічних бібліотек (`.so`/`.dll`). Будь-яка стороння бібліотека компонується статично, безпосередньо впливаючи на розмір бінарного образу, час ініціалізації та споживання оперативної пам’яті.

Підключення універсальних бібліотек загального призначення (розроблених для POSIX/Linux) несе приховані загрози:
- **Неявне використання купи (Heap)**: виклики `malloc()`, `calloc()`, `strdup()` та оператора `new` призводять до фрагментації пам’яті, ризику вичерпання RAM (Out of Memory) та недетермінізму за часом виконання.
- **Приховані системні виклики**: залежності від файлової системи (`open`, `read`, `write`), системних сокетів, сигналів або багатопоточності POSIX (`pthreads`), для яких у голому мікроконтролері відсутня базова реалізація.
- **Роздування стандартної бібліотеки (Newlib bloat)**: підтягування функцій форматування виводу на зразок `printf` із підтримкою плаваючої крапки або обробки локалей може раптово додати від 20 до 50 КБ Flash до образу прошивки.
- **C++ накладні витрати**: неконтрольоване використання механізму RTTI (`typeid`, `dynamic_cast`) та генерації виключень (`try`/`catch`/`throw`), що тягне за собою важкі таблиці розгортання стека (`.ARM.exidx`).

### Архітектурні критерії аудиту бібліотек

Перед включенням будь-якої бібліотеки у firmware слід проводити технічний аудит за такими критеріями:
1. **Стратегія роботи з пам’яттю**:
   Перевага надається бібліотекам із нульовим динамічним виділенням пам’яті (zero-allocation) або тим, що дозволяють передавати буфери пам’яті ззовні через API (caller-allocated memory). Наприклад, у серіалізаторі `nanopb` замість важкого Protocol Buffers виділення буферів відбувається статично або на стеку; у `FreeRTOS` використання функцій створення задач зі суфіксом `Static` (`xTaskCreateStatic`) дозволяє повністю обійтися без купи.
2. **Конфігурованість та модульність**:
   Якісні embedded-бібліотеки мають механізм тонкого налаштування через конфігураційні заголовні файли (наприклад, `FreeRTOSConfig.h`, `mbedtls_config.h`, `lwipopts.h`). Це дозволяє апаратно відсікти невикористовувані криптографічні шифри, мережеві протоколи чи режими планувальника ще на етапі компіляції.
3. **Безпека в контексті переривань (ISR-safety) та реентрабельність**:
   Перевірка, чи не використовує бібліотека глобальні змінні без захисту критичних секцій, та чи безпечно викликати її методи з обробників апаратних переривань.
4. **Сумісність ліцензій**:
   Використання виключно сумісних ліцензій (MIT, BSD, Apache 2.0). Ліцензії класу GPL (без винятку Linking Exception) заборонені для закритих комерційних прошивок, оскільки вимагають відкриття всього коду прошивки.

### Практики управління залежностями та ізоляція

Для збереження стабільності та відтворюваності вбудованого коду використовують перевірені інженерні підходи:
- **Фіксація версій через Git Submodules або Git Subtree**:
  Кожна зовнішня бібліотека додається у каталог `third_party/` чи `vendor/` із прив’язкою до конкретного тегу релізу або хешу коміту, виключаючи несподівані зміни інтерфейсів.
- **Використання пакетних менеджерів із профілями для крос-компіляції**:
  Сучасні менеджери (Conan, vcpkg) дозволяють чітко декларувати залежності, передавати прапорці крос-компілятора та фіксувати стан залежностей у lock-файлах.
- **Мінімалістичні альтернативи "важким" пакетам**:
  Замість стандартного `printf` застосовують компактні відкриті альтернативи (наприклад, `mpaland/printf`), які займають близько 1–2 КБ Flash і не потребують купи. Для формату JSON використовують бібліотеки зі статичним пулом пам’яті замість динамічних парсерів.

### Інструменти контролю Footprint у процесі збирання

Для запобігання потраплянню невикористовуваного коду в прошивку на рівні білд-системи застосовують прапорці компілятора та компонувальника[^gcc-overall-options]:
- `-ffunction-sections` та `-fdata-sections`: кожен метод і кожна змінна розміщуються в окремих мікросекціях об’єктного файлу.
- `-Wl,--gc-sections`: компонувальник утилізує (garbage collect) усі секції, на які немає явних посилань від точки входу програми або таблиці векторів[^dou-embedded-interview].
- `-fno-exceptions` та `-fno-rtti`: повне апаратне вимкнення механізмів виключень та динамічної типізації C++.
- **Аналіз карти пам’яті (Linker Map File)**: регулярна перевірка секції перехресних посилань (Cross Reference Table) у файлі `.map`, яка дозволяє виявити, чому конкретний модуль бібліотеки був підтягнутий у фінальний бінарник.
