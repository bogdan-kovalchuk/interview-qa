## Short answer

Компілятор робить inlining, dead-code elimination, constant propagation, loop optimization, instruction scheduling і LTO. MMIO перевіряй через `volatile` register definitions, barriers там, де потрібен порядок, disassembly/map review і target tests. <span class="warn">Busy delay loop без `volatile`, timer або intrinsic barrier може бути скорочений чи прибраний оптимізатором.</span>[^dou-embedded-interview]

## Detailed explanation

### Основні типи оптимізацій сучасного компілятора

Сучасні оптимізувальні компілятори (зокрема GCC та Clang) виконують глибоку трансформацію коду на проміжних рівнях представлення (GIMPLE, SSA, LLVM IR) з метою зменшення розміру бінарника або підвищення швидкодії[^gcc-overall-options]:

- **Inlining**: підстановка тіла функції безпосередньо в точку виклику. Усуває накладні витрати на пролог/епілог функції та передачу аргументів через регістри або стек, а також відкриває можливості для подальших локальних оптимізацій.
- **Dead-Code Elimination (DCE)**: виявлення та видалення інструкцій або цілих блоків коду, результати яких не впливають на спостережувану поведінку програми.
- **Constant Folding and Propagation**: обчислення виразів із відомими під час компіляції значеннями та підстановка обчислених констант у подальші інструкції замість звернення до пам’яті.
- **Loop Optimizations**: інваріантне винесення коду за межі циклів (Loop Invariant Code Motion, LICM), розгортання циклів (unrolling) та злиття або розщеплення ітерацій для покращення конвеєризації CPU.
- **Instruction Scheduling**: перестановка машинних інструкцій для уникнення простоїв процесорного конвеєра (pipeline stalls) через затримки читання даних або очікування результатів арифметичних операцій.
- **Link-Time Optimization (LTO)**: міжмодульна оптимізація під час компонування (`-flto`), яка дозволяє виконувати inlining та DCE між різними одиницями трансляції.

### Чому MMIO ламається при оптимізаціях і роль volatile

Апаратні периферійні регістри мікроконтролерів відображаються безпосередньо у фізичний адресний простір пам’яті (Memory-Mapped I/O, MMIO). Для компілятора операції MMIO виглядають як звичайні звернення до комірок оперативної пам’яті.

Згідно зі стандартом C ([^iso-c-n1570], розділ 5.1.2.3), компілятор оптимізує програму за правилом «якщо» (as-if rule): дозволено будь-які перетворення, доки зберігається спостережувана поведінка програми (observable behavior). До спостережуваної поведінки належать доступ до об’єктів із кваліфікатором `volatile`, запис у файли та завершення програми.

Якщо покажчик на апаратний регістр визначено без `volatile`:
1. **Кешування в регістрах CPU**: у циклі опитування прапорця (polling loop), наприклад `while (!(UART->SR & UART_SR_TXE))`, компілятор вважає, що пам’ять не може змінюватися сама по собі без явного запису з боку процесора. Тому значення регістру зчитується в регістр загального призначення `r0` лише один раз перед початком циклу, перетворюючи його на нескінченний зациклений перехід.
2. **Усунення повторних записів**: послідовні записи в один і той самий апаратний порт (наприклад, перемикання бітів для формування імпульсу на GPIO або запис байтів у FIFO) компілятор вважає надлишковими та видаляє всі попередні записи, залишаючи лише останній.

Правильне визначення регістру обов’язково використовує `volatile`:

```c
#define UART_SR   (*(volatile uint32_t *)(0x40004400U))
```

Кваліфікатор `volatile` гарантує, що кожне читання та запис у C-коді згенерує реальну асемблерну інструкцію звернення до пам’яті (`LDR`/`STR` в архітектурі ARM) у точній послідовності. Проте `volatile` не є апаратним бар’єром шини: на процесорах із неупорядкованим доступом, буферами запису або кешем (як-от ARM Cortex-M7 з інструкційним кешем та кешем даних I-Cache/D-Cache) для гарантії завершення та впорядкування транзакцій шини необхідно застосовувати апаратні бар’єри пам’яті `__DMB()` або `__DSB()` ([^armv7m-arm]).

### Деструкція порожніх циклів затримки (Busy Delay Loops)

Класична помилка початківців – створення програмних затримок за допомогою порожніх циклів:

```c
void delay_bad(uint32_t count) {
    for (uint32_t i = 0; i < count; i++) {
        /* Порожній цикл */
    }
}
```

З точки зору компілятора та стандарту C ([^iso-c-n1570]), цей цикл не виконує корисних обчислень і не взаємодіє з `volatile` змінними. На рівнях оптимізації `-O1`, `-O2` чи `-Os` оптимізатор повністю вирізає такий цикл через Dead-Code Elimination. Час виконання функції стає рівним нулю, що ламає протоколи ініціалізації датчиків, дисплеїв та мікросхем пам’яті[^dou-embedded-interview].

Для створення надійних затримок використовують:
- **Апаратні таймери**: лічильник SysTick або системний таймер периферії (наприклад, `DWT->CYCCNT` у ядрах Cortex-M3/M4/M7).
- **Компіляторний бар’єр та volatile асемблер**:

```c
void delay_nop(uint32_t count) {
    while (count--) {
        __asm__ volatile ("nop");
    }
}
```

Інструкція `__asm__ volatile` повідомляє оптимізатору про наявність сторонніх побічних ефектів, забороняючи видаляти ітерації або переставляти цикл за межі попередніх дій.

### Методи перевірки коректності оптимізації

Щоб переконатися, що оптимізатор не зламав взаємодію з периферією та таймінги:
1. **Аналіз дизасемблера (`objdump` / `GDB`)**: згенерований бінарник перевіряють командою `arm-none-eabi-objdump -d -S firmware.elf`. Необхідно переконатися, що всередині циклів опитування присутні інструкції читання з пам’яті `ldr`, а не просто повторний перехід `b`/`cbz` по вже завантаженому регістру.
2. **Перевірка карти пам’яті (`.map`)**: контроль того, що критичні функції не були вилучені компонувальником через `-Wl,--gc-sections` у разі надмірної оптимізації.
3. **Апаратна валідація на цільовій платі**: вимірювання затримок за допомогою перемикання тестового виводу GPIO та підключення цифрового осцилографа або логічного аналізатора.
