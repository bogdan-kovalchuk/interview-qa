## Short answer

Зафіксуй toolchain version, build container або package hash, CMake presets/options і dependency versions. У artifacts зберігай `.elf`, `.hex`/`.bin`, `.map`, symbol/version info, compiler flags і commit hash. **Version metadata** у firmware має дозволяти точно відтворити binary, який стоїть на пристрої.[^dou-embedded-interview]

## Detailed explanation

### Концепція відтворюваного збирання (Reproducible Builds) у Embedded

**Відтворюване збирання (Reproducible Build)** – це процес компіляції програмного забезпечення, за якого однаковий вихідний код, зафіксоване середовище збирання та однакові параметри інструментів завжди генерують бінарно ідентичний результат (біт-в-біт, однаковий хеш SHA-256) незалежно від часу збирання, операційної системи хоста чи абсолютного шляху до каталогу проекту[^dou-embedded-interview].

У розробці вбудованих систем це критично важливо з кількох причин:
- **Сертифікація та регуляторні вимоги**: у медичних виробах, автомобільній електроніці та авіації регулятори вимагають доказу того, що бінарний образ на пристрої відповідає перевіреному та протестованому вихідному коду релізу.
- **Аналіз польових помилок (Crash Post-Mortem)**: для точної розшифровки стека викликів і дампу регістрів при аварії в польових умовах необхідні налагоджувальні символи ELF саме того білду, який працює на конкретному пристрої.
- **Верифікація безпеки ланцюга постачання (Supply Chain Security)**: гарантія того, що в процес компіляції не було впроваджено сторонніх змін чи шкідливого коду.

### Усунення джерел недетермінізму компіляції

Недетермінізм у фінальному бінарнику виникає через кілька типових факторів компілятора GCC/Clang:

1. **Абсолютні шляхи файлової системи у DWARF та макросах `__FILE__`**:
   Якщо розробник компілює код у каталозі `/home/developer/project`, а сервер CI – у `/builds/runner/ci/project`, ці шляхи потрапляють у налагоджувальні секції ELF (`.debug_info`) та макроси виведення логів `assert(__FILE__)`, змінюючи бінарний образ.
   *Рішення*: застосування прапорця компілятора GCC `-ffile-prefix-map=<старий_шлях>=<новий_шлях>` або комбінації `-fdebug-prefix-map` та `-fmacro-prefix-map` ([^gcc-overall-options]), що нормалізує всі шляхи до відносних або уніфікованих (наприклад, `.`).
2. **Вбудовані часові мітки компіляції (`__DATE__`, `__TIME__`, `__TIMESTAMP__`)**:
   Використання цих макросів призводить до того, що кожна повторна компіляція тієї самої секунди генерує новий бінарник.
   *Рішення*: повна заборона макросів дати/часу або стандартизована заміна через механізм `SOURCE_DATE_EPOCH` (UNIX-час останнього коміту Git), який автоматично підтримується сучасними компіляторами.
3. **Порядок об’єднання об’єктних модулів**:
   Різні файлові системи повертають список файлів у різному порядку (через поведінку `readdir()`). Якщо передавати об’єктні файли лінкеру у невизначеному порядку, розташування функцій у Flash змінюватиметься.
   *Рішення*: суворе сортування списку вхідних файлів у білд-системі перед передачею компонувальнику.

### Фіксація середовища (Toolchain Pinning)

Для забезпечення повної ідентичності тулчейну застосовують:
- **Docker-контейнери з фіксованими хешами**: створення стандартизованого Dockerfile із фіксованою версією крос-компілятора (наприклад, `arm-gnu-toolchain-13.3.rel1`), версією CMake, Ninja та бібліотек Newlib.
- **Hermetic build systems або менеджери пакетів**: використання систем збирання класу Bazel чи пакетних менеджерів Nix / Conan із детальними файлами блокування (lockfiles), що верифікують контрольні суми всіх виконуваних бінарників.

### Вбудовування метаданих версії у Firmware Image

Для точної ідентифікації прошивки на реальному обладнанні метадані генеруються автоматично під час збирання:
- CMake викликає команду `git describe --tags --always --dirty`, яка генерує рядок версії на основі тегів Git (із прапорцем `-dirty`, якщо присутні незакомічені зміни).
- Метадані формуються у вигляді константної структури даних у спеціальній секції пам’яті (наприклад, `.version_info`):

```c
typedef struct {
    uint32_t magic;           /* Унікальний маркер прошивки */
    uint32_t version_major;
    uint32_t version_minor;
    uint32_t version_patch;
    char     git_commit[16];  /* Скорочений Git SHA */
    char     build_date[20];  /* Час коміту SOURCE_DATE_EPOCH */
    uint32_t crc32;           /* Контрольна сума образу */
} FirmwareMetadata_t;
```

Ця структура розміщується за фіксованим зміщенням у Flash через Linker Script ([^gnu-ld-manual]), що дозволяє завантажувачу або зовнішній діагностичній програмі зчитувати версію без розбирання бінарника.

### Комплект артефактів довготривалого зберігання

За результатами кожного релізного збирання в системі CI архівується повний пакет артефактів:
1. `firmware.elf`: виконуваний файл із повною таблицею символів і DWARF-метаданими для аналізу збоїв.
2. `firmware.bin` / `firmware.hex`: "чистий" бінарний образ для виробничого програмування.
3. `firmware.map`: повна карта лінкування із точними адресами та розмірами кожної функції та змінної.
4. `build_manifest.json`: файл маніфесту, що містить хеші SHA-256 усіх вихідних файлів, версію компілятора, параметри прапорців оптимізації та Git commit hash.
