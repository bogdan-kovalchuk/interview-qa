## Short answer

**Translation unit** – результат preprocessing одного `.c/.cpp` файлу разом з усіма included headers. Якщо header містить non-static object/function definition, вона потрапить у кожну translation unit і linker побачить multiple definitions. У C++ це також може порушити ODR; у headers лишають declarations, `inline`/`constexpr` або templates за правилами мови.[^dou-embedded-interview]

## Detailed explanation

### Поняття Translation Unit (Одиниця трансляції)

Згідно зі стандартом мови C ([^iso-c-n1570], розділ 5.1.1.1), вихідний файл (`.c` або `.cpp`) разом з усіма заголовними файлами, що підключаються через директиву `#include`, після завершення роботи препроцесора утворює **одиницю трансляції (Translation Unit, TU)**.

Препроцесор не аналізує семантику мови: він буквально копіює вміст кожного зазначеного заголовного файлу у вихідний потік, розгортає макроси `#define` та обробляє блоки умовного компілювання (`#ifdef`). Отримана одиниця трансляції передається компілятору і компілюється абсолютно ізольовано від інших файлів проекту у відповідний об’єктний файл (`.o`).

Кожен ідентифікатор у TU має певну область видимості (scope) та тип зв’язування (linkage):
- **Зовнішнє зв’язування (External Linkage)**: символ експортується в глобальну таблицю символів об’єктного файлу та доступний іншим TU під час компонування.
- **Внутрішнє зв’язування (Internal Linkage)**: модифікатор `static` обмежує видимість символу виключно поточною одиницею трансляції; інші TU його не бачать.
- **Відсутність зв’язування (No Linkage)**: локальні автоматичні змінні функцій та параметри.

### Механізм виникнення Multiple Definition у C

Найпоширеніша помилка розробника-початківця – розміщення визначення (definition) змінної чи функції у загальному заголовному файлі `.h`:

```c
/* config.h */
int system_timeout = 100; /* ВИЗНАЧЕННЯ глобальної змінної */

void reset_system(void) { /* ВИЗНАЧЕННЯ функції */
    /* ... */
}
```

Якщо `config.h` буде включено у два різні файли реалізації (`main.c` та `sensor.c`):
1. Препроцесор продублює цей код в обидві одиниці трансляції.
2. Компілятор успішно створить два об’єктні файли: `main.o` та `sensor.o`. В обох файлах у секції `.data` з’явиться глобальний символ `system_timeout`, а в `.text` – код функції `reset_system`, обидва із зовнішнім зв’язуванням (external linkage).
3. На етапі компонування лінкер виявить конфлікт однакових глобальних імен і зупинить збирання з помилкою:
   `ld: multiple definition of 'system_timeout'; main.o: first defined here`[^gcc-overall-options].

Поширена ілюзія – вважати, що від цього рятують директиви захисту від повторного включення (`#ifndef FOO_H ... #endif` або `#pragma once`). Include Guards запобігають дублюванню вмісту заголовка лише *в межах однієї й тієї самої* одиниці трансляції. Вони не мають жодної сили між різними TU.

Правильне вирішення у мові C:
- У заголовному файлі залишати виключно **оголошення (declarations)** через ключове слово `extern` та прототипи функцій:
  ```c
  /* config.h */
  extern int system_timeout;
  void reset_system(void);
  ```
- Власне **визначення (definition)** із виділенням пам’яті розміщувати лише в одному конкретному файлі реалізації (`config.c`).

### One Definition Rule (ODR) у мові C++

У мові C++ вимоги щодо єдиності визначень формалізовано правилом **One Definition Rule (ODR)**:
1. У межах будь-якої однієї одиниці трансляції (TU) не може бути більше одного визначення типу, змінної, функції чи шаблону.
2. У межах усієї програми звичайна функція або не-inline змінна повинні мати рівно одне визначення.
3. Класи, перелічення, inline-функції, шаблони та inline-змінні (починаючи з C++17) можуть бути визначені у кількох TU, проте їхні визначення зобов’язані бути бінарно ідентичними (складатися з однакових послідовностей токенів) і мати однаковий зміст.

**Підступна пастка: ODR Violation без діагностики лінкера (Ill-formed, No Diagnostic Required)**:
Якщо визначення структури або класу у заголовному файлі залежить від макросів компілятора, які налаштовані по-різному для різних модулів:

```cpp
/* sensor.h */
struct SensorData {
    uint32_t id;
#ifdef ENABLE_DIAGNOSTICS
    uint32_t debug_counter;
#endif
    float value;
};
```

Якщо `main.cpp` скомпільовано з прапорцем `-DENABLE_DIAGNOSTICS`, а `driver.cpp` – без нього, дві різні одиниці трансляції бачитимуть абсолютно різний розмір структури `SensorData` та різне зміщення (offset) поля `value` в пам’яті. Компонувальник не видасть жодної помилки, проте спроба доступу до поля `value` призведе до непомітного спотворення пам’яті (memory corruption) та випадкових відмов у runtime.

### Практичні інженерні правила для Embedded Headers

Для безпечного проєктування інтерфейсів у C/C++:
1. **Заголовні файли містять лише інтерфейси**: типи даних (`struct`, `enum`, `typedef`), константи (`#define` або `const`/`constexpr`), прототипи функцій та `extern` оголошення змінних.
2. **Короткі допоміжні функції**: оформлювати як `static inline` (у C) або `inline` (у C++). Модифікатор `static` надає функції внутрішнє зв’язування в кожній TU, а `inline` дозволяє компілятору підставити тіло безпосередньо в точку виклику без генерації окремого символу в таблиці лінкера.
3. **Поведінка `-fno-common`**: в старих версіях GCC змінні без `extern` у заголовках за замовчуванням трактувалися як tentative definitions (режим `-fcommon`), і лінкер "тихо" об’єднував їх в одну комірку пам’яті, приховуючи баги. Починаючи з GCC 10, за замовчуванням діє прапорець `-fno-common`, який суворо забороняє дублювання та вимагає чіткого використання `extern`[^dou-embedded-interview].
