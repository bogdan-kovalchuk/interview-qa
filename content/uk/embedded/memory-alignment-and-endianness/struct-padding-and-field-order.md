## Short answer

**Padding** – невикористані байти, які компілятор додає для alignment наступного поля або всієї структури. Якщо розташувати поля від більших alignment-вимог до менших, padding часто зменшується. <span class="warn">Не можна покладатися на padding bytes як на стабільні дані</span>: вони можуть бути неініціалізовані й не підходять для прямого порівняння чи передачі по шині.[^dou-embedded-interview]

## Detailed explanation

### Суть механізму: внутрішній та кінцевий padding

У мові C компілятор зобов’язаний розташовувати поля структури строго в порядку їхнього оголошення в коді, проте адреса кожного поля повинна задовольняти вимоги вирівнювання його типу.[^iso-c-n1570] Якщо наступне поле вимагає 4-байтового вирівнювання, а попереднє закінчилося на непарному зміщенні, компілятор вставляє байти заповнення – **padding**.

Розрізняють два типи заповнення:
1. **Internal padding (внутрішній):** байти між сусідніми полями структури, необхідні для вирівнювання наступного поля.
2. **Trailing / Tail padding (кінцевий):** байти після останнього поля структури. Вони необхідні для того, щоб загальний розмір структури `sizeof(T)` був кратний максимальному вирівнюванню серед усіх її членів `alignof(T)`. Без кінцевого padding кожен наступний елемент у масиві таких структур втрачав би коректне вирівнювання.

### Як порядок полів змінює розмір структури

Оскільки компілятор не має права самостійно змінювати черговість полів (це заборонено стандартом C), невдале розташування змінних призводить до появи численних дірок у пам’яті.[^iso-c-n1570]

Розглянемо дві структури з абсолютно однаковим набором даних:

```c
#include <stdint.h>

// Неоптимальний порядок: чергування малих і великих типів
struct Inefficient {
    uint8_t  flag1; // offset 0, розмір 1 байт
    // 3 байти internal padding
    uint32_t value; // offset 4, розмір 4 байти
    uint8_t  flag2; // offset 8, розмір 1 байт
    // 3 байти trailing padding
}; // sizeof = 12 байтів, корисних даних 6 байтів (50% втрати пам’яті!)

// Оптимальний порядок: сортування за спаданням розміру вирівнювання
struct Optimized {
    uint32_t value; // offset 0, розмір 4 байти
    uint8_t  flag1; // offset 4, розмір 1 байт
    uint8_t  flag2; // offset 5, розмір 1 байт
    // 2 байти trailing padding
}; // sizeof = 8 байтів, корисних даних 6 байтів (заощаджено 33% пам’яті)
```

В embedded-прошивках із масивами телеметрії, чергами повідомлень у RTOS або таблицями дескрипторів різниця між 12 та 8 байтами на 1000 елементів дає пряму економію 4 КБ обмеженої оперативної пам’яті (SRAM).

### Невизначеність байтів padding та ризики безпеки

Стандарт C явно визначає, що значення байтів padding є невизначеними (unspecified values).[^iso-c-n1570] Вони не ініціалізуються при звичайному присвоєнні полів структури.

Це породжує дві небезпечні пастки:
- **Помилкове порівняння через `memcmp`:** код `if (memcmp(&a, &b, sizeof(struct Inefficient)) == 0)` може повернути `false`, навіть якщо всі поля `flag1`, `value` і `flag2` абсолютно однакові. Причина в тому, що байти padding містять випадкове сміття зі стеку. Для коректного порівняння слід порівнювати кожне поле окремо.
- **Витік конфіденційних даних (Information Leak):** при відправці структури через радіоканал (BLE, Wi-Fi, LoRa), UART або збереженні у Flash байти padding передаються разом із корисними даними. У радіоефір або енергонезалежну пам’ять потрапляють фрагменти ключів шифрування чи попередніх викликів функцій зі стеку.

### Небезпека сліпого пакування (`__attribute__((packed))`)

Спроба прибрати padding за допомогою директиви `#pragma pack(1)` або атрибута `__attribute__((packed))` позбавляє структуру заповнення (`sizeof` стає 6 замість 8 або 12). Проте на 32-розрядних мікроконтролерах це має серйозну ціну:[^armv7m]
- На архітектурі ARM Cortex-M0/M0+ доступ до 32-бітного поля `value` за адресою 1 викликає фатальний апаратний fault (`HardFault`).[^armv7m]
- На Cortex-M3/M4 компілятор або генерує невирівняний доступ (який потребує додаткових тактів шини і викликає fault для інструкцій подвійних слів `LDRD` або при увімкненому `UNALIGN_TRP`), або при забороні невирівняного доступу (прапорець `-mno-unaligned-access`) змушений розгортати одну операцію в послідовність побайтових інструкцій `LDRB` із подальшими зсувами та операціями `ORR`, що збільшує розмір коду (Flash bloat) і суттєво сповільнює виконання.

### Інженерні правила проєктування

- Сортуйте поля структури за спаданням їхнього вирівнювання: `uint64_t` -> `uint32_t` -> `uint16_t` -> `uint8_t`.
- Якщо поля мають однаковий розмір, групуйте їх логічно.
- Якщо структуру необхідно передавати назовні або хешувати (наприклад, для CRC), обов’язково очищуйте її пам’ять перед заповненням: `memset(&data, 0, sizeof(data))`.
