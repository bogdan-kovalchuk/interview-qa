## Question code

```c
uint32_t ts = htonl(r->ts);
uint16_t v  = htons(r->val);
memcpy(&buf[0], &ts, 4);
memcpy(&buf[4], &v,  2);
buf[6] = r->id;
```

## Short answer

**Поле за полем, з явним byte order і фіксованими зсувами.**

Кожне багатобайтове поле спершу конвертується (`htonl`/`htons`), потім кладеться у відомий offset через `memcpy`. Однобайтове `id` не потребує swap.

Правило: `memcpy` тут ще й рятує від unaligned-trap, навіть якщо `buf` не вирівняний.[^iso-c-n1570][^embeddedinterviewlab]

## Detailed explanation

Серіалізація перетворює значення структури на послідовність байтів визначеного wire-формату. Формат потрібно задавати явно: порядок полів, ширину кожного поля, byte order багатобайтових чисел і правила для reserved або optional байтів. Не можна покладатися на те, що байтове представлення C-структури збігається з форматом протоколу: компілятор може вставляти padding, а представлення чисел залежить від реалізації.[^iso-c-n1570]

У наведеному фрагменті 32-бітне поле `ts` і 16-бітне `val` спершу перетворюються з host order у network order, а потім копіюються у визначені позиції. `id` має один байт і тому не потребує перетворення порядку байтів. Такий код передбачає, що `r` містить значення відповідних ширин, `buf` має щонайменше сім байтів, а формати полів протоколу справді відповідають 32, 16 і 8 бітам.[^embeddedinterviewlab]

`memcpy` копіює байти між об’єктами й не вимагає, щоб адреса призначення в буфері була вирівняна для `uint32_t` чи `uint16_t`. Це відрізняється від приведення `buf + offset` до вказівника на цілий тип і розіменування: такий доступ може порушити вимоги вирівнювання, а також створює ризики через правила доступу до об’єктів. Функції `htonl` і `htons` виконують перетворення значення, але самі по собі не визначають порядок полів чи їхні offsets.[^iso-c-n1570]

**Приклад розкладки:** перші чотири байти належать `ts`, наступні два – `val`, останній – `id`. Межі мають бути перевірені до запису, а розміри не варто повторювати як магічні числа в різних місцях: корисно прив’язати їх до wire-формату та перевіряти очікувану довжину повідомлення.

**Типові помилки:**

- Копіювати всю структуру й покладатися на її padding та native endianness.
- Вважати, що `htonl` серіалізує весь запис, хоча воно перетворює лише одне значення.
- Записувати багатобайтове поле через потенційно невирівняний typed pointer.

Такий підхід робить представлення повідомлення незалежним від розкладки структури в пам’яті. Під час тестування варто перевіряти конкретні очікувані байти для контрольних значень і виконувати ці тести на платформах з різним host byte order, якщо код має бути переносним.[^embeddedinterviewlab]
