## Short answer

**Alignment** змушує поля структури починатися з адрес, кратних вимогам їхніх типів або ABI. Компілятор може вставляти padding між полями й у кінці структури, тому фактичний layout не завжди дорівнює сумі розмірів полів.[^dou-embedded-interview] Для DMA, MMIO mirror-структур і binary protocol це критично: layout треба фіксувати явно або серіалізувати вручну.

## Detailed explanation

### Механізм вирівнювання та формування пам’яті (Memory Layout)

Згідно зі стандартом ISO C (§6.7.2.1) [^iso-c-n1570], елементи структури розташовуються у пам’яті послідовно відповідно до порядку їхнього оголошення. Проте адреса першого поля збігається з адресою самої структури, а кожне наступне поле повинно задовольняти вимоги вирівнювання свого типу. Щоб забезпечити це, компілятор вставляє байти заповнення (`padding bytes`):
1. **Внутрішнє заповнення (Internal Padding)**: якщо після однобайтового поля `uint8_t` оголошено чотирибайтове поле `uint32_t`, компілятор вставляє 3 байти заповнення, щоб адреса `uint32_t` була кратною 4.
2. **Кінцеве заповнення (Tail Padding)**: загальний розмір структури `sizeof` обов’язково округлюється вгору до величини, кратної найбільшому вирівнюванню серед усіх полів цієї структури. Кінцевий padding необхідний для того, щоб у масиві структур `struct SensorData arr[5];` кожен наступний елемент починався з коректно вирівняної адреси.

### Наочний приклад неефективного та оптимізованого layout

Розглянемо розміщення структури на типовому 32-розрядному мікроконтролері ARM Cortex-M [^armv7m-arm]:

```c
// Неефективна структура: сума розмірів полів = 6 байтів, але sizeof = 12 байтів!
struct SensorSampleBad {
    uint8_t  sensor_id; // 1 байт
    // [3 байти padding для вирівнювання timestamp]
    uint32_t timestamp; // 4 байти
    uint8_t  status;    // 1 байт
    // [3 байти tail padding для вирівнювання структури в масиві]
};

// Оптимізована структура: sizeof = 8 байтів
struct SensorSampleGood {
    uint32_t timestamp; // 4 байти (зсув 0)
    uint8_t  sensor_id; // 1 байт  (зсув 4)
    uint8_t  status;    // 1 байт  (зсув 5)
    // [2 байти tail padding, загальний розмір = 8, кратно 4]
};
```
Шляхом простого перегрупування полів вдалося заощадити 4 байти оперативної пам’яті на кожен екземпляр (33% економії). У буфері на 1000 вибірок це заощаджує 4 КБ RAM, що для мікроконтролера з 16–64 КБ SRAM є дуже суттєвою оптимізацією.

### Наслідки для MMIO, DMA та бінарних протоколів

У розробці вбудованих систем нерозуміння правил заповнення структури призводить до критичних несправностей:
- **Відображення карти регістрів периферії (MMIO)**: якщо структура використовується як шаблон доступу до апаратних регістрів мікроконтролера (наприклад, `GPIO_TypeDef` у CMSIS) [^armv7m-arm], неочікуваний padding зсуне адреси полів. Запис у поле конфігурації замість потрібного регістра потрапить в інший апаратний блок чи викликає `BusFault`.
- **Прямий доступ до пам’яті (DMA)**: контролер DMA передає сирі байти безпосередньо з FIFO шини в оперативну пам’ять без участі процесора. Якщо формат транзакції периферії не збігається з розташуванням полів у C-структурі через padding, зчитані дані будуть спотворені.
- **Мережеві протоколи та збереження у Flash**: поширеною помилкою є пряма відправка структур по інтерфейсах UART/CAN/SPI через `send(&data, sizeof(data))`. Оскільки правила заповнення залежать від архітектури CPU (32 біти проти 64 бітів), компілятора та прапорців оптимізації, такий пакет не є кросплатформним. Пакетні дані необхідно упаковувати явно побайтово або застосовувати строгі серіалізатори.
