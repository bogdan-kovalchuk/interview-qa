## Short answer

**Вирівнювання** означає, що поля структури розміщуються за адресами, кратними їхнім alignment-вимогам.[^dou-embedded-interview] Наприклад, `uint32_t` часто хоче адресу, кратну 4. Компілятор вставляє невикористані байти padding, щоб доступ був швидким і коректним для CPU.

Це важливо в embedded: misaligned access на деяких MCU повільний або викликає fault, а register/protocol layout може вимагати точних offset-ів. Розмір можна зменшити перестановкою полів від більших до менших, але для binary protocol або hardware registers краще явно серіалізувати дані або перевіряти layout через `static_assert` і `offsetof`.

## Detailed explanation

### Суть концепції та вимоги стандарту

Вимога вирівнювання (alignment requirement) – це обмеження цільової архітектури, згідно з яким об’єкт певного типу може розміщуватися в пам’яті лише за адресою, кратною його розміру або специфікованому ступеню двійки (зазвичай 1, 2, 4 або 8 байтів).[^iso-c-n1570]

Стандарт мови C гарантує такі правила розташування структури в пам’яті:[^iso-c-n1570]
1. Члени структури розміщуються в пам’яті строго в тому порядку, у якому вони оголошені в коді.
2. Адреса структури збігається з адресою її першого поля (offset першого елемента завжди дорівнює нулю).
3. Компілятор має право додавати порожні байти безіменного заповнення (padding) між будь-якими полями, а також після останнього поля, щоб задовольнити вимоги вирівнювання для кожного елемента та структури загалом.

Загальне вирівнювання всієї структури завжди дорівнює максимальному значенню вирівнювання серед усіх її полів.

### Апаратний рівень: чому це критично для мікроконтролерів

Більшість процесорних шин (наприклад, 32-бітна шина AHB-Lite в ARM Cortex-M) зчитують і записують дані блоками по 32 або 64 біти. Якщо 32-розрядне число `uint32_t` розташоване за адресою, кратною 4, процесор завантажує його за один машинний такт інструкцією `LDR`:[^armv7m]

- **ARM Cortex-M0 / Cortex-M0+ / Cortex-M1:** ядро взагалі не підтримує невирівняний доступ (unaligned access) на апаратному рівні. Спроба виконати `LDR` за адресою, некратною 4, негайно генерує апаратне виключення `HardFault`.[^armv7m]
- **ARM Cortex-M3 / Cortex-M4 / Cortex-M7:** ядра підтримують невирівняний доступ для базових інструкцій завантаження та збереження (`LDR`, `STR`, `LDRH`, `STRH`), проте він виконується за кілька тактів шини, що знижує швидкодію. Більше того, інструкції для роботи з подвійними словами (`LDRD`, `STRD`), множинне завантаження (`LDM`, `STM`) та операції FPU (`VLDR`, `VSTR`) вимагають строгого вирівнювання навіть на цих ядрах; інакше генерується `UsageFault` (UNALIGN trap при увімкненому біті `UNALIGN_TRP` у регістрі CCR).[^armv7m]
- **Доступ до регістрів периферії:** контролери пам’яті вимагають вирівняного доступу до областей типу Device та Strongly-Ordered. Невирівняний запис у регістр периферії апаратно викликає fault шини незалежно від налаштувань ядра.

### Приклад розташування полів і padding

Розглянемо структуру зі змішаними типами:

```c
#include <stdint.h>

struct SensorData {
    uint8_t  status;    // зміщення 0, розмір 1 байт
    // 3 байти padding (компілятор вирівнює наступний uint32_t на межу 4 байтів)
    uint32_t timestamp; // зміщення 4, розмір 4 байти
    uint16_t reading;   // зміщення 8, розмір 2 байти
    // 2 байти tail padding (вирівнювання всієї структури до кратності 4)
};
```

Повний розмір `sizeof(struct SensorData)` становить 12 байтів, хоча корисні дані займають лише `1 + 4 + 2 = 7` байтів. 5 байтів втрачаються на padding.

Кінцевий padding (tail padding) є обов’язковим: якби його не було, у масиві `struct SensorData arr[2]` другий елемент `arr[1]` починався б за зміщенням 10. Тоді його поле `timestamp` опинилося б за адресою `10 + 4 = 14`, яка не є кратною 4, що призвело б до помилки доступу на першому ж циклі обробки масиву.

### Типові помилки та пастки у прошивках

- **Кастування сирого буфера до вказівника на структуру:** популярний антипатерн `struct SensorData *pkt = (struct SensorData *)&rx_buffer[1];` для розбору пакетів, що надійшли по UART або SPI. Якщо буфер не вирівняний, перше ж читання 32-бітного поля призведе до `UsageFault` або падіння продуктивності.
- **Накладання структур на протоколи зв’язку:** відправка структури через `HAL_UART_Transmit(&huart1, (uint8_t*)&data, sizeof(data), 100)` призводить до того, що на шину передаються невизначені байти padding. Інший мікроконтролер із відмінною розрядністю або іншим компілятором прочитає хибні дані.
- **Зловживання атрибутом `__attribute__((packed))`:** усунення padding упаковкою структури часто здається легким рішенням, проте змушує компілятор генерувати важкий код побайтового збирання значень за допомогою інструкцій зсуву й маскування, або призводить до збоїв на інструкціях `LDRD`/`STRD`.

### Практичні інженерні рекомендації

- Впорядковуйте поля структури за спаданням вимог до вирівнювання: спочатку 64-бітні поля (`uint64_t`), потім 32-бітні (`uint32_t`, вказівники), потім 16-бітні (`uint16_t`) і наприкінці 8-бітні (`uint8_t`, `bool`).
- Для бінарних протоколів і пакетів зв’язку використовуйте явну побайтову серіалізацію та десеріалізацію через функції зсуву або `memcpy`.
- Фіксуйте критичне зміщення полів у коді за допомогою compile-time перевірок: `static_assert(offsetof(struct SensorData, timestamp) == 4, "offset error");`.
