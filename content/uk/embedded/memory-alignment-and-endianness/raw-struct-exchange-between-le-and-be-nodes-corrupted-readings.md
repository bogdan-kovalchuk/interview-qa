## Short answer

<span class="warn">Обмін сирими C-структурами між LE- і BE-вузлами не задає переносного формату даних.</span>

Порядок байтів числових полів, padding, вирівнювання та навіть розмір типів можуть залежати від реалізації. Конкретний offset поля й байти на дроті не можна вивести лише з назв M4 та PowerPC.

Захист: визначити wire-формат і серіалізувати кожне поле явно; перевіряти окремо його розмір та endian.[^iso-c-n1570]

## Detailed explanation

Сира копія C-структури між вузлами не є самодостатнім протоколом: її байти можуть мати різний зміст на іншій реалізації C або процесорі.[^iso-c-n1570]

У пам’яті struct може містити padding між полями та наприкінці. Стандарт C задає вимоги вирівнювання, але не фіксує універсальний offset кожного поля для всіх ABI. Окремо, багатобайтове ціле число має платформний порядок байтів. Тому однакові оголошення структури не гарантують однакового двійкового представлення на обох кінцях каналу.[^iso-c-n1570]

Не можна пояснити поведінку «працює для непарного ID, ламається для парного» лише endian або padding: ці властивості самі по собі не залежать від значення ID. Це спостереження вказує на ще одну помилку в декодуванні чи тесті й потребує перевірки фактичних байтів та layout обох збірок.

Приклад безпечнішого підходу: задати формат повідомлення як послідовність полів із визначеною шириною та порядком байтів, а потім кодувати й декодувати кожне поле окремо. Для діагностики збережіть hex-дамп повідомлення і перевірте offsets через `offsetof` у кожній збірці.

**Типові помилки:**

- Вважати, що `memcpy` серіалізує структуру або нормалізує endian.
- Вважати, що назва сімейства процесора визначає padding без перевірки ABI.
- Приписувати парність ID ефекту padding без відтворюваного доказу.

Специфікація формату має описувати wire-байти незалежно від внутрішнього layout структур у кожній програмі.
