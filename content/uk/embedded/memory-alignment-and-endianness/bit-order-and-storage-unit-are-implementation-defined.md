## Short answer

<span class="warn">C залишає реалізації вибір порядку bitfield-ів у storage unit та частину правил їх пакування.</span>

Різні ABI й компілятори можуть розмістити поля по-різному, тому однакова структура не задає переносиме представлення байтів для протоколу.

Для протоколів і регістрів задавай wire-формат явно й розбирай ціле значення масками та зсувами.[^iso-c-n1570]

## Detailed explanation

Bitfield – це поле структури із заданою шириною в бітах, але C не встановлює універсальну бітову розкладку такої структури в пам’яті. Реалізація може обрати addressable storage unit, а порядок виділення бітів усередині нього та деякі рішення про пакування залежать від реалізації; вирівнювання цього storage unit стандарт визначає як unspecified.[^iso-c-n1570]

Це важливо, коли структуру трактують як зовнішній формат. Два компілятори або ABI можуть розташувати перше поле з молодших чи старших бітів, по-різному перейти до наступної одиниці зберігання або додати padding. Кожна збірка може читати власні поля правильно, але байти в пам’яті не збігатимуться з форматом пакета чи регістра.[^iso-c-n1570]

Не плутай цей вибір із endianness. Endianness описує порядок байтів багатобайтового значення, тоді як правила bitfield визначають розкладку полів у storage unit; wire-формат може задавати обидва аспекти окремо. Твердження, що стандарт взагалі не визначає storage unit, надто широке: реалізація обирає достатню addressable unit, а стандарт установлює частину обмежень пакування.[^iso-c-n1570]

**Типові помилки:**

- Серіалізувати структуру з bitfield-ами без специфікації ABI та вважати отримані байти стабільними між платформами.
- Переносити опис регістра з документації чипа без перевірки правил компілятора й оголошення типів bitfield.

У протоколі читай байти згідно з його специфікацією, а потім виділяй поле з числового значення маскою та зсувом. Для memory-mapped регістрів також перевір вимоги виробника щодо ширини й атомарності доступу: звичайне поле структури не забезпечує цих апаратних гарантій.[^iso-c-n1570]
