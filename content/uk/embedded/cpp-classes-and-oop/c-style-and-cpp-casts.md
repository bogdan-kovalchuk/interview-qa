## Short answer

**C-style cast** виглядає як `(T)x` і може виконати одразу різні типи приведень: numeric conversion, зняття `const`, reinterpretation pointer-ів. Через це він короткий, але нечіткий і може приховати небезпечну операцію.[^dou-embedded-interview]

У C++ краще використовувати явні casts: `static_cast` для звичайних безпечніших перетворень, `const_cast` тільки для зміни cv-qualifier-ів, `reinterpret_cast` для низькорівневої переінтерпретації, `dynamic_cast` для runtime-перевірки в поліморфних класах. Вони довші, зате показують намір і легше знаходяться в коді.

## Detailed explanation

### Проблема C-style приведення типів

У мові C оператор приведення типу має єдиний синтаксис `(Type)expression`[^iso-c-n1570]. Під одним синтаксичним записом приховано принципово різні механізми: перетворення числових типів, переінтерпретація адреси покажчика, а також зняття кваліфікаторів `const` та `volatile`.

У C++ синтаксис `(Type)expression` трактується як послідовна спроба застосувати такі перетворення, зупиняючись на першому, яке успішно компілюється[^iso-cpp-n4861]:
1. `const_cast`
2. `static_cast` (з можливим подальшим розширенням доступу)
3. `static_cast`, за яким іде `const_cast`
4. `reinterpret_cast`
5. `reinterpret_cast`, за яким іде `const_cast`

Через таку поведінку C-style cast є надзвичайно небезпечним: якщо типи в проекті змінюються під час рефакторингу (наприклад, сигнатура структури чи успадкування), раніше безпечне приведення може непомітно деградувати до `reinterpret_cast` зі зняттям `const`, не видавши жодного попередження компілятора.

### Спеціалізовані оператори приведення в C++

Стандарт C++ запровадив чотири явні оператори, кожен із яких має чітко окреслену сферу відповідальності[^iso-cpp-n4861]:

1. **`static_cast<T>(v)`**:
   - Виконує перевірені на етапі компіляції безпечні перетворення: числові конверсії (`float` у `int32_t`), приведення покажчиків від похідного класу до базового (upcast), зворотне приведення (downcast) без runtime-перевірки, а також приведення з `void*`.
   - Забороняє зняття `const` або перетворення несумісних типів вказівників (наприклад, `int*` на `float*`).

2. **`const_cast<T>(v)`**:
   - Єдиний оператор, призначений виключно для додавання або зняття кваліфікаторів `const` та `volatile`.
   - Забороняє змінювати базовий тип об’єкта: спроба привести `const int*` до `double*` викличе помилку компіляції.

3. **`reinterpret_cast<T>(v)`**:
   - Здійснює побітове низькорівневе перетлумачення двійкового представлення одного типу як іншого (наприклад, приведення числової адреси до покажчика на структуру регістрів: `reinterpret_cast<UART_TypeDef*>(0x40001000)`).
   - Не генерує додаткових машинних інструкцій, але несе ризики порушення правила суворого псевдонімування (`strict aliasing`).

4. **`dynamic_cast<T>(v)`**:
   - Виконує безпечний downcast у поліморфних ієрархіях класів із перевіркою під час виконання за допомогою RTTI (Run-Time Type Information).
   - Якщо приведення покажчика неможливе, повертає `nullptr`. Для посилань у разі невдачі генерує виняток `std::bad_cast`.

### Специфіка використання в Embedded-розробці

- **Вимкнення RTTI**: У більшості прошивок для мікроконтролерів RTTI та механізм винятків вимикають прапорцями компілятора `-fno-rtti` та `-fno-exceptions` для мінімізації розміру Flash та забезпечення детермінованого часу виконання. Відповідно, `dynamic_cast` у таких проектах недоступний або заборонений стандартами кодування (MISRA C++).
- **Читабельність та пошук у коді**: Пошук `reinterpret_cast` та `const_cast` під час аудиту безпеки дозволяє миттєво знайти всі точки прямого звернення до апаратури та потенційно небезпечні місця кодової бази, що практично неможливо зробити з C-style кастами.
