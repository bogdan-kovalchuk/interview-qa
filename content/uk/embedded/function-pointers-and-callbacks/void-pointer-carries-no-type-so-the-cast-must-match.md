## Short answer

<span class="warn">Сам cast `void *` не перевіряє тип; undefined behavior виникає, якщо через результат неправильно звернутися до об’єкта.</span>

`void *` не містить runtime type information. Якщо callback очікує `struct Uart *`, а driver передав вказівник на `struct Spi`, compiler не перевірить відповідність після стирання типу; розіменування як `struct Uart` може порушити вимоги вирівнювання або правила доступу до типізованого об’єкта.[^iso-c-n1570]

Захист: роби registration API typed там, де можливо; перевіряй, що передано очікуваний об’єкт; не reuse-ь один callback signature для несумісних context object-ів без wrapper-а.[^iso-c-n1570]

## Detailed explanation

`void *` – універсальний тип вказівника на об’єкт у C: він не зберігає під час виконання відомості про початковий тип. Це робить його придатним для загального API на кшталт callback із context pointer-ом, але відповідальність за узгодження типу лишається програмі. Перетворення вказівника на об’єкт у `void *` і назад до того самого типу вказівника зберігає значення; сам cast не перевіряє, що переданий об’єкт має очікуваний тип.[^iso-c-n1570]

Проблема виникає, коли код отримує адресу одного об’єкта, але трактує її як вказівник на інший несумісний тип. Наприклад, якщо callback очікує `struct Uart *`, а зареєстрований context насправді вказує на `struct Spi`, cast до `struct Uart *` зазвичай компілюється. Помилка проявляється пізніше, коли код читає поле: адреса може бути неправильно вирівняна для цільового типу, а доступ через невідповідний lvalue порушує правила effective type/aliasing; наслідком є undefined behavior, пошкоджені дані або дефект, що залежить від оптимізації.[^iso-c-n1570]

Приклад: callback для UART може очікувати структуру з полями `rx_buffer` і `length`. Якщо замість неї передали стан SPI, той самий байтовий зсув може означати зовсім інше поле або виходити за межі об’єкта. Навіть коли обидві структури випадково мають однаковий розмір і вирівнювання, це не робить доступ через неправильний тип коректним. Результат не можна передбачити за одним лише cast-ом, а помилка може з’явитися тільки на іншій архітектурі чи після зміни оптимізації.[^iso-c-n1570]

Щоб уникнути помилки, поєднуйте реєстрацію callback і context в одній функції, документуйте очікуваний тип, а де інтерфейс це дозволяє – використовуйте типізований wrapper замість одного нетипізованого callback для різних структур. Перевірка magic field або версії може допомогти виявити помилку під час налагодження, але не замінює правильний тип і не виправляє невирівняний вказівник. Якщо callback зберігає context, перевіряйте також, що сам об’єкт ще існує під час виклику.[^iso-c-n1570]

**Типові помилки:**

- Вважати, що наявність явного cast-а гарантує сумісність об’єктів.
- Робити висновок про коректність доступу лише з того, що тест пройшов на одній платформі.

Під час перевірки простежте пару «місце реєстрації – місце читання»: який саме об’єкт передали, до якого типу його приводять, і чи відповідають його строк життя та вирівнювання очікуваному використанню.[^iso-c-n1570]
