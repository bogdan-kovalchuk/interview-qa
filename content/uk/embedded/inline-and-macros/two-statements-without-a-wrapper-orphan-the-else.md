## Question code

```c
#define RST() a(); b()

if (err)
    RST();
else
    ok();
```

## Short answer

<span class="warn">У наведеному прикладі розгортається у `if (err) a(); b(); else ok();`</span> – після окремого `b();` компілятор знаходить `else` без відповідного `if`, тому програма не компілюється.[^iso-c-n1570]

Тільки `a()` належить `if`, але в цьому прикладі наступний `else` спричиняє синтаксичну помилку; без `else` окремий `b();` виконувався б незалежно від умови.[^iso-c-n1570]

Захист: `#define RST() do { a(); b(); } while(0)` – тоді весь блок прив’язаний до `if`.[^iso-c-n1570]

## Detailed explanation

Проблема проявляється, коли такий макрос викликають як тіло `if` або `else` і після нього пишуть альтернативну гілку. У наведеному коді препроцесор замінює `RST()` двома statements, після чого парсер бачить `if (err) a(); b(); else ok();`. Перша інструкція `a();` є тілом `if`; друга, `b();`, є окремим наступним statement. Коли розбирач доходить до `else`, попередній `if` уже завершений, отже виникає синтаксична помилка unmatched `else`.[^iso-c-n1570]

Це конкретний наслідок граматики `if` у C та текстової природи макросу. Макрос не створює блоку автоматично: його replacement list вставляється до синтаксичного розбору. Тому форматування виклику на кількох рядках не змінює фактичної структури програми. Перевірити структуру можна, подивившись на розгорнутий препроцесором код.[^iso-c-n1570]

Є споріднений варіант з одним statement у макросі, наприклад `#define RST() a();`. Він не створює dangling `else`, але якщо до нього безпечно приєднати наступний statement `b();`, той усе одно виконуватиметься незалежно від умови. Саме тому рішення має забезпечити єдине statement тіло, а не просто прибрати `else` чи переставити відступи.[^iso-c-n1570]

Приклад виправлення: `#define RST() do { a(); b(); } while (0)`. Тоді весь блок є одним statement, і `if (err) RST(); else ok();` має однозначний розбір. Це не захищає від усіх макропасток: аргументи все ще можуть бути підставлені кілька разів, а типи не перевіряються як у функції. Якщо макрос не мусить бути statement-макросом, звичайна або `static inline` функція часто є яснішим вибором.[^iso-c-n1570]

**Типові помилки:**

- Звинувачувати відступи: вони не змінюють граматику після підстановки.
- Додавати фігурні дужки лише навколо зовнішнього `if`, не виправляючи структуру самого макросу.
- Узагальнювати, що `b()` у наведеному двооператорному прикладі виконається безумовно: саме цей текст із `else` не компілюється; без `else` друга дія була б окремою.
