## Question code

```c
#define SQR(x) ((x) * (x))
int a = 2;
int b = SQR(a++);
```

## Short answer

<span class="warn">Стандарт C не визначає результат цього виразу: це undefined behavior.</span>

Макрос підставляє аргумент у два місця: `((a++) * (a++))`. Дужки рятують від precedence, але не від double evaluation. Два інкременти одного scalar object у межах одного виразу не впорядковані між собою, тому стандарт C не визначає ні результат множення, ні фінальне значення `a`.

Захист: правильні дужки не лікують side effects; для аргументів з ефектами потрібна `static inline` функція або локальна змінна перед макросом.[^iso-c-n1570]

## Detailed explanation

Макрос `SQR(x)` текстово підставляє аргумент двічі, тому виклик `SQR(a++)` після preprocessing стає `((a++) * (a++))`. Це вже не один інкремент, а два side effects на тому самому scalar object в одному виразі. У C вони не впорядковані одне відносно одного; коли side effect на об’єкті не впорядкований щодо іншого side effect на ньому або щодо читання його значення, поведінка undefined.[^iso-c-n1570]

Отже, не можна сказати, що `a` збільшиться рівно двічі, або що `b` стане певним числом. Компілятор може видати попередження, згенерувати код, який на конкретному запуску виглядає очікуваним, або оптимізувати його інакше. Такий результат не створює гарантії для іншої збірки чи архітектури. Дужки навколо параметра в макросі допомагають з precedence, але не змінюють кількість його входжень.

Звичайна функція поводиться інакше: аргументний вираз обчислюється для передавання параметра один раз, а вже функція працює з отриманим значенням. Для square helper це може бути `static inline` із типізованим параметром. Якщо макрос все ж потрібен, передавайте лише вирази без side effects або спершу збережіть результат у локальну змінну, а тоді передайте її.

**Типові помилки:**

- Вважати, що `SQR(a++)` просто збільшує `a` двічі й повертає квадрат старого значення. Порядок side effects тут не визначений.
- Думати, що додаткові дужки виправляють повторну оцінку. Вони змінюють групування, а не кількість підстановок.
- Покладатися на результат одного компілятора без діагностики. Попередження може допомогти знайти дефект, але відсутність попередження не робить код коректним.
