## Short answer

При передачі масиву у функцію він <span class="warn">затухає (decays) до вказівника</span>: `void f(int arr[])` ≡ `void f(int *arr)`.

`sizeof(arr)` всередині функції = `sizeof(int*)` = 4 або 8 (розмір вказівника), а не розмір масиву.

Реальний кейс: змінили `int16_t buffer[256]` на `int16_t *buffer`, але залишили `sizeof(buffer)/sizeof(buffer[0])` -> обробляли лише 2 елементи замість 256.

Рішення: передавати розмір явно: `void f(int *arr, size_t n)`.[^embeddedinterviewlab]

## Detailed explanation

### Правило трансформації параметрів-масивів у стандарті C

У мові C масив ніколи не передається у функцію за значенням як цілісний об’єкт. Згідно зі стандартом ISO/IEC 9899 (C11, пункт 6.7.6.3 Function declarators, параграф 7), будь-яке оголошення параметра функції, що має тип «масив типу T», автоматично коригується (adjusted) компілятором до типу «вказівник на T» (`T*`).[^iso-c-n1570]

Це означає, що для транслятора такі сигнатури є абсолютно тотожними:

```c
void process_buffer(int arr[256]);
void process_buffer(int arr[]);
void process_buffer(int *arr);
```

Вказане у квадратних дужках число `256` компілятор повністю ігнорує під час перевірки типів. Параметр `arr` усередині тіла функції стає звичайною локальною змінною-вказівником типу `int*`, якій під час виклику передається адреса нульового елемента переданого масиву (array decay, пункт 6.3.2.1).[^iso-c-n1570]

### Поведінка оператора sizeof та розрядність платформи

Оператор `sizeof` обчислює розмір виразу на етапі компіляції виключно на основі його статичного типу (пункт 6.5.3.4).[^iso-c-n1570] Оскільки тип `arr` всередині функції було скориговано до вказівника `int*`, оператор `sizeof(arr)` повертає розмір самого вказівника на цільовій архітектурі:

- **4 байти** – на 32-розрядних мікроконтролерах (ARM Cortex-M, RISC-V RV32, ESP32);
- **8 байтів** – на 64-розрядних процесорах (AArch64, x86-64);
- **2 байти** – на 8/16-розрядних платформах (AVR ATmega, MSP430).

Справжній обсяг пам’яті вихідного буфера на стороні викликача при цьому повністю губиться.

### Реальні аварії в embedded: пошкодження буферів та помилки копіювання

Ця пастка є однією з найнебезпечніших причин виникнення критичних помилок у системних прошивках:

1. **Неповне очищення пам’яті (zeroing failure):** виклик `memset(arr, 0, sizeof(arr));` очистить лише перші 4 байти (одне 32-бітне слово), залишивши решту 255 слів неініціалізованими або заповненими залишками конфіденційних ключів шифрування чи старих пакетів.
2. **Усічення даних під час передачі:** `HAL_UART_Transmit(&huart1, (uint8_t*)arr, sizeof(arr), 100);` відправить по інтерфейсу лише 4 байти корисного навантаження замість усього кадру.
3. **Хибні лічильники циклу:** обчислення `size_t n = sizeof(arr) / sizeof(arr[0]);` дає значення `4 / 4 = 1`, через що цикл обробки виконає рівно одну ітерацію.

### Надійні патерни передачі масивів та статичний аналіз

Для запобігання втраті розміру вбудований код повинен дотримуватися безпечних практик:

- **Явна передача довжини:** завжди передавати розмір буфера окремим аргументом: `void process(int *arr, size_t length)`.
- **Кваліфікатор static у C99:** запис `void process(int arr[static 256]);` документує мінімально гарантований розмір буфера і дозволяє статичному аналізатору GCC генерувати попередження, якщо переданий аргумент має меншу довжину.
- **Вказівник на масив:** якщо розмір суворо фіксований, передавати вказівник на масив: `void process(int (*arr)[256]);`. Тоді `sizeof(*arr)` дасть точний розмір у `256 * sizeof(int) = 1024` байти.
- **Діагностика компілятора:** увімкнення прапорця `-Wsizeof-array-argument` у GCC або Clang змушує компілятор генерувати обов’язкове попередження при спробі взяти `sizeof` від параметра-масиву.[^gcc-warning-options]
