## Question code

```c
int **pp;
*pp = malloc(10*sizeof(int));
```

## Short answer

<span class="warn">Wild pointer – UB.</span> `int **pp;` – неініціалізований double pointer, містить garbage-адресу.

`*pp = malloc(...)` – розіменовує `pp` (UB!) і записує адресу виділеної пам’яті за невідомою адресою. Це може зіпсувати будь-яку область пам’яті.

Правильно:

```c
int *p = NULL;
int **pp = &p;
*pp = malloc(10*sizeof(int));
```

Завжди ініціалізуй вказівники перед використанням.[^embeddedinterviewlab]

## Detailed explanation

### Суть проблеми та стандарт ISO C

У наведеному фрагменті змінна `pp` оголошена як автоматична локальна змінна типу «вказівник на вказівник на `int`» (`int **`). Згідно зі стандартом ISO C (ISO/IEC 9899:2011, §6.7.9 та §6.3.2.1), неініціалізовані об’єкти з автоматичною тривалістю зберігання мають невизначене значення (`indeterminate value`), яке в розмовній практиці називають сміттям (garbage)[^iso-c-n1570].

Вираз `*pp = malloc(10 * sizeof(int))` виконується у два кроки:
1. Функція `malloc` виділяє блок динамічної пам’яті розміром 40 байтів і повертає його адресу.
2. Операція непрямої адресації `*pp` розіменовує вказівник `pp`. Оскільки значення `pp` не є дійсним покажчиком на об’єкт типу `int*`, розіменування призводить до невизначеної поведінки (`undefined behavior`)[^iso-c-n1570].

На практиці це означає, що адреса нововиділеного динамічного блоку записується за випадковою адресою, яку в той момент містив стек.

### Робота на рівні пам’яті та асемблера ARM Cortex-M

В архітектурі ARM Cortex-M локальні змінні розташовуються у стеку (`SP`) або у регістрах загального призначення. При вході у функцію покажчик стека зміщується, але пам’ять стека не очищається нулями – вона містить залишкові дані від попередніх викликів функцій або контекстів переривань.

В асемблері Thumb-2 для ARM Cortex-M цей код компілюється у таку послідовність інструкцій[^armv7m-arm]:

```assembly
MOVS    R0, #40             ; 10 * sizeof(int) = 40 байтів
BL      malloc              ; виклик malloc, результат (адреса) повертається в R0
LDR     R1, [SP, #pp_offset]; R1 = випадкове значення (wild pointer) зі стека
STR     R0, [R1]            ; запис адреси блоку за випадковою адресою в R1
```

Результат виконання інструкції `STR R0, [R1]` повністю залежить від випадкового значення у `R1`:
- **Помилка апаратної шини (`BusFault` або `HardFault`)**: якщо значення `R1` потрапляє у невикористану область пам’яті або намагається записати у Flash-пам’ять (`0x08000000` на STM32), контролер шини генерує відмову, переводячи ядро в обробник `HardFault`[^armv7m-arm].
- **Пошкодження критичних даних (Silent Data Corruption)**: якщо `R1` випадково вказує на дійсний діапазон SRAM (змінні іншого потоку FreeRTOS, стек, структуру периферійного дескриптора), запис перезапише ці дані. Програма продовжить роботу, але впаде у випадковому місці значно пізніше.
- **Втрата пам’яті (Memory Leak)**: покажчик на виділений буфер втрачається назавжди, оскільки його неможливо прочитати та звільнити через `free()`.

### Типова причина помилки та правильні шаблони

Розробник зазвичай припускається такої помилки, коли плутає рівні непрямої адресації (`indirection level`), намагаючись створити динамічний масив або передати подвійний вказівник як вихідний параметр (`out-parameter`).

Коректні варіанти реалізації:

1. **Якщо потрібен одновимірний динамічний буфер через вихідний параметр:**
   ```c
   int *p = NULL;
   int **pp = &p;                   // pp вказує на валідний вказівник p
   *pp = malloc(10 * sizeof(int));  // запис адреси безпосередньо у змінну p
   ```

2. **Якщо створюється двовимірний масив (масив вказівників):**
   ```c
   int **pp = malloc(10 * sizeof(int *)); // виділення пам’яті під масив адрес
   if (pp != NULL) {
       for (size_t i = 0; i < 10; i++) {
           pp[i] = malloc(20 * sizeof(int)); // виділення кожного рядка
       }
   }
   ```

### Практичні інженерні рекомендації

- Завжди ініціалізуйте вказівники при оголошенні: `int *p = NULL;`.
- Використовуйте попередження компілятора GCC/Clang: `-Wall -Wextra -Wuninitialized -Werror=uninitialized`.
- У статичному аналізі коду (MISRA C:2012 Rule 9.1) заборонено читати значення об’єктів з автоматичною тривалістю зберігання до їх явного запису.
- В embedded-системах намагайтеся уникати невиправданого використання динамічного виділення пам’яті (`malloc`/`free`) на користь статичних буферів, оскільки вичерпання або пошкодження купи (`heap corruption`) важко діагностувати без налагоджувача JTAG/SWD.
