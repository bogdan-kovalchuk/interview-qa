## Short answer

**Pointer cast + dereference**: `uint32_t x = *(uint32_t*)bytes;` – потенційний UB (strict aliasing, misalignment). Компілятор може оптимізувати "неправильно".

**memcpy**: `uint32_t x; memcpy(&x, bytes, 4);` – завжди коректно: не порушує aliasing, компілятор оптимізує до однієї інструкції LDR, якщо адресу вирівняно.

Правило: для type punning використовуй `memcpy` (або `union` у C). Pointer cast безпечний лише для `char*`/`unsigned char*`.[^embeddedinterviewlab]

## Detailed explanation

### Правило Strict Aliasing та його порушення

Згідно зі стандартом ISO/IEC 9899 (§6.5p7), доступ до збереженого значення об’єкта дозволено здійснювати лише через lvalue-вираз сумісного типу або через типи символів (`char`, `signed char`, `unsigned char`).[^iso-c-n1570] Це фундаментальне обмеження називається **`strict aliasing rule`**.

Коли розробник виконує пряме приведення вказівника для інтерпретації сирих байтів іншим типом даних (наприклад, зчитування 32-бітного цілого з байтового масиву):
```c
uint8_t buffer[4];
uint32_t val = *(uint32_t *)buffer; /* Порушення strict aliasing! */
```
Компілятор на рівні оптимізації `-O2`/`-O3` вважає, що вказівники несумісних типів ніколи не можуть посилатися на одну й ту саму область пам’яті. Оптимізатор може переставити місцями читання та запис або кешувати старе значення в регістрі процесора, що призводить до непомітних і вкрай важких для локалізації помилок під час виконання прошивки.[^iso-c-n1570]

### Апаратні обмеження вирівнювання (Data Alignment) на ARM Cortex-M

Другою критичною загрозою прямого приведення вказівників у вбудованих системах є вимоги апаратного вирівнювання адрес даних:[^arm-cortex-m0-alignment]
1. Байтний масив `uint8_t buffer[4]` може бути розміщений у пам’яті за довільною, зокрема непарною адресою (базове вирівнювання 1 байт).
2. Тип `uint32_t` вимагає 4-байтового вирівнювання (адреса повинна бути строго кратна 4).
3. **Cortex-M0 / Cortex-M0+:** Не підтримують невирівняний доступ до пам’яті на апаратному рівні. Інструкція `LDR`, виконана за адресою, некратною 4, миттєво генерує апаратний виняток `HardFault`.[^arm-cortex-m0-alignment]
4. **Cortex-M3 / M4 / M7:** Хоча ядра підтримують непарний доступ для звичайної оперативної пам’яті за рахунок додаткових тактів шини, доступ до областей `Device` та `Strongly-Ordered` (регістри периферії) або виконання інструкцій завантаження кількох слів (`LDM`, `STM`, `LDRD`) за невирівняною адресою так само викликає `UsageFault` або `HardFault`.[^arm-cortex-m0-alignment]

### Чому `memcpy` є найнадійнішим стандартом

Використання стандартної функції `memcpy` є повністю портативним і безпечним способом реінтерпретації бітового представлення даних (`type punning`):[^iso-c-n1570]
```c
uint32_t val;
memcpy(&val, buffer, sizeof(val));
```
- **Легальність зі стандарту:** Семантика `memcpy` визначена через копіювання послідовності `unsigned char`, що прямо дозволено винятком правила `strict aliasing` (ISO/IEC 9899 §6.5p7).[^iso-c-n1570]
- **Оптимізація компілятора:** Розробники іноді побоюються накладних витрат на виклик функції `memcpy`. Проте сучасні компілятори (GCC, Clang) розпізнають `memcpy` фіксованого розміру (1, 2, 4 або 8 байтів) як вбудовану функцію (`builtin`). Якщо адреса вирівняна, компілятор замінює виклик `memcpy` однією машинною інструкцією `LDR`. Якщо вирівнювання невідоме або не гарантоване, компілятор генерує оптимальну послідовність побайтового читання (`LDRB`), повністю уникаючи виклику бібліотечної функції та захищаючи від апаратних збоїв.[^embeddedinterviewlab]

### Порівняння з `union`

У мові C (починаючи з C99 TC3) читання неактивного поля об’єднання `union` формально дозволене для `type punning` (Annex J.5.7).[^iso-c-n1570] Проте у мові C++ така операція залишається суворим `undefined behavior` (де для бітового копіювання починаючи з C++20 введено шаблон `std::bit_cast`). Таким чином, `memcpy` залишається універсальним стандартом для обох мов.
