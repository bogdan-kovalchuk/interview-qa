## Question code

```c
int a=1,b=2;
int *p=&a,*q=&b;
printf("%d", p<q);
```

## Short answer

<span class="warn">Undefined behavior за стандартом C</span>. Реляційне порівняння (`<`, `>`) вказівників з різних об’єктів не визначено стандартом.

На практиці (більшість платформ, flat memory): результат залежить від розміщення змінних у пам’яті (порядок на стеку залежить від компілятора), тож не portable.

Дозволено: `p == q`, `p != q` – порівняння на рівність між будь-якими вказівниками. Реляційні – тільки в межах одного масиву.[^embeddedinterviewlab]

## Detailed explanation

### Вимоги стандарту ISO C щодо реляційного порівняння

Відповідно до стандарту ISO/IEC 9899 (§6.5.8p5), оператори реляційного порівняння (`<`, `>`, `<=`, `>=`) над вказівниками строго визначені **виключно тоді**, коли обидва вказівники вказують:[^iso-c-n1570]
- на один і той самий об’єкт або на елементи одного й того самого масиву (включно з адресою на один елемент за його межею `one-past-the-end`);
- на поля однієї й тієї самої структури (при цьому вказівник на пізніше оголошене поле структури порівнюється як більший).

Якщо два вказівники посилаються на незалежні, не пов’язані між собою об’єкти (як у наведеному прикладі зі змінними `a` та `b`), їхнє реляційне порівняння спричиняє **`undefined behavior` (невизначену поведінку)**.[^iso-c-n1570]

### Чому стандарт забороняє реляційне порівняння непов’язаних вказівників

Історично та архітектурно це обмеження пов’язане з сегментованими моделями пам’яті (наприклад, реальний режим x86, пам’ять окремих DSP або мікроконтролерів із банковою пам’яттю):[^embeddedinterviewlab]
- Вказівники на таких платформах складаються із сегмента (банка) та зміщення (`segment:offset`). Порівняння зміщень для різних сегментів позбавлене фізичного сенсу без ресурсомісткої нормалізації адреси.
- **Оптимізації компілятора:** Знаючи, що вираз `p < q` для непов’язаних об’єктів є `undefined behavior`, оптимізатор компілятора має право припустити, що ця гілка коду недосяжна, або підставити константне значення `0` чи `1` на власний розсуд, видаливши реальні перевірки під час оптимізації `-O2`/`-O3`.[^iso-c-n1570]

### Порівняння на рівність проти реляційного порівняння

На відміну від реляційних операторів, оператори рівності `==` та `!=` (ISO/IEC 9899 §6.5.9) повністю дозволені для будь-яких двох вказівників сумісного типу:[^iso-c-n1570]
- Вираз `p == q` гарантовано повертає `0` (false), оскільки змінні `a` та `b` є різними об’єктами з унікальними адресами в пам’яті.
- Вираз `p != q` гарантовано повертає `1` (true).

### Реальна поведінка на мікроконтролерах та безпечні альтернативи

На 32-бітних архітектурах із плоскою лінійною пам’яттю (ARM Cortex-M, RISC-V) вказівники фізично є 32-бітними числовими адресами:[^embeddedinterviewlab]
- Під час виконання процесор порівняє числові адреси змінних `a` та `b` на стеку. Результат (`0` або `1`) залежатиме виключно від того, у якому порядку компілятор вирішив розмістити змінні у стековому кадрі, а також від вирівнювання (`alignment padding`).
- Порядок розміщення локальних змінних у стеку не регламентується стандартом і може змінюватися між різними версіями компілятора, наборами прапорців чи навіть при додаванні нової непов’язаної змінної.
- **Як виконати коректне адресне порівняння:** Якщо системному програмісту дійсно необхідно перевірити відносне розташування адрес у пам’яті (наприклад, для перевірки, чи належить буфер до заданого регіону SRAM або перевірки перетину діапазонів пам’яті), вказівники необхідно явно привести до цілочисельного типу `uintptr_t` з `<stdint.h>`:[^iso-c-n1570]
  ```c
  if ((uintptr_t)p < (uintptr_t)q) {
      /* Порівняння цілих чисел є детермінованим і повністю безпечним */
  }
  ```
