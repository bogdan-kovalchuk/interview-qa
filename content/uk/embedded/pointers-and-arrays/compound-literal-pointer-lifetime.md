## Question code

```c
int *p = &(int){5};
printf("%d", *p);
```

## Short answer

**Так, коректно** у межах того ж блоку. `(int){5}` – compound literal (C99): тимчасовий об’єкт зі storage duration автоматичного блоку.

<span class="warn">Але dangling pointer</span> якщо вийти за межі блоку: `int *p; { p = &(int){5}; } *p; // UB – блок закінчився`

GCC може не попередити. Безпечне використання: лише у тому ж scope де literal визначений.[^embeddedinterviewlab]

## Detailed explanation

### Семантика compound literals та тривалість зберігання за стандартом C99

Синтаксис `(type-name){ initializer-list }`, представлений у стандарті C99 (пункт §6.5.2.5), створює складений літерал (compound literal).[^iso-c-n1570] На відміну від звичайних літералів-констант, складений літерал створює повноцінний безіменний об’єкт у пам’яті, який є lvalue, а отже, до нього можна застосувати унарний оператор взяття адреси `&`.

Тривалість існування (storage duration) цього об’єкта строго регламентована стандартом:
- Якщо складений літерал оголошено на рівні файлу (поза межами будь-якої функції), він має статичну тривалість зберігання (`static storage duration`), тобто існує впродовж усього часу роботи програми.
- Якщо складений літерал оголошено всередині тіла функції, він має автоматичну тривалість зберігання (`automatic storage duration`), прив’язану до найближчого блоку фігурних дужок `{ ... }`, у якому він визначений.[^iso-c-n1570]

У наведеному фрагменті покажчик `p` та літерал `(int){5}` оголошені в одному й тому самому блоці видимості. Об’єкт існує на стеку впродовж усього виконання блоку, тому розіменування `*p` під час виклику `printf` є повністю коректним і стандартизованим.

### Пастка часу життя (lifetime trap) та висячі вказівники

Основна небезпека compound literals криється у вкладених блоках та циклах. Як тільки потік виконання виходить за межі закривної фігурної дужки `}`, час життя об’єкта автоматично завершується:

```c
int *dangling_ptr;
{
    dangling_ptr = &(int){42};
} /* Час життя (int){42} закінчився тут */

printf("%d\n", *dangling_ptr); /* Undefined Behavior: доступ через висячий покажчик! */
```

Після виходу з блоку `dangling_ptr` перетворюється на висячий покажчик (dangling pointer). Пам’ять стека, де знаходилося значення 42, вважається вільною і буде перезаписана наступними викликами функцій або локальними змінними. Оскільки компілятори C (зокрема GCC та Clang) далеко не завжди генерують попередження на такі вкладені вирази, подібні баги можуть тривалий час залишатися непоміченими під час тестування.

### Практика використання у вбудованих системах та чергах повідомлень

У прошивках мікроконтролерів складені літерали часто використовують для зручної ініціалізації конфігураційних структур під час виклику функцій ініціалізації периферії:

```c
uart_init(&(uart_config_t){ .baudrate = 115200, .parity = PARITY_NONE });
```

Такий підхід повністю безпечний, якщо функція `uart_init` лише вичитує параметри або копіює структуру за значенням. Проте виникає критичний дефект, якщо функція драйвера або операційної системи RTOS зберігає отриманий покажчик у статичну змінну чи відправляє його в асинхронну чергу (queue):

```c
/* КРИТИЧНА ПОМИЛКА: черга зберігає покажчик на тимчасовий об’єкт у стеку */
os_queue_send(event_queue, &(event_msg_t){ .id = CMD_START }, sizeof(void*));
```

Коли завдання-обробник вичитає цей покажчик із черги, вихідна функція вже завершить роботу, її стек буде розмотано, а дані повідомлення – спотворено. Для асинхронної взаємодії в embedded C дані повинні або копіюватися у чергу за значенням, або розміщуватися у статичних/динамічних буферах із контрольованим часом життя.
