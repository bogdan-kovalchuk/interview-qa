## Question code

```c
uint8_t *p = (uint8_t*)0x1000;
p++;
printf("%p", (void*)p);
```

## Short answer

`0x1001`.

Pointer arithmetic масштабується по `sizeof(*p)`. Для `uint8_t*`: `sizeof(uint8_t) = 1`, тому `p++` -> адреса + 1 байт.

Якби `uint32_t *p = (uint32_t*)0x1000; p++;` -> `0x1004` (кроком 4 байти).

Правило: `p + n` = `(char*)p + n * sizeof(*p)`.[^embeddedinterviewlab]

## Detailed explanation

### Масштабування адресної арифметики за стандартом C

За стандартом ISO/IEC 9899 (§6.5.6 Additive operators, пункти 7–9), додавання цілого числа до вказівника масштабується на розмір об’єкта, на який цей вказівник посилається[^iso-c-n1570].
Фізична адреса обчислюється за правилом:
`Нова_адреса = Базова_адреса + n * sizeof(*p)`

У наведеному прикладі:
- `p` оголошено як `uint8_t*`, тобто вказівник на беззнаковий 8-бітний байт.
- За стандартом C99/stdint.h розмір `uint8_t` суворо дорівнює 1 байту (`sizeof(uint8_t) == 1`).
- Оператор постфіксного інкременту `p++` еквівалентний додаванню одиниці: `p = p + 1`.
- Зсув становить `1 * sizeof(uint8_t) = 1 * 1 = 1` байт.
- Отже, нова адреса дорівнює `0x1000 + 1 = 0x1001`.
- Специфікатор `%p` виведе значення `0x1001` (або `1001` залежно від реалізації стандартної бібліотеки).

### Порівняння поведінки з різними типами даних

Якби вказівник мав інший базовий тип, крок інкременту був би пропорційним розміру цього типу:
- `uint16_t *p = (uint16_t*)0x1000; p++;` змістить адресу на `1 * 2 = 2` байти, даючи результат `0x1002`.
- `uint32_t *p = (uint32_t*)0x1000; p++;` змістить адресу на `1 * 4 = 4` байти, даючи результат `0x1004`.
- `struct SensorPacket *p = (struct SensorPacket*)0x1000; p++;` при розмірі структури 24 байти змістить адресу на 24 байти, тобто до `0x1018`.

Такий підхід забезпечує універсальність: незалежно від складності типу даних, операція `p++` завжди переміщує вказівник на наступний логічний елемент масиву.

### Відображення в машинний код ARM Cortex-M

Процесори архітектури ARM мають розвинену систему індексації адрес у пам’яті[^armv7m-arm].
При проходженні масиву вказівником компілятор транслює адресну арифметику в високоефективні інструкції з пост-інкрементом або апаратним зсувом:
- Для `uint8_t`: `LDRB r0, [r1], #1` – завантаження байта в регістр `r0` з одночасним інкрементом адреси в `r1` на 1 байт за один машинний такт.
- Для `uint32_t`: `LDR r0, [r1], #4` – завантаження слова з автоматичним збільшенням адреси на 4 байти.
- Довільний індексний доступ `p[i]` для 32-бітних слів реалізується через базово-індексну адресацію зі зсувом: `LDR r0, [r1, r2, LSL #2]`, де індекс у регістрі `r2` апаратно множиться на 4 (зсув вліво на 2 біти) без додаткових витрат процесорного часу.

### Інженерні аспекти у вбудованому C

1. **Робота з послідовними інтерфейсами (UART, SPI, I2C)**: кадри даних та пакети протоколів надходять у вигляді потоку байтів. Використання `uint8_t*` є стандартом де-факто для буферів передачі та прийому, оскільки інкремент вказівника чітко відповідає зсуву на один отриманий байт.
2. **Небезпека зведення типів**: перетворення байтового буфера `uint8_t rx_buf[64]` до `uint32_t*` для швидкого парсингу призводить до того, що `p++` пропускатиме по 4 байти, а на платформах із суворим вирівнюванням (ARM Cortex-M0) непарна адреса буфера викличе апаратне виключення `HardFault`.
3. **Обмеження стандарту на арифметику**: стандарт C гарантує коректність адресної арифметики лише в межах виділеного масиву плюс один елемент за його межами (one-past-the-end element)[^iso-c-n1570]. Арифметика над довільними абсолютними числовими адресами (як у прикладі `0x1000`) є специфічною для embedded-систем і вимагає уважного контролю карти пам’яті контролера з боку розробника.
