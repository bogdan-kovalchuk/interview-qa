## Short answer

**Dangling pointer** – вказівник, що вказує на <span class="warn">вже звільнену або знищену</span> пам’ять.

Причини:

1. Повернення адреси локальної змінної: `int* f(){ int x=5; return &x; }` – x знищена при поверненні;
2. Після `free(ptr)` без обнулення: `free(ptr); *ptr = 1;` – undefined behavior (UB);
3. Вказівник на об’єкт, термін дії якого закінчився.

Небезпека: пам’ять <span class="warn">виглядає валідною</span> до її перевикористання. Баги надзвичайно важко відтворити.[^embeddedinterviewlab]

## Detailed explanation

### Механізм виникнення та невизначена поведінка (UB)

Висячий покажчик (dangling pointer) – це покажчик, який продовжує зберігати числову адресу об’єкта після завершення часу його життя (lifetime) або після звільнення відповідної області пам’яті.

Згідно зі стандартом C (ISO/IEC 9899 §6.2.4), щойно завершується час життя об’єкта, значення будь-якого покажчика, що посилався на нього, стає невизначеним (indeterminate).[^iso-c-n1570] Будь-яка спроба розіменувати такий покажчик для читання або запису є грубою невизначеною поведінкою (undefined behavior).

Головна підступність полягає в так званій «ілюзії валідності»: у фізичній пам’яті SRAM біти щойно звільненої комірки не стираються миттєво. На простих синтетичних тестах читання через висячий покажчик може повертати старе коректне значення, створюючи хибне враження працездатності коду. Проте за реального навантаження ця область негайно перезаписується іншими підсистемами.

### Типові сценарії: розмотування стека, купа та асинхронні переривання

У практиці вбудованого програмування виділяють три головні причини появи висячих покажчиків:

1. **Повернення адреси автоматичної змінної зі стека:**
   ```c
   int* get_temperature(void) {
       int temp = read_sensor();
       return &temp; /* КРИТИЧНО: пам’ять temp знищується під час повернення */
   }
   ```
   Під час виходу з функції процесор відновлює покажчик стека (`ADD SP, SP, #offset` або `POP`). Збережена адреса вказує на ділянку стека, яка буде перетерта першим же наступним викликом будь-якої іншої функції або апаратним кадром переривання (ISR stack frame).[^armv7m-arm]
2. **Використання після звільнення (use-after-free):**
   Виклик `free(ptr)` повертає блок динамічної пам’яті менеджеру купи (heap allocator). Змінна `ptr` при цьому залишається незмінною і продовжує зберігати стару адресу. Запис `*ptr = value` пошкоджує службові структури алокатора (заголовки блоків, двозв’язні списки вільних ділянок), що призводить до краху прошивки під час наступного виклику `malloc` або `free`.
3. **Реалокація буфера (`realloc`):**
   Якщо функція `realloc(buf, new_size)` переміщує блок пам’яті на нове місце, старий покажчик стає висячим. Усі інші покажчики, які посилалися на елементи старого буфера, також миттєво інвалідуються.
4. **Вихід із вкладеного блоку або завершення задачі RTOS:**
   Збереження покажчика на локальну змінну блоку `{ ... }` у глобальну структуру чи відправка адреси локальної структури в чергу повідомлень RTOS між завданнями з різними стеками.

### Наслідки у прошивках та методи інженерного запобігання

У мікроконтролерних системах наслідки розіменування dangling pointer зазвичай катастрофічні:
- **Тихе спотворення пам’яті (memory corruption):** запис через висячий покажчик перетирає випадкові глобальні прапорці, дескриптори завдань RTOS (TCB) або лічильники контурів керування.
- **Пошкодження адреси повернення:** якщо покажчик вказує на стек, запис може перезаписати збережений регістр `LR` (Link Register) або `PC` у стековому кадрі, через що під час інструкції `BX LR` процесор стрибне за випадковою адресою й викличе `HardFault`.[^armv7m-arm]
- **Вразливості безпеки:** у системах із підключенням до мережі (IoT) атаки класу use-after-free дозволяють зловмисникам захоплювати потік керування.

**Інженерні практики захисту:**
- **Обнулення після звільнення:** одразу після виклику `free(p)` записувати `p = NULL;` (розіменування нульового покажчика гарантовано викличе передбачуваний fault замість тихого псування даних).
- **Статичний аналіз та правила MISRA:** суворе дотримання правила MISRA C:2012 Rule 18.6, яке прямо забороняє копіювання адреси об’єкта з автоматичною тривалістю зберігання в об’єкти, що живуть довше за нього.
- **Передача буферів через виклик:** замість повернення покажчиків із функцій використовувати підхід із передачею виділеного буфера зверху вниз: `void get_temperature(int *out_temp)`.
- **Увімкнення попереджень компілятора:** прапорці `-Wall -Wextra -Wreturn-local-addr` на етапі збирання.
