## Question code

```c
int arr[256];
int *p=arr;
for(uint8_t i=0;
i<256;
i++) *p++=i;
```

## Short answer

<span class="warn">Так, це нескінченний цикл:</span> беззнаковий `uint8_t i` при `i=255` після `i++` згортається (wrap-around) у 0, тож умова `0 < 256` завжди істинна.

Цикл ніколи не завершується; виправлення: `for(int i=0; i<256; i++)` або `for(size_t i=0; i<256; i++)`.

GCC з `-Wtype-limits` попереджає про завжди істинну умову (типова помилка для буферів розміром 256).[^embeddedinterviewlab]

## Detailed explanation

### Причина виникнення нескінченного циклу

Наведений фрагмент коду є класичною пасткою переповнення цілих чисел (integer wrap-around) у мові C:[^iso-c-n1570]
- Змінна `i` оголошена з типом `uint8_t` (беззнакове 8-бітне ціле), діапазон значень якого становить від `0` до `255` (`UINT8_MAX = 2^8 - 1`).[^iso-c-n1570]
- Відповідно до правил цілочисельного підвищення типів (integer promotions, ISO/IEC 9899 §6.3.1.1), у виразі порівняння `i < 256` операнд `i` неявно підвищується до типу `int` зі збереженням числового значення.[^iso-c-n1570]
- Оскільки максимальне можливе значення для типу `uint8_t` дорівнює `255`, умова `i < 256` залишається **істинною абсолютно завжди** (для будь-якого допустимого значення, яке здатна прийняти змінна `i`).
- Згідно зі стандартом C (§6.2.5p9), переповнення беззнакових типів чітко визначене математичним модулем 2^n:[^iso-c-n1570] після досягнення значення `255` операція `i++` призводить до циклічного згортання значення (`wrap-around`) у `0`. У результаті умова виходу ніколи не стає хибною, і цикл продовжується нескінченно.

### Катастрофічні наслідки для пам’яті (Buffer Overflow)

На відміну від простого зациклення процесора, у цьому коді на кожній ітерації виконується інкремент вказівника та запис даних:
```c
*p++ = i;
```
1. Масив `arr` має розмір рівно 256 елементів типу `int` (у 32-бітних архітектурах це 256 * 4 = 1024 байти).
2. Після 256 ітерацій вказівник `p` виходить за межі виділеного буфера `arr`.
3. Оскільки масив зазвичай розміщується на стеку функції, подальший запис починає неконтрольовано перезаписувати сусідні локальні змінні, збережений покажчик кадру (`FP`), адресу повернення з функції (`LR / Return Address`) та системні дані стека процесора.
4. Це призводить до критичного руйнування стека (`stack corruption`), виникнення винятку `HardFault` під час спроби повернення з функції або до виконання стороннього коду через перетирання адрес переходу.[^embeddedinterviewlab]

### Поведінка сучасних оптимізуючих компіляторів

Сучасні компілятори (GCC та Clang) здатні виявити подібну конструкцію ще на етапі статичного аналізу:[^iso-c-n1570]
- За наявності прапорців `-Wall -Wextra` або `-Wtype-limits` компілятор видає діагностичне попередження: `warning: comparison is always true due to limited range of data type [-Wtype-limits]`.
- У разі ввімкнення оптимізації (`-O2` або `-O3`) компілятор аналізує, що умова завершення ніколи не досягається, а запис виходить за межі масиву (що є `undefined behavior`). Компілятор може повністю видалити перевірку виходу, згенерувати безумовний стрибок або навіть викинути весь наступний за циклом код як недосяжний, викликавши непередбачувану поведінку пристрою.

### Коректні варіанти реалізації

Для безпечної ітерації по буферах розміром 256 елементів застосовують один із таких підходів:

1. **Використання типу лічильника ширшого діапазону:**
   ```c
   for (size_t i = 0; i < 256; i++) {
       arr[i] = (int)i;
   }
   ```
2. **Ітерація через порівняння вказівників (Pointer Iteration):**
   ```c
   int * const end = arr + 256;
   for (int *p = arr; p != end; p++) {
       *p = (int)(p - arr);
   }
   ```
3. **Застосування циклу `do-while` (якщо тип обов’язково має бути `uint8_t`):**
   ```c
   uint8_t i = 0;
   do {
       arr[i] = i;
   } while (++i != 0);
   ```
