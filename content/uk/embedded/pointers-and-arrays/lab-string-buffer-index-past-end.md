## Question code

```c
char buf[4]="abc";
buf[4]='\0';
```

## Short answer

<span class="warn">Buffer overflow!</span> `char buf[4] = "abc"` ініціалізує `buf` значеннями `{'a','b','c','\0'}`. Масив має 4 елементи з індексами `0..3`, тому `buf[4]` – це п’ятий елемент, розташований за межами масиву.

Додаткова проблема: літерал `"abc"` уже містить `\0` на позиції 3, тому рядок від початку є коректно завершеним.

Якби було `char buf[3] = "abc"` – у C компілятор запише три символи без `\0` (усікання без помилки), а в C++ видасть помилку; розмір буфера завжди має бути не меншим за довжину рядка + 1 байт для термінатора (`>= len + 1`).[^embeddedinterviewlab]

## Detailed explanation

### Суть дефекту: помилка на одиницю (Off-by-one Error)

У наведеному фрагменті коду поєднано дві взаємопов’язані помилки: грубе порушення меж масиву (*buffer overflow*) та нерозуміння правил ініціалізації рядків у мові C.

Згідно зі стандартом ISO/IEC 9899:201x (C11), пункт 6.7.9 (пункт 14), ініціалізація символьного масиву рядковим літералом `char buf[4] = "abc";` копіює всі байти рядка разом із неявним нульовим термінатором [^iso-c-n1570]. Рядковий літерал `"abc"` складається з чотирьох символів: `'a'`, `'b'`, `'c'` та `'\0'`.
Масив `buf` має розмір 4 елементи з допустимими індексами `0`, `1`, `2` та `3`:
* `buf[0] = 'a'`
* `buf[1] = 'b'`
* `buf[2] = 'c'`
* `buf[3] = '\0'` (рядок уже коректно завершений нуль-термінатором!)

Операція `buf[4] = '\0';` намагається записати значення у п’ятий елемент масиву. Оскільки індекс `4` виходить за межі виділеного об’єкта, цей запис є класичним виходом за межі пам’яті (*buffer overflow*), що викликає `undefined behavior` [^iso-c-n1570].

### Наслідки у стеку викликів мікроконтролера ARM Cortex-M

Якщо масив `buf` оголошений як локальна змінна функції, він розміщується у стеку. Наслідки запису за межі масиву залежать від структури стекового кадру:
1. **Пошкодження суміжних змінних**: безпосередньо за адресою `buf + 4` може зберігатися інша локальна змінна (наприклад, прапорець статусу або лічильник циклу). Запис нуля спотворює логіку роботи програми.
2. **Спрацьовування канарейки стека (Stack Canary)**: при складанні з прапорцем `-fstack-protector` компілятор розташовує спеціальне контрольне слово за локальними буферами. Запис `\0` за адресою `buf[4]` пошкоджує канарейку, викликаючи виклик функції `__stack_chk_fail()` та аварійний рестарт системи.
3. **Пошкодження адреси повернення (Return Address)**: якщо апаратний захист відсутній, перезапис може спотворити значення регістра зв’язку `LR` (Link Register), збережене у стеку при виклику підпрограми. При поверненні з функції процесор здійснить перехід за невалідною адресою, що спричинить виняток `HardFault` або `UsageFault` (INVSTATE).

### Тонкощі ініціалізації: C проти C++

Варто відзначити різницю між стандартами C та C++ щодо розміру рядкового буфера:
* **У мові C (C11 §6.7.9 p14)** дозволено запис `char buf[3] = "abc";` [^iso-c-n1570]. У цьому випадку компілятор копіює три символи, відкидаючи нуль-термінатор без помилки компіляції. Масив виявляється незавершеним, і будь-яка спроба викликати `strlen(buf)` або `printf("%s", buf)` призведе до виходу за межі при читанні.
* **У мові C++** аналогічний запис `char buf[3] = "abc";` викликає обов’язкову помилку компіляції (*initializer-string for char array is too long*), оскільки стандарт C++ забороняє втрату завершального нуля.

### Інженерні практики запобігання

* **Автоматичне визначення розміру**: якщо рядок ініціалізується фіксованим літералом, дозвольте компілятору самостійно обчислити необхідний розмір:
  ```c
  char buf[] = "abc"; /* Розмір автоматично стає рівним 4 байтам */
  ```
* **Запас під термінатор**: при оголошенні фіксованого буфера завжди закладайте константу розміру:
  ```c
  #define MAX_NAME_LEN 3
  char buf[MAX_NAME_LEN + 1] = "abc";
  ```
* **Попередження компілятора**: вмикайте прапорці `-Wall -Wextra -Warray-bounds -Wstringop-overflow`. Сучасні компілятори GCC та Clang на етапі збирання попереджають про очевидний запис за межі масиву `buf[4]`.
