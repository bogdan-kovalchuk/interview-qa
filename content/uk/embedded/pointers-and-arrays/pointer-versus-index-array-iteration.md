## Short answer

Pointer iteration: `for(int *p=arr; p!=arr+n; p++) use(*p);` Index iteration: `for(int i=0; i<n; i++) use(arr[i]);`

На сучасних компіляторах з оптимізацією (`-O2`): **код зазвичай ідентичний** – компілятор сам перетворює між формами.

Але: pointer iteration уникає повторного обчислення базової адреси (`arr + i` кожен раз). Без оптимізації pointer може бути швидшим. У embedded (без оптимізації): pointer iteration ефективніша для Cortex-M0.[^embeddedinterviewlab]

## Detailed explanation

### Дві парадигми ітерації: вказівники проти індексів

У мові C обхід масиву можна реалізувати двома канонічними шляхами (ISO/IEC 9899 §6.5.2.1):[^iso-c-n1570]
```c
/* Варіант 1: Ітерація через індекс */
for (size_t i = 0; i < N; i++) {
    process(arr[i]);
}

/* Варіант 2: Ітерація через вказівник */
int * const end = arr + N;
for (int *p = arr; p != end; p++) {
    process(*p);
}
```
Хоча обидва підходи семантично еквівалентні, їхнє виконання на рівні машинного коду залежить від цільової архітектури мікроконтролера та рівня оптимізації компілятора.[^embeddedinterviewlab]

### Різниця в машинному коді без оптимізації (-O0)

При вимкненій або мінімальній оптимізації (часто під час покрокового відлагодження у flash-пам’яті):[^armv7m-arm]
1. **Індексна ітерація:** На кожній ітерації компілятор зобов’язаний виконати вираз `arr[i] == *(arr + i)`. Це потребує: завантаження значення `i` з пам’яті стека, множення на розмір елемента (`LSL #2` для 4-байтних цілих чисел), додавання до базової адреси масиву `arr` і, нарешті, зчитування значення за отриманою адресою.
2. **Ітерація через вказівник:** Адреса поточного елемента вже міститься безпосередньо у змінній-вказівнику `p`. Для переходу до наступного елемента достатньо виконати швидке додавання фіксованої константи: `p++` транслюється в одну інструкцію `ADDS r0, r0, #4` або використання постинкрементного завантаження `LDR r1, [r0], #4`.[^armv7m-arm]
Тому в неоптимізованому коді обхід через вказівники виконується помітно швидше і займає менше машинних тактів.

### Робота оптимізатора (-O2, -O3): індукційні змінні та згортання

При ввімкненні сучасних рівнів оптимізації різниця між обома формами практично нівелюється завдяки алгоритмам оптимізатора:[^embeddedinterviewlab]
- **Зниження вартості операцій (Strength Reduction) та усунення індукційних змінних (Induction Variable Elimination):** Компілятор GCC або Clang автоматично перетворює індексну форму у вказівникову, замінюючи повторне обчислення `arr + i * 4` на інкремент базової адреси в регістрі процесора.
- **Апаратні режими адресації Thumb-2 (ARM Cortex-M3/M4/M7):** Архітектура підтримує інструкції завантаження зі зсувом регістра за один такт шини без додаткових витрат: `LDR r0, [r1, r2, LSL #2]` (де `r1` – база `arr`, `r2` – індекс `i`). В результаті машинний код для обох варіантів стає **абсолютно ідентичним**.[^armv7m-arm]
- **Векторизація та розгортання циклів (Loop Unrolling & SIMD):** При оптимізації під ядра з обчислювальними розширеннями (наприклад, Cortex-M4 з DSP або Cortex-M55 з Helium) компілятор самостійно розгортає цикли та використовує інструкції пакетного читання кількох слів (`LDMIA` або векторні `VLDR`), незалежно від синтаксису у вихідному коді C.[^armv7m-arm]

### Специфіка молодших ядер (ARM Cortex-M0/M0+) та інженерні висновки

- **Cortex-M0 / M0+:** Архітектура ARMv6-M має обмежений набір інструкцій Thumb-1. Вона не підтримує постинкрементні адресації або довільні зміщення з масштабуванням у більшості інструкцій `LDR`. На цих ядрах ітерація через вказівники генерує менший бінарний розмір і потребує менше регістрів загального призначення, що критично в умовах жорсткого дефіциту флеш-пам’яті.[^embeddedinterviewlab]
- **Безпека та читабельність (MISRA C):** У промисловому коді та стандартах функціональної безпеки перевагу часто надають **індексній ітерації**: вона значно легше піддається статичному аналізу, гарантує строгий контроль діапазону індексів і мінімізує ризик випадкового виходу вказівника у заборонені ділянки пам’яті (buffer overflow).
