## Question code

```c
int arr[5];
arr[5] = 0;
```

## Short answer

<span class="warn">Out-of-bounds write -> undefined behavior.</span> Валідні індекси: `0..4`, а `arr[5]` – за межами масиву.

У пам’яті `arr[5]` знаходиться одразу за масивом: це може бути інша локальна змінна, адреса повернення, saved LR, тож наслідки – тихе пошкодження даних або crash при поверненні з функції (зіпсована адреса повернення).

Захист: `-fsanitize=address`, явні перевірки індексів, `static_assert(i < ARRAY_SIZE)`.[^embeddedinterviewlab]

## Detailed explanation

### Семантика меж масиву та статус one-past-the-end у стандарті C

В оголошенні `int arr[5];` створюється суцільний масив із п’яти елементів типу `int`. За стандартом ISO/IEC 9899 (C11, пункт 6.5.2.1), валідними індексами для доступу до елементів є діапазон від `0` до `4` включно.[^iso-c-n1570] Вираз індексації `arr[5]` синтаксично еквівалентний розіменуванню зміщеного вказівника `*(arr + 5)`.

Стандарт C (пункт 6.5.6 Additive operators) дозволяє обчислювати адресу елемента, наступного одразу за останнім елементом масиву – так званий вказівник one-past-the-end (`&arr[5]` або `arr + 5`).[^iso-c-n1570] Обчислення такого вказівника є коректним і широко використовується для перевірки умов завершення циклів (наприклад, у патернах `for (int *p = arr; p < arr + 5; ++p)`). Проте стандарт суворо забороняє розіменування цього граничного вказівника: операція `*(arr + 5)` або запис `arr[5] = 0;` виходить за межі виділеного об’єкта і є класичним out-of-bounds доступом, що спричиняє undefined behavior (пункт J.2).[^iso-c-n1570]

### Наслідки виходу за межі масиву в пам’яті embedded-систем

У мікроконтролерах із пласкою адресацією та відсутністю повноцінного MMU наслідки несанкціонованого запису за межі масиву залежать від секції пам’яті, де розміщено `arr`:

- **Стек (локальна змінна):** згідно з ABI (наприклад, ARM AAPCS для Cortex-M), стек росте вниз. Запис `arr[5] = 0;` адресує 4 байти безпосередньо над буфером у кадрі стека. Це призводить до перезапису сусідніх локальних змінних, збереженого регістра кадру (R7/R11) або збереженої адреси повернення (Link Register, LR). Якщо пошкоджується адреса повернення, функція коректно завершить своє тіло, але під час виконання інструкції `BX LR` процесор здійснить перехід за невалідним або спотвореним значенням (наприклад, зі скинутим нульовим бітом адреси Thumb-режиму), що миттєво викличе HardFault або UsageFault (INVSTATE).
- **Секції .bss або .data (глобальна або статична змінна):** масив розміщується в оперативній пам’яті (SRAM) поряд з іншими глобальними структурами. Запис у `arr[5]` тихо спотворює стан змінної, розміщеної лінкером за адресою завершення `arr`. Якщо там розташовано лічильник таймера, дескриптор DMA або прапорець стану FSM, система стикається з важковловлюваним збоєм реального часу (heisenbug).

### Вплив undefined behavior на оптимізації компілятора

Сучасні компілятори (GCC, Clang) будують дерево оптимізацій, спираючись на припущення, що програма не містить невизначеної поведінки. Якщо компілятор виявляє запис `arr[5] = 0;`, він має право вважати дану гілку виконання недосяжною або припустити, що розмір масиву насправді більший. Це призводить до агресивного видалення наступних перевірок у коді (dead code elimination) або перевпорядкування операцій запису в пам’ять.

### Захисні механізми та виявлення на етапі збирання

Для запобігання подібним дефектам у вбудованому ПЗ застосовують комплексну стратегію захисту:

- **Попередження компілятора:** прапорці `-Wall -Wextra -Warray-bounds -Wstringop-overflow` змушують GCC діагностувати вихід за межі масиву ще під час трансляції коду, якщо індекс відомий статично.[^gcc-warning-options]
- **Стекові канарки:** прапорець `-fstack-protector-strong` вставляє перед збереженим LR магічне число (canary word), перевірка якого перед виходом із функції генерує виклик аварійного обробника у разі пошкодження стека.
- **Статичні перевірки:** макроси перевірки індексів на етапі компіляції (`_Static_assert` у C11) для константних виразів.
- **Апаратний захист (MPU):** налаштування Memory Protection Unit дозволяє розмістити захисні сторінки (guard pages) навколо стека та критичних структур ядра, перетворюючи тихе руйнування пам’яті на миттєвий MemManage Fault.
