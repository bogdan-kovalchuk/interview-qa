## Short answer

Без `volatile` компілятор може:
1. <span class="warn">Кешувати</span> значення регістру у CPU регістрі і не перечитувати (пропустить апаратну зміну);
2. <span class="warn">Видалити "зайві" записи</span> (dead store elimination) – якщо значення не читається далі;
3. <span class="warn">Переупорядкувати</span> операції для оптимізації.

З `volatile`: кожен read/write реально виконується у порядку написання.

Патерн: `volatile uint32_t * const GPIOA_ODR = (volatile uint32_t*)0x40020014U;`[^embeddedinterviewlab]

## Detailed explanation

Вбудоване програмування мікроконтролерів базується на механізмі Memory-Mapped I/O (MMIO), де регістри керування, конфігурації та статусу периферійних модулів (GPIO, UART, SPI, таймери) відображаються безпосередньо у загальний 32-бітний адресний простір пам’яті процесора. Кваліфікатор типу `volatile` є обов’язковим інструментом для взаємодії з такими регістрами через покажчики.[^iso-c-n1570]

### Кваліфікатор volatile та спостережувана поведінка програми (Observable Behavior)

Стандарт ISO/IEC 9899 (§6.7.3 Type qualifiers, пункт 7) визначає, що доступ до об’єкта з кваліфікатором `volatile` має побічні ефекти (side effects), які не піддаються звичайному аналізу потоку керування програми.[^iso-c-n1570]

Відповідно до концепції «абстрактної машини C» (§5.1.2.3 Program execution), компілятор має право здійснювати будь-які агресивні оптимізації коду за правилом «as-if», за однієї фундаментальної умови: зовнішня спостережувана поведінка програми (observable behavior) не повинна змінюватися. До спостережуваної поведінки стандарт C відносить виключно:
1. Послідовність звернень до `volatile`-об’єктів;
2. Операції введення/виведення (I/O через файлові потоки);
3. Стан даних під час завершення виконання програми.

Таким чином, для будь-якої змінної або адреси, позначеної `volatile`, оптимізатор компілятора позбавлений права видаляти або спрощувати читання чи записи, а також змінювати порядок звернень відносно точок слідування (sequence points).[^iso-c-n1570]

### Що відбувається без volatile: три типові збої прошивки

Якщо взаємодіяти з апаратними регістрами через звичайний покажчик (наприклад, `uint32_t *reg = (uint32_t *)0x40020014;`), оптимізатор компілятора (`-O2` або `-O3`) застосує стандартні перетворення, які призведуть до відмови обладнання:[^embeddedinterviewlab]

1. **Кешування у регістрах CPU (Missing Hardware Updates):**
   При очікуванні готовності периферійного пристрою за прапорцем статусу:
   ```c
   uint32_t *uart_sr = (uint32_t *)0x40004400;
   while (!(*uart_sr & (1 << 7))) { /* очікування TXE */ }
   ```
   Компілятор вважає, що пам’ять не може змінюватися сама собою, оскільки в тілі циклу записів немає. Оптимізатор одноразово зчитує `*uart_sr` у регістр `r0` перед початком циклу і зациклює перевірку `r0`. Якщо при вході прапорець був 0, програма зависає у вічному циклі, навіть коли периферія вже встановила біт у реальному залізі.
2. **Видалення «зайвих» записів (Dead Store Elimination):**
   При формуванні тактового імпульсу або стробу скидання:
   ```c
   *ctrl_reg = 0x01; // увімкнути строб
   *ctrl_reg = 0x00; // вимкнути строб
   ```
   З погляду компілятора, перший запис є «мертвим» (dead store), оскільки його результат одразу затирається нулем без жодного проміжного читання. Компілятор повністю викидає перший запис, тому на фізичному виводі мікроконтролера імпульс взагалі не з’являється.
3. **Перевпорядкування інструкцій (Instruction Reordering):**
   Компілятор може змінити послідовність налаштування бітів конфігураційного регістру та біта активації периферії заради мінімізації затримок конвеєра, що порушує суворий порядок ініціалізації з даташиту.

### Машинний код ARM Cortex-M: різниця між звичайним та volatile доступом

При наявності `volatile` кожна операція читання строго транслюється в інструкцію `LDR`, а кожен запис – в інструкцію `STR` на системній шині:[^armv7m-arm]

```assembly
// Код із volatile: реальний доступ до шини AHB/APB
    LDR     r1, =0x40020014   // адреса GPIOA_ODR
    LDR     r2, [r1]          // реальна шинна транзакція читання (LDR)
    ORR     r2, r2, #1        // встановлення біта 0
    STR     r2, [r1]          // реальна шинна транзакція запису (STR)
```

При цьому важливо пам’ятати: кваліфікатор `volatile` керує виключно генерацією інструкцій компілятором. Він не є апаратним бар’єром пам’яті ядра ARM і не захищає від перевпорядкування шинних транзакцій апаратним контролером шин чи буфером запису (write buffer). Для апаратної синхронізації в ядрах Cortex-M4/M7 додатково використовують інструкції архітектурних бар’єрів `__DMB()` (Data Memory Barrier) та `__DSB()` (Data Synchronization Barrier).[^armv7m-arm]

### Стандартні патерни оголошення регістрів

1. **Ідіома константного покажчика на volatile-дані:**
   ```c
   // Значення в регістрі може апаратно змінюватися, але сам вказівник є незмінним:
   volatile uint32_t * const GPIOA_ODR = (volatile uint32_t *)0x40020014UL;
   ```
2. **Патерн CMSIS на основі структур:**
   У промислових бібліотеках виробників MCU (CMSIS від ARM) застосовується макрос `__IO` (що розгортається у `volatile`):[^armv7m-arm]
   ```c
   typedef struct {
       __IO uint32_t MODER;   // Mode register
       __IO uint32_t OTYPER;  // Output type register
       __IO uint32_t OSPEEDR; // Output speed register
       __IO uint32_t ODR;     // Output data register
   } GPIO_TypeDef;

   #define GPIOA ((GPIO_TypeDef *)0x40020000UL)
   ```
