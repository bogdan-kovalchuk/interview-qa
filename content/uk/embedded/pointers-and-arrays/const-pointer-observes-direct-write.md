## Question code

```c
int x=5;
const int *p=&x;
x=10;
printf("%d",*p);
```

## Short answer

`10`.

`const int *p = &x` – вказівник на const int: забороняє змінювати `*p` (через цей вказівник). Але `x` – не const, тож зміна `x = 10` через пряме ім’я – легальна.

`*p` читає значення `x` = 10. `const` захищає від запису через `p`, але не робить `x` незмінним – це важлива відмінність: `const int *p` vs `const int x`.[^embeddedinterviewlab]

## Detailed explanation

### Механізм виконання та read-only view через покажчик

Програма виведе `10`. Щоб зрозуміти цей результат, необхідно чітко розрізняти властивості самого об’єкта в пам’яті та властивості типу покажчика, через який здійснюється доступ:

1. Змінна `x` оголошена як звичайне змінюване ціле число (`int x = 5;`). Її пам’ять виділена в доступній для запису області (SRAM або стек), і пряме присвоєння `x = 10;` є абсолютно коректною стандартизованою операцією.
2. Оголошення `const int *p = &x;` створює покажчик, який надає інтерфейс «тільки для читання» (read-only view) до комірки пам’яті `&x`.[^iso-c-n1570]
3. Кваліфікатор `const` у цьому випадку накладає обмеження виключно на операції модифікації через покажчик: вираз `*p = 20;` призведе до помилки компіляції (`assignment of read-only location`). Проте `const` жодним чином не перетворює саму змінну `x` на незмінну константу.
4. Оскільки `p` зберігає фізичну адресу `&x`, під час виконання операції розіменування `*p` процесор зчитує поточний вміст цієї адреси. Оскільки значення було змінене на 10 через прямий ідентифікатор `x`, функція `printf` виводить актуальне число 10.

### Константний покажчик проти константного об’єкта

Принципова різниця полягає в тому, де саме був створений об’єкт:

- **Змінний об’єкт через `const*` (наш випадок):** об’єкт `x` мутабельний. Покажчик лише обмежує випадкову модифікацію через конкретний інтерфейс. Будь-яка інша функція або прямий доступ можуть безпечно змінювати `x`.
- **Константний об’єкт (`const int x = 5;`):** об’єкт первинно оголошений як константа. У мікроконтролерах лінкер може розташувати його безпосередньо у Flash-пам’яті (секція `.rodata`). Якщо спробувати обійти захист примусовим приведенням типу `int *hack = (int*)&x; *hack = 10;`, це призведе до невизначеної поведінки (undefined behavior, ISO C §6.7.3 пункт 6).[^iso-c-n1570] На апаратному рівні спроба запису у Flash викличе фатальне переривання `BusFault` або `HardFault`.

### Оптимізації компілятора, аліасинг та необхідність volatile в embedded

Коли компілятор бачить весь контекст функції, його аналізатор псевдонімів (alias analysis) фіксує зв’язок `p == &x`. Побачивши послідовність `x = 10; printf("%d", *p);`, оптимізатор (`-O2`) може навіть не виконувати реальних інструкцій читання з пам’яті через регістр `LDR`, а просто підставити константу 10 у регістр `R1` перед викликом `printf`.

Проте у вбудованих системах виникає інша критична ситуація:
Якщо змінна `x` модифікується асинхронно – наприклад, у перериванні (ISR) чи модулем DMA, а основний потік чекає на прапорець через покажчик `const int *p`:
```c
/* НЕБЕЗПЕЧНО для ISR/DMA */
while (*p == 5) {
    /* Очікування завершення DMA */
}
```
Оскільки покажчик не має кваліфікатора `volatile`, компілятор вважає, що значення пам’яті не може змінюватися ззовні без явних операцій запису в поточному потоці. Оптимізатор завантажить `*p` у регістр процесора один раз перед циклом і створить нескінченний цикл, проігнорувавши оновлення `x` перериванням.

Для коректного спостереження зовнішніх або асинхронних модифікацій у firmware тип обов’язково комбінують із `volatile`:
```c
const volatile int *p = &x;
```
Такий запис гарантує захист від випадкового запису прошивкою (`const`), але зобов’язує компілятор генерувати реальний фізичний цикл читання з шини на кожній ітерації (`volatile`).
