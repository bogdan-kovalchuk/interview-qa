## Short answer

В **C**: присвоєння `void*` до `T*` (і навпаки) не потребує explicit cast – автоматичне перетворення, тож `int *p = malloc(n);` – коректно у C.

В **C++**: <span class="warn">обов’язковий explicit cast</span>: `int *p = (int*)malloc(n);`.

Обмеження void*:
- Не можна розіменувати без cast;
- Не можна pointer arithmetic (стандарт C);
- Не зберігає type-safety.

Перед розіменуванням: `*(int*)vp = 42;`. Це правило зберігає правильний тип доступу.[^embeddedinterviewlab]

## Detailed explanation

### Семантика void* у стандарті C та відмінності від C++

Тип `void*` є універсальним нетипізованим вказівником на об’єкт (generic pointer). Він здатний зберігати адресу будь-якого об’єкта даних у пам’яті, проте позбавлений інформації про реальний тип і розмір цих даних.[^iso-c-n1570]

Між мовами C та C++ існує фундаментальна різниця в правилах перетворення типів:
- **У мові C (ISO/IEC 9899 §6.3.2.3):** Покажчик на будь-який тип об’єкта може неявно (автоматично) перетворюватися на `void*`, і навпаки – `void*` неявно перетворюється на покажчик на будь-який цільовий тип без явного приведення (cast).[^iso-c-n1570]
  ```c
  int *p = malloc(10 * sizeof(int)); // абсолютно коректно у C
  ```
  Явне приведення `(int*)malloc(...)` у мові C вважається надлишковим, а в історичних стандартах C89 могло маскувати помилку відсутності включення заголовка `<stdlib.h>`.
- **У мові C++ (ISO/IEC 14882 §7.3.12):** З міркувань безпеки типізації неявне перетворення з `void*` на типізований покажчик заборонене.[^iso-cpp-n4861] Необхідно обов’язково вказувати явне приведення типів (`static_cast<int*>(ptr)` або C-style cast `(int*)ptr`).

### Фундаментальні обмеження нетипізованого покажчика

Через те, що тип `void` є незавершеним типом (incomplete type), використання `void*` має жорсткі обмеження:[^iso-c-n1570]
1. **Неможливість прямого розіменування:**
   Вираз `*vp` не компілюється, оскільки компілятор не знає, скільки байтів потрібно прочитати або записати (1, 2, 4 чи 8 байтів) і як інтерпретувати двійковий код комірки (як ціле число, число з рухомою комою чи структуру). Для доступу до даних обов’язковий явний cast до конкретного типу: `*(int*)vp = 42;`.
2. **Заборона адресної арифметики:**
   Операції `vp++`, `vp + 1` або `vp1 - vp2` заборонені стандартом C, оскільки крок зміщення вказівника визначається як `sizeof(*p)`, а для `void` оператор `sizeof` не визначений. Примітка: компілятор GCC містить розширення (GNU extension), яке вважає `sizeof(void) == 1`, проте використання арифметики над `void*` порушує переносність коду за стандартом ISO C.

### Ризики вирівнювання (Alignment) та безпеки типів у вбудованих системах

Використання `void*` у прошивках пов’язане з потенційними апаратними пастками:[^iso-c-n1570]
- **Порушення апаратного вирівнювання:** Стандарт гарантує, що покажчик на об’єкт можна безпечно привести до `void*` і назад до **початкового** типу. Проте, якщо передати буфер байтів через `void*` і привести його до `uint32_t*`, адреса може виявитися некратною 4. На мікроконтролерах ARM Cortex-M0 це викличе фатальне апаратне виключення `HardFault`.
- **Повна втрата контролю типів:** Компілятор позбавлений можливості перевірити, чи відповідає переданий блок пам’яті очікуванням приймача. Якщо функція очікує вказівник на `struct MotorConfig`, а через `void*` передано покажчик на `int`, помилка проявиться лише під час виконання як важкодіагностоване спотворення пам’яті.

### Типові патерни використання у прошивках (RTOS, HAL, Callbacks)

Попри обмеження, `void*` незамінний для побудови універсальних інтерфейсів:[^embeddedinterviewlab]
- **Контекст зворотного виклику (User context / Callback data):**
  ```c
  typedef void (*button_cb_t)(void *context);
  ```
  Функція реєстрації приймає покажчик на екземпляр драйвера або структуру конфігурації користувача.
- **Вхідні параметри задач RTOS:**
  У FreeRTOS функція створення задачі `xTaskCreate` приймає параметр `void * const pvParameters`, який потім всередині тіла задачі безпечно розпаковується у відому структуру конфігурації.
