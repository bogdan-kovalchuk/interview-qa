## Question code

```c
int arr[3]={1,2,3};
int *p=arr;
p--;
printf("%d",*p);
```

## Short answer

<span class="warn">Так, undefined behavior (UB).</span> `p = arr` вказує на `arr[0]`. Операція `p--` формує адресу `arr - 1`, що лежить <span class="warn">поза межами масиву</span>.

Допустимі вказівники для `arr[3]`: від `arr` (= `arr + 0`) до `arr + 3` (one-past-the-end). `arr - 1` – це UB вже на етапі обчислення адреси, а не лише при її розіменуванні.

Оптимізатор компілятора припускає, що UB у коді відсутнє, що призводить до непередбачуваних оптимізацій (видалення коду чи перевпорядкування); отже, формувати `arr - 1` заборонено стандартом.[^embeddedinterviewlab]

## Detailed explanation

### Вимоги стандарту ISO C до адресної арифметики

Згідно зі стандартом ISO/IEC 9899:201x (C11), пункт 6.5.6 (Additive operators, p8), адресна арифметика суворо регламентує межі об’єкта, на який посилається вказівник [^iso-c-n1570]. Якщо вказівник адресує елемент масиву, додавання чи віднімання цілого значення є валідним лише тоді, коли результуючий вказівник вказує на елемент того самого масиву або на один елемент за його межами (так званий *one-past-the-end pointer*).

Якщо обчислення виходить за ці межі, виникає `undefined behavior` (невизначена поведінка) безпосередньо в момент обчислення адреси [^iso-c-n1570]:
* Для масиву `int arr[3]` законними є значення вказівника від `&arr[0]` до `&arr[3]` включно (при цьому `arr + 3` дозволено лише формувати для порівняння меж, але заборонено розіменовувати).
* Вираз `p--`, де `p == &arr[0]`, формує значення `arr - 1`. Оскільки воно розташоване перед початком масиву, сам факт обчислення такого вказівника порушує стандарт і спричиняє `undefined behavior`.
* Розіменування `*p` у виклику `printf("%d", *p)` є повторним проявом `undefined behavior`, оскільки виконується читання пам’яті за невалідною адресою.

### Поведінка на рівні процесора ARM Cortex-M та компілятора

На рівні апаратних інструкцій архітектури ARM Cortex-M локальний масив `arr` розміщується у стековому кадрі (`stack frame`). Покажчик стека `SP` (r13) резервує пам’ять зміщенням униз.

Операція `p--` транслюється компілятором в інструкцію віднімання:
```assembly
SUBS    r1, r1, #4       @ r1 містив адресу arr[0], тепер r1 = arr - 4
LDR     r0, [r1]         @ спроба завантажити слово за адресою перед масивом
```

На рівні мікроконтролера наслідки залежать від контексту виконання:
1. **Зчитування непередбачуваних даних**: в архітектурі ARM Cortex-M використовується спадний стек (full-descending stack за AAPCS, де адреси стека зменшуються вниз). Збережені регістри кадру (`LR`, `R7`) розташовані за вищими адресами, а `arr - 1` (зміщення на 4 байти нижче `&arr[0]`) вказує в бік дна стека. За цією адресою можуть міститися інші локальні змінні, виділені нижче `arr`, або невиділена пам’ять за поточним покажчиком `SP` (де зберігаються залишкові дані попередніх викликів або куди під час виклику переривання процесор апаратно збереже стек-фрейм).
2. **Апаратний виняток (Fault)**: якщо стек задачі FreeRTOS розташований на межі області SRAM, а блок захисту пам’яті (MPU) налаштований на виявлення виходу за межі стека, читання спричинить `MemManage` або `HardFault`.
3. **Агресивна оптимізація компілятора (-O2 / -O3)**: оптимізатор спирається на припущення, що `undefined behavior` у коректному коді відсутнє. Якщо компілятор виявляє декремент нижче початку масиву, він може припустити, що ця гілка коду недосяжна, і повністю видалити виклик `printf` або змінити порядок виконання сусідніх інструкцій.

### Типові пастки у прошивках

Поширена помилка у вбудованих системах виникає під час спроби реалізувати зворотний обхід буфера:

```c
/* ПОМИЛКА: формування вказівника arr - 1 на останній ітерації */
int *p = &arr[2];
while (p >= arr) {
    send_uart((uint8_t)*p);
    p--;
}
```

Після обробки елемента `arr[0]` операція `p--` обчислює `arr - 1`. Навіть якщо умова `p >= arr` зупиняє цикл на наступній перевірці, вказівник `p` уже отримав невалідне значення, що формально є `undefined behavior` [^iso-c-n1570]. На деяких сегментованих або DSP-архітектурах це може викликати переповнення адресного регістра.

### Практичні інженерні рекомендації

* **Використовуйте індексацію для зворотних циклів**: замість декременту вказівників застосовуйте змінні типу `size_t` або звичайні індекси:
  ```c
  for (size_t i = 3; i > 0; --i) {
      send_uart((uint8_t)arr[i - 1]);
  }
  ```
* **Дотримуйтесь вимог MISRA C**: правило MISRA C:2012 Rule 18.1 вимагає, щоб адресна арифметика генерувала вказівники виключно всередині масиву або допустиму адресу `one-past-the-end`.
* **Застосовуйте санітайзери під час хостового тестування**: запуск тестів із прапорцями `-fsanitize=undefined,address` гарантовано виявляє вихід за нижню межу масиву ще до прошивання у мікроконтролер.
