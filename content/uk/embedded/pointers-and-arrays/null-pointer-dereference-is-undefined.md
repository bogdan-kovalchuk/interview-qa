## Short answer

**NULL pointer** – гарантовано невалідна адреса (null pointer constant): у C визначений як `0` або `(void*)0`, у C++ – `nullptr`.

Розіменування NULL -> <span class="warn">undefined behavior</span>. На Cortex-M: адреса `0x00000000` – початок Flash (Vector Table), тож запис туди -> HardFault або пошкодження Vector Table.

Захист: завжди перевіряй перед розіменуванням: `if(p != NULL) *p = val;`; Ініціалізуй: `int *p = NULL;`[^embeddedinterviewlab]

## Detailed explanation

### Визначення NULL pointer за стандартом C

За стандартом ISO/IEC 9899 (§6.3.2.3 Pointers, пункт 3), цілочисельний константний вираз зі значенням 0 або такий вираз, приведений до типу `void*` (наприклад, `0` або `(void*)0`), називається константою нульового вказівника (null pointer constant)[^iso-c-n1570].

Макрос `NULL` визначено в системних заголовних файлах `<stddef.h>`, `<stdlib.h>` тощо. Стандарт гарантує:
- Якщо константу нульового вказівника присвоїти вказівнику будь-якого типу, утворюється нульовий вказівник (null pointer).
- Нульовий вказівник гарантовано не вказує на жоден дійсний об’єкт або функцію.
- Будь-які два нульові вказівники при порівнянні оператором `==` є рівними.
- У логічному контексті (`if (p)`) нульовий вказівник оцінюється як `false`, а будь-який ненульовий – як `true`.

У C++11 для подолання неоднозначностей перевантаження цілих чисел введено ключове слово `nullptr` типу `std::nullptr_t`.

### Статус розіменування: Undefined Behavior

Згідно з ISO/IEC 9899 (§6.5.3.2 Address and indirection operators, пункт 4), спроба розіменування нульового вказівника є невизначеною поведінкою (undefined behavior)[^iso-c-n1570]. Стандарт навмисно не вимагає обов’язкового генерування виключення, залишаючи поведінку на розсуд апаратури та операційної системи.

### Апаратні наслідки на ARM Cortex-M

На десктопних операційних системах (Linux, Windows) з віртуальною пам’яттю сторінка з нульовою адресою не відображена, і спроба доступу викликає негайний `Segmentation fault`.
У мікроконтролерах ситуація кардинально інша, оскільки адреса `0x00000000` є реальною фізичною адресою в адресному просторі:
1. **Вміст нульової адреси в Cortex-M**:
   За адресою `0x00000000` розташована таблиця векторів переривань (Vector Table)[^armv7m-arm]:
   - За адресою `0x00000000` знаходиться початкове значення покажчика стека (MSP – Main Stack Pointer).
   - За адресою `0x00000004` знаходиться адреса обробника скидання (Reset Handler).
2. **Операція читання (`val = *p` при `p == NULL`)**:
   На мікроконтролері без MPU читання за адресою `0x0` не викликає апаратного збою! Інструкція `LDR r0, [r1]` прочитає початкове значення стека MSP або вектор скидання з Flash-пам’яті. Програма продовжить роботу, отримавши сміттєві дані, що маскує баг і призводить до важковловимих помилок.
3. **Операція запису (`*p = val` при `p == NULL`)**:
   За адресою `0x00000000` зазвичай відображається незалежна пам’ять Flash. Спроба виконати інструкцію запису `STR` на шину Flash викликає апаратну помилку шини `BusFault` (Precise Data Access Error), яка ескалується в `HardFault`[^armv7m-arm]. Якщо ж таблицю векторів було релоковано в SRAM за нульовою адресою, запис тихо пошкодить вказівник стека або адресу обробника переривання, викликавши фатальний збій мікроконтролера при наступному перериванні.
4. **Захист за допомогою MPU**:
   У надійних прошивках перший регіон модуля захисту пам’яті (MPU) конфігурують на покриття діапазону `0x00000000`–`0x000000FF` з атрибутом повної заборони доступу (No Access). Будь-яка спроба читання чи запису негайно згенерує `MemManageFault`, що дозволяє миттєво локалізувати розіменування NULL у налагоджувачі.

### Оптимізації компілятора навколо NULL

Оскільки розіменування нульового вказівника є undefined behavior, оптимізатори компілятора (GCC `-O2`) вважають, що вказівник, який розіменовується, ніколи не дорівнює NULL:
```c
void process(int *ptr) {
    int x = *ptr;
    if (ptr == NULL) { // Компілятор повністю видалить цю перевірку!
        handle_error();
    }
}
```
Якщо розробник помилково спочатку розіменував вказівник, а потім додав перевірку на `NULL`, компілятор оптимізує код і викине перевірку разом із викликом `handle_error()`, що створює критичну вразливість.

### Практичні правила безпеки

1. Завжди ініціалізувати вказівники: `uint8_t *p = NULL;`.
2. Завжди перевіряти вказівники, отримані ззовні або з функцій виділення пам’яті (`malloc`), перед їх розіменуванням: `if (p != NULL)`.
3. Використовувати макроси перевірки `assert(p != NULL)` на етапі розробки.
4. Обнуляти вказівник одразу після звільнення ресурсу: `free(p); p = NULL;` (запобігання dangling pointer).
