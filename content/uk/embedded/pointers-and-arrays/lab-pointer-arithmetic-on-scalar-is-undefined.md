## Question code

```c
int a=1;
int *p=&a;
int *q=&a;
q++;
printf("%d",*q);
```

## Short answer

<span class="warn">Undefined behavior</span>. Операція `q++` формує валідний past-the-end покажчик, проте розіменування `*q` є невизначеною поведінкою (UB): об’єкт `a` трактується як одноелементний масив, за межами якого дійсних елементів немає.

Адресна арифметика визначена в межах масиву. Для окремих скалярних змінних дозволено обчислювати past-the-end покажчик `&a + 1`, проте розіменування `*(&a + 1)` або вихід далі ніж на 1 елемент є UB.

Крім того, компілятор може розмістити `a` у регістрі без адреси в RAM, тому спроба читання `*q` зчитує непередбачувані дані або спричиняє апаратний збій.[^embeddedinterviewlab]

## Detailed explanation

### Що стверджує стандарт C: скаляр як одноелементний масив

У фрагменті коду розглядається зміщення покажчика за межі одиничної змінної `a`:[^iso-c-n1570]
```c
int a = 1;
int *p = &a;
int *q = &a;
q++;
printf("%d", *q);
```

Згідно зі стандартом ISO/IEC 9899 (§6.5.6 p7), для цілей адресної арифметики будь-який покажчик на скалярний об’єкт, який не є елементом масиву, розглядається моделлю мови C точно так само, як покажчик на перший елемент уявного масиву довжиною в один елемент (`int[1]`).[^iso-c-n1570]

### Чому q++ дозволено, а *q є фатальною помилкою (UB)

Стандарт C чітко розмежовує обчислення адреси та її розіменування:[^iso-c-n1570]
1. **Інкремент `q++` є коректним:**
   Відповідно до §6.5.6 p8, дозволяється формувати покажчик, що вказує на один елемент за межі масиву (one-past-the-end pointer). Оскільки змінна `a` трактується як масив із одного елемента, значення `&a + 1` є валідним граничним покажчиком. Програма має право обчислювати цю адресу та порівнювати її з іншими покажчиками на цей же об’єкт.
2. **Розіменування `*q` є Undefined Behavior:**
   Той самий пункт стандарту (§6.5.6 p8) категорично стверджує: якщо покажчик вказує на один елемент за межі масиву, забороняється використовувати його як операнд унарного оператора розіменування `*`. Спроба обчислити вираз `*q` є класичною невизначеною поведінкою (`undefined behavior`).

### Що реально відбувається у пам’яті та на стеку ARM Cortex-M

На практиці поведінка прошивки залежить від архітектури та налаштувань оптимізації:[^embeddedinterviewlab]
- **Стековий кадр:** Якщо змінна `a` розташована на стеку, операція `q++` формує адресу сусіднього 32-бітного слова. Цим сусіднім словом може бути інша локальна змінна функції, службовий стек-канарка (stack canary для захисту від переповнення), збережений покажчик кадру або збережений регістр зв’язку `LR` (адреса повернення з функції).
- **Витік даних або аварія:** Читання `*q` зчитує непередбачувані дані зі стека. Якщо ж виконати запис `*q = 0;`, це може пошкодити збережену адресу повернення `LR`, і при виході з функції мікроконтролер виконає перехід за випадковою адресою, спричинивши негайний `HardFault`.
- **Регістрова оптимізація:** Сучасний компілятор із прапорцями `-O2` може взагалі не виділяти змінній `a` пам’яті у RAM, а розмістити її значення безпосередньо у регістрі загального призначення процесора (наприклад, `r4`). Оператор взяття адреси `&a` змушує компілятор виділити для `a` комірку на стеку (spill to stack), проте пам’ять за межами цієї комірки не ініціалізується.

### Оптимізації компілятора та ризики для надійності прошивки

Сучасні компілятори спираються на припущення про відсутність невизначеної поведінки під час аналізу потоку керування:[^iso-c-n1570]
- Оскільки `*q` є `undefined behavior`, оптимізатор має право припустити, що виконання програми ніколи не дійде до цієї інструкції, або викинути виклик `printf` взагалі як мертвий код.
- Поширена ілюзія програмістів-початківців у embedded полягає у спробі обходити змінні на стеку арифметикою покажчиків, сподіваючись, що вони лежать у порядку оголошення. Стандарт C не гарантує жодного порядку чи неперервності розташування незалежних змінних у пам’яті: компілятор вільно змінює їхній порядок, додає байти вирівнювання (padding) або видаляє невикористовувані змінні.
