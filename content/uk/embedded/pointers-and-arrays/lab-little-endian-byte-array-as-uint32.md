## Question code

```c
uint8_t arr[4]={0x01,0x02,0x03,0x04};
uint32_t *p=(uint32_t*)arr;
printf("%08X",*p);
```

## Short answer

`04030201`.

На little-endian (Cortex-M) байти у пам’яті: `[01][02][03][04]`. При читанні як `uint32_t`: молодший байт – перший у пам’яті: LSB=0x01, потім 0x02, 0x03, MSB=0x04. Значення: `0x04030201`.

<span class="warn">Увага</span>: такий cast може бути misaligned на MCU без підтримки. Безпечно: `uint32_t val; memcpy(&val, arr, 4);`[^embeddedinterviewlab]

## Detailed explanation

### Механіка порядку байтів Little-Endian у пам’яті

У системі з порядком байтів Little-Endian (стандартному для ядер ARM Cortex-M та архітектури x86) молодший байт багатобайтового числа (Least Significant Byte, LSB) зберігається за найменшою адресою пам’яті.[^embeddedinterviewlab]

Масив `uint8_t arr[4] = {0x01, 0x02, 0x03, 0x04};` розташовується в пам’яті за послідовними адресами:
- Адреса `A + 0`: байт `0x01` (молодший байт, біти 0..7);
- Адреса `A + 1`: байт `0x02` (біти 8..15);
- Адреса `A + 2`: байт `0x03` (біти 16..23);
- Адреса `A + 3`: байт `0x04` (старший байт, біти 24..31).

Коли цей 4-байтовий фрагмент пам’яті зчитується як єдине 32-бітне число через покажчик `uint32_t*`, процесор збирає значення у регістрі відповідно до ваги кожного розряду:[^iso-c-n1570]
```c
value = (0x04 << 24) | (0x03 << 16) | (0x02 << 8) | 0x01; // 0x04030201
```
Форматований вивід `%08X` друкує це 32-бітне число у шістнадцятковому вигляді з доповненням нулями: `04030201`. На архітектурі Big-Endian (наприклад, мережевий порядок байтів або контролери PowerPC) результат був би зворотним: `01020304`.

### Порушення вирівнювання (Alignment) та апаратні виключення ARM

Наведений код містить приховану фатальну загрозу для вбудованих платформ. Масив `uint8_t` має природне вирівнювання за межею 1 байта (`alignof(uint8_t) == 1`). Компілятор може розташувати `arr` за довільною адресою в RAM або на стеку, зокрема за адресою, некратною 4 (наприклад, `0x20000001` або `0x20000003`):[^arm-cortex-m0-alignment]
- **Ядра ARMv6-M (Cortex-M0, Cortex-M0+):** Апаратна підтримка невирівняного доступу повністю відсутня. Виконання інструкції 32-бітного завантаження `LDR` за некратною 4 адресою апаратно генерує фатальне виключення `HardFault`.[^arm-cortex-m0-alignment]
- **Ядра ARMv7-M (Cortex-M3, Cortex-M4, Cortex-M7):** Процесор підтримує невирівняне читання слів ціною додаткових циклів шини, проте якщо в регістрі керування `SCB->CCR` виставлено біт `UNALIGN_TRP`, будь-який невирівняний доступ негайно викличе переривання `UsageFault`.[^armv7m-arm] Крім того, інструкції пакетного завантаження `LDM`/`STM` та робота з подвійними словами `LDRD` завжди вимагають вирівнювання на всіх ядрах без винятку.

### Порушення правила Strict Aliasing Rule

Пряме приведення `(uint32_t*)arr` порушує правило суворого псевдонімування (strict aliasing rule, ISO C §6.5 p7).[^iso-c-n1570] Стандарт забороняє звертатися до об’єкта одного типу через покажчик на несумісний тип. За умов увімкненої оптимізації (`-O2`, `-O3`) компілятор вважає, що покажчики різних типів не посилаються на ту саму ділянку пам’яті, що може призвести до викидання читання з пам’яті або перевпорядкування інструкцій процесора.

### Безпечні та переносні інженерні альтернативи

У промисловому коді для вбудованих систем цей антипатерн замінюють на надійні рішення:[^iso-c-n1570]
- **Використання `memcpy`:**
  ```c
  uint32_t val;
  memcpy(&val, arr, sizeof(val));
  ```
  Компілятори розпізнають виклик `memcpy` як вбудовану ідіому (builtin) і генерують оптимальні машинні інструкції без виклику підпрограми та без ризику `HardFault`.
- **Явні побайтові зсуви:**
  ```c
  uint32_t val = (uint32_t)arr[0] |
                 ((uint32_t)arr[1] << 8) |
                 ((uint32_t)arr[2] << 16) |
                 ((uint32_t)arr[3] << 24);
  ```
  Цей підхід є абсолютно переносним, не залежить від вирівнювання буфера та завжди детерміновано розбирає Little-Endian потік незалежно від архітектури процесора.
