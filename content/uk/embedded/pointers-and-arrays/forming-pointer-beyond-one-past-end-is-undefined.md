## Question code

```c
int arr[4]={1,2,3,4};
int *p=arr;
int *q=arr+5;
```

## Short answer

<span class="warn">Так, undefined behavior (UB) вже при формуванні `arr+5`</span>.

Для масиву `arr[4]` (4 елементи) допустимі вказівники: `arr` до `arr+4` включно (one-past-the-end). `arr+5` виходить за one-past-the-end -> <span class="warn">UB навіть без розіменування</span>.

Компілятор може використовувати це припущення для оптимізації, що призводить до непередбачуваної поведінки. GCC з `-fsanitize=undefined` виявить це.[^embeddedinterviewlab]

## Detailed explanation

У мовах C та C++ вихід за межі масиву під час адресної арифметики є однією з найбільш підступних помилок. Поширена хибна думка полягає в тому, що помилка виникає лише в момент розіменування покажчика (`*q`). Насправді ж згідно зі стандартом ISO/IEC 9899 (§6.5.6 Additive operators) саме **обчислення** неприпустимої адреси вже породжує `undefined behavior`.[^iso-c-n1570]

### Нормативні вимоги стандарту ISO C до меж покажчиків

Стандарт ISO/IEC 9899:2011 (§6.5.6 p8) чітко регламентує межі допустимої адресної арифметики для покажчиків на елементи масиву:[^iso-c-n1570]
- Якщо масив має розмір N елементів (у даному випадку `int arr[4]`, тобто N = 4), дозволеними є покажчики на елементи від `arr[0]` до `arr[N-1]`, а також один спеціальний покажчик безпосередньо за останнім елементом – `arr + N` (умовний `arr[4]`, так званий *one-past-the-end pointer*).
- Якщо вираз обчислює адресу, яка виходить за межі діапазону від `arr + 0` до `arr + N` включно (як у випадку `arr + 5`), поведінка програми стає невизначеною:
  > «If both the pointer operand and the result point to elements of the same array object, or one past the last element of the array object, the evaluation shall not produce an overflow; otherwise, the behavior is undefined».[^iso-c-n1570]

### Спеціальний статус one-past-the-end покажчика

Покажчик `arr + 4` є винятком, спеціально гарантованим стандартом C для зручності організації циклів та ітерацій (аналогічно ітераторам `container.end()` у C++):
- Його дозволено **формувати** та **порівнювати** з іншими вказівниками того самого масиву (наприклад, `for (int *p = arr; p < arr + 4; ++p)`).
- Його суворо **заборонено розіменовувати** (`*(arr + 4)` – це `undefined behavior`), оскільки він не адресує дійсний елемент масиву.[^iso-c-n1570]

Будь-який наступний крок (наприклад, `arr + 5` або `arr - 1`) негайно виходить за межі легального вікна і є незаконним сам по собі, навіть якщо отримане значення ніколи не читається і не змінюється через розіменування.[^iso-c-n1570]

### Апаратний контекст та оптимізації компілятора

Чому розробники стандарту встановили таку жорстку заборону навіть без розіменування:
1. **Сегментні архітектури та переповнення:** в історичних або спеціалізованих мікроконтролерних архітектурах із сегментною моделлю пам’яті (наприклад, архітектури DSP або 16-бітні контролери) додавання зміщення може викликати переповнення регістру зміщення чи перехід через межу сегмента, генеруючи апаратне переривання або некоректний селектор.
2. **Розташування на межі пам’яті:** якщо масив `arr` розташований у самому кінці адресної пам’яті мікроконтролера (наприклад, верхня адреса оперативної пам’яті SRAM `0x20003FF0` на STM32), операція `arr + 5` може викликати арифметичне переповнення 32-бітного беззнакового значення адреси і її циклічний перехід до `0x00000004`.
3. **Агресивні оптимізації компілятора:** сучасні оптимізатори (GCC, Clang) спираються на припущення, що `undefined behavior` у коректній програмі ніколи не настає. Наприклад, якщо компілятор бачить умову виду `if (p + 5 < p)`, він має право повністю видалити цей блок перевірки як недосяжний, оскільки легальний покажчик не може переповнюватися.

### Пастки у драйверах та засоби виявлення

У вбудованому ПЗ ця пастка часто виникає при розборі мережевих пакетів або кадрів шини CAN/UART:
- Обчислення вказівника на кінець пакету за формулою `ptr = buffer + packet_len + CRC_SIZE` без попередньої перевірки розміру буфера призводить до створення невалідного покажчика.
- **Діагностика:** налагоджувальний збірник під GCC/Clang із прапорцем `-fsanitize=undefined` (UBSan) вставляє інструкції перевірки (`pointer-overflow`) та повідомляє про помилку вже у рядку формування `arr + 5`.
