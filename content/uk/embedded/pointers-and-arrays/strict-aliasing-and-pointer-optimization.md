## Short answer

**Pointer aliasing** – ситуація, коли два або більше вказівників посилаються на одну область пам’яті.

Strict aliasing rule (C99 §6.5): компілятор може вважати, що вказівники різних типів не alias-ують (окрім `char*`/`unsigned char*`). Це дозволяє більш агресивну оптимізацію.

Порушення: `int x; float *fp = (float*)&x; *fp = 1.0f;` -> undefined behavior (UB).

Захист: `memcpy` для type punning, `char*` для byte access, `restrict` для явної гарантії no-aliasing.[^embeddedinterviewlab]

## Detailed explanation

Поняття aliasing (псевдонімізації покажчиків) та правило strict aliasing належать до найважливіших концепцій системного програмування на мовах C та C++, які безпосередньо впливають на продуктивність та коректність генерованого машинного коду.[^iso-c-n1570]

### Концепція aliasing та його вплив на оптимізатор компілятора

**Pointer aliasing** – це ситуація, коли два або більше покажчиків посилаються на ту саму або перекривні області фізичної пам’яті.

Коли компілятор транслює код у машинний, він прагне кешувати значення змінних у регістрах процесора (наприклад, у регістрах `r0`–`r12` ядра ARM Cortex-M), щоб мінімізувати кількість повільних операцій доступу до оперативної пам’яті (`LDR` та `STR`). Проте, якщо запис через один покажчик потенційно змінює значення під іншим покажчиком, компілятор змушений щоразу скидати регістри і повторно завантажувати дані з пам’яті.

Розглянемо приклад:
```c
void compute(int *a, int *b) {
    *a += 10;
    *b += 20;
    *a += 10;
}
```
Оскільки `a` та `b` мають однаковий тип `int *`, компілятор не знає, чи не вказують вони на одну комірку пам’яті (`a == b`). Через це він не може оптимізувати вираз до `*a += 20`, а змушений виконувати чесні читання та запис для кожного кроку.

### Правило Strict Aliasing у стандарті ISO C

Для вирішення цієї проблеми стандарт ISO/IEC 9899 (§6.5 Expressions, пункт 7) запровадив **Strict Aliasing Rule**.[^iso-c-n1570]
Стандарт стверджує, що доступ до збереженого значення об’єкта дозволено здійснювати лише через lvalue-вираз сумісного типу. Зокрема, дозволеними винятками є:
1. Тип, сумісний з ефективним типом об’єкта (або кваліфікований `const`/`volatile`).
2. Відповідний знаковий або беззнаковий тип (наприклад, `int` та `unsigned int`).
3. Агрегатний тип (структура або об’єднання), що містить один із зазначених типів.
4. **Символьний тип:** `char`, `signed char` або `unsigned char` (`uint8_t`). Вказівникам на символьний тип дозволено посилатися на пам’ять будь-якого типу.[^iso-c-n1570]

За замовчуванням при прапорцях оптимізації `-O2`, `-O3` компілятор вважає, що покажчики несумісних типів (наприклад, `int *` та `float *`) ніколи не можуть вказувати на один і той самий об’єкт пам’яті.

### Приклад порушення та некоректна генерація коду

Класична помилка – спроба швидкого перетворення типів (type punning) через пряме приведення покажчиків:
```c
int x = 100;
float *fp = (float *)&x; // Порушення strict aliasing!
*fp = 1.0f;
```
На високих рівнях оптимізації компілятор має право розцінити читання `x` після запису через `*fp` як операції над абсолютно незалежними об’єктами. У результаті компілятор може видалити запис або переставити інструкції місцями, що викликає важковловиме `undefined behavior`.[^iso-c-n1570]

### Специфіка вбудованих систем: протокольні буфери та регістри

У розробці вбудованих систем (embedded firmware) це правило порушують дуже часто під час розбору бінарних пакетів мережевих інтерфейсів (CAN, SPI, UART, Ethernet):
- Приведення масиву байтів `uint8_t rx_buffer[64]` до покажчика на структуру заголовка пакету `(packet_header_t *)rx_buffer` є прямим порушенням strict aliasing (окрім проблеми невідповідності вирівнювання). Компілятор може оптимізувати код так, ніби поля структури і байтовий буфер не перекриваються.

### Безпечні інженерні методи: memcpy, union та restrict

Для уникнення `undefined behavior` застосовуються такі стандартизовані підходи:[^iso-c-n1570]

1. **Функція `memcpy`:** стандартний та найнадійніший спосіб виконання type punning. Сучасні компілятори (GCC, Clang) розпізнають фіксований розмір копіювання і замінюють виклик `memcpy` однією інструкцією завантаження/збереження регістра (`LDR`/`STR`), без жодних накладних витрат:
   ```c
   float f = 1.0f;
   uint32_t raw_bits;
   memcpy(&raw_bits, &f, sizeof(raw_bits));
   ```
2. **Об’єднання (`union`):** у мові C99/C11 запис в одне поле `union` і зчитування з іншого явно дозволено спеціальною виноскою до стандарту (type punning via union). Проте у C++ це лишається `undefined behavior` (там використовують `std::bit_cast`).
3. **Ключове слово `restrict` (C99):** застосовується до параметрів функцій для явної гарантії компілятору, що вказівники не перекриваються:
   ```c
   void dma_copy(uint32_t * restrict dst, const uint32_t * restrict src, size_t n);
   ```
   Це дозволяє компілятору генерувати високошвидкісний векторний або пакетний код без постійних перезавантажень пам’яті.
