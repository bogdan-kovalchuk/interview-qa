## Short answer

`n = 1` (на 32-bit) або `n = 2` (на 64-bit).

У параметрі функції `int arr[]` ≡ `int *arr` – decay до вказівника, тож `sizeof(arr) = sizeof(int*) = 4` (або 8), `sizeof(arr[0]) = sizeof(int) = 4`, і `4/4 = 1`.

<span class="warn">Не 8, не 256, не розмір масиву</span> – лише 1 або 2.

Завжди передавати розмір явно: `void f(int *arr, size_t n)`. Захист: `_Static_assert` у caller.[^embeddedinterviewlab]

## Detailed explanation

### Математика обчислення макроса ARRAY_SIZE у тілі функції

Широко поширений макрос обчислення кількості елементів масиву `#define ARRAY_SIZE(a) (sizeof(a) / sizeof((a)[0]))` коректно працює лише в тій області видимості, де масив оголошено як повноцінний об’єкт. Коли цей вираз застосовується до аргументу функції `void f(int arr[])`, спрацьовує правило коригування типів стандарту C (ISO/IEC 9899, пункт 6.7.6.3): тип параметра `int arr[]` трансформується у звичайний вказівник `int *arr`.[^iso-c-n1570]

У результаті оператор `sizeof` обчислює вираз не для масиву, а для вказівника:[^embeddedinterviewlab]
- `sizeof(arr)` обчислюється як `sizeof(int*)`;
- `sizeof(arr[0])` обчислюється як `sizeof(int)`.

Відношення цих двох величин `sizeof(int*) / sizeof(int)` і стає остаточним значенням змінної `n`.

### Вплив розрядності архітектури (16, 32 та 64 біти)

Оскільки розмір вказівника жорстко прив’язаний до ширини адресної шини цільового мікроконтролера чи процесора, значення `n` змінюється залежно від апаратної платформи:

1. **32-розрядні системи (ARM Cortex-M0/M3/M4/M7, ESP32, STM32):**
   `sizeof(int*) == 4`, `sizeof(int) == 4`.
   Значення виразу: `4 / 4 = 1`.
2. **64-розрядні системи (AArch64, x86-64):**
   `sizeof(int*) == 8`, `sizeof(int) == 4` (у моделі даних LP64 / LLP64).
   Значення виразу: `8 / 4 = 2`.
3. **16-розрядні архітектури (MSP430, AVR):**
   `sizeof(int*) == 2`, `sizeof(int) == 2`.
   Значення виразу: `2 / 2 = 1`.

У жодному разі вираз не поверне реальну кількість елементів буфера, навіть якщо в оголошенні параметра було записано число на зразок `void f(int arr[128])`.

### Катастрофічні наслідки у прошивках мікроконтролерів

Подібна помилка є вкрай підступною, оскільки код успішно компілюється без помилок лінкера і не викликає негайного аварійного завершення (crash) програми:

- **Тихе усічення циклу:** цикл обробки даних `for (size_t i = 0; i < n; ++i)` на 32-розрядному контролері виконається рівно один раз. Обробляється лише `arr[0]`, а решта 127 чи 255 елементів буфера ігноруються без жодних повідомлень про помилку.
- **Спотворення контрольних сум:** функція розрахунку CRC, застосована до пакету телеметрії через такий макрос, порахує хеш лише від першого слова, що призведе до відхилення пакетів приймальною стороною.
- **DMA та переривання:** завантаження значення `n` у лічильник дескриптора передачі призведе до відправки одного слова замість масиву вибірок.

### Захисні макроси, C++ span та інструменти компілятора

Для виключення таких дефектів застосовують інженерні практики захисту:

- **Прапорці компілятора:** компілятор GCC містить спеціалізоване попередження `-Wsizeof-array-argument`, яке виявляє взяття `sizeof` від параметра-масиву ще на етапі трансляції.[^gcc-warning-options]
- **Типобезпечний макрос (Linux kernel pattern):** у ядрі Linux використовується перевірка несумісності типів масиву та вказівника на етапі збирання, що викликає помилку компіляції, якщо макрос застосовано до простого вказівника:
  ```c
  #define ARRAY_SIZE(arr) \
      (sizeof(arr) / sizeof((arr)[0]) + \
       sizeof(typeof(int[1 - 2 * __builtin_types_compatible_p(typeof(arr), typeof(&(arr)[0]))])) * 0)
  ```
- **Явні контракти API:** передача розміру окремим параметром `(const int *arr, size_t count)` або обгортання масиву в структуру (`typedef struct { int data[64]; size_t len; } buffer_t;`), що гарантує збереження метаданих довжини.
