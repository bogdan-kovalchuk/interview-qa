## Short answer

**Не реєструє деструктори глобальних об’єктів через `__cxa_atexit`.**

На MCU програма зазвичай ніколи не завершується, тож dtor глобалів і не потрібні – реєстрація лише тягне runtime-інфраструктуру й ROM.

Правило: статичні об’єкти на MCU «вічні»; `-fno-use-cxa-atexit` прибирає непотрібний cleanup.[^embeddedinterviewlab]

## Detailed explanation

### Що таке `__cxa_atexit` та механізм завершення програми

Згідно зі стандартом C++ ([basic.start.term])[^iso-cpp-n4861], об’єкти зі статичною тривалістю зберігання (статичні та глобальні змінні) з нетривіальними деструкторами повинні гарантовано знищуватися у зворотному порядку до їхнього конструювання у разі нормального завершення програми (при поверненні з `main()` або виклику `std::exit()`).

Для підтримки динамічного порядку знищення у середовищі Itanium C++ ABI[^itanium-cxx-abi] компілятор генерує код, який під час ініціалізації кожного глобального об’єкта реєструє його деструктор за допомогою функції:
```c
int __cxa_atexit(void (*destructor)(void *), void *arg, void *dso_handle);
```
Ця функція веде динамічний зв’язний список або масив зареєстрованих деструкторів, що потребує виділення оперативної пам’яті (RAM) та підтягує інфраструктуру кучі (heap) або статичних службових таблиць бібліотеки C runtime (libc).

### Чому для мікроконтролерів це зайвий баласт

Архітектура вбудованого ПЗ (firmware) на bare-metal мікроконтролерах докорінно відрізняється від настільних додатків:
1. **Функція `main()` ніколи не завершується**: програма переходить у нескінченний суперцикл (`while (1)`) або віддає керування диспетчеру операційної системи реального часу (RTOS).
2. **Апаратне перезавантаження**: при вимкненні живлення, спрацьовуванні сторожового таймера (Watchdog) або системному скиданні (NVIC System Reset) мікроконтролер миттєво апаратно скидає свої регістри та пам’ять. Жоден код деструктора перед цим не викликається.
3. **ROM та RAM оверхед**: підключення механізму `__cxa_atexit` тягне в прошивку службові таблиці, код обробки динамічного завершення і функції `malloc`/`free` з бібліотеки C, роздуваючи розмір Flash на кілька кілобайтів.

### Що робить прапорець `-fno-use-cxa-atexit`

Прапорець `-fno-use-cxa-atexit` вказує компілятору не генерувати виклики `__cxa_atexit` для реєстрації деструкторів глобальних об’єктів[^gcc-cxx-dialect].

Залежно від налаштувань цільової платформи, компілятор або повністю відмовляється від реєстрації деструкторів статичних об’єктів, або переходить на класичний механізм C `atexit()`. У повністю автономних bare-metal конфігураціях (наприклад, разом із прапорцем компонувальника `--gc-sections` та вилученим runtime-завершенням) це повністю ліквідує структури даних реєстрації виходу.

### Чисті інженерні патерни для глобальних сутностей на MCU

Замість покладання на прапорці компілятора найкращою інженерною практикою в embedded C++ є створення глобальних сутностей, які взагалі не мають деструкторів:
1. **Тривіальний деструктор**:
   Оголошувати деструктор драйверів чи сервісів як `= default` або не оголошувати взагалі. Якщо клас не володіє динамічними ресурсами в heap, його деструктор вважається тривіальним, і компілятор не реєструє його в `atexit`.
2. **Статичне розміщення через `placement new` або буфери**:
   Об’єкт розміщується у виділеному статичному буфері пам’яті (наприклад, `alignas(T) std::byte storage[sizeof(T)]`) і конструюється один раз на старті без виклику деструктора.
3. **Використання `constexpr` / `constinit` (C++20)**:
   Ініціалізація константних таблиць конфігурацій безпосередньо у Flash на етапі компіляції.
