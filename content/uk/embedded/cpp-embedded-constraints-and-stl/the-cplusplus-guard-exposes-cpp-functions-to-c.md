## Question code

```c
#ifdef __cplusplus
extern "C" {
#endif
  void app_init(void);
#ifdef __cplusplus
}
#endif
```

## Short answer

**Guard `#ifdef __cplusplus` вмикає `extern "C"` лише для C++-компілятора.**

C-компілятор не знає синтаксису `extern "C"` (це C++-ключове слово); guard дозволяє одному header працювати в обох мовах.

Правило: спільні header’и завжди мають `#ifdef __cplusplus`-guard навколо `extern "C"`.[^embeddedinterviewlab]

## Detailed explanation

### Проблема сумісності спільних заголовків у багатомовних проєктах

У вбудованих проєктах часто поєднуються дві мови: системний шар (стартап-код, таблиця векторів переривань, драйвери периферії BSP, планувальник FreeRTOS) зазвичай написаний на чистому C, тоді як модулі верхнього рівня, обробка даних, алгоритми фільтрації та бізнес-логіка реалізуються на C++.

Для забезпечення модульності оголошення функцій, які C++ експортує для виклику з коду C (наприклад, точка входу в застосунок `app_init()` або функція обробки події таймера), виносять у спільний заголовковий файл (`.h`)[^iso-cpp-n4861]. Цей заголовок включається одночасно:
- у файл реалізації `.cpp`, який компілюється C++-компілятором (`arm-none-eabi-g++`);
- у системні файли `.c`, які компілюються чистим C-компілятором (`arm-none-eabi-gcc`).

### Чому C-компілятор ламається без guard

Конструкція `extern "C"` є частиною граматики мови C++, де вона задає специфікацію мовного зв’язування (linkage specification)[^iso-cpp-n4861]. 

У стандарті мови C (ISO/IEC 9899) існує ключове слово `extern`, проте синтаксис `extern` із наступним рядковим літералом (`"C"`) відсутній. Якщо C-компілятор спробує скомпілювати заголовок із «голим» `extern "C" {`, компіляція аварійно зупиниться із синтаксичною помилкою:
```text
error: expected identifier or '(' before string constant
```
Щоб зробити файл придатним для обох мов, використовують умовну компіляцію на основі стандартного макроса препроцесора `__cplusplus`:
1. Макрос `__cplusplus` стандартно визначений у будь-якому C++-компіляторі (наприклад, зі значенням `201703L` або `202002L`). C++-компілятор бачить умову `#ifdef __cplusplus` як істинну та активує блок `extern "C" { ... }`, вимикаючи декорування імен (Name Mangling).
2. Для C-компілятора макрос `__cplusplus` не визначений. Препроцесор мови C повністю вирізає директиви `extern "C" {` та `}`, залишаючи чисте оголошення функції `void app_init(void);`.

### Правила побудови C-сумісного інтерфейсу для C++ коду

Специфікація `extern "C"` вимикає декорування імен, проте вона не робить довільний C++-код автоматично зрозумілим для компілятора C. При проєктуванні C API для C++ функцій слід дотримуватися суворих обмежень:

1. **Типи параметрів та повернення (C-Compatible Types)**:
   Сигнатури функцій у спільному заголовку повинні використовувати лише типи, сумісні з мовою C (Standard Layout / POD types)[^iso-cpp-n4861]. Заборонено використовувати посилання C++ (`T&`), шаблони, класи з віртуальними функціями, `std::string_view` або стандартні контейнери. Для передачі вказівників на складні об’єкти використовують патерн непрозорого покажчика (Opaque Pointer / Handle):
   ```c
   typedef struct CppEngine CppEngine_t; // непрозорий дескриптор
   CppEngine_t* engine_create(void);
   void engine_step(CppEngine_t* engine);
   ```

2. **Заборона проникнення винятків (Exception Boundary)**:
   Якщо проєкт збирається з підтримкою винятків, виняток C++ у жодному разі не повинен вилетіти через межу `extern "C"` у C-код. Стек функцій C зазвичай збирається без таблиць розгортання (`-fno-unwind-tables`). Спроба розкрутити такий стек викличе аварійний виклик `std::terminate()`. Кожна функція-обгортка зобов’язана перехоплювати всі можливі винятки:
   ```cpp
   extern "C" int app_process_event(int event_id) noexcept {
       try {
           return cpp_dispatcher.handle(event_id);
       } catch (...) {
           return -1; // повернення C-коду помилки
       }
   }
   ```
   Або функцію слід оголошувати зі специфікатором `noexcept`.
