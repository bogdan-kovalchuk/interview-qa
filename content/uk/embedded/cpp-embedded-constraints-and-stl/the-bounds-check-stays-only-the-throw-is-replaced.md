## Short answer

<span class="warn">Ні – bounds check лишається; у libstdc++-подібних реалізаціях шлях помилки без exceptions часто веде до `abort()`/fatal handler.</span>

Тобто bounds check у `vector::at()`/`array::at()` усе ще виконується; змінюється лише реакція на провал – аварійна зупинка без діагностики замість винятку.

Захист: для гарячого шляху, де перевірка зайва, використовуй `operator[]` з власною валідацією; для безпеки – логуй перед зупинкою.[^embeddedinterviewlab]

## Detailed explanation

### Поширена омана щодо прапорця `-fno-exceptions`

Серед розробників вбудованих систем існує популярний міф: якщо скомпільувати код із прапорцем `-fno-exceptions`, компілятор нібито автоматично видалить усі перевірки меж (bounds checking) у методах `at()` контейнерів `std::vector`, `std::array` або `std::string`, зробивши їх еквівалентними прямому оператору індексації `operator[]`.

Це небезпечна помилка: **перевірочний код залишається в бінарному файлі у повному обсязі**[^iso-cpp-n4861]. Компілятор не видаляє умовну конструкцію валідації індексу – він змінює виключно дію, яка виконується у разі виявлення помилки.

### Реалізація методу `at()` у стандартних бібліотеках

Згідно зі стандартом C++ метод `at(size_type pos)` зобов’язаний перевірити умову `pos >= size()`[^iso-cpp-n4861]. У реалізаціях `libstdc++` (GCC) та `libc++` (LLVM/Clang) тіло функції влаштовано так:
```cpp
constexpr reference at(size_type __n) {
    if (__n >= size()) {
        std::__throw_out_of_range_fmt(__N("array::at: __n (which is %zu) "
                                          ">= _Nm (which is %zu)"),
                                      __n, size());
    }
    return (*this)[__n];
}
```
Коли прапорець `-fno-exceptions` увімкнено, стандартна бібліотека не використовує ключове слово `throw`. Замість цього внутрішня функція `std::__throw_out_of_range_fmt` (або `std::__throw_out_of_range`) реалізується через прямий виклик:
1. `std::terminate()` або `std::abort()`;
2. Запису повідомлення про аварію у `stderr` (якщо підключено runtime вводу-виводу);
3. Апаратного зависання або виклику інструкції `BKPT` (breakpoint) у debug-збірках.

Таким чином, у разі виходу за межі мікроконтролер не отримує керованого винятку, а негайно завершує роботу або зависає в нескінченному циклі `abort()`.

### Асемблерний код ARM Cortex-M та накладні витрати

На рівні машинного коду ARM Cortex-M виклик `array::at()` призводить до генерації інструкцій порівняння та умовного переходу при кожному зверненні:
```assembly
; r0 = адреса масиву, r1 = переданий індекс
CMP   r1, #16             ; Порівняння індексу з розміром масиву (наприклад, 16)
BCS   .L_abort_branch     ; Якщо r1 >= 16 (беззнакове порівняння carry set), перехід на збій
LDR   r0, [r0, r1, LSL #2]; Успішний шлях: завантаження 32-бітного елемента
BX    LR

.L_abort_branch:
BL    abort               ; Аварійне завершення роботи прошивки
```
У критичних за часом циклах (наприклад, цифрова фільтрація вимірювань АЦП або обробка аудіопотоку) постійне виконання гілок `CMP` та `BCS` збиває передбачення переходів і відчутно знижує продуктивність, а виклики `abort` роздувають Flash.

### Інженерні рекомендації для embedded C++

1. **Гарячі шляхи виконання (Hot paths)**:
   Там, де індекс гарантовано знаходиться в межах діапазону (наприклад, у циклі `for (size_t i = 0; i < arr.size(); ++i)`), слід застосовувати `operator[]` або range-based `for`. Оператор `[]` реалізує принцип нульових накладних витрат (zero-overhead) і компілюється в одну інструкцію `LDR`.
2. **Перевірка зовнішніх ненадійних даних**:
   Якщо індекс надходить ззовні (пакет з інтерфейсу UART, CAN, Modbus), перевірку слід виконувати явно за допомогою `if` із поверненням статусу помилки через `enum class` або `std::optional`, не допускаючи фатального краху всієї системи через виклик `abort()`:
```cpp
if (index >= telemetry.size()) {
    return StatusCode::InvalidIndex;
}
process_entry(telemetry[index]);
```
3. **Діагностика меж під час налагодження**:
   У GCC макрос `-D_GLIBCXX_ASSERTIONS` дозволяє увімкнути перевірки меж навіть усередині `operator[]` виключно для тестових збірок, залишаючи релізний код максимально швидким і компактним.
