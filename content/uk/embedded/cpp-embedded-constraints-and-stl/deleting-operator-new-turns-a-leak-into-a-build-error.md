## Short answer

**Якщо глобальний `operator new` видалений або заблокований, випадкова heap-алокація стає compile/link error.**

Об’єкти можна будувати через placement new у статично виділених буферах або pools з фіксованою місткістю. Це простіше аргументувати в memory-safety review, ніж політику «просто не використовуємо heap».

Правило: `= delete` глобального `new` перетворює no-heap policy з дисципліни на структурну гарантію.[^embeddedinterviewlab]

## Detailed explanation

### Чому динамічна пам’ять є неприпустимою в safety-critical системах

У стандартах функціональної безпеки для автомобільних систем (ISO 26262 ASIL D), авіоніки (DO-178C DAL A), промислової автоматики (IEC 61508) та настановах MISRA C++ динамічне виділення пам’яті (купи / heap) суворо обмежується або повністю забороняється під час штатної роботи. Причини полягають у таких ризиках:
1. **Фрагментація оперативної пам’яті**: постійне чергування алокацій та звільнень блоків різного розміру розбиває купу на дрібні фрагменти. Навіть якщо сумарний обсяг вільної RAM достатній, запит на черговий блок зазнає збою (Out of Memory).
2. **Недетермінованість часу виконання (WCET)**: алгоритми пошуку вільного блоку в купі (first-fit, best-fit тощо) мають змінний час роботи, що порушує детермінізм жорсткого реального часу (Hard Real-Time).
3. **Витоки пам’яті (Memory leaks)**: помилка у звільненні ресурсу з часом призводить до вичерпання RAM та аварійної зупинки пристрою.

Організаційні правила на зразок «розробники просто обіцяють не викликати `new`» не проходять строгий аудит безпеки, оскільки людський фактор неминуче призводить до випадкового використання бібліотечних функцій або контейнерів, що таємно смикають купу.

### Заборона на етапі компіляції: видалення глобального `operator new`

Найефективніший спосіб гарантувати відсутність heap у C++ проєкті – це синтаксичне видалення глобальних операторів виділення та звільнення пам’яті[^iso-cpp-n4861]:
```cpp
#include <cstddef>

void* operator new(std::size_t) = delete;
void* operator new[](std::size_t) = delete;
void operator delete(void*) noexcept = delete;
void operator delete[](void*) noexcept = delete;
void operator delete(void*, std::size_t) noexcept = delete;
void operator delete[](void*, std::size_t) noexcept = delete;
```
Якщо розробник або стороння бібліотека спробує виконати `new MyClass` чи використати контейнер на кшталт `std::vector`, `std::string` чи `std::make_unique`, компілятор негайно зупинить збирання з помилкою:
```text
error: use of deleted function 'void* operator new(std::size_t)'
```
Це перетворює абстрактну політику memory safety на жорстку механічну гарантію системи типів мови.

### Створення об’єктів без купи: placement new та статичні пули

Повна відмова від купи не означає відмови від C++ абстракцій чи динамічного життєвого циклу об’єктів:
1. **Placement new**: виклик конструктора поверх наперед виділеного статичного або стек-буфера з правильним вирівнюванням:
```cpp
alignas(Driver) std::byte driver_storage[sizeof(Driver)];
Driver* drv = new (driver_storage) Driver(USART1);

// Знищення об’єкта виключно через явний виклик деструктора (без operator delete):
drv->~Driver();
```
Синтаксис `placement new` визначено в заголовку `<new>` як inline-функцію, що просто повертає переданий покажчик `ptr` без виклику глобального `operator new(size_t)`[^iso-cpp-n4861]. Тому видалення глобального `new` не блокує `placement new`. Оскільки глобальний `operator delete` також видалений, виклик `delete drv;` викликав би помилку компіляції – завершення життєвого циклу об’єкта виконується явним викликом деструктора `drv->~Driver()`.
2. **Пули фіксованої місткості (Object Pools)**: створення пулів об’єктів фіксованого розміру, де вся пам’ять зарезервована під час компіляції у секції `.bss`, а виділення й повернення об’єкта зводиться до швидкої детермінованої операції зі зв’язним списком вільних слотів за O(1).

### Скрипти компонувальника (Linker script) та перевірка в аудиті

Для повного захисту на рівні компонувальника лінкерний скрипт налаштовують так, щоб секція купи була нульового розміру, а символи `_sbrk` або `malloc` викликали помилку компонування:
```text
ASSERT(_ebss == _end, "Error: Heap allocation detected in safety-critical firmware!");
```
Під час зовнішнього аудиту інженер надає звіт утиліти `nm` або `readelf`, який доводить повну відсутність символів `malloc`, `free`, `_sbrk` та `__cxa_allocate_exception` у фінальному ELF-файлі. Це знімає необхідність доводити відсутність витоків пам’яті математичними доказами чи тривалим стрес-тестуванням.
