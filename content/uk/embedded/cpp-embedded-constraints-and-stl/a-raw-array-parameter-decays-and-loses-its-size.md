## Short answer

<span class="warn">Він decay-иться у вказівник (втрата розміру) і показує незнання сучасних практик.</span>

`void f(int arr[])` насправді приймає `int*`; `sizeof` усередині дасть розмір вказівника. `std::array`/`std::span` зберігають розмір і безпечніші.

Захист: у C++ передавай `std::array&`, `std::span` або (контейнер + розмір), а не голий `T[]`.[^embeddedinterviewlab]

## Detailed explanation

### Механізм деградації масиву (Array Decay) у стандарті мови

У мовах C та C++ тип аргументу функції, оголошений як масив із фіксованим або нефіксованим розміром (наприклад, `void send_packet(uint8_t buffer[64])`), автоматично трансформується компілятором у звичайний покажчик на перший елемент: `void send_packet(uint8_t* buffer)`[^iso-cpp-n4861]. Цей процес називається деградацією або занепадом типу (array decay).

Число `64` всередині квадратних дужок повністю ігнорується компілятором і залишається виключно коментарем для програміста. Це породжує серйозні проблеми безпеки:
- У таку функцію можна передати масив будь-якого довільного розміру (наприклад, масив на 4 байти або 256 байтів), і компілятор не згенерує жодного попередження чи помилки.
- У функцію можна помилково передати `nullptr`, що спричинить розіменування нульового покажчика та виклик `HardFault` на мікроконтролері.

### Пастка оператора `sizeof` та переповнення буфера

Головна небезпека полягає в хибному відчутті безпеки при роботі з розміром буфера всередині функції:
```cpp
void process_telemetry(uint32_t samples[32]) {
    // ПОМИЛКА: sizeof(samples) поверне розмір покажчика (4 байти на ARM Cortex-M), а не 128!
    size_t count = sizeof(samples) / sizeof(samples[0]); // Обчислиться як 4 / 4 = 1 елемент!
    for (size_t i = 0; i < count; ++i) {
        samples[i] = 0; // Занулиться лише 1 елемент замість 32!
    }
}
```
Якщо ж розробник навпаки спробує виконати `memset(samples, 0, 32 * sizeof(uint32_t))`, покладаючись на число з оголошення, а викликач випадково передасть масив меншої місткості, відбудеться руйнування пам’яті стека (Stack Buffer Overflow) та пошкодження регістрів повернення `LR` і `PC`.

### Чому це поганий сигнал на технічному інтерв’ю

Використання синтаксису `T arr[]` або `T arr[N]` у сигнатурах функцій C++ сигналізує інтерв’юеру про те, що розробник:
1. Не розуміє семантики типів C++ та механізмів передачі параметрів у компіляторах.
2. Механічно переносить застарілі звички мови C без усвідомлення їхніх прихованих загроз для пам’яті мікроконтролера.
3. Не вміє користуватися сучасними безпечними типами STL або шаблонними посиланнями для перевірки розмірів на етапі компіляції.

### Як правильно передавати масиви у сучасному embedded C++

Залежно від архітектурних вимог у C++ застосовують такі безпечні підходи:

1. **Неволодіючий перегляд через `std::span` (C++20)**:
   Ідеальний варіант для функцій обробки буферів. Забезпечує перегляд неперервної ділянки пам’яті із збереженням інформації про її довжину без виділення heap:
```cpp
#include <span>

void process_data(std::span<const uint8_t> data) {
    for (uint8_t byte : data) {
        // data.size() точно повертає кількість переданих байтів!
    }
}
```
   Якщо розмір буфера має бути суворо фіксованим під час компіляції, використовують статичний екстент: `std::span<const uint8_t, 64>`.

2. **Посилання на `std::array`**:
   Якщо функція завжди працює з масивом фіксованого розміру, передається посилання:
```cpp
void read_sensors(std::array<int16_t, 8>& readings);
```
   Компілятор жорстко контролює розмір: передача масиву на 7 або 9 елементів викликає помилку компіляції.

3. **Посилання на сирий масив через шаблон (Zero-overhead C-array reference)**:
   Якщо проєкт зобов’язаний приймати сирі C-масиви, тип масиву не деградує у покажчик, якщо передавати його за посиланням:
```cpp
template <size_t N>
void transmit(const uint8_t (&buffer)[N]) {
    // N відоме під час компіляції, sizeof(buffer) повертає N байтів
    HAL_UART_Transmit(&huart1, buffer, N, 100);
}
```
