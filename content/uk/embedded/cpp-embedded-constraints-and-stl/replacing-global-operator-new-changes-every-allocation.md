## Short answer

<span class="warn">Це тихо змінює семантику КОЖНОЇ алокації, включно зі сторонніми бібліотеками.</span>

Будь-який код, що десь усередині кличе `new` (навіть бібліотечний), раптом піде через твій пул – з непередбачуваними наслідками для розміру/часу.

Захист: безпечніше взагалі `= delete` глобальний `operator new`, щоб випадкова heap-алокація стала compile error.[^embeddedinterviewlab]

## Detailed explanation

### Як працює заміна глобального `operator new`

У мові C++ функції виділення динамічної пам’яті `operator new`, `operator new[]`, `operator delete` та `operator delete[]` мають глобальну видимість і за замовчуванням визначаються стандартною бібліотекою як замінні (replaceable functions)[^iso-cpp-n4861]. Якщо користувач визначає власну версію `void* operator new(std::size_t)`, компонувальник замінює нею стандартну реалізацію для всієї програми.

В інженерній практиці розробники іноді намагаються підмінити глобальний `operator new` власним пулом блоків фіксованого розміру (fixed-size block pool) або статичною ареною пам’яті. Мета здається привабливою: уникнути системної купи (`malloc`) і зовнішньої фрагментації RAM без переписування коду з викликами `new`. Проте таке рішення несе критичні приховані загрози для надійності прошивки.

### Приховані загрози глобальної підміни на пул

1. **Невідповідність розміру запиту (Size Mismatch)**:
   Пуловий алокатор оперує блоками суворо фіксованого розміру (наприклад, 64 байти). Якщо код запитує виділення 128 або 256 байтів, алокатор не має іншого виходу, окрім як повернути `nullptr` або викинути виняток. За вимкнених винятків (`-fno-exceptions`, стандартний прапорець для MCU) виклик `new` призводить до розіменування нульового покажчика або аварійної зупинки `abort()`. Навіть якщо пул нарізає великі блоки для розміщення дрібних запитів, виникає катастрофічна внутрішня фрагментація пам’яті.

2. **Захоплення алокацій сторонніх бібліотек**:
   Підміна глобального `operator new` є глобальною: вона застосовується не лише до власного коду, але й до всіх скомпільованих бібліотек (криптографія mbedTLS, файлові системи LittleFS/FatFs, C++-обгортки FreeRTOS, стек TCP/IP або USB-CDC). Будь-який сторонній код, що виконує внутрішню алокацію пам’яті, несподівано почне виснажувати призначений для системних задач пул.

3. **Складність парного звільнення та вирівнювання**:
   Стандарт C++ вимагає парної заміни цілої групи операторів[^iso-cpp-n4861]:
   - Одиничний та масивний виділювачі: `operator new(size_t)` та `operator new[](size_t)`.
   - Оператори з підтримкою вирівнювання C++17: `operator new(size_t, std::align_val_t)`.
   - Оператори звільнення з розміром C++14: `operator delete(void*, size_t)`.
   Якщо користувацький пул не реалізує всі перевантаження з однаковою логікою, різні одиниці трансляції будуть використовувати несумісні пари виділення/звільнення, що призведе до руйнування пам’яті.

4. **Проблема потокобезпеки (Thread Safety) в RTOS**:
   Стандартний `operator new` розрахований на безпечний виклик із будь-якого потоку. Простий кастомний пул без блокування переривань або м’ютексів RTOS при одночасному виклику з двох завдань або з контексту переривання призведе до стану перегонів (race condition) та фатального пошкодження списку вільних блоків (free list corruption).

### Безпечні альтернативи: заборона або локалізація

Замість глобальної підміни оператора у надійних прошивках застосовують два детерміновані підходи:

1. **Повна заборона глобальної купи через `= delete`**:
   Якщо стандарти проєкту (наприклад, MISRA C++ або DO-178C) забороняють використання купи після старту, найнадійнішим способом є оголошення глобальних операторів видаленими[^iso-cpp-n4861]:
   ```cpp
   void* operator new(std::size_t) = delete;
   void* operator new[](std::size_t) = delete;
   void operator delete(void*) noexcept = delete;
   void operator delete[](void*) noexcept = delete;
   ```
   У такому разі будь-яка спроба випадкового виклику `new` або використання контейнера, що алокує пам’ять (`std::vector`, `std::string`), буде перехоплена компілятором як помилка збірки ще до прошивання мікроконтролера.

2. **Класові оператори `new` або спеціалізовані фабрики**:
   Якщо конкретному класу дійсно потрібен пуловий алокатор, перевантаження роблять локальним для цього типу:
   ```cpp
   class CanFrame {
   public:
       static void* operator new(std::size_t size) {
           return pool.allocate(size);
       }
       static void operator delete(void* ptr) noexcept {
           pool.deallocate(ptr);
       }
   private:
       static MemoryPool<sizeof(CanFrame), 16> pool;
   };
   ```
   Це ізолює семантику виділення пам’яті виключно в межах потрібного класу, не зачіпаючи сторонні модулі та системний runtime.
