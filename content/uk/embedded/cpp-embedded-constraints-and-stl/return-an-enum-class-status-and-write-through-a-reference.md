## Question code

```cpp
enum class Status { Ok, Timeout, CrcError, Busy };
Status sensor_read(uint8_t a, uint16_t& out) {
  if (!bus_ready()) return Status::Busy;
  out = raw;
  return Status::Ok;
}
```

## Short answer

**`enum class` зі статусами + дані через reference/output-параметр.**

`enum class` дає типобезпеку (на відміну від голого `enum`), а викликач зобов’язаний перевірити результат. Це embedded-аналог винятків.

Правило: return codes – дефолтний error handling без exceptions.[^embeddedinterviewlab]

## Detailed explanation

### Шаблон повернення статусних кодів

В умовах жорстких обмежень мікроконтролерів (де винятки вимкнено прапорцем `-fno-exceptions` для збереження детермінізму та розміру Flash), повернення статусних кодів є базовим інженерним стандартом обробки помилок[^iso-cpp-n4861].

При цьому використовується чіткий шаблон проєктування інтерфейсів:
1. Значення, що повертається функцією через оператор `return`, відводиться суто під статус завершення операції (`status code`).
2. Корисні дані (результат обчислень або вимірювання датчика) записуються через вихідний параметр – неконстантне посилання (`T& out`) або покажчик (`T* out`):

```cpp
enum class Status : uint8_t {
    Ok = 0,
    Timeout,
    CrcError,
    Busy
};

[[nodiscard]] Status sensor_read(uint8_t addr, uint16_t& out) {
    if (!bus_ready()) {
        return Status::Busy;
    }
    out = read_hw_register(addr);
    return Status::Ok;
}
```

### Переваги scoped enum (enum class) перед класичним C-enum

Використання `enum class` (strongly typed scoped enumeration), введеного у стандарті C++11, надає критичні переваги безпеки у порівнянні зі старими переліками мови C:
- **Заборона неявних перетворень типів**: звичайний `enum` неявно зводиться до `int`, що дозволяє випадково порівняти статус шини I2C зі статусом файлової системи або записати код помилки у звичайну лічильну змінну. `enum class` не дозволяє жодних неявних приведень – спроба порівняти різні типи викличе помилку компіляції.
- **Ізоляція простору імен**: ідентифікатори переліку не засмічують глобальну область видимості. Доступ до них здійснюється виключно через кваліфіковане ім’я `Status::Ok`, `Status::Busy`, що усуває конфлікти імен у великих бібліотеках.
- **Фіксація базового типу (`underlying type`)**: розробник може явно вказати мінімальний цілочисельний тип (наприклад, `enum class Status : uint8_t`), що гарантує фіксований розмір об’єкта в 1 байт в пам’яті Flash або RAM.

### Обов’язкова перевірка результату через [[nodiscard]]

Головний недолік кодів повернення у порівнянні з винятками полягає в тому, що викликаючий код може випадково проігнорувати повернуте значення:
```cpp
uint16_t val;
sensor_read(0x42, val); // якщо сталася помилка, val містить невизначене значення!
process(val);           // робота з неініціалізованими даними
```

Для вирішення цієї проблеми у стандарті C++17 введено атрибут `[[nodiscard]]`[^iso-cpp-n4861]. Якщо функція, помічена цим атрибутом, викликається без збереження або перевірки результату, компілятор зобов’язаний згенерувати попередження (а при увімкненому прапорці `-Werror` – фатальну помилку збірки). Це повертає суворість обробки помилок на рівень винятків без жодних runtime-витрат.

### Ефективність генерації асемблерного коду на ARM Cortex-M

З погляду машинних інструкцій та конвенції викликів AAPCS (ARM Architecture Procedure Call Standard):
- Статус функції повертається безпосередньо через процесорний регістр `r0`.
- Перевірка успішності зводиться до двох швидких інструкцій:
  ```assembly
  BL   sensor_read    ; виклик функції, результат у r0
  CMP  r0, #0         ; перевірка на Status::Ok (0)
  BNE  handle_error   ; швидкий умовний перехід у разі збою
  ```
- Жодних прихованих алокацій, блокувань або таблиць розгортання стека: оверхед дорівнює нулю та має фіксований детермінований час виконання.
