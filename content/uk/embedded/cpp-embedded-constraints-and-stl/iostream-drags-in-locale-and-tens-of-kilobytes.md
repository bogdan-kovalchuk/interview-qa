## Short answer

<span class="warn">`<iostream>` може тягнути locale, heap-буфери, глобальну ініціалізацію й десятки КБ Flash.</span>

`std::cout` ініціалізує важку інфраструктуру ще до `main()`; на MCU це часто неприйнятно. `printf` (особливо урізаний/nano) або власний trace backend зазвичай значно легші.

Правило: для логів на MCU – `printf`/власний trace backend, не `iostream`.[^embeddedinterviewlab]

## Detailed explanation

### Чому `<iostream>` призводить до роздування Flash-пам’яті

Головна причина відмови від заголовка `<iostream>` у прошивках для мікроконтролерів – це катастрофічне збільшення розміру бінарного образу (Flash overhead)[^iso-cpp-n4861]. Навіть один простий виклик оператора виведення `std::cout << x;` призводить до лінкування розгалуженої ієрархії класів стандартної бібліотеки: `std::basic_ostream`, `std::basic_ios`, `std::ios_base` та буфера потоку `std::basic_streambuf`.

У типових тулчейнах для архітектури ARM (наприклад, `arm-none-eabi-gcc` з `libstdc++`) підключення `<iostream>` збільшує розмір прошивки у Flash на 50–150 КБ. Для мікроконтролерів із загальним обсягом Flash-пам’яті 32–128 КБ (наприклад, STM32F1/F4 або nRF52) це означає вичерпання всієї доступної пам’яті ще до розміщення логіки застосунку.

### Підсистема локалізації (std::locale) та динамічна пам’ять

Ієрархія потоків у стандартній бібліотеці C++ нерозривно пов’язана з підсистемою локалізації (`std::locale`)[^iso-cpp-n4861]:
- **Фасети форматування чисел**: для перетворення цілих чисел або чисел із плаваючою комою у текст потік викликає фасети `std::num_put` та `std::numpunct`. Це тягне за собою таблиці розбору символів, віртуальні таблиці (`vtable`) фасетів та код конвертації.
- **Використання heap**: об’єкти `std::locale` та буфери `std::streambuf` у стандартній реалізації алокують динамічну пам’ять через `malloc` / `operator new`. У системах із жорсткими обмеженнями або повною забороною heap це порушує вимоги надійності та спричиняє недетерміновані паузи через фрагментацію RAM.

### Статичні конструктори до входу в main()

Стандартні потоки вводу-виводу (`std::cout`, `std::cin`, `std::cerr`) вимагають гарантованої ініціалізації до початку роботи користувацького коду. Для цього використовується службовий клас `std::ios_base::Init`, статичні екземпляри якого розміщуються у кожному трансляційному юніті, де підключено `<iostream>`[^iso-cpp-n4861].

У результаті компонувальник заповнює секцію `.init_array` адресами статичних конструкторів. До виклику функції `main()` startup-код змушений виконати ланцюжок ініціалізацій, які споживають пам’ять RAM під внутрішні структури потоків і суттєво уповільнюють холодний запуск пристрою (boot time).

### Чому printf та власні логери переважають на MCU

Класична функція `printf` або її полегшені аналоги позбавлені цих недоліків:
- **Newlib-nano**: при збиранні з прапорцем `--specs=nano.specs` бібліотека `newlib-nano` надає реалізацію `printf`, оптимізовану за розміром коду, без локалей і без динамічних алокацій.
- **Просте апаратне перенаправлення**: для виведення тексту достатньо перевизначити одну низькорівневу функцію `_write` (або `__io_putchar`), яка записує байти напряму в регістр даних передавача UART (`USART->DR` / `USART->TDR`):
```c
int _write(int file, char *ptr, int len) {
    for (int i = 0; i < len; ++i) {
        while (!(USART1->SR & USART_SR_TXE));
        USART1->DR = (uint8_t)ptr[i];
    }
    return len;
}
```
- **Легковажні C++ альтернативи**: якщо потрібна сувора типобезпека без накладних витрат, у сучасному embedded C++ використовують `std::to_chars` (який працює без локалей і без heap у фіксованому буфері) або вбудовані логери на базі рядкових літералів у `.rodata` та передачі через DMA.
