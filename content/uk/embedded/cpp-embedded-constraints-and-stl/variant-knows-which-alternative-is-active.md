## Short answer

**Type-safe tagged union: знає активний тип, автоматично керує деструкторами.**

Сирий `union` не знає, яке поле валідне (UB при читанні не того типу) і не викликає деструктори складних типів. `std::variant` тримає discriminator і безпечно працює через `std::visit` або `std::get_if`.

Правило: поліморфні типи фіксованого набору без heap – `std::variant`, а не голий `union`.[^embeddedinterviewlab]

## Detailed explanation

### Концепція типобезпечного об’єднання (Tagged Union)

`std::variant` (стандартизований у C++17) – це типобезпечний контейнер із розпізнаванням активного типу (tagged union або discriminated union)[^iso-cpp-n4861]. Він призначений для збереження рівно одного значення із фіксованого набору наперед визначених типів.

На відміну від поліморфізму на базі віртуальних функцій і покажчиків (`vtable`), `std::variant` розміщує дані безпосередньо у своєму тілі (in-place) на стеку або у статичній пам’яті, повністю виключаючи динамічне виділення пам’яті (heap). Це робить його ідеальним інструментом для представлення повідомлень протоколів (CAN, UART), подій кінцевих автоматів (FSM) та результатів вимірювань датчиків.

### Проблеми класичного `union` у C та C++

Класичне об’єднання `union`, успадковане з C, має два критичні недоліки, неприпустимі у надійних прошивках:
1. **Відсутність інформації про активний тип та Type Punning**:
   `union` виділяє спільну ділянку пам’яті для всіх своїх полів, але не зберігає інформації про те, яке саме поле було записано останнім. Зчитування поля `b`, якщо перед цим було записано поле `a` іншого типу (так званий type punning), у мові C++ є невизначеною поведінкою (Undefined Behavior, UB)[^iso-cpp-n4861]. Компілятор при оптимізаціях `-O2`/`-Os` має право припустити, що змінні різних типів не перетинаються в пам’яті (strict aliasing rule), що призводить до непояснюваних збоїв на апаратурі.
2. **Некерований життєвий цикл складних типів**:
   Якщо поле `union` містить нетривіальний конструктор або деструктор (наприклад, RAII-буфер, структуру із захистом ресурсів або контейнер), компілятор C++ видаляє конструктори та деструктори самого `union`. Розробник зобов’язаний вручну викликати деструктор попереднього поля через явний синтаксис `obj.~T()` та будувати нове поле через `placement new`. Будь-яка помилка веде до витоку пам’яті або повторного вивільнення ресурсів.

### Анатомія та розміщення `std::variant` у пам’яті

`std::variant` вирішує ці проблеми на системному рівні:
- **Буфер даних**: виділяється спільна ділянка пам’яті, розмір якої дорівнює максимальному розміру серед типів-альтернатив, а вирівнювання відповідає максимальному вирівнюванню серед них.
- **Дискримінатор (Type Tag)**: цілочисельне поле індексу (зазвичай `uint8_t`), яке зберігає номер поточного активного типу (0, 1, 2...).
- **Автоматичний RAII**: при зміні значення `std::variant` компілятор автоматично генерує виклик деструктора для старого активного типу перед створенням нового об’єкта.

Розмір об’єкта у Flash/RAM визначається як розмір найбільшого типу плюс розмір дискримінатора та вирівнювання:
```cpp
#include <variant>
#include <cstdint>

struct Heartbeat { uint32_t uptime; };
struct Temperature { float celsius; };
struct Fault { uint8_t code; };

using Packet = std::variant<Heartbeat, Temperature, Fault>;
// sizeof(Packet) на 32-бітному ARM: 4 байти (дані) + 1 байт (tag) + 3 байти (padding) = 8 байтів
```

### Безпечний доступ та диспетчеризація через `std::visit`

Для роботи зі значеннями `std::variant` у коді без винятків (`-fno-exceptions`) застосовують два безпечні методи:
1. **Перевірка покажчика через `std::get_if<T>`**:
   Функція `std::get_if<T>(&var)` перевіряє дискримінатор і повертає покажчик на значення, якщо активний тип збігається з `T`, або `nullptr`, якщо активний інший тип. Вона ніколи не викидає винятків:
```cpp
if (const auto* temp = std::get_if<Temperature>(&packet)) {
    apply_calibration(temp->celsius);
}
```
2. **Патерн Visitor через `std::visit`**:
   Дозволяє обробляти всі варіанти без громіздких конструкцій `if-else` або `switch`. Компілятор формує таблицю стрибків за дискримінатором і перевіряє вичерпність обробки всіх альтернатив під час компіляції:
```cpp
struct PacketProcessor {
    void operator()(const Heartbeat& h) { watchdog_kick(h.uptime); }
    void operator()(const Temperature& t) { log_temp(t.celsius); }
    void operator()(const Fault& f) { enter_safe_mode(f.code); }
};

std::visit(PacketProcessor{}, packet);
```
