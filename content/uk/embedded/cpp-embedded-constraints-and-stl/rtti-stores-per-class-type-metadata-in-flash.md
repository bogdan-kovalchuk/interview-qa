## Short answer

**RTTI (run-time type information) зберігає метадані типу на клас у Flash; вимкнення економить ROM.**

Наслідки: недоступний `dynamic_cast` (використовуй `static_cast`, коли тип відомий) і `typeid` (заміни на template specialization / tag dispatch). Virtual-функції працюють – vtable ≠ RTTI.

Правило: без RTTI покладайся на compile-time знання типів, а не runtime-перевірки.[^embeddedinterviewlab]

## Detailed explanation

### Що таке RTTI та чому його вимикають в embedded

RTTI (Run-Time Type Information) – це механізм мови C++, що забезпечує визначення точного динамічного типу об’єкта під час виконання програми через покажчик або посилання на його базовий клас[^iso-cpp-n4861].

Для роботи RTTI компілятор розміщує в бінарному файлі спеціальні статичні структури даних у пам’яті Flash[^gcc-fno-rtti]:
- **Об’єкти `std::type_info`**: для кожного класу, який має хоча б одну віртуальну функцію (поліморфний клас), формується дескриптор типу.
- **Текстові рядки імен типів**: дескриптор зберігає текстову назву класу для підтримки методу `typeid(obj).name()`. У великих проєктах сотні рядків назв класів безглуздо займають кілобайти коштовної Flash-пам’яті мікроконтролера.
- **Таблиці зв’язків успадкування**: структури, що описують ієрархію базових і похідних класів для перевірки допустимості низхідного приведення типів (downcasting) при множинному та віртуальному успадкуванні.
- **Службовий покажчик у vtable**: кожна таблиця віртуальних методів (`vtable`) містить покажчик на відповідний об’єкт `type_info` (зазвичай зі зміщенням `-1` перед першим віртуальним методом).

У вбудованих системах цей функціонал використовується вкрай рідко, проте за замовчуванням призводить до відчутного роздування бінарного образу (ROM overhead). Вимкнення RTTI за допомогою прапорця `-fno-rtti` повністю видаляє ці метадані з прошивки.

### Що саме блокує прапорець -fno-rtti

При використанні прапорця компілятора `-fno-rtti` стають недоступними дві ключові мовні конструкції[^gcc-fno-rtti]:
1. **Оператор `dynamic_cast`**: спроба виконати `dynamic_cast<Derived*>(base_ptr)` викликає помилку компіляції (`error: cannot use 'dynamic_cast' with '-fno-rtti'`). Оскільки в runtime немає метаданих про спорідненість типів, компілятор не здатний безпечно перевірити коректність приведення за покажчиком.
2. **Оператор `typeid`**: заборонено звернення до `typeid` над поліморфними типами та використання заголовка `<typeinfo>`.

### Що продовжує працювати: vtable та віртуальні функції

Поширеною помилкою є припущення, нібито вимкнення RTTI скасовує таблиці віртуальних функцій (`vtable`) або забороняє використання віртуальних методів.

Віртуальні виклики та динамічний поліморфізм C++ чудово працюють і без RTTI:
```cpp
class Sensor {
public:
    virtual void init() = 0;
    virtual ~Sensor() = default;
};

class TempSensor : public Sensor {
public:
    void init() override { /* налаштування I2C */ }
};

void start(Sensor* s) {
    s->init(); // працює штатно при -fno-rtti!
}
```

На рівні асемблера ARM Cortex-M виклик віртуального методу не задіює RTTI: процесор просто вичитує адресу таблиці vtable з першого слова об’єкта, бере адресу функції за фіксованим зміщенням і здійснює непрямий перехід `BLX`:
```assembly
LDR  r1, [r0]       ; завантаження адреси vtable
LDR  r2, [r1, #0]   ; завантаження адреси першої віртуальної функції
BLX  r2             ; стрибок на реалізацію init()
```
Різниця полягає лише в тому, що слот `type_info` у таблиці vtable занулюється або взагалі виключається оптимізатором.

### Альтернативи в embedded-коді без RTTI

1. **Compile-time поліморфізм**:
   Замість віртуальних функцій та динамічних перевірок використовують шаблони, концепт-перевірки (C++20 Concepts) або ідіому CRTP (Curiously Recurring Template Pattern), що повністю усуває витрати часу на непрямі виклики.
2. **Статичне приведення типів (`static_cast`)**:
   Якщо архітектура гарантує точний тип об’єкта за контрактом (наприклад, фабричний метод створює відомий клас драйвера), замість `dynamic_cast` застосовують пряме приведення `static_cast<Derived*>(ptr)`.
3. **Ручна типізація (Tag Dispatch / Type Enum)**:
   Якщо перевірка типу в runtime дійсно необхідна, у базовий клас додають цілочисельний ідентифікатор типу (наприклад, `enum class DeviceType : uint8_t`). Це дає змогу організувати безпечний `switch` за типом об’єкта без накладних витрат RTTI.
