## Short answer

**Компілятору потрібне повне визначення шаблону в кожному TU (translation unit), щоб інстанціювати його під конкретні типи.**

Якщо визначення сховати в `.cpp`, інші translation units не зможуть згенерувати потрібну інстанціацію -> linker error. Тому шаблони кладуть у заголовки.

Правило: визначення шаблонів – у header; для контролю інстанціацій використовуй `extern template`.[^embeddedinterviewlab]

## Detailed explanation

### Модель компіляції C++ та одиниці трансляції

У мовах C та C++ збирання проєкту базується на незалежній обробці окремих одиниць трансляції (Translation Units, TU).[^iso-cpp-n4861] Одиниця трансляції – це один файл вихідного коду `.cpp` разом із усіма файлами заголовків, підключеними через директиву препроцесора `#include`.

Компілятор обробляє кожну одиницю трансляції повністю ізольовано: він не має доступу до вихідного тексту інших `.cpp` файлів проєкту і не знає, які типи та функції використовуються сусідніми модулями.

### Чому шаблон не генерує код без використання

Шаблон класу або функції в C++ – це не скомпільований двійковий код і навіть не інструкція для процесора, а креслення (blueprint) для компілятора.[^iso-cpp-n4861]

Компілятор не генерує жодної машинної інструкції, доки шаблон не буде інстанційовано (instantiated) з конкретними аргументами типів або констант:
- Якщо оголосити сигнатури методів у `Buffer.hpp`, а їхні тіла помістити у `Buffer.cpp`: під час компіляції `Buffer.cpp` компілятор бачить лише загальний шаблон без конкретних типів і не генерує жодного символу в об’єктному файлі `Buffer.o`.
- Коли інший файл `main.cpp` включає `Buffer.hpp` і створює `Buffer<uint8_t, 32>`, компілятору для генерації машинного коду потрібні повні тіла функцій. Не маючи їх, він лише формує запит на зовнішні символи (external symbol reference).
- На етапі компонування компонувальник (linker) повідомляє про фатальну помилку:
  `undefined reference to Buffer<unsigned char, 32u>::push(unsigned char)`.

Саме тому визначення методів шаблонів за замовчуванням розміщують безпосередньо у файлах заголовків (`.hpp` або `.h`), щоб повний текст реалізації був доступний у кожній одиниці трансляції, де використовується шаблон.

### Виняток: явна інстанціація (Explicit Template Instantiation)

Якщо набір допустимих типів або розмірів відомий наперед і є фіксованим, визначення шаблону можна сховати у файл `.cpp`, використавши явну інстанціацію:[^iso-cpp-n4861]

```cpp
// RingBuffer.hpp
template <typename T, std::size_t N>
class RingBuffer {
public:
    void push(T val);
};

// RingBuffer.cpp
#include "RingBuffer.hpp"

template <typename T, std::size_t N>
void RingBuffer<T, N>::push(T val) {
    // реалізація
}

// Явна генерація двійкового коду під визначені типи
template class RingBuffer<uint8_t, 64>;
template class RingBuffer<uint16_t, 128>;
```

Тепер `RingBuffer.o` міститиме реальний машинний код для цих конкретних параметрів, і лінкер успішно зв’яже виклики.

### Керування інстанціаціями через `extern template`

Починаючи з C++11, ключове слово `extern template` дозволяє заборонити компілятору генерувати однаковий код шаблону в кожному TU, де він використовується:[^iso-cpp-n4861]
```cpp
// У загальному заголовку
extern template class RingBuffer<uint8_t, 64>;
```
Це вказує компілятору, що ця інстанціація вже створена в іншій одиниці трансляції, що значно прискорює компіляцію великих вбудованих проєктів.

### Вплив на розробку під мікроконтролери

1. **Час компіляції:** розміщення великих шаблонів у заголовках змушує компілятор парсити та оптимізувати один і той самий код у кожному файлі `.cpp`.
2. **Дедуплікація символів лінкером:** компілятор поміщає згенеровані екземпляри шаблонів у спеціальні COMDAT-секції. Компонувальник порівнює їх і залишає лише один екземпляр у фінальній Flash-пам’яті, усуваючи дублікати.
3. **Рекомендація для embedded:** невеликі функції та класи-обгортки регістрів тримайте в заголовках як `inline` шаблони, а важкі складні алгоритми виділяйте в нешаблонні `.cpp` модулі або використовуйте явну інстанціацію.
