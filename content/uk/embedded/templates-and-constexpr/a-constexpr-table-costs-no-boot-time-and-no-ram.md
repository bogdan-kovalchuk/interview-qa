## Short answer

**Вона не марнує boot time й RAM – готова константа лежить у `.rodata`.**

Startup-цикл, що рахує CRC (cyclic redundancy check) або іншу lookup-таблицю, додає затримку до `main()` і часто тримає таблицю в RAM. `constexpr` переносить це у build time, лишаючи RAM вільною.

Правило: незмінні похідні дані обчислюй на компіляції, а не в startup-коді.[^embeddedinterviewlab]

## Detailed explanation

### Суть механізму та розміщення в секціях пам’яті

У сучасних стандартах C++ (починаючи з C++14/C++17) специфікатор `constexpr` дозволяє виконувати алгоритмічні обчислення будь-якої складності (генерація тригонометричних таблиць для DSP, таблиць контрольних сум CRC-8/16/32, гамма-корекції світлодіодів тощо) безпосередньо компілятором під час збирання проєкту.[^iso-cpp-n4861]

Якщо масив оголошено як глобальна або статична `constexpr` змінна:
```cpp
inline constexpr auto crc32_table = generate_crc32_table();
```
компілятор разом із компонувальником розміщують повністю готові обчислені дані в секцію константних даних `.rodata` (read-only data). У мікроконтролерах секція `.rodata` відображається безпосередньо у внутрішню енергонезалежну Flash-пам’ять і не потребує завантаження в оперативну пам’ять (SRAM).

### Порівняльний аналіз: constexpr у Flash проти Startup-обчислення

Обчислення таблиць у коді ініціалізації (перед функцією `main()` або під час старту периферії) програє за всіма ключовими інженерними показниками:

| Критерій | Startup-генерація в runtime | `constexpr`-таблиця у Flash |
|---|---|---|
| **Використання RAM** | Виділяється пам’ять у SRAM (`.bss` або купі) | 0 байтів у RAM (зберігається в `.rodata` у Flash) |
| **Час завантаження (Boot time)** | Затримка на виконання циклів обчислення | 0 тактів CPU при старті системи |
| **Використання Flash** | Код алгоритму генерації у Flash + константи | Тільки розмір готової таблиці у Flash |
| **Надійність і детермінізм** | Можливість збою пам’яті, ризик data race | Дані захищені від запису на рівні апаратури Flash/MPU |

### Чому це критично в практичних прошивках

1. **Жорсткі вимоги до часу старту (Fast Boot Requirements):**
   У багатьох промислових та автомобільних протоколах (наприклад, шина CAN / CAN-FD) пристрій зобов’язаний відповісти на перший запит діагностики або ініціалізації протягом 50–100 мс після подачі живлення. Складні математичні цикли ініціалізації в startup-коді можуть затримати старт або спричинити перезавантаження від апаратного сторожового таймера (Watchdog Timer).
2. **Дефіцит оперативної пам’яті:**
   На мікроконтролерах класу ARM Cortex-M0+ із 4–8 КБ RAM таблиця CRC-32 на 256 32-бітних слів займає 1024 байти. Витрачати 25% доступної SRAM на константну таблицю, яка ніколи не змінюється, є грубою помилкою архітектури.
3. **Економія Flash-пам’яті на коді:**
   Для runtime-генерації потрібні як машинний код математичного алгоритму, так і поліноми. Часто код циклу генерації разом із налаштуванням займає у секції `.text` не менше місця, ніж сама згенерована таблиця у `.rodata`.

### Приклад створення compile-time таблиці на C++17

```cpp
#include <array>
#include <cstdint>

// Генератор таблиці виконується повністю під час компіляції
constexpr auto generate_crc32_table() {
    std::array<uint32_t, 256> table{};
    for (uint32_t i = 0; i < 256; ++i) {
        uint32_t crc = i;
        for (int j = 0; j < 8; ++j) {
            crc = (crc & 1) ? ((crc >> 1) ^ 0xEDB88320u) : (crc >> 1);
        }
        table[i] = crc;
    }
    return table;
}

// Таблиця обчислюється один раз при білді та лінкується у .rodata
inline constexpr auto crc32_lut = generate_crc32_table();
```

### Типові пастки та як їх уникати

- **Відсутність кваліфікатора `constexpr` у місці оголошення екземпляра:** якщо функція оголошена як `constexpr`, але змінна як `const auto table = generate_crc32_table();` всередині локальної функції, компілятор має право згенерувати runtime-виклик. Обов’язково використовуйте `constexpr` (або `consteval` у C++20) для визначення змінної.
- **Порушення ODR (One Definition Rule):** оголошення змінної у заголовку без `inline constexpr` у C++17 призведе до створення дублікатів таблиці в кожній одиниці трансляції.
- **Контроль через linker map:** завжди перевіряйте розміщення таблиці у фінальному файлі мапи лінкера (`.map`), щоб переконатися, що змінна потрапила в область пам’яті FLASH/ROM, а не в RAM.
