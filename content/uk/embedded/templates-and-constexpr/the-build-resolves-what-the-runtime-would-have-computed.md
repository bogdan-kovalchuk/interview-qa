## Short answer

**Компілятор резолвить типи й рахує значення на етапі білду – після оптимізації код може бути таким самим щільним, як ручний C, але з сильнішою типобезпекою.**

Важливо: це стосується runtime-вартості правильно спроєктованої абстракції; flash footprint і час компіляції мають реальну ціну.

Правило: zero-cost = немає обов’язкової runtime-ціни, але не «безкоштовно» у Flash і build time.[^embeddedinterviewlab]

## Detailed explanation

### Принцип нульових накладних витрат (Zero-Overhead Principle)

Концепція «zero-cost abstraction» (абстракція з нульовою вартістю) була сформульована Б’ярном Страуструпом як фундаментальний принцип дизайну C++:
1. Те, чим ви не користуєтеся, ви не оплачуєте (what you don't use, you don't pay for).
2. Те, що ви використовуєте, ви не змогли б вручну написати на асемблері чи C ефективніше (what you do use, you couldn't hand code any better).

У стандарті ISO/IEC 14882 ([dcl.constexpr] та [temp] у [^iso-cpp-n4861]) цей принцип реалізується через шаблони та `constexpr`-механізми. Вони дозволяють перенести семантичні перевірки, вибір алгоритму та обчислення констант з етапу виконання прошивки (runtime) на етап компіляції (compile-time).

### Механізм роботи на рівні асемблера ARM Cortex-M

Коли розробник використовує шаблонний клас або `constexpr`-функцію для налаштування периферійного модуля, компілятор розраховує всі бітові маски та дільники заздалегідь:

```cpp
template <uint32_t ClockHz, uint32_t BaudRate>
constexpr uint32_t calculate_uart_brr() {
    return (ClockHz + (BaudRate / 2)) / BaudRate; // Заокруглення до найближчого цілого
}

template <uint32_t ClockHz, uint32_t BaudRate>
void set_baud(USART_TypeDef* usart) {
    constexpr uint32_t brr = calculate_uart_brr<ClockHz, BaudRate>();
    usart->BRR = brr;
}
```

У ручному коді на C розробники часто або хардкодять магічні числа через препроцесорні макроси, або викликають функцію з runtime-діленням. На Cortex-M3/M4 ділення виконується апаратно за 2–12 тактів інструкцією `UDIV`, а на ядрах Cortex-M0/M0+ викликає важку софтову бібліотечну підпрограму `__aeabi_uidiv`.

Завдяки `constexpr` та інлайнінгу компілятор оптимізує функцію до однієї операції запису заздалегідь обчисленої константи:

```assembly
// Оптимізований код set_baud:
LDR     R1, =0x40013800   // USART1 базова адреса
MOV     R2, #0x0683       // Заздалегідь порахований дільник BRR (9600 при 16 МГц)
STR     R2, [R1, #0x0C]   // Запис у регістр BRR
BX      LR
```

Така абстракція забезпечує найвищий рівень типізації, але в машинному коді не має жодної інструкції накладних витрат.

### Що насправді НЕ є безкоштовним

Поняття *zero-cost* стосується виключно **часу виконання** (runtime latency, CPU cycles) та відсутності додаткових полів у RAM (наприклад, відсутність покажчика таблиці віртуальних функцій `vptr` у статичному поліморфізмі на базі CRTP). Водночас за це сплачується інша ціна:

1. **Витрати Flash-пам’яті (Code Bloat)**: Кожна окрема інстанціація шаблону з різними параметрами типу або числами породжує власний блок коду. Якщо функції занадто великі для інлайнінгу, вони повторюються у Flash.
2. **Агресивний Inlining**: Прагнення компілятора прибрати виклики функцій може призвести до роздування бінарного коду через копіювання однакових тіл функцій у кожне місце виклику.
3. **Час складання (Compile Time)**: Інтерпретація `constexpr`-коду та інстанціація глибоких метапрограмних шаблонів значно збільшують споживання оперативної пам’яті компілятором і час збирання проєкту.

### Практичне правило для Embedded-систем

У прошивках мікроконтролерів «zero-cost abstraction» означає, що програміст отримує безпеку типів і читабельний код без втрати продуктивності процесора. Проте обов’язково слід контролювати баланс між тактами CPU та витратами Flash-пам’яті, верифікуючи розмір згенерованих секцій у `.map`-файлі[^embeddedinterviewlab].
