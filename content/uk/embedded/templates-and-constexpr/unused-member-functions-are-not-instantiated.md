## Short answer

**Зазвичай ні – при неявній інстанціації class template генеруються лише member-функції, які реально потрібні.**

Це обмежує bloat: якщо у `CircularBuffer<T,N>` не викликати `pop()`, його код зазвичай не потрапить у Flash для цієї інстанціації. Винятки: explicit instantiation, virtual-функції та інші ODR-use сценарії можуть змусити згенерувати більше.

Правило: невикористані методи шаблону часто безкоштовні, але перевіряй linker map для template-heavy коду.[^embeddedinterviewlab]

## Detailed explanation

### Механізм неявної інстанціації (Implicit Instantiation)

Згідно зі стандартом ISO/IEC 14882 ([temp.inst] у [^iso-cpp-n4861]), коли шаблон класу неявно інстанціюється для конкретних аргументів, компілятор створює лише тип самого класу та оголошення його членів. Визначення функцій-членів (member function definitions) за замовчуванням **не інстанціюються**.

Тіло функції-члена шаблону компілюється в машинний код тільки в тому разі, якщо функція піддається використанню за правилом одного визначення (One Definition Rule, ODR-use) – тобто викликається в коді програми або береться її адреса:

```cpp
template <typename T, size_t Capacity>
class Queue {
public:
    void push(const T& item) { /* Логіка запису */ }
    T pop() { /* Логіка читання */ }
    void clear() { /* Очищення буфера */ }
    void dump_to_uart() { /* Важкий код форматування і виводу */ }
};

void process_data() {
    Queue<uint8_t, 128> q;
    q.push(0x55); // push() інстанціюється і потрапляє у Flash
    // pop(), clear(), dump_to_uart() НЕ викликаються і код для них НЕ генерується
}
```

У наведеному прикладі `dump_to_uart()` може містити складний алгоритм форматування рядків, проте компілятор взагалі не генерує для нього машинних інструкцій у секціях `.text`.

### Значення для гнучкості архітектури та економії пам’яті

1. **Захист від Code Bloat**: Якщо шаблонний драйвер периферії або контейнер має 20 допоміжних методів, але у вашому сценарії використовуються лише два, у Flash розмістяться тільки ці два методи.
2. **Семантична гнучкість (Duck Typing)**: Відкладена інстанціація дозволяє писати методи, вимоги яких задовольняються лише деякими типами. Наприклад, метод `dump_to_uart()` може вимагати від типу `T` наявності оператора перетворення у рядок. Доки цей метод не викликається, клас `Queue<SensorRawData, 128>` успішно компілюється, навіть якщо `SensorRawData` не вміє друкуватися.

### Сценарії-винятки: коли код генерується примусово

Існують умови, за яких компілятор зобов’язаний згенерувати машинний код навіть для тих функцій-членів, які розробник явно не викликає:

- **Віртуальні функції (Virtual Methods)**:
  Якщо метод шаблону оголошено як `virtual`, компілятор зобов’язаний згенерувати для нього машинний код і розмістити вказівник на нього в таблиці віртуальних функцій (`vtable`) відповідної спеціалізації ([temp.inst] у [^iso-cpp-n4861]). Створення `vtable` є ODR-use для всіх її методів. Тому віртуальні методи інстанціюються завжди.
- **Явна інстанціація класу (Explicit Instantiation)**:
  Директива виду `template class Queue<uint8_t, 128>;` наказує компілятору примусово інстанціювати всі без винятку функції-члени шаблону, незалежно від того, чи викликаються вони де-небудь у проєкті.
- **Взяття адреси методу**:
  Збереження вказівника на метод (наприклад, для реєстрації callback-обробника в C-бібліотеці або RTOS) робить його ODR-used.

### Інженерні рекомендації для мікроконтролерів

- Уникайте віртуальних методів усередині шаблонних класів периферії, щоб не змушувати компілятор створювати `vtable` та інстанціювати всі методи у Flash.
- Використовуйте прапорці `-ffunction-sections` та `-fdata-sections` разом із лінкерним прапорцем `-Wl,--gc-sections`. Це гарантує, що навіть випадково згенеровані слабкі символи (weak symbols), які не використовуються іншими модулями, будуть надійно вилучені під час фінального лінкування[^embeddedinterviewlab].
