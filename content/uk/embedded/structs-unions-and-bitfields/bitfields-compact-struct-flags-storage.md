## Short answer

**Бітові поля** – це поля структури з явно заданою кількістю бітів: `struct Flags { unsigned ready:1; unsigned mode:3; };`.[^dou-embedded-interview] Вони зручні для компактного зберігання прапорців або опису частин register/status word.

Обмеження: не можна взяти адресу bit-field, порядок пакування бітів, signedness і padding часто implementation-defined, тому layout може відрізнятися між компіляторами й ABI. Для hardware registers і протоколів часто надійніше використовувати маски й зсуви над `uint32_t`, а bit-fields – тільки коли layout контролюється й перевірений.

## Detailed explanation

### Синтаксис та призначення бітових полів

Бітові поля (bit-fields) – це спеціальний механізм мов C та C++, який дозволяє явно вказувати розрядність окремих членів структури або об’єднання в бітах:

```c
struct SystemFlags {
    unsigned int is_ready     : 1;
    unsigned int error_code   : 3;
    unsigned int power_mode   : 2;
    unsigned int reserved     : 2;
};
```

Згідно зі стандартом C (ISO/IEC 9899 §6.7.2.1)[^iso-c-n1570], базовим типом бітового поля може бути `_Bool`, `signed int`, `unsigned int` або інший тип, визначений реалізацією (`implementation-defined`). Головне практичне призначення бітових полів у вбудованих системах – компактне збереження прапорців та дрібних конфігураційних параметрів в оперативній пам’яті (RAM) для мінімізації споживання пам’яті.

### Обмеження мови C та адресація

Робота з бітовими полями має кілька жорстких обмежень на рівні системи типів C[^iso-c-n1570]:
1. **Неможливість взяття адреси**: до бітового поля не можна застосувати унарний оператор адреси `&`. Вираз `&flags.is_ready` призведе до помилки компіляції. Це зумовлено тим, що мінімальною адресованою коміркою пам’яті в архітектурі є байт, і покажчик мови C адресує саме байтові межі, а не окремі біти.
2. **Заборона `sizeof`**: оператор `sizeof` не може бути застосований до бітового поля, оскільки його результат вимірюється в байтах.
3. **Відсутність масивів**: не можна створювати масиви бітових полів.
4. **Посилання в C++**: у C++ неможливо створити неконстантне посилання (`non-const reference`) на бітове поле, оскільки посилання внутрішньо реалізується через покажчик.

### Недетермінованість layout та розбіжності ABI

Стандарт мови C свідомо залишає більшість параметрів розміщення бітових полів на розсуд розробників компілятора (`implementation-defined`)[^iso-c-n1570]:
- **Порядок пакування бітів**: компілятор має право розміщувати поля всередині одиниці виділення пам’яті (allocation unit) як від молодшого біта до старшого (LSB-to-MSB), так і від старшого до молодшого (MSB-to-LSB). Наприклад, один і той самий код, скомпільований різними версіями тулчейнів або під різні платформи, може мати дзеркальне розташування бітів.
- **Знаковість базового типу `int`**: якщо поле оголошене як `int flag : 1;` без явного слова `signed` чи `unsigned`, стандарт дозволяє реалізації вважати його знаковим або беззнаковим. У випадку знакового 1-бітного поля воно може приймати лише значення `0` та `-1` (у системі доповняльного коду two's complement). Запис `1` у таке поле з подальшим читанням поверне `-1`, що є класичною пасткою для розробника. Тому в embedded слід завжди явно писати `unsigned int` або `uint32_t`.
- **Перетин меж одиниць пам’яті**: чи може бітове поле перетинати межу машинного слова, залежить від ABI компілятора. Зазвичай створюється неявний padding.

### Рівень процесора ARM Cortex-M та MMIO

Процесори загального призначення (зокрема ядра ARM Cortex-M) не мають апаратних інструкцій запису довільного окремого біта за довільною адресою в RAM. Будь-який запис у бітове поле компілятор розгортає в послідовність операцій `read-modify-write` (RMW):

```assembly
LDR  r1, [r0]       ; читання цілого 32-бітного слова
ORR  r1, r1, #0x01  ; встановлення біта через логічне АБО
STR  r1, [r0]       ; запис слова назад у пам’ять
```

У багатозадачних системах з RTOS або за наявності обробників переривань (ISR) така послідовність без синхронізації створює критичний стан гонитви (race condition): якщо переривання змінить сусіднє бітове поле в тому самому слові між інструкціями `LDR` та `STR`, ці зміни будуть безповоротно затерті записом основного коду.

Для апаратних регістрів периферії (Memory-Mapped I/O, MMIO) використання бітових полів категорично не рекомендується: операція читання `LDR` може скинути апаратні статус-прапорці (read-to-clear), а повторний запис слова через `STR` може випадково очистити прапорці типу W1C (write-1-to-clear) або спричинити хибне спрацьовування апаратних тригерів.

### Інженерні рекомендації

- Використовувати бітові поля виключно для внутрішніх прапорців програми в оперативній пам’яті, де точне бітове розташування у фізичній пам’яті не має значення.
- Для регістрів мікроконтролера та бінарних протоколів (CAN, SPI, UART, TCP/IP) застосовувати явні маски, бітові зсуви над цілочисельними типами фіксованої ширини (`uint32_t`, `uint16_t`, `uint8_t`) або виділені апаратні регістри атомарного встановлення та скидання (наприклад, GPIO BSRR у STM32).
