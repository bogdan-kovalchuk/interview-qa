## Question code

```c
union Payload {
    uint16_t temperature;
    uint32_t pressure;
};

union Payload p;
```

## Short answer

<span class="warn">Сам `union` не зберігає tag-а, який повідомляє, яке поле є поточним.</span>

`union` дає змогу зберігати різні варіанти в спільній області пам’яті, але не зберігає discriminator. Якщо receiver не знає тип payload із header або enum, читання іншого поля не є надійним способом визначити тип чи значення payload.[^iso-c-n1570]

Захист: зберігай discriminator окремо, наприклад у `struct Message { enum Type type; union Payload payload; };`, і перевіряй його перед доступом до відповідного поля.[^iso-c-n1570]

## Detailed explanation

`union` зберігає свої члени в спільній області пам’яті, тому в один момент у ньому зберігають значення лише одного члена. Сам об’єкт не містить автоматичного поля, яке описує, який саме варіант записано; цю інформацію має вести програма або передавати протокол.[^iso-c-n1570]

Це корисно, коли кілька альтернативних представлень не потрібні одночасно: розмір `union` достатній для найбільшого члена. Однак економія пам’яті не робить доступ до довільного члена перевіркою типу. Якщо записати `temperature`, а потім прочитати `pressure`, програма не отримує таким способом достовірне значення тиску. Правила інтерпретації представлення залежать від мови й реалізації, а `uint16_t` та `uint32_t` ще й мають різну ширину.[^iso-c-n1570]

Зазвичай discriminator зберігають поруч із payload: enum указує, який член треба читати, а `union` зберігає саме значення. У мережевому повідомленні роль discriminator може виконувати тип із заголовка, але перед використанням треба перевірити, що заголовок коректний і що payload має достатню довжину. Якщо дані пошкоджені або тег і payload не узгоджені, доступ за неправильним членом може дати хибні дані.

Приклад безпечнішої моделі – `struct Message { enum Type type; union Payload payload; };`: спершу перевіряють `type`, потім читають тільки відповідний член. Важливо оновлювати тег і payload як одну логічну операцію, щоб код не спостерігав проміжний стан із новим тегом та старими байтами.

**Типові помилки:**

- вважати, що `union` сам знає активний член;
- пробувати вгадати тип, прочитавши альтернативний член;
- довіряти тегу з зовнішнього повідомлення без перевірки його діапазону й довжини payload.

У цій пастці проблема проявляється як правдоподібне, але неправильне число: байти залишаються тими самими, а програма тлумачить їх за іншим типом. Уникай цього, зберігаючи й перевіряючи явний discriminator перед кожним доступом до варіанта.[^iso-c-n1570]
