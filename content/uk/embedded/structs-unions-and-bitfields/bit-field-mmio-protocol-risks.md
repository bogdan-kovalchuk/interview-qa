## Short answer

**Bit-field** – поле struct із заданою кількістю бітів, наприклад `unsigned mode:3`. Його порядок бітів, allocation unit, padding і навіть signedness деяких форм залежать від implementation. <span class="warn">Для MMIO і wire protocols це небезпечно</span>: краще використовувати masks/shifts над `uint32_t`.[^dou-embedded-interview]

## Detailed explanation

### Природа бітових полів та невизначеність стандарту

Бітові поля мови C дозволяють синтаксично декларувати змінні, розмір яких менший за один машинний байт:

```c
struct UartControl {
    unsigned int rx_enable : 1;
    unsigned int tx_enable : 1;
    unsigned int baud_sel  : 4;
    unsigned int parity    : 2;
};
```

Хоча такий синтаксис виглядає наочним, стандарт C (ISO/IEC 9899 §6.7.2.1)[^iso-c-n1570] залишає фізичний спосіб розміщення бітів у пам’яті на розсуд розробника компілятора (`implementation-defined`):
- Не стандартизовано порядок виділення бітів (від молодшого LSB до старшого MSB чи навпаки).
- Не стандартизовано межі одиниці розміщення (`allocation unit`) та правила вставки вирівнювальних проміжків (padding).
- Не стандартизовано знаковість поля, якщо тип вказано як звичайний `int`.

### Чому бітові поля небезпечні для MMIO-регістрів

У вбудованих системах керування периферією мікроконтролера здійснюється через апаратні регістри, відображені в адресний простір пам’яті (Memory-Mapped I/O, MMIO)[^armv7m-arm]. Спроба описати карту регістрів через структури з бітовими полями призводить до тяжких апаратних помилок:

1. **Прихований цикл Read-Modify-Write (RMW)**:
   Апаратні системні шини процесорів ARM Cortex-M (AHB/APB) здійснюють транзакції розміром 8, 16 або 32 біти[^armv7m-arm]. Процесор не може виконати запис у довільні 3 біти пам’яті окремо. Запис у поле `baud_sel = 3;` завжди розгортається компілятором у три послідовні асемблерні кроки:
   ```assembly
   LDR  r1, [r0]          ; Читання всього 32-бітного апаратного регістра
   BFC  r1, #2, #4        ; Очищення бітів поля
   ORR  r1, r1, #0x0C     ; Встановлення нового значення
   STR  r1, [r0]          ; Запис усього 32-бітного слова назад у регістр
   ```
2. **Знищення статусних прапорців Write-1-to-Clear (W1C)**:
   Багато регістрів статусу мікроконтролерів (наприклад, регістри статусів переривань у STM32 або NXP) використовують механізм W1C: запис одиниці в біт прапорця скидає його в нуль, а запис нуля не змінює стан. Якщо у слові регістра поруч із полем конфігурації апаратно виставився статусний прапорець переривання, інструкція `LDR` прочитає значення `1`, а наступна інструкція `STR` запише `1` назад. Це призведе до випадкового очищення апаратного прапорця переривання ще до того, як процесор встигне його зареєструвати.
3. **Скидання прапорців Read-to-Clear**:
   Якщо регістр скидається простим фактом звернення на читання (наприклад, читання регістра даних FIFO або регістра помилок), читання `LDR` у циклі RMW скине апаратний статус або забере байт із черги без участі користувацької логіки.
4. **Стан гонитви (Race Condition) з перериваннями**:
   Якщо головний потік оновлює одне бітове поле регістра, а обробник переривання (ISR) оновлює інше бітове поле того самого 32-бітного регістра, несинхронізований RMW-цикл одного з потоків затре зміни, зроблені іншим.

### Чому бітові поля небезпечні для протоколів зв’язку

У бінарних протоколах передачі даних (CAN, Modbus, Ethernet, BLE, Zigbee) бітова структура кадру жорстко зафіксована стандартом. Використання бітових полів для представлення заголовків пакетів веде до проблем:
- Компілятори для різних платформ (наприклад, x86 на робочій станції та ARM на контролері) або навіть різні тулчейни (GCC, Clang, IAR, Keil) можуть по-різному упакувати бітові поля в байт (LSB-first проти MSB-first).
- Зміна опцій оптимізації або оновлення версії компілятора може непомітно змінити порядок полів або розмір padding, що робить прошивку несумісною з іншими вузлами мережі.

### Інженерний стандарт: бітові маски та CMSIS

Для надійної взаємодії з апаратурою в промисловому embedded використовують стандартизований підхід на основі явних масок і зсувів над беззнаковими цілими типами фіксованої ширини (підхід ARM CMSIS):

```c
#define UART_CR_TX_EN_Pos     (0U)
#define UART_CR_TX_EN_Msk     (0x1UL << UART_CR_TX_EN_Pos)
#define UART_CR_BAUD_Pos      (2U)
#define UART_CR_BAUD_Msk      (0xFUL << UART_CR_BAUD_Pos)

// Контрольована зміна з чітким розумінням шинної транзакції:
uint32_t reg = UART->CR;
reg &= ~UART_CR_BAUD_Msk;
reg |= (new_baud << UART_CR_BAUD_Pos) & UART_CR_BAUD_Msk;
UART->CR = reg;
```

Для керування виводами GPIO використовують виділені апаратні регістри атомарного встановлення та скидання (такі як BSRR у STM32), де запис здійснюється однією атомарною операцією `STR` без попереднього читання.
