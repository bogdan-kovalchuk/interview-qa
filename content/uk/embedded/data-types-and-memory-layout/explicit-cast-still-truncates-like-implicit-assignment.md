## Short answer

`result = 44`.

`200 + 100` обчислюється як `int` (integer promotion): `300`; явний cast `(uint8_t)` усікає до 8 біт: `300 & 0xFF = 0x2C = 44`.

Відмінність від implicit: явний cast показує усвідомлення truncation, але результат однаковий - 44.

Для portable коду: перевіряй що значення вміщується у цільовий тип перед звуженням.[^iso-c-n1570]

## Detailed explanation

Спочатку обчислюється вираз `200 + 100`. Обидві десяткові константи мають тип `int`, якщо їхні значення вміщуються в цей тип; на типовій платформі результат дорівнює `300`. Це не integer promotion: операнди вже мають тип `int`.[^iso-c-n1570]

`uint8_t`, якщо цей необов’язковий тип існує, є беззнаковим цілим типом рівно на 8 біт. Перетворення до беззнакового типу зводить значення за модулем `UINT8_MAX + 1`, тому `300` стає `44`. Те саме відбувається при неявному присвоєнні до `uint8_t`; cast робить намір явним, але не змінює результат.[^iso-c-n1570]

```c
uint8_t a = (uint8_t)(200 + 100); /* 44 */
uint8_t b = 200 + 100;           /* також 44 */
```

Не переносіть це правило на signed narrowing: коли значення не представляється цільовим знаковим типом, результат не є тим самим гарантованим модульним перетворенням. У протоколах і обчисленнях розмірів перевіряйте діапазон перед перетворенням, якщо обертання значення не задумане. Приклад припускає, що реалізація надає `uint8_t`.[^iso-c-n1570]

Перевірку можна виконати до cast: порівняти вхідне значення з `UINT8_MAX` і відхилити його, якщо воно завелике. Це важливо для довжини пакета, індексу чи зовнішнього вводу: після narrowing початкове `300` і коректне `44` нерозрізненні. Якщо modulo 256 є задумом, зафіксуйте це як частину формату, а не покладайтеся на неочевидний ефект cast.[^iso-c-n1570]
