## Short answer

**Heap fragmentation** – ситуація, коли вільної пам’яті сумарно вистачає, але вона розбита на малі несуміжні блоки. У firmware це проявляється як випадкові `malloc` failures після годин або днів роботи, особливо при різних розмірах allocation. Типова профілактика: fixed-size pools, allocate-on-startup, bounded lifetimes і відсутність heap у ISR.[^dou-embedded-interview]

## Detailed explanation

### Механізм виникнення фрагментації купи

Фрагментація динамічної пам’яті (heap fragmentation) – це стан купи, за якого сумарний обсяг вільної пам’яті є достатнім для задоволення запиту, проте жоден окремий неперервний блок не має потрібного розміру. У результаті виклик `malloc` повертає `NULL`, хоча діагностика може показувати кілобайти вільної RAM.[^freertos-heap]

Розрізняють два види фрагментації:
- **Зовнішня фрагментація (external fragmentation)**: виникає, коли вільна пам’ять розбита зайнятими ділянками на дрібні ізольовані фрагменти. Наприклад, якщо виділити три послідовні блоки по 128 байтів (A, B, C), а потім звільнити середній блок B, утвориться «дірка» на 128 байтів. Якщо згодом системі знадобиться буфер на 200 байтів, ця дірка не зможе його вмістити, і аллокатор буде змушений шукати місце далі по адресній карті.
- **Внутрішня фрагментація (internal fragmentation)**: виникає через вимоги вирівнювання (alignment) та накладні витрати на метадані чанка (chunk headers). Якщо задача запитує 13 байтів, а аллокатор округлює розмір до кратного 8 або 16 байтам для збереження вирівнювання шини процесора, невикористаний залишок втрачається для решти системи.

### Прояви у довготривало працюючому firmware (long-running firmware)

У вбудованих системах, які працюють безперервно місяцями або роками (наприклад, IoT-вузли, датчики, контролери двигунів чи мережеві шлюзи), динамічне виділення блоків різного розміру та з різним часом життя є катастрофічним фактором:
1. **Випадкові відмови `malloc` через тривалий uptime**: мікроконтролер може успішно проходити лабораторні тести протягом кількох хвилин або годин, але після сотень тисяч транзакцій передачі пакетів зв’язку купа перетворюється на «решето». Чергова спроба виділити пам’ять для буфера прийому завершується відмовою.[^dou-embedded-interview]
2. **Неможливість компактифікації (defragmentation / compaction)**: на звичайних MCU (ARM Cortex-M, RISC-V) відсутній блок керування пам’яттю (MMU) з підтримкою віртуальної трансляції адрес. Мова C оперує прямими фізичними вказівниками. Аллокатор не має права самостійно перемістити зайнятий блок пам’яті в інше місце для об’єднання вільних ділянок, оскільки це миттєво зробить усі збережені у програмі вказівники недійсними.[^freertos-heap]
3. **Хибне відчуття безпеки від загального лічильника RAM**: розробники часто контролюють лише загальний обсяг вільної пам’яті (наприклад, через функцію `xPortGetFreeHeapSize()` у FreeRTOS). Проте цей лічильник показує лише арифметичну суму всіх вільних блоків. Справжнім індикатором фрагментації є розмір найбільшого доступного неперервного вільного блока, який неухильно деградує.[^freertos-heap]

### Архітектурні альтернативи та методи профілактики

Для забезпечення детермінованості та надійності в embedded застосовують спеціальні підходи до керування пам’яттю:
- **Повна відмова від heap у runtime (allocate-on-startup)**: вся динамічна пам’ять виділяється виключно на етапі ініціалізації системи до запуску планувальника задач або головного циклу обробки. Після входу в робочий режим виклики `malloc` та `free` суворо забороняються, що відповідає настановам безпеки.[^misra-c-2023-addendum-2]
- **Пули пам’яті фіксованого розміру (Fixed-size block memory pools)**: створення кількох ареок або черг із заздалегідь визначеними розмірами блоків (наприклад, окремий пул для пакетів по 64 байти, окремий для 256 байтів). Виділення та повернення блоку з пулу виконується за сталий час O(1) без ризику зовнішньої фрагментації.
- **Аллокатори з коалесценцією (Coalescing allocators)**: якщо динамічне виділення неминуче, обирають реалізації (як-от `heap_4` або `heap_5` у FreeRTOS), що автоматично зливають суміжні вільні блоки при кожному виклику `free()`, зменшуючи зовнішню фрагментацію.[^freertos-heap]
- **Сувора заборона в ISR**: виклик функцій динамічного виділення пам’яті з обробників переривань категорично заборонений через недетермінований час виконання та ризик взаємного блокування або пошкодження структур даних аллокатора.[^misra-c-2023-addendum-2]
