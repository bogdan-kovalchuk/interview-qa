## Short answer

Локальна змінна зі `static` має static storage duration: без явного ініціалізатора її значення початково дорівнює нулю, а точне розміщення визначає реалізація.

Змінна зберігає значення між викликами функції. Якщо кілька контекстів змінюють її без синхронізації, спільний стан може порушити reentrancy та спричинити гонку.[^iso-c-n1570]

## Detailed explanation

`static` у блоці змінює storage duration змінної, а не її scope: ім'я залишається доступним лише в межах відповідного блоку, але сам об'єкт існує протягом усього виконання програми. Отже, новий виклик функції бачить попереднє значення, а не новий автоматичний об'єкт на stack.[^iso-c-n1570]

Якщо змінну не ініціалізовано явно, стандарт C задає нульове початкове значення для об'єктів зі static storage duration. `.bss` – типове рішення toolchain для таких об'єктів, але стандарт не вимагає саме цієї секції: linker script та формат виконуваного файла визначають фізичне розміщення.[^iso-c-n1570]

Постійне збереження значення має наслідок: усі виклики функції працюють з тим самим об'єктом. Це може порушити reentrancy, якщо функцію повторно викликати до завершення попереднього виклику або якщо кілька потоків змінюють стан без синхронізації. Для ISR і main loop конкретні правила доступу залежать від платформи та компілятора; не слід автоматично називати будь-яке таке спільне використання C data race.[^iso-c-n1570]

Уявімо функцію, яка використовує локальний `static` лічильник для тимчасового підрахунку під час обробки повідомлення. Другий виклик продовжить змінювати той самий лічильник, а не отримає незалежний екземпляр; якщо перший виклик ще не завершився, результати можуть змішатися. Навіть без потоків така ситуація можлива через вкладений виклик або callback.[^iso-c-n1570]

Початкове нульове значення задається мовою, але спосіб підготовки пам'яті до `main` є частиною стартового коду платформи. Поширена embedded реалізація очищає `.bss` і копіює ініціалізовані дані в RAM, однак це не гарантується C і може відрізнятися для пам'яті з особливим призначенням або власного startup code.[^iso-c-n1570]

Не плутайте збереження між викликами з гарантією атомарного доступу: `static` визначає тривалість життя, але не синхронізує читання й запис. Якщо стан спільний між потоками, потрібні атоміки або блокування, сумісні з середовищем; якщо доступ іде з ISR, механізм має бути придатним для переривань і конкретного MCU.[^iso-c-n1570]

**Як уникнути проблеми:** залишайте локальний стан автоматичним, якщо його не потрібно зберігати між викликами. Коли спільний стан потрібен, визначте всі контексти доступу та застосуйте відповідний для MCU механізм синхронізації або критичну секцію.
