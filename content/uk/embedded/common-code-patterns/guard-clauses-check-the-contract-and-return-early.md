## Question code

```c
err_t motor_set_speed(motor_t *m, int32_t rpm) {
  if (m == NULL)        return ERR_PARAM;
  if (rpm < MIN || rpm > MAX) return ERR_PARAM;
  if (m->state != RUNNING) return ERR_BUSY;
  // далі - лише валідні параметри
}
```

## Short answer

**Early-return перевірки на вході функції** проти null-розіменування і невалідних параметрів.

Після guard'ів основна логіка працює лише з гарантовано коректними даними – менше вкладеності, чистіший happy path.

Guard clauses не замінюють повний контракт: перевіряй лише передумови, визначені для цієї API, і роби це до небезпечного доступу, наприклад розіменування вказівника.[^iso-c-n1570]

## Detailed explanation

Guard clause – це рання перевірка перед основною логікою функції, яка одразу повертає помилку або інший визначений результат, якщо передумова порушена. У прикладі спочатку перевіряються вказівник, діапазон обертів і допустимий стан двигуна; тому доступ до `m->state` відбувається лише після перевірки `m != NULL`.[^iso-c-n1570]

Такий порядок робить звичайний успішний шлях менш вкладеним: після перевірок нижче можна читати код як послідовність дій для валідного запиту. Важливо визначити контракт функції: чи є нульовий вказівник помилкою, які межі включені, які стани дозволяють операцію та який error code відповідає кожній відмові. Перевірка не робить дані незмінними: якщо інший контекст паралельно змінює стан пристрою, потрібна окрема синхронізація.

Guard clauses доречні для передумов і помилок, але надмірні ранні виходи можуть приховати потрібне очищення ресурсів або сплутати керування. У C++ RAII допомагає автоматично звільняти ресурси; у C треба централізовано проходити cleanup path, якщо ресурси вже захоплені. Для конкретного прикладу перевірку `m` ставлять перед будь-яким розіменуванням, а перевірку стану – до зміни апаратури.

Приклад із безпечним порядком перевірок:

```c
if (device == NULL) return ERR_PARAM;
if (length > MAX_LENGTH) return ERR_RANGE;
/* normal path: device is non-null and length is bounded */
```

**Типові помилки:**

- Розіменувати вказівник у самій умові до null-перевірки.
- Перевірити межу після арифметики, яка може переповнитися.
- Повернути помилку, залишивши вже захоплений ресурс або змінений стан.
