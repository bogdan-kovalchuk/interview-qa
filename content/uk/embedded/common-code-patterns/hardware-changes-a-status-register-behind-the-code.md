## Short answer

**Статусний регістр змінюється апаратурою асинхронно, а не кодом.**

`volatile` каже компілятору, що звернення до об’єкта мають спостережуваний ефект, тож він має зберегти ці volatile-доступи відповідно до абстрактної машини C. Це не гарантує фізичне читання RAM, атомарність або порядок апаратних транзакцій, потрібний конкретному MCU.[^iso-c-n1570] Без цього кваліфікатора повторне читання звичайного об’єкта може бути оптимізоване, хоча пристрій змінює відповідне місце.

Для звичайних memory-mapped регістрів volatile-доступ є типовою частиною контракту з компілятором, але спосіб доступу та додаткові бар’єри визначаються платформою.[^linux-volatile-mmio]

## Detailed explanation

`volatile` – кваліфікатор типу C для об’єктів, чиї звернення мають бути враховані як спостережувані дії. Це підходить для типового memory-mapped статусного регістра, значення якого змінює периферія незалежно від потоку команд процесора. Якщо код багаторазово перевіряє звичайну змінну, оптимізатор може винести читання з циклу або використати попереднє значення, бо за правилами звичайного C він не знає про зовнішнього виробника даних. Для volatile-об’єкта кожен вираз доступу має залишатися значущим для реалізації.[^iso-c-n1570]

`volatile` не означає «завжди читати фізичну RAM» – адреса може бути пристроєм, а не RAM. Також воно не гарантує, що багатобайтове звернення атомарне, що інші ядра побачать його в потрібному порядку, або що CPU виконає бар’єр перед наступною операцією. Для цих властивостей потрібні механізми, описані архітектурою, компілятором і документацією MCU. У Linux kernel, наприклад, доступ до I/O memory зазвичай іде через платформні accessors, а не довільні покажчики volatile.[^linux-volatile-mmio]

У прикладі циклічне читання `USART1->SR` може побачити зміну прапорця, зроблену периферією. Але правильна послідовність читання `SR` та `DR`, побічні ефекти читання, маски бітів і час готовності задаються reference manual конкретного UART. Кваліфікатор не замінює ці правила й не робить некоректний протокол правильним.

Приклад: очікування прапорця у циклі має сенс лише якщо апаратний блок зрештою може його встановити, а час очікування обмежений або система має визначений recovery path. Нескінченний busy-wait без timeout може зависнути через несправний пристрій незалежно від правильності `volatile`.

**Типові помилки:**

- Вважати `volatile` засобом синхронізації між потоками або ISR і основним кодом.
- Очікувати, що воно забезпечить memory ordering чи atomic read-modify-write.
- Додавати його до звичайної shared data замість належного lock або atomic-механізму.

Застосовуйте `volatile` до периферійних об’єктів відповідно до toolchain та MCU, а для решти гарантій використовуйте спеціально визначений платформою механізм.
