## Short answer

<span class="warn">`1 << 31` – undefined behavior</span>: літерал `1` має тип signed `int`, а результат не представний у `int` на платформі з 32-бітним `int`.[^iso-c-n1570]

`1U << 31` коректний, лише якщо після integer promotions тип лівого операнда має щонайменше 32 біти; інакше кількість зсуву завелика.[^iso-c-n1570]

Для 32-бітних масок використовуй `UINT32_C(1) << n` і перевіряй, що `n < 32`; для інших ширин добирай беззнаковий тип і перевіряй його ширину.[^iso-c-n1570]

## Detailed explanation

Зсув `1 << 31` у типовій системі з 32-бітним `int` не є способом отримати маску старшого біта: результат не можна подати типом `int`, тому в C це undefined behavior. Літерал `1` має тип `int`, а тип результату зсуву визначається після integer promotions лівого операнда, а не типом, у який результат буде присвоєно.[^iso-c-n1570]

Для лівого зсуву стандарт дозволяє результат для беззнакового операнда за модульною арифметикою, але кількість зсуву має бути меншою за ширину promoted-типу. Тому суфікс `U` сам по собі не гарантує, що `1U << 31` працює на всіх C-платформах: `unsigned int` може бути вужчим. `UINT32_C(1)` задає константу принаймні потрібної точності, якщо реалізація має `uint32_t`; однак межу `n < 32` усе одно треба забезпечити окремо.[^iso-c-n1570]

Поширена помилка – вважати, що присвоєння у `uint32_t` виправляє вираз: перетворення відбувається після обчислення зсуву й не скасовує undefined behavior. Так само не можна передавати від’ємне або завелике `n` з надією, що процесор «обріже» його до допустимої кількості. У C діагностика для такого значення не обов’язково з’явиться, а оптимізатор може виходити з того, що undefined behavior не трапляється.[^iso-c-n1570]

Приклад для реалізації, де існує `uint32_t`:

```c
uint32_t bit = UINT32_C(1) << n; /* n must be less than 32 */
```

**Типова помилка:** визначати `n` через позицію біта, але не перевіряти його межу. Для поля або регістра звір ширину типу з документацією платформи й обмеж допустимий індекс до виконання зсуву.
