## Question code

```c
reg = (reg & ~PRESC_MASK)
    | ((value << PRESC_SHIFT) & PRESC_MASK);
```

## Short answer

**Спершу очисти біти поля (`& ~MASK`), потім вклади нове значення (зсунуте і замасковане).**

Маскування після зсуву обмежує результат бітами поля лише за умови, що сам зсув коректний; перевір діапазон `value` до зсуву.[^iso-c-n1570]

Правило: перед встановленням нового значення очисти старі біти поля, щоб зберегти сусідні налаштування.[^iso-c-n1570]

## Detailed explanation

Оновлення поля в звичайній змінній виконує три кроки: очищає старе поле, готує нове значення на потрібній позиції та об’єднує його з рештою регістра. Вираз `reg & ~PRESC_MASK` залишає незмінними всі біти поза полем і робить біти поля нульовими. Друга частина зсуває значення до позицій `[6:4]`, а AND із маскою відкидає біти, що виходять за межі поля. Побітове OR з’єднує ці частини.[^iso-c-n1570]

Маскування після зсуву не може виправити некоректний зсув: якщо `value` від’ємне або зсув виходить за межі promoted-типу, це undefined behavior. Перевір, що значення належить діапазону 0..7, і виконуй обчислення у беззнаковому типі достатньої ширини. Якщо API навмисно приймає більші значення, спершу явно обмеж їх до ширини поля.[^iso-c-n1570]

**Приклад:** для трьох бітів `[6:4]` нове значення `5` має бути записане як `5 << 4`. Спершу старі три біти очищаються, потім `0x50` додається до інших бітів. Значення `9` не вміщується в трибітове поле; просте маскування перетворило б його на `1`, приховавши помилку виклику. Краще відхилити таке значення або задокументувати обрізання як частину API.

**Типові помилки:**

- Виконати лише OR зі зсунутим значенням: біти, які раніше були одиницями, не очистяться.
- Застосувати `~MASK` без беззнакового типу правильної ширини й отримати неочікувані integer conversions.
- Вважати цей read-modify-write безпечним для будь-якого периферійного регістра. Апаратні регістри можуть мати write-one-to-clear біти або змінюватися перериванням; застосовуй спеціальний механізм із документації MCU.[^iso-c-n1570]
