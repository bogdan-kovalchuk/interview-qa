## Short answer

**MISRA C Rule 17.7 вимагає використовувати значення non-void функції або явно відкинути його cast до `void`.** Це не означає, що кожна функція, здатна зазнати помилки, мусить повертати error code.[^misra-c-2023-rule-17-7]

Правило стосується використання поверненого значення, а не одного патерну обробки помилок: статус можна повернути окремо, у структурі результату або за контрактом визначити, що помилка неможлива. Проєкт має встановити й перевіряти належну реакцію на значущі результати.

Явне `(void)call()` позначає свідоме відкидання, але не замінює аналіз ризику такого рішення.[^misra-c-2023-rule-17-7]

## Detailed explanation

MISRA C – набір настанов для написання C у системах, де важливі передбачуваність і контрольовані дефекти. Правило 17.7 говорить про те, як використати значення функції, що повертає не `void`: його не слід мовчки відкидати. Воно саме по собі не встановлює, що всі операції мають повертати статус або що єдино правильний інтерфейс помилки – return code. Офіційне доповнення MISRA позначає R.17.7 як required; повний нормативний текст міститься в ліцензованому документі стандарту.[^misra-c-2023-rule-17-7]

Причина такого підходу практична: ігнорований результат може містити інформацію про невдалий ввід-вивід, тайм-аут або помилку параметра, а подальший код тоді продовжить роботу зі станом, який не було оновлено. Використати результат означає передати його в умову, зберегти для подальшої обробки або явно відкинути. Вираз `(void)function()` робить останній намір видимим для читача й аналізатора; це не доводить, що результат безпечно ігнорувати.

Наприклад, якщо `write_sensor_config()` повертає статус, викликач може перевірити його й перейти до контрольованого відновлення при помилці. Але для функції, результат якої гарантовано не потрібен у певному контексті, свідоме відкидання може бути обґрунтоване. Команда проєкту має визначити, як документуються винятки та як система переходить у безпечний стан.

Приклад: відкидання `log_event()` може бути прийнятним лише якщо втрата журналу не змінює функціональну безпеку; інакше помилку запису треба обробити. Ризик залежить від контракту функції та наслідків збою, а не тільки від типу повернення.

**Типові помилки:**

- Перефразувати R.17.7 як вимогу, щоб кожна функція повертала error code.
- Думати, що cast до `void` автоматично обробив помилку; він лише явно відкинув значення.
- Плутати настанову мови C із вимогами процесу управління ризиком конкретної системи.

Отже, питання інтерв’ю перевіряє розуміння використання поверненого значення й обґрунтованого рішення, а не універсальну перевагу return codes.
