## Question code

```c
typedef struct {
  volatile uint32_t CR;  // control
  volatile uint32_t SR;  // status
  volatile uint32_t DR;  // data
} USART_t;
#define USART1 ((USART_t *)0x40011000U)
```

## Short answer

**Структура з `volatile` полями, накладена на базову адресу периферії.**

Поля йдуть у порядку, сумісному з регістрами, а потрібні зсуви треба звірити з datasheet: C дозволяє padding між членами структури. Доступ має вигляд `USART1->DR = b;`.[^iso-c-n1570]

Правило: фіксуй layout `offsetof`-асертами, щоб збіг із datasheet не зламався.[^embeddedinterviewlab]

## Detailed explanation

Цей патерн моделює відображену в пам’ять периферію як структуру C, а покажчик на структуру пов’язує її з базовою адресою, визначеною документацією MCU. Доступ до `USART1->DR` читається як звернення до поля `DR` за адресою, отриманою з адреси екземпляра й зсуву цього поля.

Порядок членів структури зберігається, але стандарт C дозволяє padding між ними та після останнього поля. Тому однакова послідовність оголошень сама по собі не доводить, що `SR` опиниться на потрібному апаратному зсуві. Типи регістрів, їх ширина й вирівнювання мають відповідати документації конкретного MCU; `offsetof` static assertions можуть виявити неочікуваний layout під час компіляції. Такі перевірки не підтверджують адресу бази або семантику регістра – це перевіряють окремо за datasheet і заголовками виробника.[^iso-c-n1570]

Кваліфікатор `volatile` на полях повідомляє компілятору, що доступи до них є спостережуваними для програми і не мають бути зведені до звичайної оптимізації неvolatile пам’яті. Він не створює апаратного регістра, не перевіряє адресу, не гарантує атомарність і не забезпечує потрібні CPU/cache barriers. Спеціальні правила peripheral memory, порядок транзакцій і side effects визначає архітектура та документація MCU.[^iso-c-n1570]

Приклад у питанні ілюстративний: для нього не наведені `stdint.h`, точна модель MCU чи перевірені offsets, тож адресу `0x40011000U` не можна переносити на інший чип. У реальному коді спершу використовуйте заголовок виробника або власний тип із підтвердженими адресою й layout. Деякі регістри мають write-one-to-clear чи read-to-clear семантику; до них не можна застосовувати звичні read-modify-write операції без перевірки документації.

**Типові помилки:**

- Припускати, що compiler ніколи не вставить padding у структуру.
- Вважати `volatile` заміною memory barrier, атомарності або драйверного протоколу доступу.
- Переносити базову адресу чи поведінку регістра між різними моделями MCU.

Отже, структура робить карту регістрів читабельною, але її коректність спирається на перевірений платформний контракт, а не лише на синтаксис C.
