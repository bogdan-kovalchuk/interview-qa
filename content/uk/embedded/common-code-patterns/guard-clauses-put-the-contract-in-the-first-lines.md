## Short answer

**Guard clauses виносять перевірку входу (null, діапазон, стан, права доступу) у перші рядки функції, тож контракт видно одразу, а основна логіка йде без вкладених `if`.**

Рецензентові легше переконатися, що небезпечні входи відсікаються до будь-яких побічних ефектів, а настанови JPL для safety-critical коду вимагають перевіряти валідність параметрів усередині кожної функції.[^holzmann-power-of-ten] Це не доводить коректність: перевірка на `NULL` не виявить хибний ненульовий вказівник, а швидший аудит – наслідок читабельності, не гарантія.[^iso-c-n1570]

## Detailed explanation

Guard clause – це перевірка передумови на початку функції з негайним виходом (зазвичай `return` коду помилки), якщо передумова не виконана. Після блоку guard-ів код основної логіки може вважати, що вхідні дані валідні, і не ховається на третьому рівні вкладених `if`. Саме тому контракт функції – що вона приймає і які помилки повертає – читається з перших рядків, і рецензент не шукає перевірки по всьому тілу.

Це узгоджується з настановами JPL для safety-critical C: правило 7 вимагає, щоб валідність параметрів перевірялася всередині кожної функції.[^holzmann-power-of-ten] Ті самі настанови прямо зазначають, що вимога простого control flow не означає єдиної точки виходу, бо ранній return у разі помилки часто простіший.[^holzmann-power-of-ten] Якщо ж стандарт кодування вашого проєкту вимагає єдиної точки виходу, guard-и оформлюють через змінну статусу, а не відмовляються від самих перевірок.

Межі підходу. Перевірка на `NULL` ловить лише нульовий вказівник: розіменування вказівника з недійсним значенням – undefined behavior, але ненульовий «висячий» вказівник guard не відрізнить від справжнього.[^iso-c-n1570] Перевірка стану – це «check-then-act»: якщо стан може змінити ISR чи інша задача, значення після перевірки може застаріти, тож потрібні критична секція або атомарність. Також guard не слід підміняти `assert`: настанови JPL описують assertions як перевірки аномалій, які можна вимкнути після тестування, тоді як guard має працювати й у релізній збірці.[^holzmann-power-of-ten] Приклад ілюстративний:

```c
status_t motor_set_speed(motor_t *m, int32_t rpm)
{
    if (m == NULL)                       { return ERR_NULL;  }
    if (!m->initialized)                 { return ERR_STATE; }
    if (rpm < RPM_MIN || rpm > RPM_MAX)  { return ERR_RANGE; }

    m->target_rpm = rpm;                 /* тут передумови вже виконані */
    return OK;
}
```

**Типові помилки:**

- Виконувати побічні ефекти (запис, виклик драйвера, розіменування) до того, як усі guard-и пройдені.
- Покладатися на `assert`, який вимикається в релізі, замість справжньої перевірки та коду помилки.
- Перевіряти стан без захисту від зміни з ISR чи іншої задачі й вважати перевірку «вічною».
- Писати guard-и в різному порядку й стилі в різних функціях – тоді втрачається головна перевага одноманітності для рецензента.
