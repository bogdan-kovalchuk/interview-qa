## Question code

```c
uint32_t start = tick();
while (!(REG->SR & FLAG)) {
  if (tick() - start > TIMEOUT_MS) return ERR_TIMEOUT;
}
```

## Short answer

**Запам’ятай стартовий тік і на кожній ітерації порівнюй різницю `tick() - start` з лімітом.**

Беззнакове віднімання дає правильну різницю й після переповнення лічильника, якщо `tick()` повертає той самий unsigned тип, що й `start`, а очікування коротше за період лічильника.[^iso-c-n1570] Так цикл не зависне назавжди, якщо апаратура не виставить прапорець: після timeout повертай помилку, а не чекай безкінечно.[^holzmann-power-of-ten]

## Detailed explanation

Ідея проста: у момент початку очікування зберігаємо поточний тік `start`, а на кожній ітерації обчислюємо, скільки тіків минуло, і порівнюємо це з лімітом. Для `uint32_t` віднімання виконується за модулем `2^32`: результат беззнакової арифметики, який не вміщається в тип, зводиться за модулем, тому переповнення тут не є undefined behavior.[^iso-c-n1570] Звідси різниця `now - start` лишається правильною, навіть якщо лічильник «перескочив» через нуль між двома зчитуваннями.

Числовий приклад. Нехай `start = 4294967280` (`0xFFFFFFF0`), а після переповнення `tick()` повертає `16`. Тоді `16 - 4294967280` за модулем `4294967296` дає `16 + 4294967296 - 4294967280 = 32` – саме стільки тіків минуло. Наївна перевірка `tick() > start + TIMEOUT_MS` для `TIMEOUT_MS = 100` ламається: `start + 100` переповнюється до `84`, і вже на першій ітерації `tick() = 4294967280 > 84` дає хибний timeout. Порівнювати треба саме різницю, а не абсолютні значення.

Умови, за яких це працює. По-перше, типи: якщо `tick()` вужчий за `start` (наприклад, 16-бітний лічильник), різниця обчислюється за модулем `2^32`, а не за періодом самого лічильника, тож після його переповнення вона стає хибною (`5 - 65530` дає не `11`, а число близько `4,29 * 10^9`); вужчі типи ще й проходять integer promotions до `int`. Якщо ж `tick()` ширший (`uint64_t`), у `start` зберігаються лише молодші 32 біти, і різниця хибна, щойно лічильник перейде `2^32`.[^iso-c-n1570] По-друге, очікування має бути коротшим за період лічильника: для 1 мс-тіка по `2^32` мс це приблизно 49,7 доби. По-третє, `tick()` має змінюватися незалежно від самого циклу, тобто його оновлює таймер або ISR; якщо polling виконується з вимкненими перериваннями чи в ISR, пріоритет якої не нижчий за ISR тіка, `tick()` стоїть, і timeout ніколи не спрацює. І регістр `REG->SR` має бути `volatile`, бо доступ до такого об’єкта компілятор виконує строго за правилами абстрактної машини і не виносить читання з циклу.[^iso-c-n1570]

Ще одна межа: цей timeout обмежує час, а не кількість ітерацій. Правило 2 з настанов JPL вимагає, щоб межу циклу міг довести статично інструмент перевірки, тож там, де це потрібно, до часового ліміту додають лічильник ітерацій.[^holzmann-power-of-ten] Наступний фрагмент ілюстративний; після спрацювання timeout прапорець перевіряють ще раз, щоб витіснення задачі на довший за ліміт час не дало хибної помилки:

```c
uint32_t start = tick();                 /* tick() повертає uint32_t */
while (!(REG->SR & FLAG)) {              /* REG->SR оголошено volatile */
    if ((uint32_t)(tick() - start) > TIMEOUT_MS) {
        return (REG->SR & FLAG) ? OK : ERR_TIMEOUT;
    }
}
return OK;
```

**Типові помилки:**

- Порівнювати абсолютні значення (`tick() > start + TIMEOUT_MS`): біля переповнення виходить хибний або пропущений timeout.
- Мати лічильник іншої ширини, ніж змінна `start`.
- Чекати прапорець у ISR або з вимкненими перериваннями, коли тік не оновлюється.
- Лишати цикл очікування без жодної межі та без коду помилки.
