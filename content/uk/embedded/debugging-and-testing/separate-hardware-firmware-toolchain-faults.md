## Short answer

Спершу перевірити power, clocks, reset, boot pins і signal levels осцилографом або logic analyzer. Потім мінімізувати firmware до known-good test: blink, UART, single peripheral, без RTOS/DMA. Якщо симптом залежить від optimization, linker script, startup або wrong flags, це схоже на toolchain/config; якщо повторюється при мінімальному коді й видно на сигналах – hardware/power issue.[^dou-embedded-interview]

## Detailed explanation

### Принцип: змінювати одну змінну за раз

Симптом на платі ("пристрій інколи перезавантажується", "SPI повертає сміття") майже ніколи не вказує напряму на причину. Робочий метод – звужувати простір підозрюваних, змінюючи по одній змінній: іншу плату з тим самим бінарником, інший бінарник на тій самій платі, інший рівень оптимізації з тим самим кодом. Важливо також пам’ятати, що категорії перетинаються: поведінка, яка змінюється від прапорців компілятора, найчастіше означає помилку в коді, а не в компіляторі.

### Крок 1: hardware baseline

Спершу перевіряють те, без чого жоден код не працює коректно:

- **Живлення** – під навантаженням, а не в спокої: просідання рейки в момент передачі радіо чи старту двигуна, пульсації, спрацювання brown-out.
- **Тактування** – чи запустився кварц, чи та частота PLL; багато MCU можуть вивести системний такт на вивід, і це видно осцилографом.
- **Reset і boot pins** – чи немає коротких імпульсів на лінії reset, чи правильний стан boot-виводів у момент старту.
- **Рівні сигналів** – чи збігаються логічні рівні пристроїв, чи є pull-up на I2C, чи немає ringing на тактових лініях.

Ознаки апаратної причини: проблема є лише на окремих екземплярах плат, залежить від температури, навантаження або дотику щупом чи пальцем, корелює з подіями в силовій частині.

### Крок 2: known-good firmware і перехресна перевірка

Далі код спрощують до мінімального тесту: blink, UART echo, одна периферія в режимі опитування, без RTOS, DMA і переривань. Якщо мінімальний тест падає – це майже напевно hardware або базова конфігурація (такти, startup). Якщо працює – складність додають поетапно, і перший крок, на якому з’являється збій, підказує підсистему.

Найсильніший прийом – перехресна матриця:

| Експеримент | Збій слідує за... | Висновок |
|---|---|---|
| той самий бінарник на кількох платах | конкретною платою | hardware, монтаж, компонент |
| різні бінарники на одній платі | конкретним бінарником | firmware або збірка |
| той самий код, інший `-O` | рівнем оптимізації | UB у коді, рідше помилка компілятора |
| той самий commit, зібраний на іншій машині | середовищем збірки | toolchain, версія SDK, прапорці |

Перед будь-якими висновками варто переконатися, що на платі справді той образ, який ви налагоджуєте. GDB `compare-sections` порівнює кожну loadable section ELF-файлу з пам’яттю target-а і показує розбіжності; з `-r` – лише read-only секції, що також ловить випадки, коли програма пошкодила власний код чи константи.[^gdb-manual]

```sh
(gdb) compare-sections
(gdb) x/4xw 0x40023800    # read peripheral registers, e.g. the RCC block on STM32F4
```

Команда `x` читає пам’ять у потрібному форматі незалежно від типів програми[^gdb-manual], тож нею зручно перевірити, чи регістри периферії справді мають ті значення, які нібито записав драйвер.

### Крок 3: ознаки toolchain- і configuration-проблем

- **Залежність від оптимізації.** Без оптимізації GCC прагне, щоб налагодження давало очікуваний результат: оператори незалежні, і після зупинки між ними змінні мають значення з коду.[^gcc-optimize-options] З `-O2` поведінка змінюється, і причиною зазвичай є undefined behavior: забутий `volatile` на змінній, яку змінює ISR, неініціалізована змінна, порушення strict aliasing. `-fstrict-aliasing` увімкнено на `-O2`, `-O3` і `-Os`, і тоді компілятор припускає, що до об’єкта не звертаються через вираз несумісного типу (з винятками, наприклад, для символьних типів).[^gcc-optimize-options] Формально це firmware bug, але проявляє його саме зміна конфігурації збірки.
- **Linker script і startup.** Неправильні розміри регіонів пам’яті, `.data`, яка не копіюється з flash, незанулений `.bss`, стек поверх heap. Карта лінкування (`-Map=app.map`) показує, де опинився кожен символ, а `--print-memory-usage` друкує заповнення регіонів, оголошених у `MEMORY`, що корисно на embedded target-ах.[^ld-options]
- **Неправильна конфігурація.** Не той define моделі MCU, інша версія HAL чи SDK, інший `-mcpu` або `-mfloat-abi` в одній бібліотеці. Ознака – той самий commit дає різні бінарники на різних машинах.

```c
#include <stdint.h>
#include <string.h>

uint32_t bits_bad(float f)
{
    return *(uint32_t *)&f;        /* violates strict aliasing: UB */
}

uint32_t bits_ok(float f)
{
    uint32_t u;
    memcpy(&u, &f, sizeof u);      /* well-defined copy of the representation */
    return u;
}
```

### Крок 4: ознаки firmware bug

Помилка в коді відтворюється на будь-якій справній платі з тим самим бінарником, часто детерміновано за певної послідовності подій. Якщо вона залежить від timing (гонка між ISR і задачею, переповнення черги), то змінюється від доданих логів чи breakpoints. Тут допомагають апаратні watchpoints, регістри fault-статусу після HardFault і GPIO-маркери з logic analyzer (qid:emb-debug-0001).

На співбесіді очікують почути саме метод: baseline hardware, мінімальний відтворюваний тест, перехресна матриця "плата × бінарник × конфігурація" і перевірка, що на target-і саме той образ, а не перелік можливих причин.
