## Short answer

Vector table містить initial SP і addresses handlers; NVIC enable-ить IRQ, виставляє pending state і вибирає найвищий priority. При вході в ISR Cortex-M автоматично stacking-ить частину registers, переходить у handler mode і може робити nested interrupts. Return from ISR через спеціальне `EXC_RETURN` відновлює context; у RTOS це також точка для context switch.[^dou-embedded-interview]

## Detailed explanation

Архітектура ARM Cortex-M містить тісно інтегрований у ядро контролер переривань – **NVIC (Nested Vectored Interrupt Controller)**. Це забезпечує детерміновану низьку латентність реакції на події та апаратне керування пріоритетами й контекстом переривань без необхідності писати складні асемблерні прологи та епілоги.[^armv7m-arm]

### Таблиця векторів (Vector Table) та регістр VTOR

Таблиця векторів є масивом 32-бітних слів. За замовчуванням після скидання вона розташована за адресою `0x00000000` (або `0x08000000` у мікроконтролерах STM32 при відображенні Flash):
- Слово 0: початкове значення головного вказівника стека (Initial `MSP`).
- Слово 1: адреса обробника скидання (`Reset_Handler`).
- Слова 2–15: адреси системних винятків архітектури (`NMI`, `HardFault`, `MemManage`, `BusFault`, `UsageFault`, `SVCall`, `PendSV`, `SysTick`).
- Слово 16 і далі: адреси векторів периферійних переривань конкретного мікроконтролера (`WWDG_IRQHandler`, `TIM2_IRQHandler`, `USART1_IRQHandler` тощо).[^cmsis-core-nvic]

Оскільки архітектура Cortex-M підтримує лише набір інструкцій Thumb-2, біт 0 кожної адреси вектора в таблиці обов’язково має дорівнювати 1. Це вказує процесору на виконання коду в режимі Thumb.

Регістр `SCB->VTOR` (Vector Table Offset Register) дозволяє перемістити таблицю векторів під час роботи прошивки в іншу адресу Flash або в оперативну пам’ять SRAM. Це необхідно для реалізації завантажувачів (Bootloader), динамічної заміни обробників або для максимального прискорення реакції на переривання завдяки відсутності Flash wait states при зчитуванні вектора з SRAM.[^armv7m-arm]

### Контролер NVIC та ієрархія пріоритетів

NVIC керує станами кожної лінії переривання:
- **Enable / Disable:** регістри `NVIC_ISER` (Set-Enable) та `NVIC_ICER` (Clear-Enable) дозволяють атомарно вмикати або вимикати лінію переривання записом одиниці у відповідний біт.
- **Pending / Active:** переривання переходить у стан *Pending* (`NVIC_ISPR`), коли надходить апаратний сигнал від периферії або програмний запис. Коли ядро бере переривання на виконання, воно стає *Active* (`NVIC_IABR`).

Пріоритети переривань задаються через регістри `NVIC_IPR`. Чим менше числове значення пріоритету, тим вищий його пріоритет (пріоритет `0` є найвищим можливим для периферійних IRQ). За допомогою регістра `SCB->AIRCR` конфігурується `PRIGROUP`, який розділяє байт пріоритету на два рівні:
1. **Preemption Priority (груповий пріоритет):** визначає, чи може переривання витіснити (перервати) інший обробник, який уже виконується.
2. **Subpriority (підпріоритет):** визначає порядок вибору переривання серед кількох одночасно очікуючих (pending) запитів із однаковим груповим пріоритетом. Підпріоритет ніколи не спричиняє витіснення поточного обробника.

### Апаратне збереження контексту (Stacking) та оптимізації

Коли NVIC ініціює вхід в ISR, апаратний блок ядра автоматично виконує збереження контексту в стек:
1. У стек (зазвичай за вказівником `PSP`, якщо код перервано в Thread Mode) зберігаються 8 регістрів базового фрейму: `R0`, `R1`, `R2`, `R3`, `R12`, `LR`, `PC` та `xPSR`.[^armv7m-arm]
2. Якщо увімкнено FPU і поточний потік використовував операції з рухомою комою, механізм Lazy Stacking резервує місце для регістрів `S0–S15` та `FPSCR`, але зберігає їх у пам’ять лише тоді, коли обробник ISR сам починає використовувати інструкції FPU.
3. Процесор переходить у `Handler Mode`, автоматично вибираючи вказівник стека `MSP`.

Для мінімізації накладних витрат процесори Cortex-M мають апаратні оптимізації:
- **Tail-chaining:** якщо на момент завершення ISR очікує інше дозволене переривання (pending), процесор не робить повний unstacking і stacking, а безпосередньо переходить на виконання наступного вектора всього за кілька тактів (зазвичай 6 тактів).
- **Late-arriving:** якщо під час збереження регістрів для поточного переривання надходить запит із вищим пріоритетом, ядро негайно перемикається на обробник вищого пріоритету, використовуючи вже збережений контекст.

### Повернення з переривання та магічний EXC_RETURN

При вході в ISR регістр повернення `LR` (Link Register) не містить адреси виклику; туди записується спеціальне значення – **`EXC_RETURN`** (наприклад, `0xFFFFFFF9` для повернення в Thread Mode з `MSP`, або `0xFFFFFFFD` для повернення в Thread Mode з `PSP`).[^armv7m-arm]

Обробник переривання є стандартною C-функцією з прототипом `void ISR_Handler(void)`. Вихід здійснюється звичайною інструкцією повернення:
```assembly
BX LR
```
Коли процесор виявляє, що в `LR` знаходиться шаблон `EXC_RETURN` (старші біти `0xFFFFFF`), він апаратно запускає процедуру unstacking: відновлює `R0–R3`, `R12`, `LR`, `PC` та `xPSR` зі стека, відновлює режим `Thread Mode` і продовжує виконання перерваного коду.

В операційних системах реального часу (RTOS) цей механізм є основою диспетчеризації задач: системне переривання `PendSV` вручну зберігає решту регістрів ядра (`R4–R11`), перемикає системний вказівник на стек іншої задачі та виконує `BX LR`, що змушує апаратний блок відновити контекст уже нової задачі.
