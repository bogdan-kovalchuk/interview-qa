# Аналіз і архітектурне бачення проєкту

**Статус:** узгоджено. ADR-0001…0012 прийнято; реалізація ще не починалась.
**Дата:** 2026-09-03.

---

## 1. Постановка задачі

Потрібна **база знань питань та розгорнутих відповідей для технічних інтерв'ю**, яка одночасно:

1. є самостійним публічним сайтом (GitHub Pages);
2. покриває Python і C/C++ як основні мовні треки;
3. масштабується на спеціалізації (Embedded, Data Science, ML, Backend, DevOps, QA тощо) і фреймворки;
4. двомовна (English + Українська) з перемиканням мови;
5. є **єдиним джерелом істини**: додавання питання автоматично породжує картку Anki;
6. дає **стабільні посилання на конкретне питання**, які вставляються у поле картки Anki як «розгорнуте пояснення».

Референс: <https://tavor118.github.io/pj_python_interview_questions_and_answers/> – Material for MkDocs, ~10 верхніх розділів (`Introduction`, `Top 100 Questions`, `Python`, `Python Framework`, `Computer Science`, `Web Development`, `Infrastructure`, `Architecture`, `Development`, `Front-end`), ручна навігація, один автогенерований `top_questions.md`, без перемикання мов.

## 3. Ключове відкриття: стек референсу вже не є безпечним вибором

Референсний сайт зроблений на Material for MkDocs. Станом на вересень 2026:

| Факт | Наслідок |
|---|---|
| MkDocs 1.x без релізів ~18 місяців; MkDocs 2.0 (pre-release) **несумісний з Material** і **прибирає підтримку плагінів**, конфіг переїжджає на TOML | плагінна екосистема MkDocs – тупикова гілка |
| `mkdocs-static-i18n` (єдиний робочий спосіб зробити двомовний MkDocs) – **офіційно заморожений**: «this project is frozen as-is» | вимога №4 стоїть на замороженій залежності |
| Material for MkDocs живий, але вже пінить `mkdocs<2` і мігрує на власний генератор **Zensical** (Rust core) | міграція попереду в будь-якому разі |
| i18n у Zensical – **тільки в роадмапі** (`zensical/backlog#2`), не реалізований | двомовність на Zensical сьогодні недоступна |

Копіювати стек референсу означає одразу побудувати сайт на замороженому i18n-плагіні поверх генератора, який готується до заміни. Для бази знань, розрахованої на роки й на тисячі вічних посилань у картках Anki, це неприйнятний ризик.

### Порівняння кандидатів

| Критерій | Material for MkDocs + static-i18n | Docusaurus | **Astro Starlight** |
|---|---|---|---|
| i18n | плагін заморожений | вбудований, зрілий | **вбудований, з fallback і нотисом** |
| Пошук | lunr; українського стемера в `lunr-languages` немає | Algolia (зовнішній сервіс) або сторонній плагін | **Pagefind у коробці, окремий індекс на мову автоматично за `lang`** |
| Валідація frontmatter | немає | немає | **Zod-схема content collections, білд падає на битому питанні** |
| Майбутнє | міграція на Zensical неминуча | стабільно | стабільно, активний розвиток |
| Вага сторінки | середня | важка (React) | **мінімальна (islands, ~0 JS)** |
| Мова тулчейна | Python | Node | Node |
| Кастомні генеровані маршрути (ролі, зрізи, `/q/{id}`) | скриптами до білду | React-роути | **file-based dynamic routes, `getStaticPaths`** |

**Рекомендація: Astro Starlight.**
Єдиний мінус – Node у тулчейні. Він компенсується головним принципом проєкту (§4.1): **контент не залежить від генератора**. Python-частина (валідація, експорт в Anki, генерація індексів) лишається на Python і нічого не знає про Astro.

> Запасний варіант, якщо Node категорично небажаний: Material for MkDocs, але двомовність робиться **двома окремими білдами** (`mkdocs.en.yml` / `mkdocs.uk.yml` з різними `docs_dir`) і власним перемикачем через `extra.alternate`, без плагіна i18n. Працює і не залежить від замороженого коду, але коштує дублювання конфігу і гіршого пошуку українською.

## 4. Архітектурні принципи

### 4.1. Контент відв'язаний від генератора

```
                 content/            ← Markdown + YAML frontmatter
                    │                  єдине джерело істини
        ┌───────────┼───────────┐
        ▼           ▼           ▼
     site/       tools/       tools/
    (Astro)   export_anki   export_json
      сайт     .tsv → .apkg   датасет/API
```

`content/` не містить жодного синтаксису, специфічного для Astro: ніякого MDX, ніяких імпортів компонентів усередині питань. Заміна генератора = переписати `site/`, не чіпаючи контент. Це прямий висновок з §3: генератори живуть 3–5 років, база знань – довше.

### 4.2. Одне питання = один файл = одна картка

Атомарність тут функціональна, а не стилістична: файл є одиницею URL, одиницею перекладу, одиницею експорту в Anki і одиницею рев'ю в PR.

### 4.3. Питання ніколи не дублюється між спеціалізаціями

Найбільша загроза для такого проєкту – розповзання копій одного питання по треках (`python/`, `data-science/`, `backend/` усі хочуть «що таке GIL»). Замість дублювання – **одна канонічна домівка + фасети + композиції** (§6).

### 4.4. Посилання в Anki – це контракт, а не URL

Картки живуть у профілях учнів роками і не перебудовуються при реструктуризації сайту. Тому в картку йде **не гарний URL сторінки**, а незмінний permalink `/{lang}/q/{id}/`, який редіректить на поточну канонічну сторінку.

### 4.5. Усе, що можна згенерувати, – генерується

Індекси тем, сторінки ролей/шляхів, сторінки тегів, таблиця прогресу, звіт про стан перекладу, `/q/` маршрути, TSV для Anki, release notes колоди. Руками пишуться лише файли питань і описи програм.

## 5. Модель контенту

### 5.1. Чотири осі

| Вісь | Що це | Де живе |
|---|---|---|
| **Track** | напрямок за мовою/платформою: `python`, `cpp`, `embedded`, `data-science`… | 1-й рівень дерева `content/{lang}/` |
| **Section** | тема всередині треку: `asyncio`, `templates`, `rtos` | 2-й рівень дерева |
| **Facets** | `level`, `type`, `frameworks`, `tags` | frontmatter питання; `roles` виводяться з `programs/*.yml` (ADR-0010 §5) |
| **Views** | згенеровані зрізи: ролі, рівні, теги, фреймворки | генеруються з фасетів |

Дерево дає **одну фізичну домівку**, фасети дають **скільки завгодно логічних входів** у те саме питання.

### 5.2. Правило канонічної домівки

> Питання живе в **найвужчому треку, у якому воно має сенс без контексту домену**.

- «Чому `std::vector` інвалідує ітератори при `push_back`?» → `cpp/stl-containers/` (сенс є без embedded).
- «Чому в embedded-C++ вимикають exceptions і RTTI?» → `embedded/cpp-in-embedded/` (без домену питання не існує).
- «Що таке GIL?» → `python/concurrency-and-gil/`; data-science отримує його через членство в програмі `data-science-engineer`, яка добирає питання за треками, секціями й тегами.

Це правило треба тримати в `meta/NAMING.md` і перевіряти на рев'ю – воно єдине, що стримує ентропію.

### 5.3. Структура файлу питання

Фіксований набір секцій робить файл машинно-читабельним: `## Short answer` іде в `Back` картки Anki, решта – тільки на сайт. Повна специфікація – `meta/CONTENT_SPEC.md`.

### 5.4. Схема ID

`{track}-{section}-{NNNN}` – `py-asyncio-0007`, `cpp-mem-0012`, `emb-rtos-0003`.

- ID **незмінний** і **ніколи не перевикористовується** (навіть після видалення питання);
- ID не залежить від фізичного розташування файлу – переміщення між секціями ID не змінює;
- ID є ключем для: permalink `/q/{id}/`, GUID нотатки Anki, крос-посилань, звітів покриття.

## 6. Спеціалізації та фреймворки

Вимога №2 – «врахувати, що можуть бути специфічні фреймворки чи напрямки». На практиці саме тут такі проєкти й помирають: спеціалізація – це не ще одна тека, а **комбінація** «мовне ядро + доменні знання + тулчейн/фреймворк».

Наївний підхід (`embedded/` як самодостатнє дерево з копіями C++-питань) дає розсинхрон уже на другому місяці.

### 6.1. Дворівнева модель

**Рівень 1 – атоми.** Питання лежать у канонічній домівці (§5.2). Спеціалізація має власний трек **тільки для доменно-специфічних питань**.

**Рівень 2 – програми (`programs/*.yml`).** Програма – декларативна композиція запитів по фасетах, яка описує підготовку до конкретної вакансії:

```yaml
# programs/embedded-cpp-engineer.yml
id: embedded-cpp-engineer
title:
  en: Embedded C++ Engineer
  uk: Інженер Embedded C++
levels: [junior, middle, senior]
include:
  - track: cpp
    sections: [memory-model-and-lifetime, pointers-and-references,
               compilation-and-linking, concurrency-and-memory-model]
  - track: embedded                 # весь трек
  - track: cs
    tags: [bit-manipulation, state-machines]
  - track: engineering
    sections: [version-control, testing]
exclude:
  - tags: [gui, web]
anki:
  package: "Interview QA - Embedded C++"   # колода лишається тематичною (ADR-0008)
```

Одна програма породжує **три артефакти одразу**:

1. сторінку-шлях на сайті `/{lang}/programs/embedded-cpp-engineer/` з чеклістом і порядком вивчення;
2. окрему колоду Anki, зібрану з тих самих нотаток – без дублювання нотаток, лише інша вибірка;
3. звіт покриття: скільки питань готові, скільки перекладені, де діри.

Додати нову спеціалізацію = додати один YAML (+ за потреби один трек доменних питань). Наявні питання переплюсовуються автоматично.

### 6.2. Де живуть фреймворки

Фреймворк не є треком верхнього рівня. Він живе **всередині домену, який ним володіє**, і додатково позначається фасетом `frameworks:`:

- `backend/frameworks/django/`, `backend/frameworks/fastapi/`
- `data-science/frameworks/pandas/`, `machine-learning/frameworks/pytorch/`
- `embedded/rtos/freertos/`, `embedded/rtos/zephyr/`
- `cpp/frameworks/qt/`, `cpp/frameworks/boost/`

Причина: питання «як влаштований lazy queryset у Django ORM» не має сенсу поза backend-контекстом, а фасет `frameworks: [django]` дозволяє зібрати «всі питання по Django» як згенерований зріз, навіть якщо частина з них фізично лежить у `python/`.

### 6.3. Верхній рівень треків

Розгорнуте дерево – у `meta/TAXONOMY.md`.

| Трек | Роль у моделі |
|---|---|
| `python`, `cpp` | мовні ядра – найбільша щільність питань, живуть незалежно від домену |
| `cs` | алгоритми, структури даних, складність – спільний фундамент |
| `systems` | ОС, пам'ять, процеси, мережі – питають і в Python, і в C++ |
| `databases` | SQL, транзакції, індекси, NoSQL |
| `engineering` | git, тестування, CI/CD, code review, SDLC |
| `system-design` | дизайн систем від junior-рівня до розподілених |
| `embedded` | доменний трек (MCU, RTOS, периферія, лінкер, стандарти безпеки) |
| `data-science`, `machine-learning`, `data-engineering` | доменні треки з власними фреймворками |
| `backend`, `devops`, `qa-automation` | доменні треки |
| `behavioral` | soft skills, поведінкові питання, процес інтерв'ю |

## 7. Топологія репозиторіїв

Питання із завдання: монорепозиторій, сабмодулі чи незалежні репозиторії.

| Варіант | Плюси | Мінуси | Вердикт |
|---|---|---|---|
| **A. Монорепозиторій** – контент, сайт і збірка Anki в одному репо | атомарний коміт «питання + картка», один CI, нуль синхронізації, розсинхрон неможливий | репо росте; дві різні збірки в одному пайплайні | **рекомендовано** |
| **B. Сабмодуль** – KB як сабмодуль у кожному deck-репо | пінінг версії, окремий реліз-цикл колод | сабмодулі на Windows болючі; два коміти на одну зміну; постійні `--recurse-submodules`; контриб'ютори ламають | лише якщо колоди мусять мати незалежний реліз-цикл |
| **C. Незалежні репо + ручна синхронізація** | нуль зв'язності | гарантований дрейф контенту – тобто зникає саме те, заради чого проєкт робиться | відхилено |

**Рекомендація: A (монорепозиторій), але з явним контрактом експорту**, щоб B лишався можливим без переписування.

### 7.1. Контракт експорту

`tools/` генерує версійований бандл, і **тільки він** є інтерфейсом для будь-якого споживача (сайт, Anki, майбутній бот чи API):

```
dist/export/
  manifest.json        # export_schema: 1, версія, дата, хеші, лічильники
  questions.json       # нормалізований датасет усіх питань з обома мовами
  anki/
    python__asyncio.tsv
    cpp__templates.tsv
```

Поки топологія A – споживач читає `dist/` локально. Якщо колись знадобиться B – той самий бандл публікується як GitHub Release asset, а deck-репо його завантажує. Код споживача не змінюється. Це і є сенс контракту.

### 7.2. Доля `python_interview_questions`

1. **Фаза 0 (зараз).** Нічого не чіпаємо. Новий репо містить лише документацію.
2. **Фаза 1.** Переносимо 23 TSV у `content/{lang}/python/**` як файли питань. Нові `id` видаються з нуля; `card::PYI_16_004` не зберігається (ADR-0011).
3. **Фаза 2.** Персистентна колекція `*.anki2` більше не потрібна: GUID рахується детерміновано від `id`, а не зберігається в бінарнику (ADR-0006, ADR-0011). Predecessor-копія лишається лише як архівний baseline.
4. **Фаза 3.** `python_interview_questions` переводиться в archived (read-only) з README-вказівником на новий репо.
5. **Фаза 4.** `cpp_interview_questions` та подібні **не створюються взагалі** – вони від початку є треками всередині KB, а окремі `.apkg` для них – просто інші цілі збірки.

**Ключовий ризик міграції:** GUID нотаток Anki. Якщо новий білдер згенерує інші GUID, учні отримають дублікати замість оновлення. Тому GUID є детермінованою функцією від стабільного ID – одне джерело, без мапи legacy (ADR-0011). Це окремий smoke-тест у quality gates ще до першого релізу.

## 8. Двомовність

### 8.1. Схема URL

Симетричні префікси для обох мов: `/en/...` і `/uk/...`, корінь `/` редіректить на `/en/`.

Чому не «англійська без префікса»: симетрія робить тривіальним перехід «та сама сторінка іншою мовою» – саме те, що потрібно і перемикачу мов, і permalink-схемі `/uk/q/{id}/` для українських карток Anki. Асиметрія (`/about` проти `/uk/about`) економить три символи і коштує спецкейсу в кожному генераторі посилань.

### 8.2. Обов'язкова мова

Fallback-механізм (у Starlight – з видимим нотисом) показує контент `defaultLocale`, коли переклад відсутній. Отже **одна мова обов'язкова для кожного питання**, друга – опціональний шар.

- `defaultLocale: en` – англійська обов'язкова. Плюси: ширша аудиторія, SEO, англомовна термінологія і так у коді, відкриті внески. Мінус: увесь наявний український контент треба перекласти перед публікацією.
- `defaultLocale: uk` – українська обов'язкова. Плюси: збігається з наявними 23 темами і з мовою карток Anki, старт без перекладу. Мінус: розворот дефолту пізніше = зміна URL усіх сторінок.

**Рекомендація:** `en` як `defaultLocale`, `uk` як повноцінний перший переклад. Це рішення з найдорожчою ціною помилки в документі – винесене в §11 на явне підтвердження. Компроміс, якщо англійська зараз не витягується: стартувати з `uk` і **одразу** тримати обидва дерева симетричними, щоб розворот був механічним.

### 8.3. Пошук

Pagefind (у Starlight з коробки) читає атрибут `lang` у HTML і будує **окремий індекс на кожну мову** без конфігурації. Спеціалізованого стемера для української немає – пошук працює на загальному алгоритмі, якість трохи нижча за англійську, але прийнятна. Для порівняння: у MkDocs-варіанті `lunr-languages` української не має взагалі.

### 8.4. Що ще перекладається, крім тексту питань

Часто забувають: назви треків і секцій у навігації, підписи фасетів (`level: middle` → «Середній»), назви програм, згенеровані сторінки-індекси. Це окремі словники (`content/i18n/{lang}.json`), а не хардкод у шаблонах.

## 9. Permalink-схема для карток Anki

Вимога №6 – найтехнічніша частина, і вона визначає довговічність проєкту.

**Контракт:** у поле картки йде **виключно** `https://{host}/{base}/{lang}/q/{id}/`.

- `/uk/q/py-asyncio-0007/` → редірект на `/uk/python/asyncio/blocking-call-freezes-event-loop/`;
- сторінки `/q/{id}/` генеруються автоматично з датасету – по одній на мову;
- перейменування файлу, переїзд питання в іншу секцію, зміна заголовка **не ламають жодної картки**;
- якщо питання вилучене – `/q/{id}/` віддає сторінку «питання вилучене» з посиланням на заміну, а не 404.

Наслідок для карток: замість плейсхолдера «Розгорнуте пояснення» потрібне окреме поле `Reference`. Це реалізовано не міграцією predecessor-моделі, а новим note type `Interview QA Basic` з п'ятьма полями від початку – `packaging/anki/note_type.md`, ADR-0010 §1.

Довжина посилання залежить від імені репозиторію: GitHub Pages дає `https://{user}.github.io/{repo}/`. Оскільки посилання розходяться по тисячах карток і стають фактично вічними, ім'я репозиторію треба зафіксувати **до першої публікації** або одразу підключити власний домен (§11).

## 10. Quality gates і автоматизація

Проєкт тримається не на дисципліні, а на CI. Мінімальний набір воріт:

| Ворота | Що ловить |
|---|---|
| Schema validation (Zod на білді + Python-валідатор) | биті frontmatter, відсутні обов'язкові поля |
| Унікальність і незмінність ID | перевикористаний або змінений `id` (звірка з `meta/id-registry.csv`) |
| Структура секцій | відсутній `## Short answer` – картка Anki буде порожня |
| Довжина `Short answer` | відповідь, яка не влазить у картку |
| Наявність джерела | питання без жодного авторитетного посилання |
| Link check | биті внутрішні крос-посилання і мертві зовнішні URL, на production-збірці |
| Permalink coverage | питання без згенерованого `/q/{id}/` |
| Anki GUID stability | нотатка, яка при перезбірці змінила GUID (= дублікати в учнів) |
| Translation report | покриття перекладом (не блокує, але видиме) |

CI: PR → валідація + білд сайту + білд бандла; merge у `main` → deploy на GitHub Pages + оновлення `dist/`.

### Ще відкрито

**Нічого.** Станом на 2026-09-04 відкритих архітектурних питань немає: ADR-0001…0012 прийнято,
схема пройшла дві хвилі дефектів і заморожена, склад frontmatter і шаблон картки зафіксовані.

Spike на реальному Anki, який тут вимагався перед M1, виконано – M0.4, десять експериментів,
`meta/migration/anki-compatibility-report.md` і `anki-tag-refresh.md`. Він підтвердив збереження
розкладу при оновленні полів, незмінність колоди наявних карток, повне заміщення тегів і
неможливість видалення нотатки через імпорт, а припущення про наслідок зміни `model_id`
спростував – що й привело до ADR-0010 §1 і ADR-0011.

---

**Закрито 2026-09-03.** Питання «хто пише англійські версії» знято: обидві мовні версії пише агент,
а наповнення відбувається поступово. Звідси:

- **мовою авторства є та, якою зручно** в конкретний момент – агент робить другу версію.
  Обов'язкового напрямку немає; на масштабі важать словник термінів і машинні перевірки паритету
  мовних версій, а не порядок написання (`I18N.md` §4a);
- **неповне питання – штатний стан**, а не дефект: рівні `stub` / `partial` / `complete`
  обчислюються з фактичного вмісту, ворота застосовуються за рівнем, а посилання в картку
  додається лише з `partial`, щоб учень ніколи не потрапив на порожню сторінку
  (`CONTENT_SPEC.md` §3a).

Це прибирає й аргумент за розворот `defaultLocale` на `uk`: обов'язковість англійської більше не
означає «перекласти все перед запуском», а лише «мати англійський `stub`».

Фасет `popularity` і генерована сторінка «Топ-100» вилучені з дизайну 2026-09-03 за рішенням
власника. Ранжувати питання за «частотою на інтерв'ю» можна було б лише експертною оцінкою, як у
референсу (`[💡21/100]` у тексті заголовка), а суб'єктивна оцінка, подана як метрика, вводить в
оману. Пріоритет замість цього виражають `level` і склад програм у `programs/`.

Наскрізна картина проєкту: `meta/PIPELINE.md`.

## 11a. Незалежне рев'ю плану

2026-09-03 план пройшов зовнішнє рев'ю (`meta/PROJECT_PLAN_REVIEW.md`). Воно **не погодило** перехід
до M1 і зафіксувало три критичні блокери та шістнадцять major-зауважень. Перевірка підтвердила
більшість із них.

Причина була системною, а не випадковою: план проєктувався ітеративно, рішення переглядалися
кілька разів, і в різних документах осіли різні їх редакції. Зокрема одночасно діяли:

- заморожена структура note type – і план змінити її з двох полів на п'ять;
- нормативне посилання `/q/{id}/` – і base path `/interview-qa/`, під яким воно було б битим;
- заборона читати `content/` напряму – і схема, у якій сайт читає саме `content/`;
- три різні правила появи `Reference` у трьох документах.

Відповіді на всі зауваження – `meta/adr/0010-plan-review-corrections.md`. Найважливіші наслідки:

| Що з'явилось | Навіщо |
|---|---|
| `meta/LIFECYCLE.md` | одна нормативна таблиця публікації з пріоритетом над усіма документами |
| ієрархія документів у `AGENTS.md` | щоб суперечність мала однозначного переможця |
| токен `qid:` замість URL у контенті | щоб посилання не залежали від base path і хоста |
| згенероване дзеркало для сайту | щоб `content/` читав рівно один компонент |
| `meta/RUBRIC.md` | щоб `level` і `type` означали те саме для двох рецензентів |
| покриття цілей у звіті | щоб «100 питань» не було критерієм приймання |
| поетапний cutover з вікном відкату | щоб міграція і архівація не були одним кроком |

Базова ідея проєкту рев'ю не змінило: сталі ID і GUID, тематичні колоди, програми як композиції,
permalink як контракт, генерований прогрес лишаються.
