# Дослідження: картки для Python-інтерв’ю

Дата перевірки джерел: 2026-09-02.

## Висновок

Для цього проєкту найкраще працює не «конспект, розрізаний на картки», а банк коротких
завдань на відтворення знань: пояснити механізм, передбачити результат коду, знайти помилку,
порівняти два підходи або обрати рішення для сценарію. Одна картка перевіряє одну головну
думку, але може мати коротке пояснення і мінімальний приклад на звороті.

Оптимальна технічна модель — одна Anki-колода, один тип нотатки `Front/Back`, окремі TSV за
темами та ієрархічні теги. Генерація ШІ має бути source-grounded і двопрохідною: окрема
генерація, потім окреме фактичне та педагогічне рев’ю.

## Що підтверджено дослідженнями

### Retrieval practice важливіша за повторне читання

Експерименти Roediger і Karpicke показали, що повторне вивчення може давати кращий негайний
результат, але попереднє тестування суттєво покращує відкладене відтворення. Отже, фронт
картки повинен змушувати сформулювати відповідь до її відкриття, а не лише впізнати знайоме
формулювання.

Джерело: [Test-Enhanced Learning: Taking Memory Tests Improves Long-Term Retention](https://doi.org/10.1111/j.1467-9280.2006.01693.x).

### Мінімальна інформація, але не мінімальний контекст

Правила SuperMemo рекомендують спочатку зрозуміти матеріал, а потім розкладати його на
прості елементи. Великі переліки та багатокомпонентні запитання створюють неоднозначне
оцінювання. Для Python це означає:

The Python-specific rules below are project inferences from the general learning principles, not
direct experimental findings about Python interview decks:

- одна головна перевірювана теза на картку;
- достатньо контексту, щоб відповідь була однозначною;
- окремі картки для визначення, механізму, наслідку та типового винятку;
- джерело для тверджень, що залежать від реалізації або версії;
- cloze — лише для точної синтаксичної форми, а не як основний тип карток.

Джерело: [20 rules of formulating knowledge in learning](https://www.super-memory.com/articles/20rules.htm).

### Одна широка колода, теми — тегами

Офіційний посібник Anki радить використовувати колоди для широких категорій, а не створювати
багато маленьких колод. Послідовний перегляд однієї теми створює контекстну підказку й може
послабити незалежне відтворення. Теги дозволяють одночасно класифікувати картку за темою,
типом, складністю, реалізацією та версією.

Джерело: [Anki Manual — Using Decks Appropriately and Using Tags](https://docs.ankiweb.net/editing.html#organizing-content).

### TSV та HTML — надійний формат обміну

Anki підтримує службові заголовки `separator`, `html`, `deck`, `notetype` і `tags column`.
Для кирилиці потрібен UTF-8. HTML дозволяє безпечно переносити рядки й форматувати Python-код.
Перший стовпець використовується для пошуку дублікатів, тому фронти мають бути стабільними.

Джерело: [Anki Manual — Text Files](https://docs.ankiweb.net/importing/text-files.html).

## Які картки потрібні для Python-інтерв’ю

| Тип | Що перевіряє | Приклад форми |
|---|---|---|
| Definition | точне значення терміна | «Що означає hashable?» |
| Mechanism | як і чому щось працює | «Як Python знаходить ім’я?» |
| Contrast | межу між близькими поняттями | «Чим `is` відрізняється від `==`?» |
| Code | прогноз і пояснення виконання | «Що виведе код і чому?» |
| Trap | типову помилку або хибну модель | «Де помилка в цьому фрагменті?» |
| Scenario | інженерне рішення та trade-off | «Що обрати для CPU-bound задачі?» |

Definition-картки потрібні як фундамент, але колода не повинна складатися лише з них.
Для інтерв’ю найцінніші Mechanism, Contrast, Code, Trap і Scenario: вони перевіряють
пояснення, а не заучене формулювання.

## Стиль запитання

Хороший фронт:

- самодостатній і має одну інтерпретацію;
- називає реалізацію або версію, якщо це впливає на відповідь;
- просить не лише результат коду, а й коротке пояснення;
- не містить прихованої підказки у назві теми;
- не є запитанням «розкажіть усе про…»;
- дозволяє чесно оцінити відповідь як правильну або неправильну.

Поганий фронт поєднує п’ять визначень, просить перелічити довгий список або залежить від
невказаного контексту. Якщо відповідь можна оцінити лише як «частково правильну», картку
потрібно розділити.

## Стиль відповіді

Відповідь починається з прямої тези. Далі, за потреби, подається механізм, мінімальний
приклад і застереження. Типова довжина — 2–5 речень; код не рахується як речення.

Для порівняння потрібно назвати критерій різниці. Для сценарію — рішення, умову, за якої
воно правильне, та ключовий trade-off. Для code-картки — результат, причина і версійна
примітка, якщо поведінка не гарантована специфікацією мови.

## Використання ШІ

Дослідження генерації освітніх запитань показує, що LLM можуть створювати корисні й
різноманітні завдання, особливо коли отримують контекст і задану таксономію. Це підтримує
використання ШІ для першої чернетки, але не робить модель авторитетним джерелом.

Applying that classroom evidence to this Python interview workflow is a project inference. It still
requires independent source verification and reviewer judgment.

Джерело: [How Useful are Educational Questions Generated by Large Language Models?](https://arxiv.org/abs/2304.06638).

Рекомендований конвеєр:

1. Людина або ШІ складає карту покриття теми за авторитетними джерелами.
2. ШІ генерує невелику порцію карток лише з переданих фрагментів.
3. Інший прохід перевіряє атомарність, дублікати, двозначність і рівень складності.
4. Технічні твердження звіряються з Python Language Reference, Standard Library docs або PEP.
5. Code-картки запускаються на заявлених версіях Python, якщо результат не очевидний зі специфікації.
6. Механічний валідатор перевіряє TSV, HTML, теги й дублікати.
7. Після реального використання складні або часто забуті картки переписуються, а не просто повторюються частіше.

ШІ не повинен:

- створювати факти «з пам’яті», коли доступне офіційне джерело;
- мовчки змішувати Python і CPython;
- називати GIL незмінною властивістю всіх реалізацій і конфігурацій;
- вигадувати «типові питання Google» без перевірного джерела;
- доповнювати колоду заради круглого числа карток;
- одночасно генерувати й остаточно затверджувати власний результат.

## Версійна політика Python

На дату дослідження остання стабільна гілка — Python 3.14; Python 3.15 перебуває на стадії
release candidate. Тому базою колоди є 3.14, а 3.15 позначається як preview до фінального
релізу. Джерело: [Python 3.14.7](https://www.python.org/downloads/release/python-3147/) та
[Python 3.15.0rc2](https://www.python.org/downloads/release/python-3150rc2/).

Особливої уваги потребують картки про конкурентність: починаючи з 3.13 CPython має
free-threaded build, а у 3.14 ця конфігурація офіційно підтримується, хоча стандартна збірка
все ще може працювати з GIL. Джерело: [Python support for free threading](https://docs.python.org/3/howto/free-threading-python.html).
