Чому reference counting сам не може звільнити unreachable reference cycle?	<span class="key">Тому що кожен об'єкт у циклі має reference count ≥ 1 від іншого об'єкта того ж циклу, і жоден refcount ніколи не досягає нуля — хоча весь цикл більше недоступний ззовні.</span> Наприклад, якщо <code>a</code> посилається на <code>b</code>, а <code>b</code> посилається на <code>a</code>, і зовнішніх посилань немає, обидва refcount дорівнюють 1. Reference counting не може відрізнити такий «мертвий» цикл від живих посилань. Для цього потрібен cyclic garbage collector.<div class="source">Джерело: <a href="https://docs.python.org/3.14/library/gc.html">Python 3.14: gc</a></div>	topic::14_cpython_internals_memory type::Mechanism level::Middle scope::Core card::PYI_14_009 ref::TV_PYTHON_INTERPRETER_06 source::PythonDocs source::Community runtime::CPython
Як cyclic garbage collector CPython виявляє unreachable container cycles поверх reference counting?	<span class="key">GC відстежує container-об'єкти (list, dict, user-defined instances), обходить граф їхніх посилань і звільняє групи об'єктів, на які немає зовнішніх (не від GC) посилань.</span> Об'єкти розподілені за трьома поколіннями (0, 1, 2); нові контейнери потрапляють у покоління 0. Коли кількість allocation мінус deallocation перевищує поріг, запускається збір. GC перевіряє, чи можна досягти об'єктів з коренів; якщо ні — вони collectable. Чому <code>__del__</code> не слід використовувати як основний механізм timely release зовнішніх resources?	<span class="key"><code>__del__</code> не гарантує ні своєчасного виклику, ні виклику взагалі: він може бути відкладений cyclic GC, пропущений при shutdown інтерпретатора, а винятки всередині нього ігноруються.</span> Конкретні ризики: (1) якщо об'єкт потрапляє в reference cycle, <code>__del__</code> викликається лише коли cyclic GC його виявить; (2) при shutdown інтерпретатора глобальні змінні можуть вже дорівнювати <code>None</code>; (3) <code>__del__</code> може викликатися з довільного потоку, що створює ризик deadlock при захопленні lock.
