Чим coroutine function, coroutine object та результат <code>await</code> відрізняються між собою?	<span class="key">Coroutine function — це <code>async def</code>-функція; coroutine object — об'єкт, який повертає виклик такої функції; результат <code>await</code> — значення, яке coroutine повертає після виконання.</span> Виклик <code>async def</code>-функції не виконує її тіло, а лише створює coroutine object. Щоб код справді виконався, цей об'єкт потрібно передати в <code>await</code>, <code>asyncio.create_task()</code> або інший механізм запуску. Які objects можна <code>await</code> і як coroutine, Task та Future пов’язані через awaitable protocol?	<span class="key"><code>await</code> приймає будь-який awaitable-об'єкт — coroutine, Task або Future, — тобто об'єкт з методом <code>__await__</code>.</span> Coroutine — це «сирий» об'єкт з <code>async def</code>. Чому просте створення кількох coroutine objects ще не запускає їх concurrently?	<span class="key">Виклик <code>async def</code>-функції лише створює coroutine object, але не планує його виконання — код не запуститься, поки об'єкт не буде <code>await</code>-нуто або передано в <code>asyncio.create_task()</code>.</span> Послідовний <code>await</code> кількох coroutine виконує їх по черзі, а не паралельно. Чому для fire-and-forget Task потрібно зберігати strong reference та явно обробляти outcome?	<span class="key">Event loop зберігає лише weak references на Tasks, тому Task без зовнішнього посилання може бути знищена GC до завершення.</span> Якщо Task завершується з exception і ніхто не читає результат, Python видасть <span class="warn">«Task exception was never retrieved»</span>. Що робить asyncio Task або callback ready після I/O, timer чи suspension point і яких fairness та exact-order guarantees application code не має припускати?	<span class="key">Event loop виконує готові callback у порядку FIFO для <code>call_soon</code>, але порядок timer-callbackів з однаковим часом є невизначеним, а строгих fairness-гарантій між Tasks немає.</span> Коли I/O завершується або спливає timer, loop додає відповідний callback у ready-чергу. Callbacks, зареєстровані через <code>call_soon</code>, викликаються в порядку реєстрації. Проте для <code>call_later</code> / <code>call_at</code> з однаковим timestamp порядок не гарантовано. Чому coroutine без suspension point може монополізувати event-loop thread?	<span class="key">Coroutine, яка не містить жодного <code>await</code>, виконується синхронно від початку до кінця, не передаючи керування event loop, і тим самим блокує виконання всіх інших Tasks та I/O.</span> Cooperative multitasking працює лише тоді, коли кожна coroutine періодично поступається через suspension point. Як один blocking call в <code>async def</code> впливає на latency всіх інших Tasks у тому самому loop?	<span class="key">Будь-який синхронний blocking call (наприклад, <code>time.sleep()</code>, I/O файлів, CPU-обчислення) зупиняє event loop на весь час виконання, затримуючи всі інші Tasks і I/O-події.</span> Рішення — винести blocking операцію в окремий thread або process через <code>asyncio.to_thread()</code> або <code>loop.run_in_executor()</code>. Як CPU-heavy coroutine або необмежена ready queue може створити starvation навіть у cooperative scheduler?	<span class="key">Навіть у cooperative моделі coroutine з довгим обчисленням між <code>await</code>-точками утримує event-loop thread і не дає виконуватися іншим Tasks, створюючи starvation.</span> Рішення: розбивати довгі обчислення на фрагменти з <code>await asyncio.sleep(0)</code> між ними, або виносити CPU-heavy роботу в <code>ProcessPoolExecutor</code> через <code>run_in_executor()</code>. <code>asyncio.sleep(0)</code> явно поступається керуванням, дозволяючи loop обробити інші ready callbacks.<div class="source">Джерело: <a href="https://docs.python.org/3.14/library/asyncio-dev.html">Python 3.14: asyncio development</a></div>	topic::16_asyncio type::Scenario level::Senior scope::Core card::PYI_16_008 ref::TV_PYTHON_ASYNC_23 source::PythonDocs source::Community
Як <code>asyncio.TaskGroup</code> гарантує, що створені в ньому Tasks завершаться до виходу з context manager?	<span class="key"><code>TaskGroup</code> — асинхронний context manager, який у <code>__aexit__</code> неявно очікує завершення всіх Tasks, створених через <code>tg.create_task()</code>, і не вийде з блоку, поки вони не завершаться.</span> Tasks створюються лише всередині <code>async with</code>-блоку. Після виходу з блоку (нормально чи через exception) <code>TaskGroup</code> чекає завершення всіх дочірніх Tasks, забезпечуючи structured concurrency.<div class="source">Джерело: <a href="https://docs.python.org/3.14/library/asyncio-task.html">Python 3.14: TaskGroup</a></div>	topic::16_asyncio type::Mechanism level::Middle scope::Core card::PYI_16_009 ref::TV_PYTHON_ASYNC_13 source::PythonDocs source::Community
Що відбувається з sibling Tasks та exceptions, коли одна Task у <code>TaskGroup</code> падає?	<span class="key">Якщо будь-яка Task у <code>TaskGroup</code> завершується з exception (окрім <code>CancelledError</code>), усі sibling Tasks скасовуються, а всі exception агрегуються в <code>ExceptionGroup</code>, який піднімається при виході з context manager.</span> Нові Tasks після першого збою додати не можна. <code>KeyboardInterrupt</code> і <code>SystemExit</code> піднімаються одразу без агрегації. Якщо тіло <code>async with</code> саме кидає exception, воно теж включається до фінального <code>ExceptionGroup</code>.<div class="source">Джерело: <a href="https://docs.python.org/3.14/library/asyncio-task.html">Python 3.14: TaskGroup</a></div>	topic::16_asyncio type::Mechanism level::Middle scope::Core card::PYI_16_010 ref::TV_PYTHON_ASYNC_13 source::PythonDocs source::Community
Коли structured concurrency через <code>TaskGroup</code> дає надійнішу lifetime та failure semantics, ніж вільний набір <code>create_task()</code>?	<span class="key"><code>TaskGroup</code> гарантує, що при падінні будь-якого завдання всі sibling-завдання скасовуються, а exception збираються в <code>ExceptionGroup</code> — тоді як набір <code>create_task()</code> потребує ручного відстеження й може залишити завдання без нагляду.</span> При виході з <code>async with TaskGroup()</code> context manager неявно awaiting всі завдання; якщо одне з них впало з exception (не <code>CancelledError</code>), решта скасовуються, нові завдання не приймаються, і після завершення всіх — raises <code>ExceptionGroup</code>. Це усуває класичну помилку «забутого» task, який тихо fail-ить.<div class="source">Джерело: <a href="https://docs.python.org/3.14/library/asyncio-task.html">Python 3.14: asyncio TaskGroup</a></div>	topic::16_asyncio type::Contrast level::Senior scope::Core card::PYI_16_011 ref::TV_PYTHON_ASYNC_13 source::PythonDocs source::Community

Коли обрати <code>wait()</code>, а коли <code>as_completed()</code> для обробки набору concurrent operations?	<span class="key"><code>wait()</code> повертає два множества <code>(done, pending)</code> і підходить для контролю через <code>return_when</code>; <code>as_completed()</code> повертає ітератор результатів у порядку завершення — зручний для потокової обробки.</span> <code>wait()</code> не скасовує pending tasks при timeout і приймає лише Task/Future (не coroutine). <code>as_completed()</code> теж не скасовує tasks при зупинці ітерації, але дає результати одразу в порядку готовності, що краще для прогрес-барів або early-exit сценаріїв.<div class="source">Джерело: <a href="https://docs.python.org/3.14/library/asyncio-task.html">Python 3.14: asyncio.wait / as_completed</a></div>	topic::16_asyncio type::Contrast level::Middle scope::Core card::PYI_16_013 ref::TV_PYTHON_ASYNC_15 source::PythonDocs source::Community
