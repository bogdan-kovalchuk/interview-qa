Які значення отримує <code>__exit__</code> при нормальному завершенні та при exception усередині <code>with</code>?	<span class="key">При нормальному завершенні <code>__exit__</code> отримує <code>(None, None, None)</code>, а при exception — <code>(exc_type, exc_val, exc_tb)</code>: клас, екземпляр і traceback.</span> Якщо exception не стався, всі три аргументи дорівнюють <code>None</code>; якщо стався — вони відповідають <code>sys.exc_info()</code>. Що означає truthy return value з <code>__exit__</code> і чому випадкове <code>return True</code> небезпечне?	<span class="key">Truthy return з <code>__exit__</code> пригнічує exception — вона не поширюється далі за межі <code>with</code>.</span> <span class="warn">Випадкове <code>return True</code> ковтає будь-який exception, включно з <code>TypeError</code>, <code>KeyboardInterrupt</code> та помилками в самому cleanup-коді.</span> Це ускладнює діагностику: баг у тілі <code>with</code> стає невидимим. Зазвичай безпечніше повертати <code>False</code> або <code>None</code> і подавлювати лише очікувані типи через явну перевірку.<div class="source">Джерело: <a href="https://docs.python.org/3.14/reference/datamodel.html#with-statement-context-managers">Python 3.14: With Statement Context Managers</a></div>	topic::09_context_managers type::Trap level::Middle scope::Core card::PYI_09_002 ref::TV_PYTHON_NAMESPACE_AND_CONTEXT_MANAGER_01 source::PythonDocs source::Community
Як гарантувати cleanup у <code>__exit__</code>, не приховавши original exception новою помилкою cleanup-коду?	<span class="key">Cleanup-код у <code>__exit__</code> треба огортати у власний <code>try/except</code>, щоб exception під час cleanup не замінив оригінальний.</span> Якщо <code>__exit__</code> викликано з exception-аргументами і cleanup кидає нову помилку без обробки, Python втратить початкову exception. Безпечний патерн: огорнути <code>self.resource.close()</code> у <code>try/except Exception</code>, залогувати помилку cleanup і повернути <code>False</code>. Якщо оригінальної exception немає, помилка cleanup може вільно поширюватися.<div class="source">Джерело: <a href="https://docs.python.org/3.14/reference/datamodel.html#with-statement-context-managers">Python 3.14: With Statement Context Managers</a></div>	topic::09_context_managers type::Scenario level::Senior scope::Core card::PYI_09_003 ref::TV_PYTHON_NAMESPACE_AND_CONTEXT_MANAGER_01 source::PythonDocs source::Community
Чим class-based context manager відрізняється від generator-based manager через <code>@contextmanager</code>?	<span class="key">Class-based визначає <code>__enter__</code> і <code>__exit__</code> як окремі методи та легко зберігає стан у <code>self</code>; generator-based використовує одну функцію з <code>yield</code>, де код до yield — це enter, а після — exit.</span> <code>@contextmanager</code> скорочує boilerplate для простих менеджерів, але створює "one-shot" об'єкт — повторне використання того самого instance викличе <code>RuntimeError</code>. Class-based підхід кращий, коли потрібна reuse, reentrancy або складна ініціалізація.<div class="source">Джерело: <a href="https://docs.python.org/3.14/library/contextlib.html">Python 3.14: contextlib</a></div>	topic::09_context_managers type::Contrast level::Middle scope::Core card::PYI_09_004 ref::TV_PYTHON_NAMESPACE_AND_CONTEXT_MANAGER_01 source::PythonDocs source::Community
Чому generator, використаний з <code>@contextmanager</code>, повинен виконати рівно один <code>yield</code>?	<span class="key">Протокол <code>@contextmanager</code> відображає один <code>yield</code> на одну пару enter/exit; нуль або більше yield ламає цей контракт.</span> Якщо generator не виконує <code>yield</code> (наприклад, достроковий <code>return</code>), <code>@contextmanager</code> raise <code>RuntimeError: generator didn't yield</code>. Якщо виконує додатковий <code>yield</code> після першого — <code>RuntimeError: generator didn't stop</code>. Це гарантує, що enter і exit виконуються рівно один раз.<div class="source">Джерело: <a href="https://docs.python.org/3.14/library/contextlib.html">Python 3.14: contextlib</a></div>	topic::09_context_managers type::Trap level::Middle scope::Core card::PYI_09_005 ref::TV_PYTHON_NAMESPACE_AND_CONTEXT_MANAGER_01 source::PythonDocs source::Community
Коли <code>contextlib.ExitStack</code> кращий за статично вкладені <code>with</code> blocks?	<span class="key"><code>ExitStack</code> потрібен, коли кількість ресурсів або cleanup-дій визначається динамічно під час виконання.</span> Статичні вкладені <code>with</code> працюють, коли ресурси відомі наперед. <code>ExitStack</code> дозволяє реєструвати контекст-менеджери та довільні callback у циклі або умовно, з гарантованим LIFO cleanup. Також зручний для "all-or-nothing" acquisition: якщо один ресурс не відкрився, вже відкриті все одно закриються.<div class="source">Джерело: <a href="https://docs.python.org/3.14/library/contextlib.html">Python 3.14: contextlib</a></div>	topic::09_context_managers type::Scenario level::Middle scope::Core card::PYI_09_006 ref::TV_PYTHON_NAMESPACE_AND_CONTEXT_MANAGER_01 source::PythonDocs source::Community
Як <code>ExitStack</code> зберігає LIFO порядок cleanup і що має статися, якщо acquisition одного з ресурсів не вдалося?	<span class="key"><code>ExitStack</code> зберігає список callback у порядку реєстрації та викликає їх у зворотному порядку (LIFO), як вкладені <code>with</code>.</span> Якщо <code>enter_context()</code> для чергового ресурсу кидає exception, <code>ExitStack</code> все одно викликає <code>__exit__</code> для всіх раніше зареєстрованих менеджерів — вже набутих ресурсів. Це забезпечує коректний cleanup навіть при частковому failure.<div class="source">Джерело: <a href="https://docs.python.org/3.14/library/contextlib.html">Python 3.14: contextlib</a></div>	topic::09_context_managers type::Mechanism level::Senior scope::Core card::PYI_09_007 ref::TV_PYTHON_NAMESPACE_AND_CONTEXT_MANAGER_01 source::PythonDocs source::Community
Чим <code>async with</code> і methods <code>__aenter__</code>/<code>__aexit__</code> відрізняються від синхронного context-manager protocol?	<span class="key"><code>__aenter__</code> і <code>__aexit__</code> — це coroutine-методи: вони повертають awaitable, який event loop має await, тоді як синхронні <code>__enter__</code>/<code>__exit__</code> викликаються як звичайні функції.</span> <code>async with</code> можна використовувати лише всередині <code>async def</code>. Семантика suppression та сама: truthy return з <code>__aexit__</code> пригнічує exception. Async-варіант потрібен, коли enter/exit виконують I/O (мережеві з'єднання, пули БД, async-locks).<div class="source">Джерело: <a href="https://docs.python.org/3.14/reference/datamodel.html#asynchronous-context-managers">Python 3.14: Asynchronous Context Managers</a></div>	topic::09_context_managers type::Contrast level::Middle scope::Core card::PYI_09_008 ref::TV_PYTHON_NAMESPACE_AND_CONTEXT_MANAGER_01 source::PythonDocs source::Community
Як <code>__aexit__</code> має завершити cleanup після <code>CancelledError</code>, не поглинувши cancellation завдання?	<span class="key"><code>__aexit__</code> має виконати cleanup і потім або не перехоплювати <code>CancelledError</code>, або повторно її підняти, щоб cancellation дійшла до завдання.</span> <code>CancelledError</code> успадковує від <code>BaseException</code>, тому звичайний <code>except Exception</code> її не зловить. <span class="warn">Якщо код навмисно подавляє <code>CancelledError</code>, він зобов'язаний викликати <code>Task.uncancel()</code>, інакше structured concurrency (TaskGroup, timeout) працюватиме некоректно.</span> Загальне правило: cleanup → re-raise.<div class="source">Джерело: <a href="https://docs.python.org/3.14/library/asyncio-task.html#task-cancellation">Python 3.14: Task Cancellation</a></div>	topic::09_context_managers type::Scenario level::Senior scope::Core card::PYI_09_009 ref::OFFICIAL source::PythonDocs
Чим reusable context manager відрізняється від reentrant context manager?	<span class="key">Reusable можна використовувати в кількох окремих <code>with</code> blocks, але не можна вкладати всередину самого себе; reentrant можна і повторно використовувати, і вкладати рекурсивно.</span> Приклад reusable: <code>contextlib.ExitStack</code>, <code>threading.Lock</code> — новий <code>with</code> працює, але вкладений <code>with</code> на тому ж instance зламає стан. Приклад reentrant: <code>threading.RLock</code>, <code>contextlib.redirect_stdout</code> — вони коректно обробляють вкладеність, зберігаючи попередній стан у внутрішньому стеку.<div class="source">Джерело: <a href="https://docs.python.org/3.14/library/contextlib.html">Python 3.14: contextlib</a></div>	topic::09_context_managers type::Contrast level::Middle scope::Core card::PYI_09_010 ref::OFFICIAL source::PythonDocs
