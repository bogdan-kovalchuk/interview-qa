Що повертають оператори <code>and</code> та <code>or</code>: обов’язково <code>bool</code> чи один зі своїх operands, і як працює short-circuit evaluation?	<span class="key"><code>and</code> і <code>or</code> повертають один зі своїх operands, а не обов'язково <code>bool</code>.</span> <code>x and y</code> обчислює <code>x</code>: якщо <code>x</code> falsy — повертає його, інакше повертає <code>y</code>. <code>x or y</code> обчислює <code>x</code>: якщо <code>x</code> truthy — повертає його, інакше повертає <code>y</code>. Short-circuit означає, що другий operand не обчислюється, якщо результат уже визначений першим.<div class="source">Джерело: <a href="https://docs.python.org/3.14/reference/expressions.html#boolean-operations">Python 3.14: Boolean operations</a></div>	topic::02_syntax_control_flow type::Mechanism level::Middle scope::Core card::PYI_02_001 ref::TV_PYTHON_CODING_01 source::PythonDocs source::Community
Яке значення матиме вираз <code>[] or "fallback"</code>, і чому його результат не є <code>True</code> або <code>False</code>?	<span class="key">Результат — <code>'fallback'</code>, тому що <code>[]</code> є falsy і <code>or</code> повертає другий operand.</span> Оператор <code>or</code> не зводить результат до <code>bool</code>, а повертає сам об'єкт, який визначив результат. Чому конструкція <code>value = user_input or default</code> може помилково замінити коректне значення <code>0</code> або порожній рядок?	<span class="key"><code>or</code> повертає перший truthy operand, тому будь-яке falsy значення (<code>0</code>, <code>""</code>, <code>[]</code>, <code>None</code>) буде замінено на <code>default</code>.</span> Якщо <code>0</code> або <code>""</code> є валідними вхідними даними, ця конструкція не розрізняє «відсутнє значення» та «коректне falsy значення». Як extended iterable unpacking працює у присвоєнні <code>head, *middle, tail = items</code> і що станеться, якщо елементів недостатньо?	<span class="key"><code>*middle</code> збирає всі проміжні елементи у <code>list</code>; для успіху потрібно щонайменше 2 елементи (для <code>head</code> і <code>tail</code>).</span> Наприклад, <code>head, *middle, tail = [1, 2, 3, 4, 5]</code> дає <code>head=1, middle=[2, 3, 4], tail=5</code>. Як evaluation order впливає на результат chained assignment або unpacking, якщо правий вираз має side effects?	<span class="key">Права частина обчислюється першою, потім цілі зліва присвоюються зліва направо; тому side effects у правому виразі впливають на всі target.</span> Наприклад, при <code>i, x[i] = 1, 2</code> (де <code>i=0, x=[0,1]</code>) спочатку обчислюється кортеж <code>(1, 2)</code>, потім <code>i</code> стає <code>1</code>, і після цього <code>x[1]</code> (вже з новим <code>i</code>) стає <code>2</code> — результат <code>x == [0, 2]</code>.<div class="source">Джерело: <a href="https://docs.python.org/3.14/reference/expressions.html#evaluation-order">Python 3.14: Evaluation order</a></div>	topic::02_syntax_control_flow type::Mechanism level::Senior scope::Core card::PYI_02_006 ref::OFFICIAL source::PythonDocs version::Py3_14

Чим capture pattern у <code>match</code> відрізняється від value pattern і чому незакваліфіковане ім’я може несподівано зв’язати нову змінну?	<span class="key">Capture pattern (голе ім'я, напр. <code>case x:</code>) завжди успішний і прив'язує subject до нового імені; value pattern (кваліфіковане ім'я, напр. <code>case Color.RED:</code>) порівнює subject через <code>==</code> з відомим значенням.</span> Якщо ви очікували, що <code>case status:</code> порівняє з наявною змінною <code>status</code>, натомість створиться нова змінна <code>status</code>, що затінить попередню. Коли guard у <code>case ... if condition</code> обчислюється і чи скасовує невдалий guard bindings, створені самим pattern?	<span class="key">Guard обчислюється лише після успішного pattern; якщо guard хибний, case не обирається, але bindings з pattern НЕ гарантовано скасовуються.</span> Language Reference явно застерігає: «Do not rely on bindings being made for a failed match. Чому порядок <code>case</code> у structural pattern matching впливає на досяжність наступних patterns?	<span class="key">Case blocks у <code>match/case</code> перевіряються зверху вниз, і після першого успішного збігу виконується його блок, а решта case ігнорується.</span> Тому ширший pattern (наприклад, capture variable або wildcard <code>_</code>) перед вужчим робить останній недосяжним — він ніколи не отримає керування. Як chained comparison <code>a &lt; b &lt; c</code> відрізняється від <code>a &lt; b and b &lt; c</code> щодо кількості обчислень середнього operand?	<span class="key">У chained comparison <code>a &lt; b &lt; c</code> середній операнд <code>b</code> обчислюється лише один раз, тоді як у <code>a &lt; b and b &lt; c</code> — двічі (якщо <code>a &lt; b</code> істинне).</span> Обидва варіанти семантично еквівалентні за результатом і short-circuit поведінкою (якщо <code>a &lt; b</code> хибне, <code>c</code> не обчислюється в жодному випадку), але chained comparison уникає повторного обчислення <code>b</code>, що важливо, коли <code>b</code> — вираз із side effects або дорогим обчисленням.<div class="source">Джерело: <a href="https://docs.python.org/3.14/reference/expressions.html#comparisons">Python 3.14: Comparisons</a></div>	topic::02_syntax_control_flow type::Contrast level::Middle scope::Core card::PYI_02_014 ref::OFFICIAL source::PythonDocs
