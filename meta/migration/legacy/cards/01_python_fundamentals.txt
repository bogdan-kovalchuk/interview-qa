Які основні етапи проходить модуль Python від source code до виконання інструкцій runtime, і на якому етапі може з’явитися bytecode?	<span class="key">У CPython source code спочатку компілюється в code object із bytecode, а потім цей code object виконується інтерпретатором.</span> До створення code object код проходить parsing та побудову AST, тому bytecode з’являється на етапі компіляції ще до виконання. Чому поділ мов лише на «compiled» та «interpreted» некоректно описує Python?	<span class="key">Compilation та interpretation описують різні етапи виконання, тому не є взаємовиключними ярликами мови.</span> Наприклад, CPython компілює source code у bytecode, після чого інтерпретатор виконує цей bytecode. Отже, ці характеристики відповідають на різні запитання й можуть співіснувати.<div class="source">Джерело: <a href="https://docs.python.org/3.14/reference/datamodel.html#objects-values-and-types">Python 3.14: objects, values and types</a></div>	topic::01_python_fundamentals type::Contrast level::Middle scope::Core card::PYI_01_005 ref::TV_PYTHON_GENERAL_04 source::PythonDocs source::Community

Чим reflection відрізняється від звичайного доступу до заздалегідь відомого атрибута об’єкта?	<span class="key">За звичайного доступу ім’я атрибута зафіксоване в коді, а reflection визначає або досліджує структуру об’єкта під час runtime.</span> Наприклад, <code>obj.run</code> звертається до відомого атрибута, тоді як <code>getattr(obj, name)</code> обирає його за runtime string, а <code>inspect</code> може досліджувати live objects. Reflection використовує звичайний attribute protocol, а не обходить його.<div class="source">Джерела: <a href="https://docs.python.org/3.14/library/functions.html#getattr">Python 3.14: getattr()</a>; <a href="https://docs.python.org/3.14/library/inspect.html">Python 3.14: inspect</a></div>	topic::01_python_fundamentals type::Contrast level::Middle scope::Core card::PYI_01_009 ref::TV_PYTHON_GENERAL_09 source::PythonDocs source::Community
Коли monkey patching може бути виправданим і які ризики воно створює для локальності змін, тестів та оновлення залежностей?	<span class="key">Monkey patching виправданий переважно як короткоживуча, контрольована підміна в тесті або вузький compatibility workaround, коли dependency injection недоступний.</span> Він приховує залежності, змінює shared state, може зробити тести order-dependent і зламатися після оновлення dependency. Чому автоматичне завантаження plugin-класів через reflection може бути гіршим за явний registry, навіть якщо усуває ручну реєстрацію?	<span class="key">Автоматичне завантаження через reflection робить набір активних plugin-класів неявним, крихким до зміни імен і таким, що не має allowlist.</span> Reflection-сканування (динамічний <code>import</code> модулів пакета, пошук підкласів через <code>__subclasses__()</code> або <code>getattr</code>) залежить від конвенцій іменування, порядку import і може підхопити непередбачені класи — test doubles, deprecated aliases або сторонні типи. Явний registry (словник чи список) дає контрольований allowlist, зменшує import-time side effects і легко тестується, бо активний набір класів видно в коді, а не ховається за runtime-скануванням.<div class="source">Джерела: <a href="https://docs.python.org/3.14/reference/executionmodel.html">Python 3.14: Execution model</a>; <a href="https://docs.python.org/3.14/library/functions.html#getattr">Python 3.14: getattr()</a></div>	topic::01_python_fundamentals type::Scenario level::Senior scope::Core card::PYI_01_011 ref::TV_PYTHON_GENERAL_09 source::PythonDocs source::Community
Як executable nature інструкцій <code>def</code> і <code>class</code> впливає на умовне визначення, повторне визначення та import-time side effects?	<span class="key"><code>def</code> і <code>class</code> — виконувані інструкції (executable statements): вони створюють об'єкт функції або класу та прив'язують ім'я під час виконання, а не на етапі компіляції.</span> Тому їх можна розміщувати всередині <code>if</code>/<code>else</code>, циклів і вкладених scope — визначиться лише та гілка, яка справді виконається. Повторний <code>def</code> або <code>class</code> з тим самим ім'ям у тій самій області просто переприв'язує ім'я до нового об'єкта. Оскільки тіло модуля виконується згору вниз при import, будь-який код на рівні модуля (I/O, мережеві виклики, print) стає import-time side effect, що ускладнює тестування та повторне використання.<div class="source">Джерела: <a href="https://docs.python.org/3.14/reference/executionmodel.html">Python 3.14: Execution model</a>; <a href="https://docs.python.org/3.14/reference/datamodel.html#creating-class-objects">Python 3.14: Creating class objects</a></div>	topic::01_python_fundamentals type::Mechanism level::Senior scope::Core card::PYI_01_012 ref::OFFICIAL source::PythonDocs
