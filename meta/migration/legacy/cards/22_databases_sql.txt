Чому index може пришвидшити read query, але збільшити storage та write cost?	<span class="key">Індекс — це окрема структура даних (зазвичай B-дерево), що зберігає копії значень індексованих колонок разом із посиланнями на рядки таблиці.</span> При читанні індекс дозволяє знайти потрібні рядки за O(log n) замість повного сканування таблиці. Але кожен <code>INSERT</code>, <code>UPDATE</code> або <code>DELETE</code> мусить оновити всі відповідні індекси, що додає I/O та CPU. Крім того, індекси займають додаткове місце на диску пропорційно кількості індексованих колонок та рядків.<div class="source">Джерело: <a href="https://www.postgresql.org/docs/current/indexes.html">PostgreSQL: Indexes</a></div>	topic::22_databases_sql type::Contrast level::Middle scope::Overview card::PYI_22_001 ref::TV_INFRASTRUCTURE_DATABASE_10 source::OfficialDocs source::Community
Як запитом повернути всіх customers, включно з нулем paid orders, і де розмістити predicate, щоб не перетворити <code>LEFT JOIN</code> фактично на <code>INNER JOIN</code>?	<span class="key">Використовуйте <code>LEFT JOIN</code> від таблиці customers до orders, а фільтр по оплачених замовленнях (наприклад, <code>status = 'paid'</code>) розміщуйте в умові <code>ON</code>, а не в <code>WHERE</code>.</span> Умова в <code>ON</code> визначає, які рядки правої таблиці з'єднуються; якщо збігу немає, customers все одно повертається з <code>NULL</code> для orders. Якщо ж той самий фільтр помістити в <code>WHERE</code>, рядки з <code>NULL</code> (customers без paid orders) будуть відфільтровані, що фактично перетворить <code>LEFT JOIN</code> на <code>INNER JOIN</code>.<div class="source">Джерело: <a href="https://www.postgresql.org/docs/current/queries-table-expressions.html">PostgreSQL: Table Expressions</a></div>	topic::22_databases_sql type::Scenario level::Middle scope::Overview card::PYI_22_002 ref::TV_INFRASTRUCTURE_SQL_05 source::OfficialDocs source::Community
Після збою між debit і credit транзакція не має залишити partial transfer: яку ACID property це ілюструє і що application все ще має вирішити для retry?	<span class="key">Це властивість Atomicity (атомарність): транзакція виконується повністю або не виконується взагалі — у разі помилки відбувається відкат усіх змін.</span> Але application все одно має вирішити проблему retry: чи безпечно повторити операцію (ідемпотентність), як визначити, чи початкова транзакція закомітилася чи ні (наприклад, через network timeout), і як уникнути дублювання побічних ефектів (email, notification) при повторній спробі.<div class="source">Джерело: <a href="https://www.postgresql.org/docs/current/transaction-iso.html">PostgreSQL: Transaction Isolation</a></div>	topic::22_databases_sql type::Scenario level::Middle scope::Overview card::PYI_22_003 ref::TV_INFRASTRUCTURE_DATABASE_17 source::OfficialDocs source::Community
Як isolation level впливає на concurrent anomalies і чому stronger isolation може вимагати retry transaction?	<span class="key">Вищий isolation level запобігає більше аномалій: Read Committed допускає non-repeatable read і phantom read, Repeatable Read усуває їх через snapshot, а Serializable усуває всі аномалії включаючи serialization anomaly.</span> Але сильніша ізоляція означає більше конфліктів: у Repeatable Read при конкурентному оновленні того ж рядка транзакція отримує помилку <code>could not serialize access due to concurrent update</code>, а в Serializable — <code>SQLSTATE 40001</code> при виявленні read/write dependencies. Application мусить перехоплювати ці помилки і повторювати транзакцію спочатку.<div class="source">Джерело: <a href="https://www.postgresql.org/docs/current/transaction-iso.html">PostgreSQL: Transaction Isolation</a></div>	topic::22_databases_sql type::Mechanism level::Senior scope::Overview card::PYI_22_004 ref::TV_INFRASTRUCTURE_DATABASE_19 source::OfficialDocs source::Community
Як primary key, foreign key, unique та check constraints переносять data integrity з application code у schema?	<span class="key">Constraints декларують правила валідації безпосередньо в схемі БД, і СУБД застосовує їх автоматично при кожній операції <code>INSERT</code>/<code>UPDATE</code>/<code>DELETE</code>, незалежно від application code.</span> <code>PRIMARY KEY</code> гарантує унікальність та NOT NULL (створює unique B-tree індекс). <code>FOREIGN KEY</code> забезпечує referential integrity — значення має існувати в referenced таблиці. <code>UNIQUE</code> запобігає дублікатам. <code>CHECK</code> валідує довільну Boolean-умову (наприклад, <code>price &gt; 0</code>). Це означає, що навіть якщо application code має баг або обходить валідацію, БД не допустить некоректних даних.<div class="source">Джерело: <a href="https://www.postgresql.org/docs/current/ddl-constraints.html">PostgreSQL: Constraints</a></div>	topic::22_databases_sql type::Mechanism level::Middle scope::Overview card::PYI_22_005 ref::TV_INFRASTRUCTURE_SQL_03 source::OfficialDocs source::Community
Чому parameterized SQL query захищає від injection, а string formatting чи escaping вручну не є надійною заміною?	<span class="key">Parameterized query розділяє SQL-структуру та дані: драйвер БД надсилає запит із placeholder'ами, а значення передаються окремо, тому вони ніколи не інтерпретуються як SQL-код.</span> При string formatting або ручному escaping завжди існують edge cases: різні кодування (наприклад, Unicode normalization), екранування лапок у різних контекстах, або помилки в логіці escaping можуть дозволити зловмиснику вставити виконуваний SQL. <span class="warn">Ніколи не конкатенуйте user input у SQL-рядок — завжди використовуйте parameterized queries або ORM з автоматичним екрануванням.</span>	topic::22_databases_sql type::Trap level::Middle scope::Overview card::PYI_22_006 ref::TV_INFRASTRUCTURE_SQL_16 source::OfficialDocs source::Community
Коли keyset pagination з unique tie-breaker у <code>ORDER BY</code> краща за <code>OFFSET/LIMIT</code> за performance та stability при concurrent writes?	<span class="key">Keyset pagination стабільно швидша при великій глибині сторінок і гарантує відсутність дублікатів/пропусків при конкурентних змінах даних.</span> <code>OFFSET/LIMIT</code> мусить прочитати й відкинути всі попередні рядки, тому продуктивність падає лінійно зі збільшенням offset; крім того, якщо між запитами сторінок дані змінюються (insert/delete), можливі дублікати або пропуски. Keyset pagination використовує значення останнього елемента попередньої сторінки як курсор (<code>WHERE (created_at, id) &lt; (:last_created_at, :last_id)</code>), тому працює за O(log n) через індекс і не чутлива до зсувів. <span class="warn">Недолік: неможливо стрибнути на довільну сторінку (тільки next/prev).</span><div class="source">Джерело: <a href="https://www.postgresql.org/docs/current/indexes-ordering.html">PostgreSQL: Indexes and ORDER BY</a></div>	topic::22_databases_sql type::Scenario level::Middle scope::Overview card::PYI_22_007 ref::TV_INFRASTRUCTURE_SQL_21 source::OfficialDocs source::Community
