Які етапи проходить <code>import package.module</code> від пошуку специфікації до виконання module code?	<span class="key"><code>import package.module</code> проходить чотири етапи: перевірка <code>sys.modules</code>, пошук <code>ModuleSpec</code> через finders, створення module object і виконання коду модуля.</span> Спочатку import machinery шукає ім'я в <code>sys.modules</code>. Якщо його немає, мета-path finders з <code>sys.meta_path</code> викликають <code>find_spec()</code> для створення <code>ModuleSpec</code>. Потім створюється module object (через <code>create_module</code> або стандартний <code>ModuleType</code>), він додається в <code>sys.modules</code> до виконання коду, і нарешті loader викликає <code>exec_module()</code>, який виконує top-level код модуля в його глобальному namespace.<div class="source">Джерело: <a href="https://docs.python.org/3.14/reference/import.html">Python 3.14: The import system</a></div>	topic::11_modules_packages_imports type::Mechanism level::Middle scope::Core card::PYI_11_001 ref::TV_PYTHON_MODULES_AND_PACKAGES_05 source::PythonDocs source::Community runtime::CPython
Яку роль відіграє <code>sys.modules</code> під час повторного імпорту того самого module name?	<span class="key"><code>sys.modules</code> — це кеш, який зберігає вже завантажені module objects; повторний <code>import</code> того самого імені повертає кешований об'єкт без пошуку та виконання коду.</span> Якщо <code>sys.modules[name]</code> містить module object, import негайно повертає його. Якщо значення дорівнює <code>None</code>, виникає <code>ModuleNotFoundError</code>. Видалення ключа з <code>sys.modules</code> змушує наступний імпорт шукати та виконувати модуль заново, створюючи новий module object.<div class="source">Джерело: <a href="https://docs.python.org/3.14/reference/import.html">Python 3.14: The import system</a></div>	topic::11_modules_packages_imports type::Mechanism level::Middle scope::Core card::PYI_11_002 ref::TV_PYTHON_MODULES_AND_PACKAGES_05 source::PythonDocs source::Community
Чому два <code>import module</code> зазвичай не виконують top-level code модуля двічі, але можуть створити різні local bindings?	<span class="key">Top-level code виконується лише при першому імпорті; усі наступні <code>import</code> повертають той самий module object з <code>sys.modules</code>, але кожен import-statement створює власні local bindings у просторі імен імпортера.</span> Наприклад, <code>import math</code> зв'язує локальне ім'я <code>math</code> з module object, а <code>from math import pi</code> зв'язує локальне <code>pi</code> безпосередньо з об'єктом <code>pi</code>. Обидва варіанти посилаються на той самий module object, але local names у модулі-імпортері різні.<div class="source">Джерело: <a href="https://docs.python.org/3.14/reference/import.html">Python 3.14: The import system</a></div>	topic::11_modules_packages_imports type::Contrast level::Middle scope::Core card::PYI_11_003 ref::TV_PYTHON_MODULES_AND_PACKAGES_05 source::PythonDocs source::Community
Як порушення import protocol або ручне редагування <code>sys.modules</code> може призвести до двох module objects для одного source file?	<span class="key">Якщо завантажити той самий файл під різними qualified names (наприклад, через <code>SourceFileLoader</code> з різними іменами або додавши різні шляхи в <code>sys.path</code>), у <code>sys.modules</code> з'являться два окремі module objects для одного source file.</span> <span class="warn">Це небезпечно, коли модуль зберігає стан (singleton, кеш, реєстр): копія-«двійник» матиме власну незалежну копію стану, і <code>isinstance</code>-перевірки класів з такого модуля можуть давати хибний результат.</span> Стандартний import protocol запобігає цьому, використовуючи fully qualified name як ключ у <code>sys.modules</code>.<div class="source">Джерело: <a href="https://docs.python.org/3.14/reference/import.html">Python 3.14: The import system</a></div>	topic::11_modules_packages_imports type::Trap level::Senior scope::Core card::PYI_11_004 ref::TV_PYTHON_MODULES_AND_PACKAGES_05 source::PythonDocs source::Community runtime::CPython
У якому порядку Python шукає module через import machinery та <code>sys.path</code>?	<span class="key">Python спочатку перевіряє <code>sys.modules</code>, потім перебирає <code>sys.meta_path</code>, а якщо спрацьовує path-based finder — послідовно обходить записи <code>sys.path</code>.</span> У <code>sys.meta_path</code> за замовчуванням три meta path finders: для built-in модулів, frozen модулів і path-based імпорту. Path-based finder перебирає <code>sys.path</code>, який ініціалізується з директорії скрипта, змінної <code>PYTHONPATH</code> та стандартних шляхів встановлення. Результати пошуку path entry finder кешуються в <code>sys.path_importer_cache</code>.<div class="source">Джерело: <a href="https://docs.python.org/3.14/reference/import.html">Python 3.14: The import system</a></div>	topic::11_modules_packages_imports type::Mechanism level::Middle scope::Core card::PYI_11_005 ref::TV_PYTHON_MODULES_AND_PACKAGES_03 source::PythonDocs source::Community
Коли absolute import доречніший за explicit relative import усередині package?	<span class="key">Absolute import (<code>from package.module import name</code>) доречніший, коли важлива читабельність, стійкість до рефакторингу та можливість запуску модуля як скрипта.</span> Absolute imports працюють незалежно від того, як модуль було запущено — імпортом чи <code>python -m</code>. Relative imports (<code>from .module import name</code>) компактніші всередині великого пакета, але крихкі: при переміщенні файлу в інший пакет усі крапки потрібно перераховувати, а запуск модуля як скрипта стає неможливим без <code>-m</code>.<div class="source">Джерело: <a href="https://docs.python.org/3.14/reference/import.html">Python 3.14: The import system</a></div>	topic::11_modules_packages_imports type::Scenario level::Middle scope::Core card::PYI_11_006 ref::TV_PYTHON_MODULES_AND_PACKAGES_07 source::PythonDocs source::Community
Чому relative import може не спрацювати під час запуску package module як звичайного script file?	<span class="key">При запуску <code>python package/module.py</code> модуль отримує <code>__name__ = '__main__'</code> і порожній (або <code>None</code>) <code>__package__</code>, тому relative import не має контексту пакета й викликає <code>ImportError</code>.</span> Relative import вимагає непорожнього <code>__package__</code>, який import machinery встановлює лише для модулів, завантажених як частина пакета. Правильний спосіб запуску — <code>python -m package.module</code>, за якого <code>__package__</code> встановлюється автоматично.<div class="source">Джерело: <a href="https://docs.python.org/3.14/reference/import.html">Python 3.14: The import system</a></div>	topic::11_modules_packages_imports type::Trap level::Senior scope::Core card::PYI_11_007 ref::TV_PYTHON_MODULES_AND_PACKAGES_02 source::PythonDocs source::Community runtime::CPython
Що означає partially initialized module під час circular import і чому не всі його names уже доступні?	<span class="key">Partially initialized module — це module object, який уже доданий у <code>sys.modules</code>, але його <code>exec_module()</code> ще не завершився, тому доступні лише ті names, що були визначені до точки циклічного імпорту.</span> Import machinery вставляє модуль у <code>sys.modules</code> до виконання коду, щоб запобігти нескінченній рекурсії. Якщо модуль A імпортує B, а B знову імпортує A, другий імпорт A повертає об'єкт, у якому визначені лише інструкції, що виконалися до рядка <code>import B</code>. Звернення до ще не визначених names викликає <code>ImportError</code> або <code>AttributeError</code>.<div class="source">Джерело: <a href="https://docs.python.org/3.14/reference/import.html">Python 3.14: The import system</a></div>	topic::11_modules_packages_imports type::Mechanism level::Middle scope::Core card::PYI_11_008 ref::TV_PYTHON_MODULES_AND_PACKAGES_06 source::PythonDocs source::Community
Модулі <code>orders</code> і <code>payments</code> імпортують один одного заради спільного protocol: який dependency-direction refactoring усуне cycle краще за local import?	<span class="key">Винести спільний protocol (або abstract base class) у третій модуль — наприклад, <code>interfaces.py</code> — щоб <code>orders</code> і <code>payments</code> залежали від нього, а не один від одного.</span> Такий підхід перетворює циклічну залежність на ієрархію: <code>interfaces</code> не знає про <code>orders</code> і <code>payments</code>, а обидва модулі імпортують <code>interfaces</code>. Це усуває cycle на рівні архітектури, на відміну від local (відкладеного) імпорту всередині функції, який лише маскування проблему й ускладнює тестування.<div class="source">Джерело: <a href="https://docs.python.org/3.14/reference/import.html">Python 3.14: The import system</a></div>	topic::11_modules_packages_imports type::Scenario level::Senior scope::Core card::PYI_11_009 ref::TV_PYTHON_MODULES_AND_PACKAGES_06 source::PythonDocs source::Community
Чим regular package з <code>__init__.py</code> відрізняється від namespace package?	<span class="key">Regular package містить файл <code>__init__.py</code>, який виконується при імпорті, і має єдиний <code>__path__</code>; namespace package не має <code>__init__.py</code> і може об'єднувати підмодулі з кількох каталогів.</span> Regular package походить з одного каталогу, а його <code>__path__</code> вказує на цей каталог. Namespace package (PEP 420, Python 3.3+) складається з «порцій» — кількох каталогів з однаковим ім'ям пакета, — а його <code>__path__</code> є динамічним ітератором, який шукає підмодулі в усіх порціях. <code>ModuleSpec.origin</code> namespace package дорівнює <code>None</code>.<div class="source">Джерело: <a href="https://docs.python.org/3.14/reference/import.html">Python 3.14: The import system</a></div>	topic::11_modules_packages_imports type::Contrast level::Middle scope::Core card::PYI_11_010 ref::TV_PYTHON_MODULES_AND_PACKAGES_04 source::PythonDocs source::Community
Які завдання доречно виконувати в package <code>__init__.py</code>, а які створюють небажані import-time side effects?	<span class="key">У <code>__init__.py</code> доречно розміщувати lightweight ініціалізацію пакета: експорт публічного API через <code>__all__</code>, convenience re-exports (<code>from .sub import Class</code>) та конфігурацію, яка не вимагає I/O.</span> Небажані import-time side effects — це heavy обчислення, мережеві виклики, запис у файли або зміна глобального стану: вони виконуються при кожному <code>import</code> пакета, уповільнюють запуск і створюють приховані залежності від порядку ініціалізації.<div class="source">Джерела: <a href="https://docs.python.org/3.14/reference/import.html#importing-packages">Python 3.14: Import system – packages</a>; <a href="https://github.com/tavor118/pj_python_interview_questions_and_answers/blob/02d57a7a9f34fd386eb8aa5c0094fe3f3c3ba141/docs/python/modules_and_packages.md">Tavor: modules and packages</a></div>	topic::11_modules_packages_imports type::Scenario level::Middle scope::Core card::PYI_11_011 ref::TV_PYTHON_MODULES_AND_PACKAGES_04 source::PythonDocs source::Community
Що саме захищає <code>if __name__ == "__main__"</code> і чого він не змінює в import semantics?	<span class="key"><code>if __name__ == "__main__"</code> захищає код від виконання під час імпорту: коли модуль запускають як скрипт, <code>__name__</code> дорівнює <code>"__main__"</code>, а при звичайному import — своїй dotted name.</span> Цей guard не змінює import semantics: модуль все одно завантажується в <code>sys.modules</code>, а якщо той самий файл запустити як скрипт і потім імпортувати, CPython створить два різні module objects (<code>__main__</code> та import name) з окремими namespace.<div class="source">Джерело: <a href="https://docs.python.org/3.14/reference/import.html#main-spec">Python 3.14: Import system – __main__</a></div>	topic::11_modules_packages_imports type::Mechanism level::Middle scope::Core card::PYI_11_012 ref::TV_PYTHON_MODULES_AND_PACKAGES_02 source::PythonDocs source::Community runtime::CPython
Чому <code>importlib.reload(module)</code> не оновлює автоматично всі раніше створені instances та names, імпортовані через <code>from ... import ...</code>?	<span class="key"><code>importlib.reload()</code> перезапускає код модуля в тому самому module object, але не оновлює назв, скопійованих через <code>from ... import ...</code> в інші модулі, і не змінює класи вже створених instance'ів.</span> Причина: <code>from ... import ...</code> копіює посилання на об'єкт у namespace importing-модуля — reload не модифікує чужі namespace. Клас-об'єкт у reload-модулі стає новим, але існуючі instance'и продовжують посилатися на старий class object. Крім того, якщо нова версія модуля не визначає якесь ім'я, його стара дефініція залишається в module dict.<div class="source">Джерело: <a href="https://docs.python.org/3.14/library/importlib.html#importlib.reload">Python 3.14: importlib.reload()</a></div>	topic::11_modules_packages_imports type::Trap level::Senior scope::Core card::PYI_11_013 ref::TV_PYTHON_MODULES_AND_PACKAGES_05 source::PythonDocs source::Community
Чим import package/module відрізняється від installable distribution project з build metadata?	<span class="key">Import package/module — це runtime-концепція: директорія з <code>__init__.py</code> або окремий <code>.py</code>-файл, який import system знаходить і завантажує.</span> Distribution project — це packaging-концепція: source tree з <code>pyproject.toml</code>, який визначає build metadata (name, version, dependencies) і описує, як build backend створює installable archive (wheel/sdist).
