Яку boundary має unit test і чому він не повинен непомітно перетворюватися на integration test?	<span class="key">Unit test перевіряє один модуль (функцію, метод, клас) ізольовано, підміняючи всі зовнішні залежності test doubles.</span> Якщо такий тест починає звертатися до реальної БД, мережі чи годинника, він втрачає головні переваги unit-рівня: миттєвий feedback, локалізацію помилки в одному модулі та відсутність flakiness. <span class="warn">Непомітна підміна doubles на реальні залежності перетворює unit test на integration test, який повільніший, крихкіший і дає хибне відчуття покриття.</span><div class="source">Джерела: <a href="https://docs.python.org/3.14/library/unittest.html">Python 3.14: unittest</a>; <a href="https://docs.pytest.org/en/stable/">pytest</a></div>	topic::18_testing type::Contrast level::Middle scope::Core card::PYI_18_001 ref::TV_COMPUTER_SCIENCE_TESTING_02 source::PythonDocs source::Community
Які контракти між components перевіряє integration test?	<span class="key">Integration test перевіряє контракти взаємодії між компонентами: формати серіалізації, схеми БД, протоколи API та порядок викликів.</span> Він не дублює перевірку внутрішньої логіки кожного компонента — це роблять unit-тести. Як збалансувати unit, integration та end-to-end tests за feedback speed, fidelity і maintenance cost?	<span class="key">Баланс визначається test pyramid: багато швидких unit-тестів, помірна кількість integration і мінімум e2e-тестів.</span> Unit-тести дають найшвидший feedback (мілісекунди) і найменший maintenance cost, але нижчу fidelity щодо реальної системи. Integration-тести дорожчі та повільніші, проте перевіряють реальні контракти між компонентами. E2e-тести мають найвищу fidelity, але найповільніші, найкрихкіші та найдорожчі. <span class="warn">Інверсія піраміди (багато e2e, мало unit) призводить до повільного CI та flaky-тестів.</span> Ризик-орієнтований підхід: критичні шляхи (payment, auth) потребують більше integration/e2e, тоді як бізнес-логіка покривається unit-тестами.<div class="source">Джерела: <a href="https://docs.python.org/3.14/library/unittest.html">Python 3.14: unittest</a>; <a href="https://docs.pytest.org/en/stable/">pytest</a></div>	topic::18_testing type::Scenario level::Senior scope::Core card::PYI_18_003 ref::TV_COMPUTER_SCIENCE_TESTING_01 source::PythonDocs source::Community
Які seams потрібні, щоб тест не залежав від реальної мережі, clock та external service?	<span class="key">Для мережі — mock HTTP-клієнта через <code>unittest.mock.patch</code> або fixture, що блокує реальні запити; для clock — <code>freezegun</code> або injectable time-provider; для external service — fake, stub або record-replay (<code>vcrpy</code>, <code>respx</code>).</span> Кожна зовнішня залежність має бути замінена контрольованим test double, щоб тест давав детермінований результат незалежно від оточення. <span class="warn">Без цих seams тести стають flaky: мережевий таймаут, зміна часу чи недоступність сервісу ламає CI.</span><div class="source">Джерела: <a href="https://docs.python.org/3.14/library/unittest.mock.html">Python 3.14: unittest.mock</a>; <a href="https://docs.pytest.org/en/stable/">pytest</a></div>	topic::18_testing type::Scenario level::Middle scope::Core card::PYI_18_004 ref::TV_COMPUTER_SCIENCE_TESTING_13 source::PythonDocs source::Community
Чому dependency injection часто робить Python code простішим для deterministic testing?	<span class="key">Dependency injection (DI) робить залежності явними параметрами, а не прихованими внутрішніми об'єктами, тому тест може передати fake/mock замість реального сервісу без <code>patch</code>.</span> Наприклад, функція, що приймає <code>http_client</code> та <code>clock</code> як аргументи, у тесті отримує <code>StubClient</code> і <code>FrozenClock</code> — жодної мережі, жодного реального часу. DI також полегшує refactor, бо залежність видно з сигнатури.<div class="source">Джерела: <a href="https://docs.python.org/3.14/library/unittest.mock.html">Python 3.14: unittest.mock</a>; <a href="https://docs.pytest.org/en/stable/">pytest</a></div>	topic::18_testing type::Mechanism level::Middle scope::Core card::PYI_18_005 ref::TV_COMPUTER_SCIENCE_TESTING_13 source::PythonDocs source::Community
Як відтворити timeout та retry behavior без flaky dependence від реального external service?	<span class="key">Mock HTTP-клієнта з <code>side_effect</code> імітує послідовність помилок і успіх, а тест перевіряє кількість викликів і backoff-логіку без реальної мережі.</span> <pre class="code-block"><code>client_mock = Mock(side_effect=[TimeoutError, TimeoutError, ok_response])<br>result = fetch_with_retry(client_mock, retries=3)<br>assert client_mock.call_count == 3</code></pre>DI підставляє mock замість реального клієнта; <code>side_effect</code> як iterable відтворює сценарій "два таймаути → успіх" детерміновано. <span class="warn">Реальні sleep у retry-логіці варто підмінювати на injectable delay-функцію, інакше тест стане повільним.</span><div class="source">Джерела: <a href="https://docs.python.org/3.14/library/unittest.mock.html">Python 3.14: unittest.mock</a>; <a href="https://docs.pytest.org/en/stable/">pytest</a></div>	topic::18_testing type::Scenario level::Senior scope::Core card::PYI_18_006 ref::TV_COMPUTER_SCIENCE_TESTING_13 source::PythonDocs source::Community
Як fixture lifecycle допомагає задати setup, yield resource і guaranteed teardown?	<span class="key">Fixture виконує код до <code>yield</code> як setup, передає ресурс тесту через значення <code>yield</code>, а код після <code>yield</code> — guaranteed teardown, який pytest виконує навіть якщо тест впав.</span> <pre class="code-block"><code>@pytest.fixture<br>def db_conn():<br>    conn = create_connection()  # setup<br>    yield conn                  # ресурс для тесту<br>    conn.close()                # teardown</code></pre>Scope визначає час життя: <code>function</code> (default) — новий ресурс на кожен тест, <code>module</code>/<code>session</code> — спільний ресурс, що зменшує overhead, але вимагає обережності з mutable state.<div class="source">Джерела: <a href="https://docs.pytest.org/en/stable/how-to/fixtures.html">pytest: fixtures</a>; <a href="https://docs.python.org/3.14/library/unittest.html">Python 3.14: unittest</a></div>	topic::18_testing type::Mechanism level::Middle scope::Core card::PYI_18_007 ref::TV_PYTHON_PYTHON_PACKAGES_06 source::PythonDocs source::Community
Коли parametrization краща за копіювання одного test body для кількох cases?	<span class="key">Parametrization краща, коли тестова логіка ідентична, а відрізняються лише вхідні дані та очікуваний результат.</span> <code>@pytest.mark.parametrize</code> генерує окремий test item для кожного набору з інформативним ID у звіті (наприклад, <code>test_parse[empty_input]</code>), що полегшує локалізацію. Копіювання body дублює логіку, ускладнює maintenance і не дає окремих test IDs. <span class="warn">Якщо тестова логіка різна для різних cases — копіювання (або окремі тест-функції) чесніше, бо parametrization змушує підганяти body під спільний знаменник.</span><div class="source">Джерела: <a href="https://docs.pytest.org/en/stable/how-to/parametrize.html">pytest: parametrize</a>; <a href="https://docs.python.org/3.14/library/unittest.html">Python 3.14: unittest</a></div>	topic::18_testing type::Scenario level::Middle scope::Core card::PYI_18_008 ref::TV_PYTHON_PYTHON_PACKAGES_06 source::PythonDocs source::Community
Як broad-scoped mutable fixture може створити order-dependent tests і state leakage?	<span class="key">Fixture з <code>scope="module"</code> або <code>scope="session"</code>, що повертає mutable об'єкт (dict, list, DB connection), створює один спільний екземпляр для всіх тестів у scope — і якщо один тест модифікує цей об'єкт, наступні тести отримують забруднений state.</span> <pre class="code-block"><code>@pytest.fixture(scope="module")<br>def shared_cache():<br>    return {}  # один dict на весь module<br><br>def test_a(shared_cache):<br>    shared_cache["key"] = "value"<br><br>def test_b(shared_cache):<br>    assert "key" not in shared_cache  # FAIL: state leakage</code></pre>Це створює order-dependent tests: результат залежить від порядку виконання. Рішення: <code>function</code> scope для mutable fixtures, immutable factory-функція, або явний reset у teardown.<div class="source">Джерела: <a href="https://docs.pytest.org/en/stable/how-to/fixtures.html">pytest: fixtures</a></div>	topic::18_testing type::Trap level::Senior scope::Core card::PYI_18_009 ref::TV_PYTHON_PYTHON_PACKAGES_06 source::PythonDocs source::Community
Для repository, який має поводитися як real in-memory storage, коли обрати Fake, а коли Stub чи interaction-verifying Mock?	<span class="key">Fake — спрощена, але робоча реалізація контракту (in-memory dict замість БД); Stub — пасивний об'єкт із фіксованими відповідями; Mock — записує виклики для interaction verification.</span> Для repository, що має поводитися як real storage, потрібен Fake, бо він реалізує повний контракт: <code>save</code>/<code>get</code>/<code>delete</code>/<code>find</code> з реальною логікою зберігання. Stub підходить, коли потрібна лише одна фіксована відповідь (<code>Mock(return_value=[user])</code>), але не підтримує довільні query. Interaction-verifying Mock (<code>mock.assert_called_with(...)</code>) доречний, коли важливий протокол викликів, а не стан сховища. <span class="warn">Fake має проходити ті самі interface-тести, що й реальна імплементація, інакше розбіжність поведінки залишиться непоміченою.</span><div class="source">Джерела: <a href="https://docs.python.org/3.14/library/unittest.mock.html">Python 3.14: unittest.mock</a>; <a href="https://docs.pytest.org/en/stable/">pytest</a></div>	topic::18_testing type::Scenario level::Middle scope::Core card::PYI_18_010 ref::TV_COMPUTER_SCIENCE_TESTING_10 source::PythonDocs source::Community
Чому під час <code>patch()</code> треба замінювати name там, де його lookup робить code under test?	<span class="key"><code>patch()</code> змінює об'єкт, на який посилається ім'я в конкретному namespace, тому патчити треба те місце, звідки code under test це ім'я бере.</span> Якщо модуль <code>b</code> робить <code>from a import SomeClass</code>, то <code>b</code> вже має власне посилання на клас, і <code>patch('a.SomeClass')</code> не вплине на код у <code>b</code>. Як over-mocking implementation details робить test suite крихкою під час behavior-preserving refactoring?	<span class="key">Якщо тест перевіряє кількість і порядок викликів внутрішніх mock-об'єктів замість спостережуваного результату, будь-який behavior-preserving рефакторинг ламає тест.</span> Наприклад, заміна послідовних викликів на один batch-запит зберігає результат, але <code>assert_called_with</code> на старому mock перестане проходити. Коли використати <code>AsyncMock</code> і що в такому тесті треба перевіряти окрім call arguments?	<span class="key"><code>AsyncMock</code> потрібен для підміни async-функцій, бо повертає awaitable і коректно працює з <code>await</code>; окрім аргументів треба перевіряти, що mock було саме await-нуто.</span> <code>AsyncMock</code> надає <code>assert_awaited()</code>, <code>assert_awaited_with()</code>, <code>await_count</code> та <code>await_args_list</code>. Як заміна real clock на injected clock або frozen time робить timeout і expiry tests детермінованими?	<span class="key">Замість <code>time.sleep()</code> і реального очікування тест керує абстракцією годинника, тому timeout, TTL та expiry перевіряються миттєво й без flakiness.</span> Код приймає clock-об'єкт (або використовується <code>freezegun</code> / <code>time_machine</code> для замороження <code>datetime.now()</code>), і тест переводить час на потрібну точку. Як відрізнити flaky test від product race та як зберегти evidence для відтворення?	<span class="key">Flaky test — тест, що іноді проходить, іноді ні без змін коду; product race — реальна конкуренція в застосунку. Різниця в тому, що flaky test відтворюється в ізоляції, а product race — лише за певного timing.</span> Для діагностики запускають тест багато разів в ізоляції (<code>pytest --count</code> або цикл), фіксують seed, timestamp, порядок виконання та логи. Якщо тест падає тільки в suite — це interaction/ordering issue; якщо й в ізоляції — треба шукати race у продукті або недетермізм у тесті.<div class="source">Джерело: <a href="https://docs.pytest.org/en/stable/">pytest</a></div>	topic::18_testing type::Scenario level::Senior scope::Core card::PYI_18_018 ref::TV_COMPUTER_SCIENCE_TESTING_01 source::PythonDocs source::Community
