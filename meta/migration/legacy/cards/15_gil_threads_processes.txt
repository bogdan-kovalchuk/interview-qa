Чим thread відрізняється від process за address space, resource sharing та failure isolation?	<span class="key">Thread виконується всередині батьківського process і має той самий address space; process має власний ізольований address space.</span> Threads спільно використовують heap, модулі, відкриті file descriptors, тоді як кожен process отримує власну копію пам'яті та потребує IPC (pickle через <code>Queue</code>/<code>Pipe</code>, shared memory через <code>Value</code>/<code>Array</code>). Які дані threads в одному process спільно бачать і які мають окремо?	<span class="key">Threads спільно бачать усі heap-об'єкти (global-змінні, модульний стан, мутабельні контейнери) та відкриті file descriptors, але кожен thread має власний стек викликів, локальні змінні та регістри.</span> Для ізольованого стану використовується <code>threading.local()</code> — значення прив'язані до конкретного thread і не видимі іншим. Як process isolation змінює модель обміну даними та обробку worker crash порівняно з threads?	<span class="key">Process isolation вимагає серіалізації даних (pickle) для IPC, але забезпечує ізоляцію crash — падіння worker не завершує батьківський process.</span> Обмін даними відбувається через <code>Queue</code>/<code>Pipe</code> (pickle), <code>Value</code>/<code>Array</code> (shared memory для C-типів) або <code>Manager</code> (proxy-об'єкти через серверний process). У threads обмін безкоштовний (спільна пам'ять), але необроблений exception у thread завершує весь process. Trade-off: ізоляція та безпека process проти накладних витрат на серіалізацію та додаткову пам'ять.<div class="source">Джерело: <a href="https://docs.python.org/3.14/library/multiprocessing.html">Python 3.14: multiprocessing</a></div>	topic::15_gil_threads_processes type::Contrast level::Senior scope::Core card::PYI_15_003 ref::TV_PYTHON_GIL_THREADS_PROCESSES_02 source::PythonDocs source::Community
Що саме серіалізує GIL у звичайній GIL-enabled build CPython?	<span class="key">GIL серіалізує виконання Python bytecode — лише один thread одночасно виконує bytecode інтерпретатора.</span> Це захищає внутрішні структури CPython (reference counts, стан об'єктів) від одночасного доступу з кількох threads. <span class="warn">GIL не серіалізує application-логіку:</span> між будь-якими двома bytecode-інструкціями GIL може бути передано іншому thread, тому складені операції не є атомарними на рівні Python-коду.<div class="source">Джерела: <a href="https://docs.python.org/3.14/library/threading.html">Python 3.14: threading</a>; <a href="https://docs.python.org/3.14/howto/free-threading-python.html">Python 3.14: free-threading</a></div>	topic::15_gil_threads_processes type::Mechanism level::Middle scope::Core card::PYI_15_004 ref::TV_PYTHON_GIL_THREADS_PROCESSES_08 source::PythonDocs source::Community runtime::CPython gil::Enabled
Чому I/O-bound threads можуть давати concurrency benefit в GIL-enabled CPython?	<span class="key">CPython звільняє GIL на час блокуючих I/O-операцій (системні виклики, мережа, файлові операції), дозволяючи іншим threads виконувати bytecode.</span> Поки один thread чекає на відповідь від мережі або диска, інший thread може захопити GIL і виконувати обчислення. Чому GIL не усуває race conditions у Python application code?	<span class="key">GIL гарантує атомарність окремої bytecode-інструкції, але складені операції (read-modify-write) складаються з кількох bytecode і можуть бути перервані між інструкціями.</span> Наприклад, <code>x += 1</code> компілюється в три bytecode: <code>LOAD x</code>, <code>ADD 1</code>, <code>STORE x</code> — між ними GIL може бути передано іншому thread. Чому спостережена atomicity окремої built-in operation у поточній CPython не є стабільним synchronization contract?	<span class="key">Атомарність окремих built-in операцій (наприклад, <code>list.append()</code>) — це деталь реалізації CPython, а не гарантія мови.</span> Ця поведінка може змінитися між версіями CPython, відрізнятися в інших реалізаціях (PyPy, GraalPy) або бути відсутньою у free-threaded build. <span class="warn">Application code ніколи не повинен покладатися на спостережену атомарність</span> — завжди використовуйте явні примітиви синхронізації (<code>Lock</code>, <code>RLock</code>) для захисту shared mutable state.<div class="source">Джерела: <a href="https://docs.python.org/3.14/library/threading.html">Python 3.14: threading</a>; <a href="https://docs.python.org/3.14/howto/free-threading-python.html">Python 3.14: free-threading</a></div>	topic::15_gil_threads_processes type::Trap level::Senior scope::Core card::PYI_15_007 ref::TV_PYTHON_GIL_THREADS_PROCESSES_08 source::PythonDocs source::Community runtime::CPython gil::Enabled
Що означає free-threaded build CPython 3.14 і як він співіснує з GIL-enabled build?	<span class="key">Free-threaded build — це окрема конфігурація CPython (з Python 3.13) з вимкненим GIL, що дозволяє threads виконуватися справжньою паралельністю на кількох CPU cores.</span> Це не runtime-перемикач, а окремий білд (configure <code>--disable-gil</code>). Визначається через <code>sys._is_gil_enabled()</code> (повертає <code>False</code>) або рядок "free-threading build" у <code>sys.version</code>. Які thread-safety assumptions про shared mutable objects треба переглянути під час переходу на free-threaded CPython?	<span class="key">У free-threaded build кілька threads одночасно виконують bytecode, тому всі access до shared mutable state потребує явної синхронізації — внутрішні блокування built-in типів є implementation detail, а не API-контрактом.</span> Ітератори спільних колекцій не thread-safe (можливі пропущені або дубльовані елементи). Коли <code>ThreadPoolExecutor</code> є доречним вибором для I/O-bound workload?	<span class="key"><code>ThreadPoolExecutor</code> доречний, коли задача проводить більшу частину часу в очікуванні зовнішніх відповідей (мережа, диск, БД), а не в обчисленнях.</span> У GIL-enabled CPython threads можуть паралельно чекати I/O, бо GIL звільняється під час системних викликів. Що таке race condition на read-modify-write sequence і чому потрібен synchronization primitive?	<span class="key">Race condition виникає, коли кілька потоків виконують read-modify-write для спільного ресурсу без синхронізації, і результат залежить від порядку interleaving операцій.</span> Наприклад, <code>counter += 1</code> — це три операції: читання, інкремент, запис. Якщо два потоки одночасно читають однакове значення, один інкремент буде втрачено. Навіть у CPython з GIL bytecode-інструкції можуть перериватися між операціями, тому потрібен <code>Lock</code> або інший synchronization primitive для атомарності на рівні додатку.<div class="source">Джерело: <a href="https://docs.python.org/3.14/library/threading.html">Python 3.14: threading</a></div>	topic::15_gil_threads_processes type::Mechanism level::Middle scope::Core card::PYI_15_014 ref::TV_PYTHON_GIL_THREADS_PROCESSES_07 source::PythonDocs source::Community runtime::CPython
Чим <code>Lock</code>, <code>RLock</code>, <code>Semaphore</code> та <code>Condition</code> відрізняються за synchronization intent?	<span class="key"><code>Lock</code> — взаємовиключення (один потік у критичній секції); <code>RLock</code> — reentrant lock, той самий потік може захоплювати повторно; <code>Semaphore</code> — лічильник, що обмежує кількість одночасних входів; <code>Condition</code> — очікування зміни стану з notify/notify_all.</span> <code>Lock</code> може звільнити будь-який потік; <code>RLock</code> — лише owning thread із відповідною кількістю <code>release()</code>. <code>Semaphore</code> підходить для пулів ресурсів (наприклад, connection pool). <code>Condition</code> потрібен для producer-consumer патернів, де один потік чекає сигналу від іншого.<div class="source">Джерело: <a href="https://docs.python.org/3.14/library/threading.html">Python 3.14: threading</a></div>	topic::15_gil_threads_processes type::Contrast level::Middle scope::Core card::PYI_15_015 ref::TV_PYTHON_GIL_THREADS_PROCESSES_04 source::PythonDocs source::Community
Які умови створюють deadlock і як lock ordering зменшує ризик?	<span class="key">Deadlock виникає, коли два або більше потоків блокуються назавжди, кожен чекаючи ресурс, утримуваний іншим; класична умова — циклічне очікування locks у різному порядку.</span> Якщо потінок A захоплює Lock1 і чекає Lock2, а потінок B захоплює Lock2 і чекає Lock1 — жоден не продовжить роботу. Lock ordering зменшує ризик: якщо всі потоки захоплюють locks у єдиному глобальному порядку (наприклад, завжди спочатку Lock1, потім Lock2), цикл неможливий.
