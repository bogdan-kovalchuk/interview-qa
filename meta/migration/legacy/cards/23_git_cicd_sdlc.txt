Чим merge commit відрізняється від rebase за history shape та commit identities?	<span class="key"><code>git merge</code> зберігає розгалужену топологію історії та оригінальні SHA комітів обох гілок, тоді як <code>git rebase</code> переписує коміти з новими SHA, роблячи історію лінійною.</span> Merge commit має два parent commits і фіксує момент злиття, не змінюючи жодного попереднього коміту. Rebase натомість послідовно застосовує коміти на новий base (подібно до cherry-pick), тому навіть ідентичний за змістом коміт отримує новий хеш через зміну parent.<div class="source">Джерела: <a href="https://git-scm.com/docs/git-merge">git-merge</a>; <a href="https://git-scm.com/docs/git-rebase">git-rebase</a></div>	topic::23_git_cicd_sdlc type::Contrast level::Middle scope::Overview card::PYI_23_001 ref::TV_DEVELOPMENT_GIT_05 source::OfficialDocs source::Community
Коли rebase local unpublished branch доречний, а коли він небезпечно переписує shared history?	<span class="key"><code>git rebase</code> доречний для локальної гілки, яку ще не push-нули у спільний репозиторій; він небезпечний для опублікованої гілки, бо переписує SHA і ламає історію колег.</span> Локально rebase дозволяє очистити історію від зайвих merge-комітів і зробити її лінійною перед створенням PR. Якщо ж гілку вже push-нули, rebase змінює хеші комітів, і будь-який колега, що витягнув старі SHA, отримає конфлікти та дублікати комітів при наступному pull.<div class="source">Джерело: <a href="https://git-scm.com/docs/git-rebase">git-rebase</a></div>	topic::23_git_cicd_sdlc type::Scenario level::Middle scope::Overview card::PYI_23_002 ref::TV_DEVELOPMENT_GIT_04 source::OfficialDocs source::Community
Коли для undo в shared history обрати <code>git revert</code>, коли <code>git reset</code> допустимий для unpublished commits і як reflog допомагає відновити lost local tip?	<span class="key"><code>git revert</code> — для скасування комітів у shared history (створює новий commit із протилежними змінами); <code>git reset</code> допустимий лише для ще не push-нутих комітів; <code>git reflog</code> зберігає всі попередні позиції <code>HEAD</code> і дозволяє знайти SHA втраченого коміту.</span> Revert не переписує існуючу історію, тому безпечний для push. Reset переміщує вказівник гілки назад — <code>--hard</code> додатково очищає index і working tree. Якщо reset видалив потрібний коміт з гілки, <code>git reflog</code> показує, де був <code>HEAD</code> раніше (наприклад, <code>HEAD@{2}</code>), і коміт можна відновити через <code>git reset</code> або <code>git cherry-pick</code> на цей SHA, поки reflog не протерміновано (типово 30–90 днів).<div class="source">Джерела: <a href="https://git-scm.com/docs/git-revert">git-revert</a>; <a href="https://git-scm.com/docs/git-reset">git-reset</a>; <a href="https://git-scm.com/docs/git-reflog">git-reflog</a></div>	topic::23_git_cicd_sdlc type::Scenario level::Middle scope::Overview card::PYI_23_003 ref::OFFICIAL source::OfficialDocs
Зміна торкається payment calculation: який мінімальний required CI gate з unit, integration та static checks слід обрати за failure risks?	<span class="key">Для payment calculation мінімальний CI gate — unit-тести на граничні значення та формати валют, інтеграційні тести з реальною БД або її емуляцією, і статичні перевірки (linter + type checker).</span> Помилка в обчисленнях має високий failure risk (фінансові збитки, некоректні транзакції), тому пропускати будь-який рівень перевірок неприпустимо. Unit-тести покривають формули та edge cases, інтеграційні — взаємодію з БД та зовнішніми сервісами, а static checks ловлять помилки типів і невикористані змінні до запуску тестів. Merge дозволено лише після повного «зеленого» pipeline.<div class="source">Джерело: <a href="https://docs.github.com/en/actions/get-started/continuous-integration">GitHub Actions: Continuous Integration</a></div>	topic::23_git_cicd_sdlc type::Scenario level::Middle scope::Overview card::PYI_23_004 ref::TV_DEVELOPMENT_CI_CD_01 source::OfficialDocs source::Community
Коли обрати rolling, blue-green чи canary deployment за blast radius, traffic control і rollback speed?	<span class="key">Rolling — поступове оновлення інстансів без даунтайму, простий але повільний rollback; blue-green — два повних середовища з миттєвим rollback через перемикання трафіку; canary — найменший blast radius через прогресивне нарощування частки трафіку на нову версію.</span> Rolling підходить для звичайних релізів, коли потрібна простота і нульовий даунтайм. Blue-green — коли критична швидкість rollback (перемикання load balancer за секунди) і є ресурси на повне дублювання середовища. Canary — для ризикових змін (наприклад, payment logic), де потрібно спочатку перевірити нову версію на малій частці користувачів і лише потім нарощувати трафік.<div class="source">Джерело: <a href="https://docs.cloud.google.com/deploy/docs/deployment-strategies">Google Cloud Deploy: Deployment Strategies</a></div>	topic::23_git_cicd_sdlc type::Scenario level::Middle scope::Overview card::PYI_23_005 ref::TV_DEVELOPMENT_CI_CD_02 source::OfficialDocs source::Community
Як CI run на кожен pull request скорочує feedback loop і зменшує integration risk порівняно з рідкими manual integrations?	<span class="key">Автоматичний CI run на кожен PR миттєво повідомляє розробника про помилки, поки обсяг змін малий і їх легко локалізувати, тоді як рідкі manual integrations накопичують несумісні зміни від кількох розробників.</span> Кожен PR запускає linters, unit- та integration-тести, тому дефект виявляється в межах однієї невеликої зміни — дебаг швидкий. При рідкій інтеграції конфлікти та помилки сумісності накопичуються тижнями, і їх усунення вимагає значно більше часу. Merge дозволено лише після проходження всіх CI-перевірок.<div class="source">Джерело: <a href="https://docs.github.com/en/actions/get-started/continuous-integration">GitHub Actions: Continuous Integration</a></div>	topic::23_git_cicd_sdlc type::Mechanism level::Middle scope::Overview card::PYI_23_006 ref::TV_DEVELOPMENT_CI_CD_01 source::OfficialDocs source::Community
Коли reviewer має схвалити неідеальну зміну, яка покращує overall code health, а коли defect risk або новий technical debt вимагає доопрацювання?	<span class="key">Reviewer має схвалити зміну, якщо вона беззаперечно покращує загальний стан кодової бази, навіть якщо не ідеальна; відмовити — якщо зміна погіршує code health, додає небажану функціональність або створює критичний technical debt.</span> Незначні зауваження (стилістика, освітні поради) варто позначати префіксом «Nit:» і не блокувати через них merge. Натомість порушення style guide, некоректний дизайн або неконсистентність із кодовою базою вимагають доопрацювання. Баланс: не перешкоджати прогресу заради дрібниць, але й не накопичувати борг, який згодом змусить переписувати зміну.<div class="source">Джерело: <a href="https://google.github.io/eng-practices/review/reviewer/standard.html">Google Engineering Practices: How to do a code review</a></div>	topic::23_git_cicd_sdlc type::Scenario level::Senior scope::Overview card::PYI_23_007 ref::OFFICIAL source::OfficialDocs
