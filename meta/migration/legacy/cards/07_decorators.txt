Коли обчислюється decorator expression і коли викликається wrapper, який decorator повернув?	<span class="key">Decorator expression обчислюється один раз під час визначення функції, а wrapper викликається при кожному виклику декорованої функції.</span> Тобто <code>@dec</code> виконує <code>dec(func)</code> immediately в scope, де визначена функція, і повертає wrapper-об'єкт. Сам wrapper запускається лише тоді, коли хтось викликає декороване ім'я. Це означає, що важка логіка ініціалізації (наприклад, відкриття файлу) потрапляє в decoration time, а per-call логіка — у wrapper.<div class="source">Джерело: <a href="https://docs.python.org/3.14/reference/compound_stmts.html#function-definitions">Python 3.14: function definitions</a></div>	topic::07_decorators type::Mechanism level::Middle scope::Core card::PYI_07_001 ref::TV_PYTHON_DECORATORS_01 source::PythonDocs source::Community
У якому порядку застосовуються два decorators <code>@outer</code> і <code>@inner</code>, записані над однією функцією?	<span class="key">Decorators застосовуються знизу вгору: спочатку <code>@inner</code>, потім <code>@outer</code>, тобто еквівалент <code>func = outer(inner(func))</code>.</span> Кожний наступний decorator отримує результат попереднього.<pre class="code-block"><code>def outer(func):<br>    print('outer applied')<br>    return func<br><br>def inner(func):<br>    print('inner applied')<br>    return func<br><br>@outer<br>@inner<br>def hello(): pass</code></pre>Вивід при визначенні: <code>inner applied</code>, потім <code>outer applied</code>.<div class="source">Джерело: <a href="https://docs.python.org/3.14/reference/compound_stmts.html#function-definitions">Python 3.14: function definitions</a></div>	topic::07_decorators type::Code level::Middle scope::Core card::PYI_07_002 ref::TV_PYTHON_DECORATORS_01 source::PythonDocs source::Community
Які проблеми з metadata, introspection і debugging виникають, якщо wrapper не використовує <code>functools.wraps</code>?	<span class="key">Без <code>functools.wraps</code> декорована функція втрачає <code>__name__</code>, <code>__doc__</code>, <code>__qualname__</code> та <code>__annotations__</code> — замість них підставляються атрибути wrapper-функції.</span> Наприклад, <code>example.__name__</code> стане <code>'wrapper'</code>, а <code>__doc__</code> — <code>None</code>. Це ламає <code>help()</code>, stack traces показують неправильне ім'я, а інструменти на кшталт Sphinx генерують хибну документацію. Рішення — викликати <code>@functools.wraps(func)</code> на wrapper.<div class="source">Джерело: <a href="https://docs.python.org/3.14/library/functools.html#functools.wraps">Python 3.14: functools.wraps</a></div>	topic::07_decorators type::Trap level::Middle scope::Core card::PYI_07_003 ref::TV_PYTHON_DECORATORS_07 source::PythonDocs source::Community
Чого <code>functools.wraps</code> не гарантує щодо фактичної call signature wrapper-функції?	<span class="key"><code>functools.wraps</code> копіює лише metadata-атрибути (<code>__name__</code>, <code>__doc__</code>, <code>__qualname__</code>, <code>__annotations__</code>, <code>__type_params__</code>) і встановлює <code>__wrapped__</code>, але не змінює реальні параметри wrapper-функції.</span> Wrapper залишається функцією з <code>(*args, **kwargs)</code>. <code>inspect.signature()</code> за замовчуванням переходить за <code>__wrapped__</code> і показує оригінальну сигнатуру, але фактичний callable приймає будь-які аргументи — тому помилки невідповідності параметрів виникають лише всередині wrapper-а або в обгорнутій функції.<div class="source">Джерело: <a href="https://docs.python.org/3.14/library/functools.html#functools.wraps">Python 3.14: functools.wraps</a></div>	topic::07_decorators type::Mechanism level::Senior scope::Core card::PYI_07_004 ref::TV_PYTHON_DECORATORS_07 source::PythonDocs source::Community
Чим decorator factory відрізняється від самого decorator і на якому етапі обробляються її arguments?	<span class="key">Decorator factory — це функція, що повертає decorator; її аргументи обчислюються один раз при decoration, а повернутий decorator потім застосовується до функції.</span> Наприклад, <code>@has_perm('view')</code> спочатку викликає <code>has_perm('view')</code> (factory), яка повертає справжній decorator, і вже він отримує декоровану функцію. Без factory синтаксис <code>@decorator(arg)</code> неможливий, бо decorator приймає лише один аргумент — callable.<div class="source">Джерело: <a href="https://docs.python.org/3.14/reference/compound_stmts.html#function-definitions">Python 3.14: function definitions</a></div>	topic::07_decorators type::Contrast level::Middle scope::Core card::PYI_07_005 ref::TV_PYTHON_DECORATORS_05 source::PythonDocs source::Community
Як спроєктувати decorator з двома чіткими call forms, <code>@trace</code> і <code>@trace(level=2)</code>, не переплутавши decorated callable з configuration arguments?	<span class="key">Треба перевірити, чи перший аргумент є callable: якщо <code>func is not None</code> — це bare <code>@trace</code>, інакше повернути partial-декоратор з конфігурацією.</span> Типовий патерн: outer-функція приймає <code>func=None, *, level=1</code>. Якщо <code>func</code> — callable, застосувати wrapper одразу; якщо <code>None</code> — повернути decorator, який замкне <code>level</code>. Альтернатива — <code>functools.partial</code> або окремий factory. Головне — не намагатися відрізнити callable від конфігурації за типом аргументу, бо callable може бути будь-яким об'єктом з <code>__call__</code>.<div class="source">Джерело: <a href="https://docs.python.org/3.14/reference/compound_stmts.html#function-definitions">Python 3.14: function definitions</a></div>	topic::07_decorators type::Scenario level::Senior scope::Core card::PYI_07_006 ref::TV_PYTHON_DECORATORS_06 source::PythonDocs source::Community
Коли callable class є кращою реалізацією stateful decorator за closure?	<span class="key">Callable class краща, коли стан потрібно явно ініціалізувати, скидати, серіалізувати або коли логіка досить складна для кількох методів.</span> Closure зручна для простого лічильника, але callable class дає: (1) явний <code>__init__</code> з валідацією параметрів, (2) доступ до стану через атрибути для тестування та reset, (3) можливість реалізувати <code>__repr__</code> для debugging. Closure ж не дозволяє легко розділити конфігурацію від runtime-стану без додаткових trickів.<div class="source">Джерело: <a href="https://docs.python.org/3.14/glossary.html#term-decorator">Python 3.14: decorator glossary</a></div>	topic::07_decorators type::Scenario level::Middle scope::Core card::PYI_07_007 ref::TV_PYTHON_DECORATORS_02 source::PythonDocs source::Community
Чим class decorator відрізняється від metaclass за моментом і областю впливу на class object?	<span class="key">Class decorator отримує вже повністю побудований class object і може його модифікувати або замінити; metaclass контролює сам процес створення class через <code>__new__</code>, отримуючи name, bases та namespace до існування об'єкта.</span> Class decorator застосовується після виконання body класу — він post-factum змінює атрибути. Metaclass визначає, як class будується (наприклад, автоматична реєстрація, валідація полів). Class decorator простіший і локальніший; metaclass — потужніший, але впливає на всю ієрархію наслідування.<div class="source">Джерела: <a href="https://docs.python.org/3.14/reference/compound_stmts.html#function-definitions">Python 3.14: function definitions</a>; <a href="https://docs.python.org/3.14/glossary.html#term-decorator">Python 3.14: decorator glossary</a></div>	topic::07_decorators type::Contrast level::Senior scope::Core card::PYI_07_008 ref::TV_PYTHON_DECORATORS_02 source::PythonDocs source::Community
Як порядок stacking decorators впливає на authorization, caching і logging, якщо кожен wrapper може не викликати наступний?	<span class="key">Порядок визначає, який wrapper виконується першим (зовнішній = верхній decorator), і якщо він не викличе наступний — внутрішні decorator-и пропускаються.</span> Для authorization + caching + logging: authorization має бути найзовнішнішим, щоб відхилити запит до caching/logging. Якщо logging стоїть зовні authorization, то навіть відхилені запити логуються. Якщо caching зовні authorization — кешований результат може обійти перевірку прав. <span class="warn">Кожен wrapper, що не викликає <code>func(*args, **kwargs)</code>, фактично блокує весь ланцюжок нижче.</span><div class="source">Джерело: <a href="https://docs.python.org/3.14/reference/compound_stmts.html#function-definitions">Python 3.14: function definitions</a></div>	topic::07_decorators type::Scenario level::Middle scope::Core card::PYI_07_009 ref::TV_PYTHON_DECORATORS_01 source::PythonDocs source::Community
Чому state у closure decorator може створити race condition при паралельних викликах обгорнутої функції?	<span class="key">Closure зберігає спільний mutable state в enclosing scope, і всі потоки, що викликають декоровану функцію, звертаються до однієї й тієї ж змінної без синхронізації.</span> У CPython з GIL прості операції типу <code>x += 1</code> для integer атомарні на рівні bytecode, але складніші патерни (check-then-act, оновлення dict/list з умовами) не є атомарними навіть з GIL. У free-threaded CPython (3.13+) навіть прості операції не захищені GIL, тому closure-state потребує явного lock (наприклад, <code>threading.Lock</code>) або immutable state.<div class="source">Джерело: <a href="https://docs.python.org/3.14/glossary.html#term-decorator">Python 3.14: decorator glossary</a></div>	topic::07_decorators type::Trap level::Senior scope::Core card::PYI_07_010 ref::TV_PYTHON_DECORATORS_02 source::PythonDocs source::Community runtime::CPython
Як decorator для <code>async def</code> має зберегти awaitability та коректне поширення exceptions?	<span class="key">Wrapper має бути оголошений через <code>async def</code> і використовувати <code>await</code> для виклику оригінальної корутини — це зберігає awaitability та природне поширення exceptions.</span> Якщо wrapper написати як звичайну <code>def</code>, виклик decorated функції поверне обгортку з не-awaited coroutine object замість реального результату, а <code>inspect.iscoroutinefunction()</code> для такої функції покаже <code>False</code>. Для підтримки синхронних і асинхронних функцій одним декоратором перевіряють тип через <code>inspect.iscoroutinefunction()</code> і диспатчать на <code>async def wrapper</code> або <code>def wrapper</code> відповідно, застосовуючи <code>@functools.wraps(func)</code> для збереження метаданих. Exceptions з оригінальної корутини поширюються через <code>await</code> природним чином — caller отримає той самий тип exception без додаткового оброблення.<div class="source">Джерела: <a href="https://docs.python.org/3.14/reference/compound_stmts.html#function-definitions">Python 3.14: Function definitions</a>; <a href="https://docs.python.org/3.14/library/functools.html#functools.wraps">Python 3.14: functools.wraps</a></div>	topic::07_decorators type::Mechanism level::Senior scope::Core card::PYI_07_011 ref::TV_PYTHON_DECORATORS_08 source::PythonDocs source::Community
Що станеться з decorated name, якщо decorator поверне <code>None</code> замість callable?	<span class="key">Ім'я decorated функції буде зв'язане з <code>None</code>, і будь-який її виклик підніме <code>TypeError: 'NoneType' object is not callable</code>.</span> Синтаксис <code>@decorator</code> еквівалентний <code>func = decorator(func)</code>: що повернув декоратор, те й стане новим значенням імені.
