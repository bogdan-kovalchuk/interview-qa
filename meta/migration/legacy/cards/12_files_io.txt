Яка межа між <code>str</code> та <code>bytes</code> в text I/O і де мають відбуватися encoding та decoding?	<span class="key">Text I/O працює з <code>str</code>, binary I/O — з <code>bytes</code>; кодування (encoding) відбувається при записі <code>str</code> → <code>bytes</code>, а декодування (decoding) — при читанні <code>bytes</code> → <code>str</code>.</span> У CPython шар <code>TextIOWrapper</code> розташований поверх буферизованого бінарного потоку: при <code>write()</code> він кодує текст у байти й передає їх нижче, при <code>read()</code> — декодує прочитані байти назад у <code>str</code>. Бінарний шар (<code>BufferedWriter</code>/<code>BufferedReader</code>) не виконує ні кодування, ні трансляції newlines.<div class="source">Джерело: <a href="https://docs.python.org/3.14/library/io.html">Python 3.14: io — Text I/O vs Binary I/O</a></div>	topic::12_files_io type::Mechanism level::Middle scope::Core card::PYI_12_001 ref::TV_PYTHON_FILES_AND_IO_03 source::PythonDocs source::Community runtime::CPython

Чим <code>flush()</code> Python stream відрізняється від <code>os.fsync()</code> і чому жоден із них не слід описувати як універсальну hardware-durability guarantee?	<span class="key"><code>flush()</code> виштовхує дані з внутрішнього буфера Python у буфер ОС, а <code>os.fsync(fd)</code> змушує ОС записати дані на фізичний носій.</span> Проте навіть <code>os.fsync()</code> не гарантує повної hardware-durability: диск-кеш контролера, RAID-буфер або файловий system journal можуть затримати фізичний запис. Як <code>seek()</code> і <code>tell()</code> використовуються для random access і чому offsets text streams не завжди можна трактувати як character positions?	<span class="key">У binary mode <code>seek()</code> і <code>tell()</code> працюють із byte offsets; у text mode <code>tell()</code> повертає «opaque cookie», а <code>seek()</code> підтримує лише <code>seek(0)</code> і відновлення з <code>tell()</code>.</span> У text mode з кодуванням на кшталт UTF-8 один символ може займати 1–4 байти, тому позиція в байтах не збігається з позицією в символах. CPython використовує внутрішній алгоритм для відновлення позиції, тому довільні числові offset у text mode не підтримуються і можуть дати undefined behavior.<div class="source">Джерело: <a href="https://docs.python.org/3.14/library/io.html">Python 3.14: io — TextIOBase.seek()</a></div>	topic::12_files_io type::Mechanism level::Middle scope::Core card::PYI_12_008 ref::TV_PYTHON_FILES_AND_IO_06 source::PythonDocs source::Community runtime::CPython

Чому string-prefix check не визначає path containment за наявності <code>..</code> і як <code>Path.resolve()</code> змінює lexical path перед порівнянням?	<span class="key">Рядковий <code>startswith()</code> не враховує <code>..</code> та symlinks: шлях <code>/data/public/../secret</code> лексично починається з <code>/data/public</code>, але фактично вказує на <code>/data/secret</code>.</span> <code>Path.resolve()</code> робить шлях абсолютним, розгортає всі symlinks та усуває <code>..</code> через реальну структуру файлової системи. Як задати custom JSON encoding для непідтримуваного type, не втрачаючи явного wire schema?	<span class="key">Передати <code>default</code>-функцію (або підкласити <code>json.JSONEncoder</code>) для кодування, і <code>object_hook</code> — для декодування, використовуючи dict із маркерним ключем як wire-схему.</span> Наприклад, <code>complex</code> можна зберігати як <code>{"__complex__": true, "real": …, "imag": …}</code>. Чому JSON round trip не зберігає автоматично всі Python types та object identities?	<span class="key">JSON визначає лише сім type-ів (object, array, string, number, true, false, null), тому більшість Python-типів при серіалізації втрачаються або перетворюються.</span> Ключі dict стають <code>str</code> (навіть якщо були <code>int</code> або <code>tuple</code>), <code>tuple</code> перетворюється на <code>list</code>, <code>set</code> і custom класи взагалі не підтримуються без <code>default</code>. Object identity (<code>is</code>) не зберігається, бо JSON не має концепції посилань — кожен декодований об'єкт є новою інстанцією, а циклічні структури викликають <code>RecursionError</code> ще на кодуванні.<div class="source">Джерело: <a href="https://docs.python.org/3.14/library/json.html">Python 3.14: json</a></div>	topic::12_files_io type::Trap level::Senior scope::Core card::PYI_12_012 ref::TV_PYTHON_FILES_AND_IO_12 source::PythonDocs source::Community

Коли обрати <code>StringIO</code>, а коли <code>BytesIO</code> для in-memory stream?	<span class="key"><code>StringIO</code> — коли дані типу <code>str</code> (текст), <code>BytesIO</code> — коли <code>bytes</code> або <code>bytearray</code> (бінарні дані).</span> <code>StringIO</code> наслідує <code>io.TextIOBase</code> і підтримує newline-translation через параметр <code>newline</code>. <code>BytesIO</code> наслідує <code>io.BufferedIOBase</code>, не виконує жодного кодування/декодування та надає <code>getbuffer()</code> для zero-copy доступу до буфера. Якщо API очікує текстовий stream — <code>StringIO</code>, якщо бінарний (зображення, серіалізовані дані, мережеві пакети) — <code>BytesIO</code>.<div class="source">Джерело: <a href="https://docs.python.org/3.14/library/io.html">Python 3.14: io</a></div>	topic::12_files_io type::Contrast level::Middle scope::Core card::PYI_12_014 ref::TV_PYTHON_FILES_AND_IO_07 source::PythonDocs source::Community
