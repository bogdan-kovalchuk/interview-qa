Чому <code>except Exception</code> зазвичай безпечніший за bare <code>except</code> для application-level обробки?	<span class="key">Bare <code>except</code> перехоплює всі <code>BaseException</code>, включно з <code>SystemExit</code> і <code>KeyboardInterrupt</code>, тоді як <code>except Exception</code> пропускає ці signal-винятки.</span> Класи <code>SystemExit</code>, <code>KeyboardInterrupt</code> і <code>GeneratorExit</code> успадковуються безпосередньо від <code>BaseException</code>, а не від <code>Exception</code>. Тому <code>except Exception</code> дозволяє процесу завершитися через <code>sys.exit()</code> або реакцією на Ctrl-C, що критично для graceful shutdown.<div class="source">Джерела: <a href="https://docs.python.org/3.14/library/exceptions.html">Python 3.14: Built-in Exceptions</a>; <a href="https://docs.python.org/3.14/tutorial/errors.html">Python 3.14: Errors and Exceptions</a></div>	topic::10_exceptions type::Scenario level::Middle scope::Core card::PYI_10_001 ref::TV_PYTHON_EXCEPTIONS_01 source::PythonDocs source::Community
Як порядок кількох <code>except</code> clauses впливає на досяжність handlers для subclass exceptions?	<span class="key">Python перевіряє <code>except</code> clauses зверху вниз і спрацьовує перший збіг; якщо parent class стоїть перед child, handler для child стає недосяжним.</span> Наприклад, <code>except Exception</code> перед <code>except ValueError</code> перехопить <code>ValueError</code> першим, і другий clause ніколи не виконається — interpreter видасть <code>SyntaxWarning</code> або <code>SyntaxError</code> для таких dead-code handlers. Правильний порядок: від найвужчих (subclass) до найширших (parent).<div class="source">Джерело: <a href="https://docs.python.org/3.14/tutorial/errors.html">Python 3.14: Errors and Exceptions</a></div>	topic::10_exceptions type::Mechanism level::Middle scope::Core card::PYI_10_002 ref::TV_PYTHON_EXCEPTIONS_02 source::PythonDocs source::Community
Коли перехоплення <code>BaseException</code> може зламати graceful shutdown або cancellation semantics?	<span class="key"><code>except BaseException</code> перехоплює <code>SystemExit</code>, <code>KeyboardInterrupt</code> і <code>GeneratorExit</code>, що блокує штатне завершення процесу, зупинку через Ctrl-C та закриття генераторів.</span> <span class="warn">Якщо такий handler не re-raise-ить виняток, інтерпретатор не вийде через <code>sys.exit()</code>, а генератор не зможе звільнити ресурси при <code>.close()</code>.</span> Виправдано лише на найвищому рівні application loop з явним re-raise або логуванням перед виходом.<div class="source">Джерела: <a href="https://docs.python.org/3.14/library/exceptions.html">Python 3.14: Built-in Exceptions</a>; <a href="https://docs.python.org/3.14/reference/compound_stmts.html#the-try-statement">Python 3.14: The try statement</a></div>	topic::10_exceptions type::Trap level::Senior scope::Core card::PYI_10_003 ref::TV_PYTHON_EXCEPTIONS_14 source::PythonDocs source::Community
Коли виконується <code>else</code> у конструкції <code>try/except/else/finally</code> і навіщо виносити туди success-path code?	<span class="key"><code>else</code> виконується лише тоді, коли <code>try</code> завершився без exception і без <code>return</code>/<code>break</code>/<code>continue</code>.</span> Винесення success-path code в <code>else</code> запобігає випадковому перехопленню exceptions, які не стосуються ризикованої операції в <code>try</code>: якщо код у <code>else</code> кине виняток, його не оброблять попередні <code>except</code> clauses, а <code>finally</code> все одно виконається для cleanup.<div class="source">Джерело: <a href="https://docs.python.org/3.14/reference/compound_stmts.html#the-try-statement">Python 3.14: The try statement</a></div>	topic::10_exceptions type::Mechanism level::Middle scope::Core card::PYI_10_004 ref::TV_PYTHON_EXCEPTIONS_10 source::PythonDocs source::Community

Як exception у <code>finally</code> може замаскувати original exception і як зберегти діагностичний контекст?	<span class="key">Якщо <code>finally</code> кидає новий exception, він стає зовнішнім, а оригінальний exception зберігається лише як <code>__context__</code> — traceback показує переважно новий.</span> <span class="warn">Оригінальна причина може загубитися при логуванні, якщо не перевірити <code>__context__</code>.</span> Щоб зберегти контекст, у <code>finally</code> слід обгорнути cleanup у внутрішній <code>try/except</code>, залогувати помилку cleanup і дати оригінальному exception поширюватися, або використати <code>raise ... from</code> для явного chaining.<div class="source">Джерело: <a href="https://docs.python.org/3.14/reference/compound_stmts.html#the-try-statement">Python 3.14: The try statement</a></div>	topic::10_exceptions type::Trap level::Senior scope::Core card::PYI_10_006 ref::TV_PYTHON_EXCEPTIONS_06 source::PythonDocs source::Community
Чим implicit exception chaining відрізняється від явного <code>raise NewError(...) from original</code>?	<span class="key">Implicit chaining автоматично встановлює <code>__context__</code>, коли exception виникає всередині <code>except</code>-блоку; явний <code>from</code> встановлює <code>__cause__</code> і демонструє прямий причинний зв'язок.</span> Implicit показується як «During handling of the above exception, another exception occurred», а явний — як «The above exception was the direct cause of the following exception». Встановлення <code>__cause__</code> автоматично ставить <code>__suppress_context__ = True</code>, тому traceback показує <code>__cause__</code>, а не <code>__context__</code>.<div class="source">Джерела: <a href="https://docs.python.org/3.14/library/exceptions.html">Python 3.14: Built-in Exceptions</a>; <a href="https://docs.python.org/3.14/tutorial/errors.html">Python 3.14: Errors and Exceptions</a></div>	topic::10_exceptions type::Contrast level::Middle scope::Core card::PYI_10_007 ref::TV_PYTHON_EXCEPTIONS_08 source::PythonDocs source::Community
Коли використовують bare <code>raise</code> усередині handler і чому <code>raise exc</code> може змінити traceback presentation?	<span class="key">Bare <code>raise</code> всередині <code>except</code> повторно кидає той самий exception object без зміни traceback; <code>raise exc</code> додає поточний frame до traceback.</span> Bare <code>raise</code> зберігає оригінальний traceback, що важливо для діагностики. <code>raise exc</code> (навіть того самого об'єкта) інтерпретується як новий raise і додає frame поточної позиції, що може заплутати при аналізі стеку викликів.<div class="source">Джерела: <a href="https://docs.python.org/3.14/tutorial/errors.html">Python 3.14: Errors and Exceptions</a>; <a href="https://docs.python.org/3.14/reference/compound_stmts.html#the-try-statement">Python 3.14: The try statement</a></div>	topic::10_exceptions type::Mechanism level::Middle scope::Core card::PYI_10_008 ref::TV_PYTHON_EXCEPTIONS_05 source::PythonDocs source::Community
Як <code>raise ... from None</code> впливає на відображення exception context і коли це виправдано?	<span class="key"><code>raise NewError(...) from None</code> встановлює <code>__cause__ = None</code> і <code>__suppress_context__ = True</code>, тому traceback приховує implicit <code>__context__</code>.</span> Оригінальний exception залишається доступним через атрибут <code>__context__</code>, але не відображається. Виправдано, коли внутрішній exception є деталлю реалізації і не несе корисної інформації для користувача бібліотеки — наприклад, при трансформації низькорівневого exception у зрозумілий API-level exception.<div class="source">Джерела: <a href="https://docs.python.org/3.14/library/exceptions.html">Python 3.14: Built-in Exceptions</a>; <a href="https://docs.python.org/3.14/tutorial/errors.html">Python 3.14: Errors and Exceptions</a></div>	topic::10_exceptions type::Scenario level::Senior scope::Core card::PYI_10_009 ref::TV_PYTHON_EXCEPTIONS_08 source::PythonDocs source::Community
Які властивості роблять custom exception hierarchy стабільною частиною library API?	<span class="key">Базовий клас, що успадковується від <code>Exception</code>, з ієрархією підкласів для різних категорій помилок, і достатньо специфічні імена для точного catching.</span> Стабільна ієрархія дозволяє споживачам перехоплювати на потрібному рівні абстракції: загальний базовий клас для всієї бібліотеки, проміжні класи для категорій (наприклад, <code>ConnectionError</code>, <code>ValidationError</code>), і конкретні класи для окремих умов. Чому custom exception зазвичай має наслідувати <code>Exception</code>, а не <code>BaseException</code>?	<span class="key">Custom exception має наслідувати від <code>Exception</code>, щоб звичайний <code>except Exception</code> його перехоплював, не чіпаючи системних <code>SystemExit</code>, <code>KeyboardInterrupt</code> та <code>GeneratorExit</code>.</span> Ці три класи (плюс <code>BaseExceptionGroup</code>) наслідують безпосередньо від <code>BaseException</code>, оминаючи <code>Exception</code>. Яку проблему вирішують <code>ExceptionGroup</code> та <code>except*</code> у concurrent code?	<span class="key"><code>ExceptionGroup</code> дозволяє підняти кілька незалежних exception одночасно, а <code>except*</code> — вибірково обробити потрібні типи, не втрачаючи решти.</span> У concurrent code (наприклад, <code>asyncio.TaskGroup</code>) кілька задач можуть згенерувати різні exception. Коли EAFP доречніший за LBYL і як race між check та action може зробити LBYL некоректним?	<span class="key">EAFP доречніший, коли перевірка стану не гарантує його незмінність до моменту дії — класичний race TOCTOU (time-of-check to time-of-use).</span> LBYL спочатку перевіряє умову, потім виконує дію; між цими кроками стан може змінитися (інший потік, мережевий запит, файл видалено). EAFP одразу виконує дію й ловить exception, уникаючи вікна race. Як залогувати exception із traceback, не дублюючи його бездумно на кожному рівні call stack?	<span class="key">Логувати exception із traceback треба на одному рівні — зазвичай найнижчому, де exception вперше перехоплено, — використовуючи <code>logger.exception()</code> або <code>logger.error(..., exc_info=True)</code>.</span> На вищих рівнях або не логувати traceback, або додавати лише контекст без <code>exc_info</code>. <code>logger.exception()</code> автоматично бере traceback з <code>sys.exc_info()</code>, тому повторний виклик на кожному рівні створить дублікати в логах.
