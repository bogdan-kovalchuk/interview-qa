# Звіт про сумісність Anki для M0.4

Дата вимірювання: 2026-09-03.

## Середовище і версії

| Параметр | Виміряне значення |
|---|---|

| Python | 3.14.2, fallback на Python 3.12 не знадобився |

| `genanki` | 0.13.1 |
| Anki schema | `col.ver = 18`, `PRAGMA user_version = 0` |
| Опції імпорту | `merge_notetypes=true`, `update_notes=always`, `update_notetypes=always`, `with_scheduling=false`, `with_deck_configs=false` |
| Оригінал до запуску | SHA-256 `E5139052A2849AA01F6FA76349D7FCB7010C8AE16641E179ED5CCD38A38A0F5C` |
| Оригінал після запуску | SHA-256 `E5139052A2849AA01F6FA76349D7FCB7010C8AE16641E179ED5CCD38A38A0F5C` |

Anki GUI не запускався. Перед копіюванням і після експериментів процес Anki був відсутній. Хеші
оригіналу збігаються. Бібліотека `anki` відкривала лише копії у scratch-каталозі.

### Розбіжність між brief і реальною колекцією

Надана поточна `collection.anki2` має 852 нотатки, 852 картки та 141 615 рядків `revlog`, але лише
одна наявна картка має `reps > 0`. Усі 852 нотатки належать моделі `1778510992002`
(`Electronics Basic`). Модель `1788409800655` існує, але має нуль нотаток. Жоден GUID і жоден
`Front` із 392 predecessor-нотаток не збігся з поточною колекцією.

Тому вимірювання виконано на двох ізольованих fixtures:

- точна копія predecessor-колекції для моделі `1788409800655`: 392 нотатки, 392 картки,
  23 тематичні колоди;
- backup реального профілю від 2026-08-06 для scheduling: 15 284 нотатки, 15 284 картки,
  893 картки з `reps > 0`; у двопольовій одношаблонній моделі `1778510992002` було 779 таких
  карток.

Це дозволило виміряти механіку імпорту на справжніх scheduling-значеннях, але не довело, що
цільові 392 нотатки вже є у поточному профілі користувача.

### A. Міграція note type

template не змінилися.

### C. Нерухомість колоди

У пакеті для 20 history-нотаток було задано `Spike::Genanki Different Deck`. Після імпорту всі
наявні картки лишилися у своїй початковій колоді
`Embedded::Electronics and PCB Design::S01: Introduction to Electronics`. Переміщених Card ID: 0.

### D. Suspension і flags

Перед повторним імпортом призупинено картки `1778513602434`, `1778513602435`,
`1778513602436`: їх `queue` став `-1`. Карткам `1778513602437`, `1778513602438`,
`1778513602439` задано flags `1`, `2`, `3`. Після native-Anki reimport і після `genanki` update
всі значення лишилися ідентичними. Решта scheduling-полів із таблиці B також не змінилася.

### E. Відсутність видалення

Надійний контроль отримано під час G: пакет містив 20 із 392 target-нотаток. До імпорту було 392,
після імпорту було 392. Усі GUID поза пакетом залишилися. Native-Anki subset-контроль першого
проходу був невалідним через описану помилку `ExportLimit` і не використовується у вердикті.

### F. Оновлення тегів

Запланована зміна була такою:

- зберегти `spike-keep-seed`;
- вилучити `spike-remove-seed`;
- додати `spike-added`;
- зберегти початковий `Лекція_03`.

Пакет містив `spike-added spike-keep-seed Лекція_03`, але destination-нотатка після імпорту мала
лише `Лекція_03`, бо native-Anki імпорт узагалі не застосував update. Крім того, обидва seed-теги
помилково було створено лише у staging-копії, а не у destination перед імпортом. Тому не можна
визначити, чи importer вилучає відсутній у пакеті тег. Harness після запуску виправлено, повторного
вимірювання не було.

### G. Еквівалентність `genanki`

`genanki` отримав явні `model_id`, назви, ord та ids усіх полів, template id і ord, а також точні
GUID нотаток.

| Перевірка | Результат |
|---|---|
| Порожня колекція | створено рівно 20 нотаток і 20 карток, цільова структура note type збіглася |
| Мігрувана target-копія | `392 → 392`, importer: `updated = 20`, поля оновлено, модель і колоди не змінилися |
| Копія з real history | `15 284 → 15 284`, importer: `updated = 20`, scheduling, suspension, flags, модель і колоди не змінилися |

Технічна еквівалентність для потрібного проєкту сценарію підтверджена. `genanki` можна залишити
цільовим builder, якщо release smoke-тест використовує ті самі явні ids та перевіряє fingerprint.

### H. Ідемпотентний reimport

Target-пакет імпортовано двічі поверх уже оновленої target-копії. Кількість нотаток на кожному
кроці: `392`, `392`, `392`. Другий імпорт класифікував записи як дублікати без створення нових.

### I. Пакети, що перетинаються

У порожню колекцію імпортовано два `genanki`-пакети по п'ять нотаток. Вони мали два спільні GUID.
Після обох імпортів було рівно вісім нотаток. Для GUID `l%+a[n^J.?` і `s}r[E]:~sK` картки лишилися
в `Spike::Overlap::First`, тобто у колоді першого пакета. Другий importer log показав три `new`
і два `duplicate`.

### J. Зміна note type

Контрольний пакет мав ті самі три GUID, але `model_id = 1788410800654`, поля `Prompt`, `Response`
і template `Control Card`. Результат суттєво відрізняється від поточного тексту ADR:

- нотаток лишилося 392, кожний GUID лишився унікальним;
- `mid` трьох наявних нотаток змінився з `1788409800655` на `1788410800654`;
- Anki об'єднав поля у структуру `Prompt`, `Response`, `Front`, `Back`, `Reference`, `Sources`,
  `QID`; перші два значення стали порожніми, а старі п'ять змістилися на ord 2–6;
- note type отримав два templates: новий `Control Card` ord 0 і старий `Card 1` ord 1;
- кількість карток зросла з 392 до 395; кожна з трьох нотаток отримала нову картку ord 0, а
  наявна картка зберегла ID, але стала ord 1;
- importer не повернув помилки; log: три `duplicate`, `found_notes = 3`.

Отже створення нового note type не дало дубліката нотатки, але спричинило destructive structural
merge, зміщення полів та дублікати карток. Заборона змінювати note type правильна, але її поточне
пояснення неправильне. Результат прив'язаний до явно зафіксованих вище опцій імпорту.

**Уточнення 2026-09-03 (ADR-0010 §1).** Цей результат вимагає, щоб у колекції-призначенні вже
існувала нотатка з тим самим GUID. Оскільки таких колекцій не виявлено, він не забороняє **обрати**
новий note type для першого релізу – він забороняє **міняти** `model_id` після нього. Разом з
ADR-0011 (нові детерміновані GUID) комбінація, здатна відтворити цей merge, не виникає.

## Наслідки для ADR

### ADR-0006

**Підтверджено частково.** Однаковий GUID дозволив `genanki` оновити 20 наявних нотаток без
дублікатів і без зміни scheduling. Явне встановлення GUID у `genanki` працює. Формулу
детермінованого GUID spike не перевіряв.

Потребує окремого блокера міграції: у наданому real profile немає жодного GUID із predecessor і
немає нотаток цільової моделі. Твердження про extraction legacy GUID із цієї live collection не
можна вважати доведеним. Джерелом 392 GUID фактично лишається predecessor-колекція.

**Закрито 2026-09-03 (ADR-0011).** Мапу legacy-GUID скасовано: GUID рахується детерміновано від
`id` для всіх карток, extraction не виконується взагалі.

### ADR-0008

**Підтверджено.** Наявну картку імпорт не переміщує. Перетин двох пакетів не створює другу
нотатку; спільна картка лишається в колоді першого пакета. Це прямо підтримує правило, що та сама
нотатка в різних distribution packages повинна мати той самий GUID і ту саму тематичну колоду.

### ADR-0009

**Підтверджено для текстових полів і scheduling, потребує revision для note type.** Безпечність
редагування `Front`, `Back`, `Reference`, `Sources`, `QID` підтверджена на 20 картках із реальним
history. Твердження про безпечне оновлення тегів було невиміряним на момент цього звіту;
довимірено окремо – `meta/migration/anki-tag-refresh.md`, і воно підтверджене.

Неправильний текст у §2:

> зміна `model_id` note type → Anki вважає це іншим типом нотатки → усі нотатки дублюються

Запропонована заміна:

> Пакет із тим самим GUID і іншим `model_id` за опцій `merge_notetypes=true`,
> `update_notes=always`, `update_notetypes=always` може перевести наявну нотатку на merged note
> type, змінити ord полів і templates та створити додаткові картки. Це structural corruption навіть
> без дубліката нотатки, тому будь-яка зміна `model_id` заборонена і блокується fingerprint gate.

### ADR-0010 §1

**Міграційний append підтверджено на predecessor-копії; пояснення заборони нового note type
спростовано.** Додавання трьох полів до наявного `model_id` зберегло 392 нотатки, field ids
`Front`/`Back`, template id і вміст. Новий fingerprint наведено в A.

Неправильний текст:

> Anki зіставляє нотатки за GUID, але оновлення ігнорується, якщо в нотатки змінився note type.
> Усі 392 наявні нотатки перестали б оновлюватись.

Запропонована заміна:

> За перевірених опцій імпорту Anki не ігнорує конфлікт note type: він може змінити `mid` наявної
> нотатки, об'єднати поля та templates і створити додаткові картки. Тому новий note type
> заборонений: наслідок не «update ignored», а destructive structural merge.

Питання, чому live profile має нуль нотаток на target model, лишилось без відповіді. Воно
закрите оцінкою ціни, а не з'ясуванням: див. ADR-0011, розділ про найгірший випадок.

### ADR-0010 §7

**Підтверджено.** `genanki 0.13.1` створив пакет з явними `model_id`, field ids, ord, template id та
GUID, який коректно імпортувався у порожню колекцію і оновив обидві наявні fixtures без
дублікатів. Повернення до package `anki` як builder за цим spike не потрібне.

## Неперевірене на момент цього звіту

AnkiDroid та AnkiMobile тут недоступні, тож поведінка suspension на mobile і embedded fonts
лишалась неперевіреною, а tag refresh потребував окремого чистого вимірювання. Жодних припущень
про ці результати не зроблено.

**Закрито після звіту:**

| Що | Де |
|---|---|
| tag refresh | `meta/migration/anki-tag-refresh.md` – чисте вимірювання на власній фікстурі |
| embedded fonts на AnkiDroid | ручний прогін `Interview QA Font Check.apkg` на пристрої: усі 5 гарнітур × latin + кирилиця |
| suspension і прогрес на живій колекції | ручна перевірка власника: видалена картка не повернулась, прогрес не скинувся, правка тексту безпечна |

Лишається неперевіреним лише AnkiMobile – пристрою немає. Це не блокує нічого: жодне рішення
проєкту на нього не спирається.
