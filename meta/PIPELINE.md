# Як влаштований проєкт: наскрізна картина

Цей документ відповідає на одне питання: **як усе працює разом**. Решта документів у `meta/`
описують окремі частини; тут – вся дорога від «я хочу додати питання» до «картка в Anki в учня
має робоче посилання на сайт».

Ревізія від 2026-09-03 після уточнення пріоритетів власника.

## 3. Життя одного питання

Конкретно, з іменами файлів.

**Крок 1. Автор створює один файл.**

```
content/uk/python/asyncio/blocking-call-freezes-event-loop.md
```

```markdown
---
id: py-asyncio-0007
title: Чому блокуючий виклик підвішує весь event loop asyncio?
track: python
section: asyncio
level: middle
type: mechanism
tags: [event-loop, blocking-io]
status: review
content_revision: 1
sources:
  - {title: "Python 3.14: Developing with asyncio", url: "...", kind: official}
---

## Short answer
Event loop працює в одному потоці й передає керування лише на `await`. Блокуючий
виклик не віддає керування, тому всі інші задачі чекають на його завершення.

## Detailed explanation
...розгорнуто, кілька абзаців...

## Example
...

## Pitfalls
...
```

Це **єдиний файл, який пише людина**. Усе інше – похідне.

**Крок 2. Валідація.**

```powershell
python -m iqa validate
```

Перевіряє схему, унікальність ID, наявність `## Short answer`, наявність джерела, словники фасетів.
Ті самі перевірки виконує CI на PR.

**Крок 3. Збірка сайту.**

Генератор бере `content/`, будує:
- сторінку питання `/uk/q/py-asyncio-0007/blocking-call-freezes-event-loop/`;
- короткий permalink `/uk/q/py-asyncio-0007/` → веде на неї;
- сторінку-індекс секції `/uk/python/asyncio/` зі списком питань;
- навігацію, пошук, зрізи за тегами і рівнями.

**Крок 4. Експорт.**

```powershell
python -m iqa export
```

```
dist/export/
  questions.json
  anki/python__asyncio.tsv
```

У TSV рядок для нашого питання:

| Front | Back | Reference | Tags | GUID |
|---|---|---|---|---|
| Чому блокуючий виклик… | `<HTML з ## Short answer>` | `https://…/interview-qa/uk/q/py-asyncio-0007/` | `topic::python::asyncio level::middle role::python-backend qid::py-asyncio-0007` | детермінований з `id` |

**Крок 5. Збірка колод.**

```powershell
python -m iqa deck build --program python-backend
```

→ `dist/decks/Interview QA - Python Backend.apkg`

**Крок 6. Учень імпортує пакет.**

Anki зіставляє нотатки за GUID: нові додає, наявні оновлює, розклад повторень зберігає.

**Крок 7. Учень бачить картку**, натискає «Розгорнуте пояснення» і потрапляє на сторінку сайту.

## 4. Колоди й пакети – найзаплутаніше місце

Формулювання «генеруються колоди по напрямках» приховує конфлікт, який треба розв'язати явно.

### Механіка Anki, з якої все випливає

- Нотатка має поля і теги. З нотатки за шаблоном народжуються картки.
- **Кожна картка лежить рівно в одній колоді.** Нотатка не може бути в двох колодах.
- При імпорті `.apkg` нотатки зіставляються **за GUID**: збіг → оновлення, немає збігу → нова.
- Картки наявних нотаток **лишаються у своїй поточній колоді** – імпорт їх не переміщує.

### Наївне рішення і чому воно ламається

«Колода = напрямок»: `Interview QA::Embedded C++`, `Interview QA::Python Backend`.

Питання «що таке undefined behavior» потрібне обом напрямкам. Якщо воно є в обох пакетах з тим
самим GUID, то в учня, який імпортував обидва, воно опиниться в тій колоді, куди потрапило першим,
а друга колода буде неповною. Якщо дати різні GUID – учень вчитиме те саме питання двічі.
Обидва результати погані.

### Рішення

Розділити три різні речі, які всі називають «колодою»:

| Поняття | Чим є | Приклад |
|---|---|---|
| **Пакет** (`.apkg`) | одиниця розповсюдження = вибірка питань під напрямок | `Interview QA - Embedded C++.apkg` |
| **Колода** | дерево організації всередині Anki = **завжди тематичне** | `Interview QA::C++::Templates` |
| **Тег** | фасет для власних фільтрів учня | `role::embedded-cpp level::senior` |

Тобто: **напрямок вирішує, які картки ви отримаєте; колода завжди відображає тему.**

Що це дає:

- перетин пакетів нешкідливий – та сама нотатка, той самий GUID, та сама колода; учень вчить її раз;
- учень бачить логічну тематичну структуру, а не дублювання;
- «вчити тільки embedded» робиться фільтрованою колодою за тегом `role::embedded-cpp` – це
  штатний механізм Anki;
- пакетів може бути скільки завгодно без перебудови дерева колод.

### Що публікуємо

| Пакет | Вміст |
|---|---|
| `Interview QA - Python Backend.apkg` | програма `python-backend` |
| `Interview QA - Embedded C++.apkg` | програма `embedded-cpp` |
| `Interview QA - Data Science.apkg` | програма `data-science` |
| `Interview QA - Full Library.apkg` | усе |

Кожен пакет самодостатній: учневі не треба спочатку ставити «базовий», щоб додати «спеціалізацію».

### Що перевіряє smoke-тест перед кожним релізом

1. імпорт пакета в чисту колекцію – кількість нотаток збігається з очікуваною;
2. повторний імпорт того самого пакета – кількість не зросла;
3. імпорт двох пакетів, що перетинаються – перетин не задублювався;
4. імпорт нової версії поверх старої – розклад повторень збережений.

Пункти 3 і 4 – саме ті, де помилка виявляється не в CI, а в скаргах учнів. Вони мають бути
автоматизовані, а не перевірятись руками.

## 5. Посилання в картці

**Формат:** `https://bogdan-kovalchuk.github.io/interview-qa/{lang}/q/{id}/`

**Чому короткий permalink, а не адреса сторінки.** Картки живуть у профілях учнів роками і не
перебудовуються, коли ми міняємо таксономію чи формулювання. Тому:

- канонічна адреса сторінки: `/uk/q/py-asyncio-0007/blocking-call-freezes-event-loop/`
  (`slug` у ній лише для читабельності й пошукових систем);
- у картку йде коротка форма `/uk/q/py-asyncio-0007/`, яка веде на канонічну;
- зміна назви питання, переїзд у іншу секцію, реорганізація всього дерева – **жодна картка не
  ламається**.

Порівняйте з референсом, де адреса питання – це якір із тексту заголовка
(`/python/general/#які-основні-особливості-має-python-21100`): будь-яке редагування формулювання
вбиває посилання.

**Коли посилання з'являється.** Завжди, з першого дня.

Це наслідок правила «скелет існує завжди» (`CONTENT_SPEC.md` §3a): питання створюється повністю –
обидві мовні версії, усі секції, сторінка, картка. Ненаписане позначається маркером `TODO`, а не
відсутнє. Тому сторінка за посиланням існує ще до того, як на ній щось написано, і чесно показує,
чого саме там поки немає.

Що це дає замість умовності «додавати посилання чи ні»:

- **нічого не зсувається** – ID, URL, GUID і місце в колоді існують з моменту створення питання.
  Учень не отримує нові картки пачками з кожним релізом, він отримує наповнення наявних;
- **дірки видно** – і на сторінці, і у звіті `/status/`, і тегом `todo::` в Anki;
- **немає ручних кроків** – не існує задачі «не забути додати посилання», «не забути створити
  англійську версію», «не забути завести картку».

Межа скелета проходить по Anki, і задає її механіка імпорту, а не наш вибір: **імпорт не змінює
стан карток, які вже є в колекції учня**. Тому стан картки при першій появі остаточний, і порожню
картку відвантажувати немає сенсу – вона або назавжди лишиться призупиненою, або назавжди шумітиме
в черзі. Картка їде в пакет тоді, коли її `Short answer` цією мовою вже написано; GUID при цьому
зарезервований з першого дня, тож нічого не зсувається (`ANKI_INTEGRATION.md` §8).

Облік дірок веде таблиця прогресу (`PROGRESS_TRACKING.md`), а не колода учня.

учнів. Після переходу на детермінований GUID він потрібен рівно один раз – щоб витягнути наявні
GUID у CSV. Далі збірка стає повністю відтворюваною з нуля. Це найбільше спрощення в усій міграції.

**Astro Starlight** (зафіксовано 2026-09-03). Вирішальним був статус двомовності: власник
підтвердив, що EN+UK потрібні з першого дня. Без цієї вимоги кращим вибором був би Material for

його плагін i18n заморожений, а в наступника Material (Zensical) i18n ще не реалізовано.

Практичні наслідки для роботи:

- `site/` – єдина частина проєкту на Node; `content/`, `tools/`, `packaging/` лишаються Python;

- контент лишається чистим Markdown без MDX, тож заміна генератора надалі коштує тільки `site/`.

Усе інше в цьому документі від вибору генератора не залежить.

## 9. Чому один файл на питання, а не як у референсі

Референс тримає одну сторінку на тему і питання всередині як заголовки `###`. Це зручніше писати.
Я перевірив цей варіант ще раз – і він розбивається саме об ваш пріоритет 3.

Щоб питання стало карткою, при ньому мусять жити структуровані дані: рівень, тип, теги, напрямки,
джерела, ознака експорту, стабільний ID. У схемі «сторінка на тему» їх нема куди подіти, окрім як
вписувати в текст заголовка. Референс це вже й робить – оцінка важливості у нього зашита
в заголовок як `[💡21/100]` і парситься регуляркою. Один фасет так витягнути можна, шість – ні.

Frontmatter кріпиться до файлу. Отже питання = файл.

Побічні вигоди: PR з одним питанням читається як один файл; двоє авторів не конфліктують; переклад
відстежується по кожному питанню окремо; адреса сторінки стабільна за побудовою.

Ціна: тисячі файлів і неможливість вести навігацію руками. Тому навігація генерується – але вона
все одно мусила б генеруватись при 2000 питань.

## 9a. Зручність і масштабованість

Це проєкт для власного навчання, який заодно публічний. Тому головний критерій рішень – не чистота
архітектури, а скільки зусиль коштує додати 500-те питання порівняно з десятим.

### Що робить щоденну роботу дешевою

| | |
|---|---|
| **Один файл на дію** | додати питання = створити один файл; виправити = змінити один файл. Немає кроку «а тепер онови ще картку, індекс і навігацію» |
| **Ніякої церемонії** | немає тек `drafts/ready/rejected`, немає ручного трекінгу покриття, немає `manifest.json`, який треба синхронізувати з контентом |
| **Плейсхолдер – норма** | питання виходить у світ, щойно має коротку відповідь; решта дописується коли завгодно, і картка сама отримає посилання |
| **Мова – яка зручно** | пишете тією, якою думаєте; другу робить агент |
| **Один вхід** | `python -m iqa new / validate / export / deck build` – не треба пам'ятати п'ять скриптів |
| **Помилки ловить машина** | схема, ID, структура, паритет мов, посилання. Голова не тримає правил, які може перевірити валідатор |

### Що не зламається на масштабі

Порівняння з підходом референсу, який чудово працює на 700 питаннях і перестає на 2500:

| Навантаження | Референс | Тут |
|---|---|---|
| Навігація | `nav:` у конфізі вручну | генерується з дерева |
| Нове питання в темі | дописати в кінець довгого файлу | окремий файл, конфліктів у git немає |
| Реорганізація тем | ламає всі якорі-посилання | нічого не ламає – таксономії немає в адресах |
| Метадані питання | вписані в текст заголовка | frontmatter, скільки завгодно полів |
| Другий напрямок | нова тека з копіями питань | один YAML, питання переплюсовуються |
| Друга мова | немає механізму | окремий файл, fallback і звіт покриття |
| Пошук | один індекс | окремий індекс на мову, автоматично |

Три речі, які тримають масштаб і які не варто чіпати:

1. **Таксономії немає в URL.** Тому дерево можна перебудовувати скільки завгодно разів – це
   найчастіша операція на етапі росту і вона мусить бути безкоштовною.
2. **Питання ніколи не копіюється.** Напрямки і зрізи будуються вибіркою по фасетах, тому
   виправлення в одному місці виправляє всюди.
3. **Усе, що можна вивести, – виводиться.** Індекси, навігація, зрізи, TSV, колоди, звіти. Руками
   пишуться тільки питання і кілька YAML з програмами.

### Де це коштує дорожче за референс

Чесно: старт. У референсу шлях «поставив mkdocs – пишеш Markdown». Тут спершу треба схема,
валідатор і експортер (M1–M3). Ця вартість платиться один раз і повертається приблизно на сотому
питанні – далі кожне наступне дешевше, бо його не треба вручну заводити ще й у колоду, індекс і
навігацію.

## 10. Робочі сценарії

**Додати питання.**
`python -m iqa new --track python --section asyncio` → створює файл з ID і шаблоном → автор пише →
`iqa validate` → PR → CI → merge → сайт оновився. Картка з'явиться в наступному релізі колоди.

**Виправити помилку у відповіді.**
Правка одного файлу. Сайт оновлюється при merge; картка – при наступному релізі колоди, з
оновленням наявної нотатки за GUID, без втрати розкладу.

**Додати напрямок.**
Один `programs/*.yml`. Наявні питання підбираються за фасетами; специфічні дописуються у власний
трек. Новий `.apkg` з'являється автоматично.

**Випустити колоди.**
Тег `deck-v2026.09` → CI ганяє smoke-тести імпорту → публікує `.apkg` у GitHub Release.

**Розгорнути пояснення для мігрованої картки.**
Дописати `## Detailed explanation` у наявний файл → сторінка наповнюється. Картка при цьому не
змінюється: `Reference` у неї вже є з моменту, коли вона поїхала (`meta/LIFECYCLE.md`). Реліз колоди
для такої правки не потрібен взагалі.
