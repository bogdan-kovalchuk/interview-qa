# Сайт і звіт прогресу

Astro Starlight, дві локалі, GitHub Pages за стандартною адресою `/interview-qa/`. `site/` –
єдина частина проєкту на Node.

## Потік даних

```
content/{lang}/**            авторський Markdown, генератор-агностичний
      ↓ tools/iqa/mirror.py  дзеркало у site/src/content/docs/  (у .gitignore)
      ↓ astro build          production-збірка з base=/interview-qa
      ↓ dist/export/         questions.json, progress.*, вхід для Anki
```

**`content/` читає рівно один компонент – `tools/`.** Сайт споживає згенероване дзеркало, а не
`content/` напряму: Starlight отримує стандартну структуру і штатний `docsLoader`, а в
згенерований frontmatter можна вкласти обчислене – `completeness`, канонічний URL, стан перекладу,
посилання на джерело в GitHub. Ціна – крок збірки і подвоєння файлів на диску під час білду.
Watch-режим перегенеровує дзеркало при зміні `content/`.

## URL

```
/                          → /en/
/en/python/asyncio/        індекс секції: список питань
/en/q/py-asyncio-0007/     resolver page → канонічна адреса
/en/q/py-asyncio-0007/blocking-call-freezes-event-loop/    канонічна
/en/status/                таблиця прогресу
```

Обидві мови мають префікс – симетрично. Асиметричний варіант економить три символи і коштує
спецкейсу в кожному місці, де будується посилання «та сама сторінка іншою мовою».

Адреса питання **не містить таксономії**: реорганізація секцій інакше породжувала б редіректи.
`slug` у канонічній адресі потрібен лише для читабельності й при резолві ігнорується.

Коротка форма `/{lang}/q/{id}/` – **resolver page**, а не HTTP-редірект: статичний хостинг не
віддає 301. Вона несе `<link rel="canonical">`, виконує негайну навігацію і показує видиме
посилання як fallback. У стані `withdrawn` – надгробок з посиланням на заміну, а не 404.

## Локалізація

```js
starlight({
  defaultLocale: 'en',
  locales: { en: { label: 'English', lang: 'en' }, uk: { label: 'Українська', lang: 'uk' } },
})
```

Starlight показує сторінку `defaultLocale` з видимим нотисом, коли переклад відсутній. У штатному
режимі цього не має бути видно: обидва мовні файли створюються одночасно з питанням.

**Жодного українського чи англійського рядка в шаблонах – тільки ключі.** Що саме перекладається:

| Об'єкт | Де живе переклад |
|---|---|
| `title`, `description` питання | frontmatter відповідного мовного файлу |
| **видимі назви секцій** (`Short answer` → «Коротка відповідь») | `meta/vocabulary.yml` |
| назви треків і секцій у навігації, підписи фасетів | `meta/vocabulary.yml` |
| назви програм | `programs/*.yml`, поле `title.{lang}` |
| UI Starlight | вбудовані переклади + перекриття |

Заголовки секцій легко проґавити: у джерелі вони завжди англійські ідентифікатори, тож без запису
у словнику українська сторінка відрендерить `## Short answer` англійською.

## Пошук

Pagefind (у Starlight з коробки) читає `lang` з `<html>` і будує окремий індекс на кожну мову
автоматично. Спеціалізованого стемера для української немає – працює загальний алгоритм; для
технічного контенту це майже непомітно, бо ключові терміни й так латиницею.

Варто індексувати `id` і теги як фільтровані атрибути – тоді пошук за `py-asyncio-0007` або за
тегом працює без окремої сторінки.

## Звіт прогресу

Скелет існує завжди, тому головне питання щодня – **де саме дірки**. Таблиця **генерується** з
самих файлів; заявити «тут готово» неможливо.

| Артефакт | Для чого |
|---|---|
| `dist/export/progress.csv` | відкрити, відсортувати, спланувати |
| `dist/export/progress.json` | вхід для сайту |
| `/{lang}/status/` | сторінка з фільтрами за треком, секцією, мовою, повнотою, програмою |
| `python -m iqa report --todo` | взяти наступну задачу |

Один рядок = одне питання. Колонки: ідентичність (`id`, `track`, `section`, `slug`, `status`,
`level`, `type`); по кожній мові – чи існує файл, чи написано кожну обов'язкову секцію,
`completeness`, чи потребує узгодження з іншою мовою; далі похідне – кількість джерел і чи є
не-`community`, резолвність `qid:`, `card_{lang}` зі значенням `ships` або `blocked:<причина>`,
членство в програмах, GUID, `updated`.

Та сама таблиця згортається на трьох рівнях: секція → трек → проєкт, і окремо по програмах, мовах
і типах секцій. Останній розріз найкорисніший – він показує **системні** дірки, коли цілий клас
роботи не зроблено ніде.

### Покриття цілей, а не лише секцій

Таблиця відповідає на «які секції заповнені», але не на «чи достатньо я підготовлений». Ціль виду
«100 питань по C++» стимулює дійти до числа, а не закрити прогалини.

`meta/objectives/{track}.yml` описує цілі на рівні **секції**:

```yaml
- id: cpp-mem-lifetime
  title: {en: Object lifetime and ownership, uk: Час життя об'єкта і володіння}
  section: cpp/memory-model-and-lifetime
  levels: [junior, middle, senior]
  signals:
    - розрізняє automatic, static, dynamic і thread storage duration
    - пояснює, коли дає UB звернення до знищеного об'єкта
    - обирає між value, reference і smart pointer з обґрунтуванням
```

Звіт показує для кожної цілі: скільки питань її закривають, на яких рівнях, і чи є серед них хоча б
одне `complete`. Ціль без жодного `complete` вважається незакритою, скільки б `stub` на неї не
посилалося. **Кількість карток стає наслідком, а не критерієм приймання.**

Повна competency-матриця по ролях зараз була б вигадуванням наперед: цілі рівня секції робляться
для треків, які реально наповнюються.

Сторінка `/status/` – це те, що робить «work in progress» чесним: незавершеність показана як дані,
а не як дисклеймер у футері.

## Знахідки spike, які треба врахувати при повній збірці

Виміряно на M0.3 і досі не застосовано, бо повного сайту ще немає:

- Starlight трактує `slug` як маршрут цілком – дзеркало має писати
  `slug: {lang}/q/{id}/{file-slug}`;
- стандартна 404 генерує canonical на неіснуючі адреси – потрібна власна сторінка;
- корінь `/interview-qa/` **не створюється сам** – обіцяний редірект на `/en/` з цієї конфігурації
  не випливає.
