# Конвенції іменування

Назви тут – це водночас URL, ключі перекладу, теги Anki та ідентифікатори в експорті.
Змінити назву пізніше дорого, тому правила жорсткі.

---

## 1. Загальні правила

| Об'єкт | Формат | Приклад |
|---|---|---|
| Трек (тека 1-го рівня) | `kebab-case`, однина або усталений термін | `python`, `cpp`, `data-science` |
| Секція (тека 2-го рівня) | `kebab-case`, множина або `noun-and-noun` | `stl-containers`, `memory-and-linker` |
| Файл питання | `kebab-case`, 3–7 слів, описує **суть**, не форму | `why-gil-blocks-cpu-bound-threads.md` |
| ID питання | `{track}-{section}-{NNNN}` | `py-asyncio-0007` |
| Тег | `kebab-case`, без префікса | `event-loop`, `undefined-behavior` |
| Програма | `{role}-{specialization}` | `embedded-cpp-engineer` |
| Anki-колода | Title Case з `::` | `Interview QA::Python::Asyncio` |

Заборонено в шляхах: пробіли, підкреслення, кирилиця, крапки крім розширення, числові префікси (`01_`, `02_`).

**Чому без числових префіксів.** Наявний Anki-репозиторій використовує `01_python_fundamentals`.
Для файлів це зручно, для URL – ні: порядок мусить бути даними (`order:` у frontmatter або
`sidebar.order`), а не частиною адреси. Інакше вставка теми між 03 і 04 ламає посилання.

## 2. Назви файлів питань

Файл називається за **змістом відповіді**, а не за текстом питання:

| ✗ Погано | ✓ Добре |
|---|---|
| `question-14.md` | `iterator-invalidation-on-vector-push-back.md` |
| `what-is-gil.md` | `gil-serializes-bytecode-execution.md` |
| `django.md` | `django-queryset-laziness-and-evaluation.md` |
| `memory.md` | `stack-vs-heap-allocation-tradeoffs.md` |

Причина: у теці на 40 файлів назви – це фактично зміст; «що таке X» не розрізняє нічого.

Ім'я файлу **не є контрактом** – його можна змінювати, бо посилання в Anki йдуть через `/q/{id}/`.
Але зміна імені має супроводжуватись записом у `meta/redirects.csv`, щоб не ламати зовнішні посилання.

## 3. Схема ID

```
{track-prefix}-{section-prefix}-{NNNN}
```

Префікси треків (фіксовані, 2–4 літери):

| Трек | Префікс | Трек | Префікс |
|---|---|---|---|
| python | `py` | embedded | `emb` |
| cpp | `cpp` | data-science | `ds` |
| cs | `cs` | machine-learning | `ml` |
| systems | `sys` | data-engineering | `de` |
| databases | `db` | backend | `be` |
| engineering | `eng` | devops | `ops` |
| system-design | `sd` | qa-automation | `qa` |
| behavioral | `bhv` | | |

Префікс секції – скорочення назви секції до 3–8 літер. Він фіксується один раз у
`meta/section-prefixes.csv` (`track, section, prefix, created`), а не в реєстрі питань: префікс
належить секції, а не питанню, і в реєстрі повторювався б у кожному рядку.

**Незмінні правила:**

1. ID присвоюється один раз і не змінюється – навіть при переїзді питання в інший трек.
2. Номер `NNNN` ніколи не перевикористовується, навіть після видалення питання.
3. ID не парситься для отримання розташування – розташування знає тільки датасет.
4. Реєстр `meta/id-registry.csv` (`id, created, status, current_path`) є арбітром; CI звіряє з ним.
   `current_path` – шлях **без сегмента `{lang}`**: `python/practical-coding/merge-…md`. Питання
   є двома файлами, а колонка одна, і мовний префікс у ній зробив би реєстр брехливим щодо
   другого файлу. Мови додає споживач, як і в `qid:`-токені.

Наслідок п.1: `py-asyncio-0007` може фізично лежати в `backend/async-and-scaling/`. Це нормально
і навмисно – ID кодує походження, а не поточну адресу.

## 4. Теги проти секцій

| Використати секцію | Використати тег |
|---|---|
| ознака стабільна і структурна | ознака перетинає секції |
| питання належить рівно одній | питань з ознакою може бути будь-де |
| потрібна сторінка в навігації | потрібен лише зріз/фільтр |

Приклад: `concurrency-and-gil` – секція; `deadlock` – тег (зустрічається в `cpp`, `systems`,
`databases`, `python`).

Теги не мають ієрархії. Якщо хочеться `python/asyncio/tasks` – це секція, а не тег.

## 5. Фасети та їх значення

Нормативні enum `level`, `type` і `status` оголошені **лише** в `CONTENT_SPEC.md` §2. Цей документ
не дублює їх, щоб словники не розходилися. Довільні значення відхиляє валідатор.

| Фасет | Правило значення |
|---|---|
| `level` | enum з `CONTENT_SPEC.md` §2; операційні критерії – `RUBRIC.md` §1 |
| `type` | enum з `CONTENT_SPEC.md` §2; операційні критерії – `RUBRIC.md` §2 |
| `status` | enum з `CONTENT_SPEC.md` §2; переходи й наслідки – `LIFECYCLE.md` |
| `frameworks` | `kebab-case` імена з `meta/frameworks.yml` |

`roles` у frontmatter **немає**: членство в програмах виводиться з `programs/*.yml`
(`CONTENT_SPEC.md` §2, ADR-0010 §5). Фасет, що дублював би виведене значення, розійшовся б з ним
першої ж збірки.

## 6. Розв'язання конфліктів домівки

Коли дві секції претендують на питання:

1. **Правило найвужчого треку** (`ANALYSIS.md` §5.2) – головне.
2. Якщо обидві однаково вузькі – виграє та, у якій питання **вперше поставлять на інтерв'ю**.
3. Якщо і це не розрізняє – злити секції. Дві секції, що постійно сперечаються за питання, – це
   одна секція з двома назвами.
4. Ніколи не копіювати файл. Зв'язок з другою секцією робиться тегом або `see-also`.

Відомі конфлікти, які треба вирішити при реалізації:

| Конфлікт | Рішення |
|---|---|
| `backend/api-design` vs `system-design/api-design` | лишити в `system-design`, з `backend` посилатись |
| `python/frameworks/numpy` vs `data-science/frameworks/numpy` | канонічно в `data-science` |
| `python/testing` vs `engineering/testing` | мовно-специфічне (pytest) – у `python`; загальні принципи – в `engineering` |
| `cs/data-structures` vs `cpp/stl-containers` | теорія – в `cs`, реалізація та її гарантії – в `cpp` |
| `databases/sql-queries` vs `data-science/sql-for-analytics` | базовий SQL – в `databases`, аналітичні патерни – в `data-science` |

## 7. Іменування колод Anki

```
Interview QA
├─ Python
│  ├─ Asyncio
│  └─ Collections
├─ C++
│  └─ Templates
└─ Programs
   └─ Embedded C++
```

- Роздільник – `::` (вимога Anki).
- Назви колод – англійською навіть для українського контенту: учень бачить дерево колод у своєму
  профілі поряд з іншими, і латиниця сортується передбачувано.
- Колода-програма не дублює нотатки – вона зібрана з тих самих нотаток іншою вибіркою.

**Міграція з наявного репозиторію:** поточний корінь – `Python Interview Questions` з 23 підколодами
виду `01 Python Fundamentals`. Перенесення в `Interview QA::Python` не є перейменуванням наявних
нотаток: за ADR-0010 §1 і ADR-0011 картки збираються заново, на новому note type і з новими
детермінованими GUID. Втрачати нема чого – цих нотаток немає в жодній колекції (виміряно,
`meta/migration/anki-compatibility-report.md`). Стара колода, якщо десь існує, лишається окремо
і не чіпається; це має бути описано в release notes першої колоди.
